이 자료의 핵심 주제는 LLM이 답변을 생성하는 과정, 그 과정에서 GPU 메모리가 사용되는 방식, 그리고 여러 사용자의 요청을 효율적으로 처리하기 위한 기술이다.

이를 이해하려면 LLM의 계산 방식부터 메모리 관리, 어텐션(Attention), KV Cache, 추론 최적화까지 연결해서 살펴봐야 한다.

---

## 1. LLM은 어떻게 작동하며, 왜 메모리가 중요한가?

### 1) LLM이 답변을 생성하는 기본 과정

ChatGPT와 같은 LLM은 사용자가 질문을 입력하면 답변 전체를 한꺼번에 만들어내는 것이 아니라, 다음에 올 토큰(Token)을 하나씩 예측하는 방식으로 작동한다.

토큰은 모델이 텍스트를 처리하는 기본 단위다. 한글 한 글자, 단어의 일부, 영어 단어, 문장부호 등이 각각 하나 이상의 토큰으로 처리될 수 있다.

예를 들어 사용자가 "대한민국의 수도는 어디야?"라고 질문하면 다음과 같은 과정이 진행된다.

1. 입력한 문장을 토큰으로 변환한다.
2. 토큰을 숫자 벡터로 변환해 신경망에 입력한다.
3. Transformer의 여러 층에서 입력 정보를 계산한다.
4. 다음 토큰에 대한 확률을 구하고 하나를 선택한다.
5. 생성된 토큰을 문맥에 추가해 다음 토큰을 예측한다.
6. 종료 조건을 만족할 때까지 반복한다.

이 과정에서 모델은 이전에 입력되거나 생성된 토큰의 정보를 참고해야 한다.

문제는 문장이 길어질수록 처리해야 할 정보가 많아지고, 여러 사용자의 요청이 동시에 들어오면 메모리 사용량도 증가한다는 것이다.

그래서 LLM을 실제 서비스로 운영하려면 모델 자체의 성능뿐 아니라 GPU 메모리를 얼마나 효율적으로 사용하는지가 중요하다.

### 2) CPU와 GPU는 어떤 역할을 담당하는가?

CPU와 GPU는 모두 계산을 수행하는 장치지만 설계 목적이 다르다.

- **CPU(Central Processing Unit)** 는 운영체제, 프로그램 실행, 요청 관리, 데이터 입출력 등 다양한 작업을 처리한다. 복잡한 제어와 순차적인 작업에 적합하다.
- **GPU(Graphics Processing Unit)** 는 많은 수의 계산을 병렬로 수행하도록 설계되었다. LLM에서 사용하는 행렬곱과 같은 연산을 대량으로 처리하는 데 유리하다.

LLM 추론에서는 일반적으로 CPU가 요청을 관리하고 데이터를 준비하며, GPU가 신경망의 주요 연산을 담당한다. 실제 계산은 CUDA와 같은 GPU 프로그래밍 환경 및 연산 라이브러리를 통해 수행된다.

두 장치는 사용하는 메모리에도 차이가 있다.

| 구분 | CPU | GPU |
| --- | --- | --- |
| 주요 메모리 | 시스템 RAM | GPU VRAM |
| 주요 역할 | 프로그램과 요청 관리 | 신경망 계산 |
| 특징 | 다양한 제어 작업에 적합 | 대량의 병렬 연산에 적합 |
| LLM에서 중요 요소 | 데이터 처리, 스케줄링 | 연산 성능, 메모리 용량 및 대역폭 |

여기서 중요한 개념이 메모리 대역폭(Memory Bandwidth) 이다.

메모리 대역폭은 일정 시간에 메모리에서 얼마나 많은 데이터를 읽거나 쓸 수 있는지를 의미한다.

GPU의 연산 능력이 충분하더라도 필요한 데이터를 메모리에서 빠르게 가져오지 못하면 계산 장치가 대기하게 된다.

따라서 LLM의 처리 속도는 GPU의 연산 성능과 메모리 대역폭 모두에 영향을 받는다.

### 3) GPU 메모리에는 무엇이 저장되는가?

LLM을 GPU에서 실행하면 메모리는 크게 세 가지 용도로 사용된다.

#### (1) 모델 가중치(Model Weights)

모델이 학습을 통해 얻은 파라미터다. 모델을 실행하는 동안 대부분 메모리에 유지된다.

가령 파라미터가 70억 개인 7B 모델을 FP16으로 저장한다면, 파라미터 하나가 2바이트이므로 가중치만 약 14GB가 필요하다.

같은 모델을 4비트로 저장한다면 단순 계산으로 약 3.5GB가 된다. 다만 실제 메모리에는 양자화 관련 정보와 추가 데이터가 포함된다.

#### (2) KV Cache

이미 처리한 토큰의 어텐션 계산 결과 중 Key와 Value를 저장하는 영역이다.

이 정보는 모델이 새로운 토큰을 생성할 때 재사용한다. 입력 문장이 길어지거나 동시에 처리하는 요청이 많아질수록 KV Cache도 커진다.

#### (3) 중간 계산 결과와 작업 공간

신경망의 각 층에서 계산하는 임시 텐서, 연산에 필요한 버퍼, 런타임 관리 데이터 등이다.

이 메모리는 연산 과정에 따라 생성되고 해제되며, 특정 순간에는 사용량이 크게 증가할 수 있다.

결국 GPU 메모리 사용량은 대략 다음과 같이 이해할 수 있다.

$$
\text{GPU 메모리} \approx \text{가중치}+\text{KV Cache}+\text{중간 계산 및 기타 메모리}
$$

7B 모델의 가중치를 4GB 안팎으로 줄였다고 해서 4GB GPU에서 실제 추론이 항상 가능해지는 것은 아니다. KV Cache와 임시 메모리를 추가로 확보해야 하기 때문이다.

### 4) 물리적 메모리와 가상 메모리

메모리를 효율적으로 관리하려면 물리적 메모리와 가상 메모리의 차이도 알아야 한다.

- **물리적 메모리**는 RAM이나 VRAM처럼 실제 하드웨어에 존재하는 저장 공간이다.
- **가상 메모리**는 프로그램이 사용하는 논리적인 주소 공간이다. 프로그램이 사용하는 주소와 실제 데이터가 저장된 물리적 주소를 대응시키는 방식으로 작동한다.

운영체제는 메모리를 일정한 크기의 페이지(Page) 단위로 관리한다. 덕분에 프로그램에는 연속된 메모리처럼 보이더라도 실제 데이터는 서로 떨어진 물리적 공간에 저장될 수 있다.

이 방식에는 중요한 장점이 있다.

메모리의 빈 공간이 여러 곳에 나뉘어 있더라도 각각을 활용할 수 있고, 서로 다른 프로그램의 메모리를 구분하여 관리할 수 있다.

여기서 메모리 단편화(Fragmentation) 라는 문제가 등장한다.

메모리에 사용할 수 있는 공간이 남아 있어도 여러 부분에 나뉘어 있거나, 할당된 영역 내부에 사용하지 못하는 공간이 생기면 실제 활용 효율이 낮아진다.

LLM의 KV Cache 관리에도 이와 유사한 문제가 발생한다. 요청마다 필요한 메모리 크기가 다르고, 답변을 생성하면서 필요한 공간이 계속 증가하기 때문이다.

이 문제를 해결하기 위해 등장한 대표적인 기술이 뒤에서 설명할 PagedAttention이다.

## 2. 어텐션과 KV Cache가 작동하는 원리

### 1) 어텐션은 무엇을 계산하는가?

Transformer의 핵심 연산 중 하나가 어텐션(Attention)이다.

어텐션은 현재 토큰을 처리할 때 다른 토큰들의 정보를 얼마나 반영할 것인지 계산하는 방법이다.

예를 들어 문장에서 어떤 단어의 의미를 판단하려면 그 단어만 살펴보는 것보다 앞뒤의 관련 단어를 함께 살펴보는 것이 유리하다.

LLM의 자기회귀적 생성 과정에서는 현재 위치가 앞선 토큰들의 정보를 참고하도록 어텐션이 구성된다.

어텐션 계산에 사용하는 것이 Query(Q), Key(K), Value(V) 다.

- **Query**는 현재 토큰이 다른 토큰들과 얼마나 관련되는지 계산하는 데 사용되는 벡터다.
- **Key**는 관련도를 계산할 때 비교되는 벡터이며, **Value**는 관련도에 따라 실제로 결합할 정보가 담긴 벡터다.

기본적인 어텐션 계산식은 다음과 같다.

$$
\operatorname{Attention}(Q,K,V)
=\operatorname{softmax}\left(\frac{QK^T}{\sqrt{d_k}}\right)V
$$

수식을 쉽게 풀면 다음과 같다.

1. 먼저 Query와 Key를 비교해 토큰 사이의 관련도 점수를 계산한다.
2. 이 점수를 정규화하여 어텐션 가중치를 만든다.
3. 마지막으로 해당 가중치를 Value에 적용해 필요한 정보를 결합한다.

이 계산은 Transformer의 여러 층에서 반복된다.

### 2) 새로운 토큰을 생성할 때 이전 정보가 필요한 이유

LLM은 이전 문맥을 바탕으로 다음 토큰을 예측한다.

따라서 새로운 토큰을 생성할 때는 이전 토큰들의 Key와 Value가 다시 필요하다.

KV Cache를 사용하지 않는다면 매번 전체 문맥에 대해 필요한 Key와 Value를 다시 계산해야 한다.

반면 이전 토큰의 Key와 Value를 저장해 두었다면, 새로운 토큰에 해당하는 계산만 추가하면 된다.

이것이 KV Cache의 핵심이다.

여기서 Query를 함께 저장하지 않는 이유도 이해할 필요가 있다.

새로운 토큰의 어텐션을 계산할 때 필요한 것은 현재 토큰의 Query와 지금까지의 Key, Value다. 과거 토큰들의 Query는 이미 해당 토큰들의 어텐션 계산에 사용되었기 때문에 새로운 토큰을 계산할 때 직접 재사용할 필요가 없다.

따라서 KV Cache는 이름 그대로 Key와 Value를 저장한다.

### 3) Prefill과 Decode의 차이

LLM 추론은 크게 Prefill과 Decode라는 두 단계로 구분할 수 있다.

#### (1) Prefill: 입력 처리

Prefill은 입력 문장을 처음 처리하는 단계다.

사용자가 긴 질문이나 문서를 입력하면 모델은 입력 토큰들을 Transformer에 통과시키면서 정보를 계산한다.

입력 토큰들의 처리는 GPU에서 상당 부분 병렬화할 수 있다. 동시에 이후 생성 과정에서 사용할 Key와 Value를 계산해 KV Cache에 저장한다.

일반적으로 입력 토큰이 많을수록 Prefill에 필요한 연산량도 증가한다.

#### (2) Decode: 토큰 생성

Decode는 답변을 한 토큰씩 생성하는 단계다.

Prefill 이후 첫 번째 출력 토큰이 선택되면, 모델은 그 토큰을 문맥에 추가하고 다음 토큰을 생성한다.

이후에도 동일한 작업을 반복한다.

#### (3) 예시: 입력 1,000토큰과 출력 100토큰

가령 사용자가 1,000토큰의 질문을 입력하고 모델이 100토큰의 답변을 생성한다고 가정하자.

Prefill에서는 처음 입력된 1,000토큰을 처리한다. 그 이후에는 Decode 과정을 반복하면서 출력 토큰을 생성한다.

한 번의 Decode 단계에서 새 토큰 하나를 처리하므로, 출력 토큰 100개를 생성하려면 순차적으로 이어지는 생성 단계가 필요하다.

KV Cache가 있으면 매 단계에서 기존 1,000개 이상의 토큰에 대한 Key와 Value를 새로 계산하는 작업을 줄일 수 있다.

### 4) Prefill과 Decode는 성능 병목도 다르다

Prefill과 Decode는 GPU를 사용하는 특성이 다르다.

- **Prefill**은 여러 토큰을 병렬로 처리하면서 큰 행렬 연산을 수행한다. 그래서 일반적으로 GPU의 연산 성능이 중요한 단계다.
- 반대로 **Decode**는 한 번에 새로운 토큰 하나를 생성하고, 기존 모델 가중치와 KV Cache를 반복해서 읽는다.
  특히 동시 요청 수가 적으면 GPU가 수행하는 연산에 비해 읽어야 하는 데이터가 많아져 메모리 대역폭이 주요 병목이 되기 쉽다.

이러한 차이 때문에 두 단계의 성능을 서로 다른 지표로 평가한다.

- **TTFT(Time To First Token)** 는 요청을 보낸 후 첫 번째 출력 토큰이 나올 때까지 걸리는 시간이다. 대기열, 입력 처리, Prefill 등이 영향을 준다.
- **TPOT(Time Per Output Token)** 는 출력 토큰을 생성하는 데 걸리는 평균 시간으로, 답변 생성 속도를 평가할 때 사용한다.

긴 문서에 질문하는 서비스는 Prefill 성능이 중요하고, 긴 답변을 생성하는 서비스는 Decode 성능이 특히 중요할 수 있다.

KV Cache는 주로 Decode에서 반복 계산을 줄이는 데 중요한 역할을 한다.

## 3. KV Cache 메모리를 효율적으로 관리하는 방법

### 1) KV Cache는 얼마나 많은 메모리를 사용하는가?

KV Cache는 입력 토큰과 생성된 토큰의 Key, Value를 저장한다.

따라서 사용량은 주로 다음 요소들에 의해 결정된다.

모델의 Transformer 층 수가 많을수록 저장할 정보가 증가한다. Key와 Value의 차원도 영향을 주며, 저장에 사용하는 데이터 정밀도도 중요하다.

또한 문맥에 포함된 토큰 수와 동시에 처리하는 요청 수가 늘어나면 전체 KV Cache의 메모리 사용량도 증가한다.

#### (1) 계산식과 변수

기본적인 계산식은 다음과 같다.

$$
\begin{aligned}
\text{KV Cache 크기}={}&2\times L\times H_{kv}\\
&\times D\times T\times B
\end{aligned}
$$

여기에서 각 변수는 다음을 의미한다.

- $L$: Transformer 층 수
- $H_{kv}$: Key와 Value의 헤드 수
- $D$: 헤드 하나의 차원
- $T$: 저장하는 전체 토큰 수
- $B$: 원소 하나의 바이트 수

맨 앞의 2는 Key와 Value를 각각 저장하기 때문이다.

#### (2) 계산 예시

실제로 계산해 보자.

Transformer가 32개 층이고, Key와 Value의 헤드가 각각 8개이며, 헤드 차원이 128이고 FP16을 사용한다고 가정하자.

토큰 하나를 저장하는 데 필요한 용량은 다음과 같다.

$$
2\times32\times8\times128\times2
=131{,}072\text{ bytes}
$$

이는 약 **128KiB**다.

따라서 문맥 길이가 **4,096토큰**이라면 KV Cache만 약 **512MiB**가 필요하다.

동일한 길이의 요청을 **8개** 동시에 처리한다면 약 **4GiB**가 된다.

이 수치는 계산 원리를 설명하기 위한 가상의 모델 설정이며, 실제 사용량은 모델 구조와 캐시 구현에 따라 달라진다.

이 계산에서 중요한 점은 모델 가중치는 그대로 유지되더라도, 사용자 요청이 많아지면 KV Cache가 차지하는 메모리가 크게 증가한다는 것이다.

따라서 LLM 서비스의 최대 동시 처리량은 GPU 연산 성능뿐 아니라 KV Cache에 사용할 수 있는 메모리 용량에 따라서도 결정된다.

### 2) 기존 KV Cache 관리 방식의 문제

각 사용자 요청에 필요한 KV Cache의 크기는 서로 다르다.

어떤 사용자는 100토큰의 질문을 보내고, 다른 사용자는 5,000토큰의 문서를 입력한다. 답변 길이도 각 요청마다 달라진다.

이때 모든 요청에 동일한 최대 길이만큼 메모리를 미리 할당한다면 낭비가 발생한다.

예를 들어 요청마다 최대 4,096토큰을 처리할 수 있도록 메모리를 예약했지만 실제로는 500토큰만 사용하는 경우, 남은 공간의 상당 부분을 활용하지 못할 수 있다.

반대로 실제 사용하는 만큼만 연속적인 메모리 공간을 계속 확장하는 방식도 관리가 복잡하다.

토큰이 생성될 때마다 KV Cache가 늘어나고, 다른 요청이 종료되면서 메모리 공간이 해제되기 때문이다.

이 과정에서 메모리 단편화 문제가 발생할 수 있다.

결과적으로 GPU에 여유 메모리가 남아 있더라도 새로운 요청에 필요한 공간을 확보하기 어려운 상황이 생길 수 있다.

### 3) PagedAttention은 무엇인가?

이러한 문제를 해결하기 위해 vLLM에서 도입한 대표적인 기술이 PagedAttention이다.

PagedAttention의 핵심은 KV Cache를 하나의 큰 연속 공간으로 관리하는 대신, 일정한 크기의 블록(Block)으로 나누어 저장하고 관리하는 것이다.

앞에서 설명한 운영체제의 가상 메모리 관리 방식과 유사한 아이디어를 활용한다.

예를 들어 KV Cache 블록 하나가 16개 토큰의 데이터를 저장한다고 가정하자.

어떤 요청에서 40토큰의 정보를 저장해야 한다면 16토큰짜리 블록 두 개와 나머지 8토큰을 위한 블록 하나, 총 세 개의 블록을 사용한다.

이때 실제 GPU 메모리에서 세 블록이 반드시 연속해서 배치될 필요는 없다.

시스템은 각 요청의 논리적인 토큰 위치가 실제 어느 물리적 블록에 저장되는지 관리한다.

새로운 토큰이 생성되어 기존 블록이 가득 차면 추가 블록을 확보하고, 요청이 종료되면 사용하던 블록을 반환한다.

이렇게 하면 필요한 만큼 메모리를 점진적으로 할당할 수 있다.

또한 요청마다 최대 출력 길이에 해당하는 메모리를 처음부터 모두 예약할 필요가 줄어든다.

PagedAttention은 KV Cache의 메모리 낭비를 줄이고, 같은 GPU에서 더 많은 요청을 동시에 처리할 수 있도록 돕는다.

다만 블록의 마지막에 사용되지 않은 공간이 남을 수 있으므로 메모리 낭비가 완전히 사라지는 것은 아니다. 블록 크기에 따라 관리 효율과 낭비되는 공간도 달라질 수 있다.

### 4) 일반적인 KV Cache와 Prefix Caching의 차이

KV Cache와 관련해 알아두면 좋은 기술이 Prefix Caching이다.

- **일반적인 KV Cache**는 하나의 요청에서 이미 처리한 토큰의 정보를 재사용한다.
- 반면 **Prefix Caching**은 여러 요청 사이에 공통으로 등장하는 입력 구간의 KV Cache를 재사용하는 기술이다.

예를 들어 동일한 시스템 프롬프트와 문서가 여러 요청의 앞부분에 반복해서 등장한다면, 조건이 맞을 경우 해당 구간의 Key와 Value를 다시 계산할 필요가 없다.

이 기능을 사용하면 반복되는 공통 입력에 대한 Prefill 계산량을 줄일 수 있다.

다만 캐시 재사용에는 조건이 있다. 토큰 배열과 앞선 문맥이 동일해야 하며, 모델이나 관련 설정도 호환되어야 한다.

공통 입력이 중간에 달라지면 이후 구간의 어텐션 계산 결과도 달라질 수 있으므로 무조건 재사용할 수는 없다.

Prefix Caching은 공통 프롬프트가 많은 챗봇이나 문서 기반 서비스에서 특히 효과적일 수 있다.

### 5) KV Cache를 줄이는 다른 기술들

KV Cache의 메모리 사용량을 줄이는 방법은 여러 가지가 있다.

#### (1) GQA

대표적인 방법이 GQA(Grouped-Query Attention) 다.

일반적인 Multi-Head Attention에서는 Query, Key, Value가 각각 여러 개의 헤드를 사용한다.

GQA는 여러 Query 헤드가 상대적으로 적은 수의 Key와 Value 헤드를 공유하도록 구성한다.

그 결과 어텐션 계산에 필요한 KV Cache의 크기를 줄일 수 있다.

예를 들어 Query 헤드가 32개이더라도 KV 헤드를 8개만 사용한다면, 동일한 헤드 차원과 데이터 정밀도에서 일반적인 32개 KV 헤드 구조보다 KV Cache 사용량이 약 4분의 1로 감소한다.

#### (2) KV Cache 양자화

KV Cache 자체를 더 낮은 비트 정밀도로 저장하는 방법도 있다.

FP16 대신 FP8 등의 형식을 활용하면 원소당 저장 용량을 줄일 수 있다. 다만 모델과 실행 환경의 지원 여부, 정확도에 미치는 영향, 실제 연산 효율을 확인해야 한다.

#### (3) FlashAttention

또 다른 기술인 FlashAttention은 어텐션 계산 과정의 중간 데이터를 효율적으로 처리한다.

이는 주로 어텐션 연산의 메모리 접근량과 임시 메모리 사용량을 줄이는 기술로, KV Cache의 저장 공간을 블록 단위로 관리하는 PagedAttention과는 해결하는 문제가 다르다.

즉, LLM의 메모리 최적화는 가중치뿐 아니라 KV Cache의 크기, 중간 계산 과정, 메모리 할당 방식까지 함께 고려해야 한다.

## 4. 실제 AI 서비스에서 GPU를 효율적으로 사용하는 방법

### 1) 사용자가 여러 명이면 무엇이 달라지는가?

개인적으로 LLM을 실행하는 것과 여러 사용자가 동시에 접속하는 서비스를 운영하는 것은 차이가 크다.

한 명의 사용자에게 답변하는 경우에는 해당 요청에 필요한 계산과 메모리를 관리하면 된다.

그러나 동시에 10명, 100명의 사용자가 질문한다면 요청마다 입력 길이와 생성할 답변의 길이가 달라진다.

어떤 요청은 Prefill을 수행하고, 다른 요청은 Decode를 진행하고 있을 수 있다. 이미 답변을 완료한 요청도 있고, 새로 들어온 요청도 있다.

따라서 GPU에 들어오는 작업을 어떻게 묶고 어떤 순서로 실행할 것인지 결정해야 한다.

이 작업을 담당하는 핵심 요소가 스케줄러(Scheduler)다.

스케줄러는 요청들의 실행 순서를 관리하고, 제한된 GPU 메모리와 연산 자원 안에서 처리할 작업을 선택한다.

### 2) Batching과 Continuous Batching

GPU는 여러 데이터를 동시에 처리할 때 효율이 높아질 수 있다.

#### (1) Batching

Batching은 여러 요청을 묶어 하나의 배치로 처리하는 방식이다.

예를 들어 서로 다른 사용자의 요청 8개를 묶어서 GPU에서 함께 계산할 수 있다.

하지만 전통적인 고정 배치 방식에서는 문제가 발생한다.

각 요청의 답변 길이가 다르기 때문에 어떤 요청은 일찍 끝나고 다른 요청은 계속 생성해야 한다.

이미 끝난 요청의 자리가 비어 있어도 배치 구성이 고정되어 있으면 새로운 요청을 효율적으로 투입하기 어렵다.

#### (2) Continuous Batching

이 문제를 개선하는 방식이 Continuous Batching(연속 배칭) 이다.

Continuous Batching은 추론이 진행되는 동안 배치를 동적으로 관리한다.

요청 하나가 완료되면 사용하던 자원을 반환하고, 대기하고 있는 새로운 요청을 처리 대상에 추가할 수 있다.

이 방식은 GPU가 처리할 수 있는 작업을 지속적으로 공급하여 전체 처리량을 높이는 데 도움이 된다.

vLLM과 같은 추론 엔진에서 Continuous Batching과 효율적인 KV Cache 관리를 함께 사용하는 이유가 여기에 있다.

다만 GPU가 처리하는 요청 수를 무조건 늘린다고 모든 사용자의 응답이 빨라지는 것은 아니다.

전체 처리량은 증가하더라도 개별 요청의 지연 시간이 길어질 수 있기 때문에 적절한 동시성 관리가 필요하다.

### 3) 메모리가 부족하면 어떻게 해결하는가?

LLM 실행 중 GPU 메모리가 부족해지는 현상을 OOM(Out Of Memory)이라고 한다.

OOM은 모델을 처음 불러올 때 발생할 수도 있고, 정상적으로 실행되던 모델이 긴 입력이나 많은 동시 요청을 처리하면서 발생할 수도 있다.

원인에 따라 해결 방법이 달라진다.

#### (1) 모델 가중치가 큰 경우

모델 가중치가 너무 큰 경우에는 더 작은 모델을 사용하거나 가중치를 양자화할 수 있다.

예를 들어 FP16을 INT8이나 4비트 양자화 형식으로 바꾸면 가중치를 저장하는 데 필요한 메모리가 감소한다.

#### (2) KV Cache가 큰 경우

KV Cache가 너무 큰 경우에는 입력 문맥 길이, 최대 생성 토큰 수, 동시 처리 요청 수를 조정할 수 있다.

GQA를 지원하는 모델을 선택하거나 KV Cache 양자화 기능을 활용하는 방법도 고려할 수 있다.

#### (3) 중간 계산 메모리가 부족한 경우

중간 계산 과정에서 메모리가 부족한 경우에는 배치 크기를 줄이거나, 메모리 효율적인 어텐션 연산을 사용하거나, 실행 설정을 조정할 수 있다.

여기서 기억해야 할 점은 가중치 양자화와 KV Cache 양자화가 서로 다른 대상에 적용된다는 사실이다.

가중치를 4비트로 줄여도 KV Cache가 FP16으로 유지될 수 있다. 따라서 가중치의 크기를 크게 줄였는데도 긴 문맥을 처리할 때 메모리가 부족할 수 있다.

### 4) CPU 메모리를 함께 사용하면 해결될까?

#### (1) CPU Offloading

GPU 메모리가 부족할 때 일부 데이터를 CPU의 시스템 RAM으로 옮기는 방법도 있다.

이를 CPU Offloading이라고 한다.

모델 가중치나 일부 캐시 데이터를 CPU 메모리에 보관하다가 필요할 때 GPU로 가져오는 방식이다.

이 방법을 사용하면 제한된 VRAM으로 더 큰 모델이나 작업을 처리할 수 있다.

그러나 CPU와 GPU 사이에서 데이터를 전송하는 데 시간이 필요하다.

특히 CPU와 GPU가 별도의 메모리를 사용하는 시스템에서는 데이터 전송 경로의 대역폭과 지연 시간이 성능에 영향을 준다.

LLM의 Decode 단계에서는 모델 가중치와 과거 토큰의 정보를 반복해서 사용하기 때문에 데이터 이동이 자주 발생하면 생성 속도가 크게 느려질 수 있다.

따라서 CPU Offloading은 메모리 용량 부족을 해결하기 위한 선택지지만, 실제 성능은 데이터 이동량과 하드웨어 구성에 따라 평가해야 한다.

#### (2) Tensor Parallelism

GPU를 여러 개 사용하는 방법도 있다.

하나의 모델을 여러 GPU에 나누어 배치하는 Tensor Parallelism 같은 기술을 사용하면 GPU 한 개에 들어가지 않는 모델도 실행할 수 있다.

다만 여러 GPU가 중간 계산 결과를 주고받는 통신 비용이 추가되므로, GPU 수를 늘렸을 때 성능이 비례해서 증가하는 것은 아니다.

### 5) 실제 성능은 무엇으로 평가해야 하는가?

LLM 추론 시스템의 성능을 평가할 때는 단순히 모델 실행 성공 여부나 GPU 메모리 사용량만 살펴보면 충분하지 않다.

확인해야 할 중요한 지표들이 있다.

| 지표 | 의미 |
| --- | --- |
| TTFT | 요청 이후 첫 토큰까지 걸린 시간 |
| TPOT | 출력 토큰 하나를 생성하는 평균 시간 |
| Throughput | 초당 처리하는 요청 또는 토큰의 수 |
| GPU 메모리 사용량 | 모델과 캐시 등에 사용 중인 메모리 |
| 동시 처리 요청 수 | 동시에 처리하는 사용자 요청의 수 |
| OOM 발생 여부 | 메모리 부족으로 실행이 실패하는지 |

#### (1) 응답 속도와 처리량

여기서 TTFT와 TPOT는 사용자 한 명이 체감하는 응답 속도와 직접적인 관련이 있다.

Throughput은 서비스 전체가 처리하는 작업량을 의미한다.

두 지표는 항상 같은 방향으로 움직이지 않는다.

예를 들어 배치 크기를 늘리면 전체 처리량이 증가할 수 있지만, 동시에 개별 요청이 기다려야 하는 시간이 늘어날 수도 있다.

#### (2) 메모리 측정값 구분

또한 GPU 메모리를 측정할 때는 측정값의 종류를 구분해야 한다.

PyTorch와 같은 프레임워크에서는 실제 텐서에 할당된 메모리와 메모리 할당자가 확보해 둔 예약 메모리가 다르게 나타날 수 있다.

nvidia-smi에서 확인하는 프로세스의 GPU 메모리 사용량도 PyTorch의 텐서 할당량과 차이가 날 수 있다.

이미 사용이 끝난 텐서의 공간이 재사용을 위해 예약 상태로 남아 있기 때문이다.

따라서 메모리 최적화 전후의 성능을 비교하려면 동일한 조건에서 메모리 사용량, 최대 메모리 사용량, 요청 지연 시간과 처리량을 함께 측정해야 한다.

### 6) LLM 추론과 이미지 생성 모델의 차이

생성형 AI는 텍스트 외에도 이미지와 같은 데이터를 생성한다.

이미지 생성에 사용하는 확산 모델(Diffusion Model) 역시 GPU의 연산 성능과 메모리 용량에 영향을 받는다.

다만 LLM과 계산 방식에는 차이가 있다.

- **LLM**은 일반적으로 토큰을 순차적으로 생성하면서 KV Cache를 활용한다.
- 반면 **확산 모델**은 노이즈가 포함된 표현에서 여러 단계에 걸쳐 노이즈를 제거해 이미지를 생성하는 방식을 사용한다.

따라서 확산 모델의 추론 성능에는 이미지 해상도, 생성 단계 수, 모델 구조, 배치 크기, 중간 텐서의 크기 등이 중요한 영향을 준다.

두 유형 모두 모델 가중치와 중간 계산 결과를 위한 GPU 메모리가 필요하지만, 병목과 최적화 방법에는 차이가 있다.

실제 서비스를 설계할 때는 모델의 종류와 연산 방식에 맞춰 GPU 자원 관리 전략을 선택해야 한다.

## 5. 최종 정리: 이번 내용에서 반드시 이해해야 할 것

### 1) 전체 흐름

이번 학습을 하나로 연결하면 다음과 같다.

1. LLM은 입력 토큰을 처리하는 Prefill과 토큰을 순차적으로 생성하는 Decode를 거쳐 답변을 만든다.
2. 이 과정에서 GPU는 모델 가중치를 읽고 어텐션을 비롯한 신경망 연산을 수행한다.
3. Decode에서 이전 토큰의 Key와 Value를 매번 다시 계산하면 비효율적이므로 KV Cache를 사용해 이전 계산 결과를 재사용한다.
4. KV Cache는 계산량을 줄이는 대신 GPU 메모리를 추가로 사용한다. 문맥이 길어지고 동시에 처리하는 사용자가 많아질수록 이 메모리는 증가한다.
5. PagedAttention은 KV Cache를 블록 단위로 관리하여 메모리 사용 효율을 높인다. Continuous Batching은 여러 요청을 동적으로 묶어 GPU 처리량을 개선한다.
6. 여기에 가중치 양자화, KV Cache 양자화, GQA, 메모리 효율적인 어텐션, CPU Offloading 등의 기술을 상황에 맞게 적용할 수 있다.

### 2) 추론 최적화의 세 가지 핵심

결국 LLM 추론 최적화의 핵심은 세 가지다.

1. **불필요한 계산을 줄이는 것.** KV Cache와 Prefix Caching이 대표적이다.
2. **제한된 GPU 메모리를 효율적으로 사용하는 것.** 양자화와 PagedAttention 등이 여기에 해당한다.
3. **GPU가 여러 요청을 효율적으로 처리하도록 만드는 것.** Batching, 스케줄링, 연산 최적화 등이 이 역할을 한다.

이 세 가지 원리를 이해하면 LLM이 느려지는 이유, GPU 메모리가 부족해지는 원인, vLLM과 같은 추론 엔진을 사용하는 목적을 연결해서 이해할 수 있다.
