title: "D53. GPU 메모리와 LLM 추론"
---

LLM으로 챗봇을 만들면 짧은 질문에는 잘 답하다가, 긴 문서를 넣었을 때 답변이 늦어지거나 메모리가 부족해질 수 있습니다. 같은 모델을 사용해도 입력 길이와 답변 길이에 따라 필요한 계산과 저장 공간이 달라지기 때문입니다.

여기서는 **LLM이 답변을 만드는 과정과 그 과정에서 GPU 메모리가 쓰이는 곳**을 배웁니다. 이를 이해하면 모델 크기, 대화 길이, 동시 요청 수를 조정할 때 무엇이 달라지는지 설명할 수 있습니다.

## 학습 목표와 흐름

| 배울 내용 | 이해할 내용 |
|---|---|
| 토큰과 Attention | 문장이 모델의 입력이 되고 다음 토큰이 선택되는 과정 |
| Prefill과 Decode | 입력을 한꺼번에 읽는 단계와 토큰을 이어 만드는 단계 |
| KV 캐시 | 이전 계산을 재사용하는 이유와 필요한 저장 공간 |
| GPU 메모리 | 가중치·캐시·중간값이 각각 차지하는 공간 |
| 속도와 요청 처리 | 응답 시간을 측정하고 생성 작업을 관리하는 방법 |

## 자습

### 1. LLM이 질문을 읽고 답변을 만드는 과정

챗봇에 질문을 보내면 모델은 먼저 글을 계산할 수 있는 숫자로 바꿉니다. 글을 나누어 처리하는 단위가 Token(토큰)이고, 각 토큰을 나타내는 정수 번호가 Token ID(토큰 ID)입니다. 토크나이저가 문자열을 토큰 ID 목록으로 변환합니다.

모델은 각 ID를 Embedding(임베딩) 벡터로 바꿉니다. 벡터는 여러 숫자로 이루어진 표현입니다. 이 표현이 여러 층을 지나면서 앞뒤 문맥을 반영하고, 마지막에는 다음에 나올 토큰들의 점수가 계산됩니다.

**질문 → 토큰 ID → 임베딩 → 여러 층의 계산 → 다음 토큰 점수 → 토큰 선택**

이 과정에서 Weight(가중치)는 학습으로 정해진 계산 기준이고, Hidden state(은닉 상태)는 현재 입력을 처리하면서 만들어진 표현입니다. 같은 모델에 다른 질문을 넣으면 같은 가중치를 사용하면서 서로 다른 은닉 상태를 계산합니다.

GPT 계열 모델은 학습할 때 앞의 토큰을 보고 다음 토큰을 예측하도록 가중치를 조정합니다. 추론할 때는 학습된 가중치로 다음 토큰을 선택하고, 선택한 토큰을 입력 뒤에 붙여 그다음 토큰을 예측합니다. 이 과정이 반복되어 답변이 만들어집니다.

### 2. 문맥을 반영하는 Attention과 Q·K·V

다음 토큰을 고르려면 앞에서 나온 내용 중 무엇을 얼마나 참고할지 정해야 합니다. Transformer는 **Attention(어텐션)**으로 토큰 사이의 관계를 계산하고, 그 관계에 따라 정보를 섞습니다.

CNN은 가까운 위치를 묶어 특징을 만들고, RNN은 앞 단계의 상태를 다음 단계로 전달합니다. Transformer에서는 각 위치가 참고할 위치들과의 관계를 직접 계산합니다. 위치 정보는 토큰의 순서를 알려주고, 마스크는 참고할 수 있는 범위를 정합니다.

Attention 계산을 위해 각 토큰의 표현을 세 종류의 벡터로 변환합니다. 이 변환에도 학습된 가중치가 사용됩니다.

| 값 | 이름 | 계산에서 하는 일 |
|---|---|---|
| Q | Query(쿼리) | 현재 위치에서 참고할 정보를 찾기 위한 비교 기준 |
| K | Key(키) | 각 위치가 Q와 비교할 특징 |
| V | Value(값) | 비중에 따라 섞어 전달할 정보 |

먼저 Q와 각 K를 비교해 점수를 구합니다. 점수를 조절하고 마스크를 적용한 뒤, Softmax(소프트맥스)로 합이 1인 비율을 만듭니다. 마지막으로 그 비율만큼 각 V를 반영합니다.

예를 들어 세 위치의 비율이 0.1·0.2·0.7이고 V가 각각 [10, 0]·[0, 10]·[10, 10]이면 결과는 [8, 9]입니다. 세 번째 위치의 정보가 가장 큰 비중으로 들어갑니다.

이 계산을 식으로 모으면 다음과 같습니다.

$$O=\operatorname{softmax}\left(\frac{QK^{\mathsf T}}{\sqrt d}+M\right)V$$

$d$는 Q·K 벡터의 차원이며, $\sqrt d$로 나누어 점수 크기를 조절합니다. $M$은 마스크입니다. 허용된 위치에는 0을, 가릴 위치에는 매우 작은 값을 더해 Softmax 뒤의 비중이 0에 가까워지게 합니다.

이 계산을 여러 묶음으로 나누는 단위가 Head(헤드)입니다. 각 헤드는 서로 다른 가중치로 관계를 계산합니다. Attention map(어텐션 맵)은 선택한 층과 헤드에서 나온 비율을 그림으로 보여줍니다. 행은 정보를 읽는 위치, 열은 참고하는 위치이고, 칸의 값은 해당 위치에 배분한 비중입니다.

### 3. 입력 처리와 답변 생성, 그리고 KV 캐시

LLM이 답변을 이어 쓸 때마다 질문 전체를 처음부터 계산하면 같은 작업을 반복하게 됩니다. 이를 줄이기 위해 이전 토큰에서 계산한 K와 V를 저장해 둡니다. 이 저장 공간이 **KV cache(KV 캐시)**입니다.

GPT 계열의 Causal mask(인과적 마스크)는 각 위치가 자신과 앞선 위치만 참고하도록 합니다. 뒤에 새 토큰이 붙어도 이전 위치가 참고하는 내용은 그대로이므로, 이전 K·V를 다음 계산에서 재사용할 수 있습니다.

답변 생성은 다음 두 단계로 나눌 수 있습니다.

| 단계 | 하는 일 | KV 캐시의 변화 |
|---|---|---|
| Prefill(입력 처리) | 질문·문서·대화 기록을 읽고 첫 답변 토큰을 예측 | 입력 위치의 K·V 저장 |
| Decode(순차 생성) | 직전에 선택한 토큰을 처리해 다음 토큰 예측 | 새 위치의 K·V 추가 |

예를 들어 질문을 읽고 첫 답변 토큰을 선택했다면, 다음 단계에서는 그 토큰의 Q·K·V를 계산합니다. 새 Q는 저장된 K들과 새 K를 참고하고, 그 비율로 저장된 V들과 새 V를 섞습니다. 각 층은 자신의 K·V를 따로 보관합니다.

이 구조 때문에 입력이 길어지면 처음 읽을 내용이 많아지고, 답변이 길어지면 순차 생성 횟수와 캐시 길이가 늘어납니다. KV 캐시는 메모리를 사용해 반복 계산을 줄이는 방법입니다.

여러 요청이 공통으로 사용하는 앞부분의 계산을 재사용하는 것은 Prefix cache(프리픽스 캐시)입니다. 한 답변 안에서 사용하는 KV 캐시를 이해하면, 공통 시스템 메시지 같은 내용을 요청 사이에서 재사용하는 원리로 이어집니다.

### 4. 가중치와 요청에 필요한 GPU 메모리

사용할 GPU를 고르거나 처리할 수 있는 대화 길이를 정하려면 메모리가 어디에 쓰이는지 나누어 봐야 합니다. 모델을 로드하면 가중치가 올라가고, 질문을 처리하는 동안 캐시와 중간 계산값이 추가됩니다.

| 메모리를 사용하는 대상 | 크기를 좌우하는 조건 |
|---|---|
| 가중치 | 파라미터 수와 저장 자료형 |
| KV 캐시 | 층 수·KV 헤드 수·토큰 수·요청 수·자료형 |
| 중간 계산값 | 입력 길이·배치 크기·연산 구현 |
| 실행 환경 | CUDA와 라이브러리가 사용하는 공간 |

가중치 저장량은 파라미터 수에 값 하나의 바이트 수를 곱해 계산합니다. FP16과 BF16은 값 하나에 2바이트를 사용하므로, 가중치가 15억 개인 모델은 가중치에 약 3GB를 사용합니다. 같은 양을 GiB로 쓰면 약 2.794GiB입니다. GB는 $10^9$바이트, GiB는 $1024^3$바이트입니다.

KV 캐시는 K와 V를 층마다, 토큰마다 저장합니다. 일반적인 저장량 계산은 다음과 같습니다.

$$\text{KV 바이트}=2\times L\times H_{KV}\times D_{head}\times T\times B\times s$$

$L$은 층 수, $H_{KV}$는 KV 헤드 수, $D_{head}$는 헤드 차원입니다. $T$는 저장한 토큰 수, $B$는 함께 처리하는 요청 수, $s$는 원소당 바이트입니다. 맨 앞의 2는 K와 V 두 종류를 뜻합니다.

Qwen2.5-1.5B-Instruct는 28층, Q 헤드 12개, KV 헤드 2개, 헤드 차원 128을 사용합니다. 여러 Q 헤드가 K·V를 공유하는 GQA(그룹 쿼리 어텐션) 구조이므로, 위 식에는 KV 헤드 수인 2를 넣습니다.

FP16에서 토큰 하나의 KV 저장량은 $2\times28\times2\times128\times2=28,672$바이트, 즉 28KiB입니다. 1,024토큰인 요청 하나는 28MiB, 같은 길이의 요청 두 개는 56MiB입니다. 이 값에 가중치와 중간 계산값 등의 공간을 더해 실행에 필요한 메모리를 파악합니다.

### 5. 긴 입력의 메모리 부담을 줄이는 FlashAttention

긴 문서를 입력하면 Attention에서도 많은 중간값이 생깁니다. 토큰이 $N$개일 때 각 위치 사이의 점수를 한꺼번에 만들면 $N\times N$ 행렬이 필요합니다. 1,000토큰에서 100만 칸이던 행렬이 2,000토큰에서는 400만 칸으로 커집니다.

이 큰 행렬을 GPU 메모리에 쓰고 다시 읽는 데도 시간이 걸립니다. **FlashAttention은 계산을 작은 블록으로 나누어 처리하면서 이 메모리 이동을 줄입니다.**

GPU의 HBM(고대역폭 메모리)은 큰 가중치와 텐서를 보관하고, GPU 내부의 SRAM(정적 메모리)은 작지만 빠른 작업 공간으로 사용됩니다. FlashAttention은 작은 블록을 빠른 메모리로 가져와 점수 계산·Softmax·가중합을 이어 수행합니다.

Online softmax(온라인 소프트맥스)는 블록을 차례로 처리하면서 전체에 맞는 정규화 값과 출력을 누적하는 방법입니다. 덕분에 전체 점수 행렬을 HBM에 보관하는 부담을 줄일 수 있습니다.

KV 캐시는 이전 토큰의 계산을 재사용하고, FlashAttention은 Attention 내부의 중간값 저장과 이동을 줄입니다. 두 방법은 서로 다른 부분을 줄이므로 함께 사용할 수 있습니다. PyTorch의 SDPA(스케일 조정 내적 어텐션) 기능은 입력과 장치 조건에 맞는 Attention 구현을 선택해 계산합니다.

### 6. 메모리 사용량과 OOM 메시지를 읽는 방법

실행 중 메모리가 부족해졌다면 어떤 값이 늘었는지 확인해야 합니다. GPU 전체의 여유 공간과 현재 프로그램의 텐서 사용량은 측정 범위가 다릅니다.

| 지표 | 보여주는 값 | 확인하는 상황 |
|---|---|---|
| Free(여유량) | GPU에서 현재 사용할 수 있는 공간 | 모델을 올리기 전 |
| Allocated(할당량) | 현재 프로그램의 살아 있는 PyTorch 텐서 | 모델·입력·출력의 사용량 확인 |
| Reserved(예약량) | PyTorch가 확보한 전체 공간 | 텐서와 재사용할 빈 공간 확인 |
| Peak(최대값) | 측정 구간의 가장 높은 텐서 사용량 | 생성 도중의 순간 최대값 확인 |

Reserved 안에는 Allocated가 포함됩니다. 텐서를 더 이상 참조하지 않으면 할당량이 줄고, 그 공간은 이후 텐서에 재사용할 수 있도록 예약량에 남습니다. 이 메모리 관리는 토큰의 K·V를 보관하는 KV 캐시와 용도가 다릅니다.

OOM(메모리 부족) 메시지를 읽을 때는 먼저 이번에 추가로 요청한 양과 현재 여유량을 비교합니다. 모델을 올리는 순간 실패했다면 가중치와 기존 모델의 메모리를, 긴 질문을 처리하다 실패했다면 입력 길이·캐시·중간값을 살펴봅니다. 요청을 함께 처리하다 실패했다면 동시 요청 수의 영향을 확인합니다.

`nvidia-smi`는 GPU와 실행 중인 프로그램의 상태를 보여줍니다. 여기서 GPU-Util은 최근 구간에 연산이 실행된 시간의 비율입니다. 모델을 올려 둔 채 질문을 기다리면 연산 활동은 낮아져도 가중치 메모리는 계속 사용합니다.

### 7. 사용자가 느끼는 응답 속도의 측정

챗봇의 속도는 답변이 시작될 때까지의 기다림과, 시작된 답변이 이어지는 속도로 나누면 이해하기 쉽습니다. 긴 문서를 읽는 서비스와 긴 글을 쓰는 서비스는 두 구간에 주는 부담도 다릅니다.

**TTFT(Time to First Token, 첫 토큰 시간)**는 요청 후 첫 토큰을 얻을 때까지 걸린 시간입니다. **생성 속도**는 측정 구간에 새로 생성한 토큰 수를 그 구간의 시간으로 나눈 값입니다. 입력 처리까지 포함한 전체 속도를 측정할지, 첫 토큰 이후의 Decode 속도를 측정할지 정해 기록합니다.

속도를 비교할 때는 같은 GPU·모델·입력 길이·출력 길이를 사용합니다. 첫 실행에는 준비 작업이 포함되므로 Warm-up(예열)을 거친 뒤 반복 측정합니다. GPU 계산은 CPU의 명령 전달과 별도로 진행되기 때문에, 시간 측정 경계에서 계산 완료를 기다립니다.

실제 서비스에서는 요청 대기열, 토큰화, 통신 시간도 사용자의 기다림에 포함됩니다. 모델 계산 시간과 서비스 응답 시간을 각각 기록하면 지연이 어느 구간에서 발생하는지 찾을 수 있습니다.

### 8. 모델을 API에 연결하고 생성을 끝내는 과정

여러 사용자가 챗봇을 이용하려면 입력을 받아 모델에 전달하고, 만들어진 답을 돌려주는 API가 필요합니다. 모델과 토크나이저를 서버 시작 시 준비해 두면 요청마다 같은 모델을 재사용할 수 있습니다.

**요청 검사 → 대화 형식 적용 → 토큰 길이 확인 → 모델 생성 → 답변 반환**

Chat template(대화 형식)은 사용자·시스템·모델의 메시지를 역할 표시와 함께 모델 입력으로 구성합니다. 이전 대화도 입력에 들어가므로, 대화 형식을 적용한 전체 입력의 토큰 수를 확인합니다. 이렇게 얻은 길이가 캐시와 입력 처리량을 결정하는 기준이 됩니다.

동시에 생성하는 요청이 늘면 요청별 캐시와 중간값도 늘어납니다. 한 번에 하나씩 생성하도록 구성하면 나머지 요청은 대기열에서 기다립니다. 비동기 요청 처리는 기다리는 동안 다른 요청의 검사나 응답을 진행하게 합니다.

사용자가 답변 생성을 취소할 때는 모델 계산도 끝내야 합니다. 화면이 출력 읽기를 멈춘 뒤에도 별도 생성 작업이 계속 돌 수 있으므로, 생성 쪽에서 확인할 중지 신호를 전달합니다.

**취소 요청 → 중지 신호 전달 → 생성 반복에서 확인 → 생성 종료 → 작업 종료 확인**

이 과정으로 사용하지 않을 답변의 추가 계산을 끝내고 다음 요청을 처리할 수 있습니다.

## 이해 확인

> [!question]- 질문과 답변이 길어질 때 각각 무엇이 늘어나나요?
> 질문이 길면 Prefill에서 처리할 입력이 늘고, 답변이 길면 Decode 반복 횟수가 늘어납니다. 처리한 토큰이 많아질수록 보관할 KV 캐시도 커집니다.

> [!question]- KV 캐시에는 무엇을 저장하며 왜 다시 사용할 수 있나요?
> 층별로 이전 위치의 K·V를 저장합니다. 인과적 마스크 때문에 새 토큰이 붙어도 이전 위치의 계산 조건이 유지됩니다.

> [!question]- KV 캐시와 FlashAttention은 어떤 작업을 줄이나요?
> KV 캐시는 이전 토큰의 재계산을 줄이고, FlashAttention은 Attention 중간값의 저장과 메모리 이동을 줄입니다.

> [!question]- Allocated와 Reserved는 어떤 관계인가요?
> Reserved는 살아 있는 텐서의 Allocated와 재사용할 빈 공간을 포함합니다.

> [!question]- 사용자가 생성을 취소하면 서버에서 어떤 처리가 필요한가요?
> 생성 작업에 중지 신호를 전달하고, 생성 반복이 이를 확인해 끝난 뒤 작업의 종료를 확인합니다.
