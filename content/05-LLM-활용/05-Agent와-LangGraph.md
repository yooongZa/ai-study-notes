title: "05. Agent와 LangGraph"
---

사용자가 “문서에서 지난달 실적을 찾고 합계를 계산해 줘”라고 요청하면 검색과 계산이 함께 필요합니다. 첫 검색에서 자료가 부족하면 질문을 바꾸거나 다른 도구를 선택해야 합니다. 이 강의에서는 **모델의 판단을 도구 실행과 연결하고, 진행 상태를 관리하는 방법**을 배웁니다.

## 학습 목표와 흐름

모델이 도구를 요청하고 프로그램이 실행하는 과정을 먼저 익힙니다. 이어서 LangGraph의 상태·노드·연결로 작업 순서를 표현합니다. 대화 기록을 유지하고, 중단한 작업을 재개하며, 완료 조건에 따라 실행을 끝내는 과정까지 연결합니다.

## 자습

### 1. 작업 순서를 미리 정하는 방식과 결과를 보고 선택하는 방식

항상 “문서 검색 → 요약 → 저장”으로 끝나는 작업은 처리 순서를 미리 정할 수 있습니다. 이런 흐름이 Workflow(워크플로)입니다. 결과에 따라 간단한 분기를 추가할 수도 있습니다.

검색한 문서에 필요한 수치가 없어서 다른 검색어를 고르거나, 계산 결과를 읽고 추가 자료를 찾는 작업은 다음 행동을 판단해야 합니다. Agent(에이전트)는 목표와 현재 결과를 바탕으로 다음 행동을 선택하며 일을 진행하는 시스템입니다.

한 작업 안에서 고정 절차와 모델의 선택을 함께 사용할 수 있습니다. 입력 형식은 코드로 검사하고, 자료를 찾을 검색어는 모델이 고르도록 구성하는 식입니다. 목표와 완료 조건이 분명해야 선택한 행동이 필요한 결과로 이어지는지 확인할 수 있습니다.

### 2. 도구 호출 요청이 실제 실행으로 이어지는 과정

현재 재고나 정확한 계산값이 필요하면 모델이 사용할 조회·계산 기능을 준비해야 합니다. Tool(도구)은 이름, 설명, 입력 형식, 실제 실행 함수를 묶은 구성 요소입니다. 설명에는 언제 사용하고 어떤 결과를 돌려주는지 적습니다.

프로그램이 도구 명세를 모델에 전달하면 모델은 필요한 도구 이름과 인수를 출력합니다. 이것이 Tool call(도구 호출 요청)입니다. 실행기는 인수와 권한을 확인해 함수를 호출하고, 나온 결과를 모델에 돌려줍니다. 모델은 이 결과로 답변하거나 다음 도구를 선택합니다.

요청에는 호출 ID가 붙습니다. 여러 도구를 요청했을 때 결과가 어느 요청에 대한 것인지 연결하는 값입니다. LangChain의 `AIMessage`는 응답과 도구 요청을 담을 수 있고, `ToolMessage`는 해당 호출의 결과를 전달합니다. `bind_tools()`는 모델에 도구 명세를 연결하는 메서드이며 실제 실행은 에이전트 실행기가 맡습니다.

### 3. 여러 작업을 배치하는 방법

실적 보고서를 작성한다면 자료 수집 후 계산은 순서가 필요하지만, 서로 다른 지점의 자료 수집은 독립적으로 진행할 수 있습니다. 작업 사이의 의존 관계를 보면 적합한 실행 구조를 고르기 쉽습니다.

| 구조 | 사용하는 상황 |
|---|---|
| 순차 처리 | 앞 결과가 다음 입력이 되는 검색·요약·작성 |
| 분기 | 질문 종류에 따라 검색 또는 계산 도구 선택 |
| 병렬 처리 | 서로의 결과 없이 수행할 수 있는 자료 수집 |
| 계획과 위임 | 큰 목표를 하위 작업으로 나누고 결과를 취합 |
| 평가와 수정 | 초안을 기준에 따라 검사하고 부족한 부분 보완 |

여러 작업의 결과를 합칠 때는 반환 형식과 중복 처리 기준을 정합니다. 필요한 입력, 맡긴 범위, 완료 조건이 명확하면 서로 다른 작업의 결과도 하나의 답으로 연결할 수 있습니다.

### 4. LangGraph의 상태·노드·연결로 실행을 표현하는 방법

검색 후 답변을 만들고, 근거가 부족하면 다시 검색하는 흐름에서는 현재 정보와 다음 작업을 함께 관리해야 합니다. LangGraph는 처리할 작업을 그래프로 연결하고 그 사이에 State(상태)를 전달합니다.

상태에는 질문, 검색 결과, 답변, 시도 횟수처럼 실행을 이어 갈 값을 담습니다. Node(노드)는 상태를 읽어 처리하고 바뀔 필드를 반환하는 함수입니다. Edge(연결)는 다음에 실행할 노드를 정합니다. 조건부 연결은 현재 상태를 보고 경로를 고릅니다.

예를 들어 상태의 검색 결과가 충분하면 답변 생성으로, 비어 있으면 질문 확인으로 갈 수 있습니다. 노드 내부에는 일반 Python 계산이나 모델·도구 호출이 들어갑니다. 따라서 노드를 한 번 방문했다고 모델도 한 번 호출됐다고 세기보다 각각의 실제 호출을 기록해야 합니다.

Python의 `TypedDict`는 상태 딕셔너리의 키와 자료형을 표시합니다. 기본적으로 노드가 반환한 필드는 새 값으로 갱신됩니다. 여러 결과를 누적하려면 Reducer(갱신 규칙)를 정합니다. 메시지 누적, 중복 제거, 최신 값 선택은 서로 다른 규칙입니다.

### 5. 대화와 실행 상태를 저장하는 방법

“그 문서의 두 번째 항목도 설명해 줘”라는 질문에 답하려면 앞서 읽은 문서와 대화의 맥락이 필요합니다. 상태의 메시지 목록에 갱신 규칙을 연결하면 노드가 새 메시지만 반환해도 기록을 이어 갈 수 있습니다. LangGraph의 `add_messages`는 새 ID의 메시지를 추가하고 같은 ID의 메시지는 갱신하는 함수입니다.

진행 중인 작업을 나중에 이어가려면 메시지 외에도 중간 결과와 진행 정보를 저장합니다. 특정 시점의 상태와 실행 정보가 Checkpoint(체크포인트)이고, 이를 저장하고 불러오는 구성 요소가 Checkpointer(체크포인터)입니다. `thread_id`는 어떤 대화·실행의 상태를 사용할지 구분합니다.

`InMemorySaver`는 현재 프로세스의 메모리에 상태를 보관합니다. 프로그램을 종료한 뒤에도 이어가려면 데이터베이스 등에 저장하는 체크포인터가 필요합니다. 같은 `thread_id`로 새 입력을 보내는 것은 저장 상태에 입력을 적용해 시작하는 동작이며, 중단된 작업을 재개할 때는 그 목적에 맞는 재개 입력을 전달합니다.

### 6. 외부 입력을 기다린 뒤 작업을 재개하는 방법

문서를 외부로 전송하기 전에 사용자가 내용을 확인해야 한다면, 확인할 정보를 내보내고 실행을 멈춥니다. LangGraph의 `interrupt()`는 이런 중단을 표현하는 함수입니다. 체크포인터와 실행 ID를 설정한 그래프에서 사용합니다.

응답이 도착하면 같은 실행 ID로 `Command(resume=응답)`을 전달합니다. 응답 값은 해당 `interrupt()`의 반환값으로 사용됩니다. 재개 시에는 중단된 노드의 처음부터 다시 실행하므로, 그 앞에 둔 외부 저장·전송 작업은 재실행 여부를 고려해 배치해야 합니다. [LangGraph 중단과 재개](https://docs.langchain.com/oss/python/langgraph/interrupts)

대화 기록의 메시지 ID는 메시지 갱신에, 도구의 호출 ID는 요청과 결과 연결에, `thread_id`는 실행 상태 구분에 사용됩니다. 각각 무엇을 가리키는지 구분하면 중단·재개와 대화 관리가 쉬워집니다.

### 7. 저장된 기억에서 지금 필요한 정보를 고르는 방법

오랫동안 사용한 도우미에는 대화와 작업 기록이 많이 쌓입니다. 다음 질문에 답할 때는 그중 관련된 정보만 골라 입력에 넣어야 합니다. 실행을 잇는 체크포인트, 여러 대화에 걸쳐 보관할 사용자 설정, 지금 모델이 읽을 문맥은 용도가 다릅니다.

Generative Agents는 경험을 저장하고 최근성·중요도·현재 질문과의 관련성을 고려해 기억을 선택하는 구조를 제시합니다. 여러 기록에서 앞으로 쓸 정보를 정리하는 Reflection(성찰)을 거쳐 다음 계획에 활용합니다.

예를 들어 평일 저녁에 30분 공부할 수 있다는 조건과 최근 행렬 곱 질문을 함께 고르면, 행렬 곱 복습 계획을 만들 수 있습니다. 사용자가 직접 말한 시간 조건과 기록에서 추정한 복습 필요성은 구분해 저장합니다. 긴 기록을 줄일 때는 확정된 조건, 결정 사항, 미완료 작업, 도구 요청과 결과의 관계를 유지합니다.

### 8. 반복 실행을 마치는 기준

추가 검색과 수정이 가능한 에이전트에는 언제 끝낼지도 필요합니다. 필요한 근거와 답변을 얻었으면 완료하고, 같은 검색과 실패가 반복되면 원인을 확인합니다. 횟수·시간·토큰 한도, 추가 정보가 필요한 상태도 종료 이유로 구분합니다.

LangGraph의 `recursion_limit`은 한 실행에서 허용하는 Super-step(그래프 실행 단계) 수를 제한합니다. 같은 단계에서 여러 노드가 실행될 수 있으므로 실제 도구·모델 호출량은 별도로 셉니다. 진행 기록에는 방문 노드, 사용 도구, 결과, 종료 이유를 남겨 목표 달성 여부를 확인합니다.
