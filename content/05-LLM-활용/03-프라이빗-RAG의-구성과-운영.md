---
title: "03. 프라이빗 RAG의 구성과 운영"
---

사내 문서로 RAG를 만들 때는 답변 품질과 함께 원문·질문이 처리되는 위치를 정해야 합니다. 문서 임베딩, 검색 저장소, 답변 생성이 서로 다른 서버에서 이루어질 수 있기 때문입니다. 이 강의에서는 **RAG의 전체 데이터 흐름을 내부 환경에 구성하고 관리하는 방법**을 배웁니다.

## 학습 목표와 흐름

먼저 각 구성 요소가 어떤 데이터를 받는지 확인합니다. 이어서 벡터와 원문을 연결해 보관하고, 사용자 권한과 문서 판본에 맞게 검색하는 방법을 익힙니다. 마지막에는 내부 모델의 처리 속도와 검색·답변 품질을 나누어 확인합니다.

## 자습

### 1. 문서와 질문이 처리되는 위치를 정하는 이유

원문을 외부로 보내지 않는 조건이라면 임베딩을 만드는 과정부터 살펴봐야 합니다. 외부 임베딩 API를 호출하면 본문이 그 서버로 전달됩니다. 내부에 벡터 저장소를 두었더라도 생성 모델이 외부에 있으면 질문과 검색한 본문이 다시 외부로 이동합니다.

Private RAG(프라이빗 RAG)는 문서 처리·검색·생성을 정해진 내부 환경에서 수행하도록 구성합니다. 내부 임베딩 모델은 청크와 질문을 벡터로 바꾸고, 내부 검색 저장소는 벡터와 문서 정보를 보관하며, 내부 생성 모델은 질문과 근거를 읽고 답합니다.

PDF 파서, 이미지 분석기, 재정렬 모델도 같은 흐름에 포함됩니다. 실행 로그에 원문이나 질문을 남긴다면 로그의 저장 위치도 정해야 합니다. 각 단계에 들어가는 데이터와 나오는 데이터를 따라가면 필요한 구성 요소가 분명해집니다.

### 2. 벡터와 본문을 함께 관리하는 검색 저장소

검색 결과를 답변에 사용하려면 가까운 벡터가 어느 문장을 나타내는지 알아야 합니다. 그래서 각 청크에 ID를 부여하고 벡터, 본문 또는 본문 위치, 문서 정보를 연결해 저장합니다.

Qdrant에서는 같은 검색 설정을 사용하는 항목을 Collection(컬렉션)에 모읍니다. Point(항목)는 ID·벡터·Payload(부가 데이터)를 가집니다. Payload에는 본문, 페이지, 부모 조항 ID, 문서 판본, 열람 범위 등을 넣을 수 있습니다. 컬렉션의 벡터 차원과 거리 계산 방식은 임베딩 모델에 맞춥니다.

프로그램 안에서 저장소를 사용하는 임베디드 방식은 한 실행 환경에서 흐름을 익히기 좋습니다. 여러 서비스가 같은 자료를 사용하면 서버 방식으로 분리할 수 있습니다. 이 경우에는 저장 위치·접속 주소·접근 제어·백업을 함께 관리합니다.

### 3. 사용자에게 허용된 문서에서 검색하는 방법

같은 질문이라도 사용자에 따라 열람할 수 있는 문서가 다를 수 있습니다. 검색의 목적은 **해당 사용자가 볼 수 있는 문서 중에서 관련 근거를 찾는 것**입니다. 검색 후보를 정할 때 권한 조건을 적용하면 허용된 본문만 생성 모델에 전달할 수 있습니다.

문서에는 부서나 접근 등급 같은 정보를 저장하고, 검색 요청에는 로그인한 사용자의 권한에서 구한 조건을 넣습니다. 사용자가 질문에 적은 부서 이름은 검색 내용이고, 실제 열람 범위는 서비스가 확인한 권한 정보입니다.

Metadata filter(메타데이터 필터)는 이런 조건을 표현합니다. 여러 필드를 모두 만족해야 하는 조건과 하나만 만족해도 되는 조건을 나누어 구성할 수 있습니다. 권한 외에도 시행일, 문서 종류, 적용 중인 판본을 검색 범위로 지정할 때 사용합니다.

### 4. 문서와 임베딩 모델이 바뀔 때 갱신하는 방법

휴가 규정이 개정되면 이전 조항과 새 조항이 함께 검색되지 않도록 적용 판본을 관리해야 합니다. 문서 ID와 수정 정보를 보관하면 해당 문서의 청크를 찾아 새 내용으로 교체할 수 있습니다. 답변 출처에도 필요한 시행일을 남깁니다.

임베딩 모델의 변경은 저장된 모든 벡터의 의미에 영향을 줍니다. 새 모델로 문서 벡터를 다시 만들고 질문도 그 모델의 입력 규칙으로 처리합니다. 벡터 차원이 같아도 모델이 학습한 좌표의 의미는 달라질 수 있으므로 별도 컬렉션에서 새 검색 결과를 확인한 뒤 전환하는 방법이 유용합니다.

이 과정에서 본문·출처·문서 ID를 유지하면 이전 검색과 새 검색이 같은 근거를 찾는지 비교할 수 있습니다. 모델 이름과 판본, 전처리 규칙도 벡터와 함께 관리할 정보입니다.

### 5. 내부 모델의 처리 시간과 메모리를 조절하는 방법

문서가 많아지면 청크를 한 개씩 임베딩하는 시간이 길어집니다. 여러 청크를 묶는 Batch(배치) 처리는 한 번에 계산할 입력을 늘려 장치를 더 잘 활용하게 합니다. 배치를 키우면 중간 계산값도 늘어나므로 처리량과 최대 메모리를 함께 확인합니다.

FP16 같은 계산 자료형을 사용할 때도 같은 문서에서 속도와 검색 결과를 비교합니다. 청크 길이, 배치 크기, 모델의 입력 한도와 접두어를 맞춘 상태에서 측정해야 어떤 설정의 효과인지 알 수 있습니다.

생성 모델은 검색한 근거를 읽는 데 필요한 길이와 답변 품질을 기준으로 고릅니다. 문서 준비 단계의 임베딩 속도와 질문 한 건의 응답 시간은 사용 시점이 다르므로 따로 기록합니다.

### 6. 검색 성공과 답변 정확성을 나누어 확인하는 이유

정답 조항을 찾았어도 모델이 “남은 이용 시간”의 조건을 잘못 해석할 수 있습니다. 이때 검색 결과를 늘리기 전에 이미 전달한 조항과 답변을 대조해야 합니다. 반대로 정답 조항이 빠졌다면 청킹, 검색 표현, 필터를 먼저 살핍니다.

**원문 추출 → 권한을 적용한 검색 → 실제 모델 입력 → 생성 답변**의 결과를 연결해 남기면 오류가 생긴 위치를 찾기 쉽습니다. 자료에 답이 없는 질문도 포함해, 모델이 확인할 수 없는 내용을 어떻게 처리하는지 봅니다. 다음 강의에서는 이 비교를 일정한 평가 기준으로 정리합니다.
