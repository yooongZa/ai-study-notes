---
title: "06. 에이전트의 계획과 MCP와 복구"
---

에이전트가 여러 도구를 사용하면 중간 결과에 따라 계획을 바꾸거나 실패한 작업을 이어 가야 합니다. 검색은 성공했지만 계산에 필요한 항목이 빠질 수도 있고, 서버의 일시적인 오류로 도구 호출이 실패할 수도 있습니다. 이 강의에서는 **계획·실행·검사를 연결하고 실패 원인에 맞게 복구하는 방법**을 배웁니다.

## 학습 목표와 흐름

큰 목표를 하위 작업으로 나누는 방법부터 시작합니다. 이어서 MCP로 외부 도구와 요청·결과를 주고받는 구조를 익힙니다. 마지막에는 재시도, 입력 수정, 대체 경로, 사용자 확인을 구분하고 종료 이유를 기록합니다.

## 자습

### 1. 목표를 실행할 작업으로 나누는 방법

“두 지점의 매출을 비교해 원인을 설명해 줘”라는 요청에는 자료 수집, 기간과 단위 확인, 차이 계산, 원인 근거 검색이 필요합니다. 어떤 작업이 먼저 끝나야 다음 작업을 할 수 있는지 정하면 도구를 실행할 순서도 드러납니다.

Plan-and-act(계획 후 실행)는 필요한 하위 작업과 순서를 먼저 정하는 방식입니다. 실행 결과를 얻으면 완료 조건을 검사하고 남은 계획을 수정합니다. 자료가 없는 기간은 추가 조회로 보완하고, 계산이 끝난 항목은 다음 설명 단계로 넘깁니다.

여러 단계의 작업은 **계획 → 행동 → 관찰 → 다음 판단**의 반복으로 이어집니다. ReAct처럼 판단과 도구 행동을 번갈아 이어 가거나, 초안을 만들고 Reflection(결과 검토)으로 수정할 부분을 정할 수 있습니다. 큰 하위 작업을 다시 작은 작업으로 나누는 재귀적 분해에는 깊이와 전체 작업 수의 한도를 둡니다. 어떤 방식이든 실행 후 얻은 결과를 기준으로 다음 행동을 정합니다.

### 2. 도구 설명과 결과 형식이 다음 판단에 필요한 이유

“검색”이라는 이름만으로는 사내 문서를 찾는지 웹을 찾는지 알기 어렵습니다. 에이전트가 알맞은 도구를 고르려면 대상, 사용 상황, 필수 입력, 반환 내용을 도구 설명에 담아야 합니다. 입력의 필드와 자료형을 정한 Schema(스키마)는 올바른 인수를 구성하는 데 사용합니다.

결과에도 다음 판단에 필요한 정보가 있어야 합니다. 성공하면 본문과 출처, 계산값과 단위 등을 반환합니다. 실패하면 잘못된 입력인지, 연결 문제인지, 결과가 비어 있는지 구분합니다. 검색 결과가 비었다는 정보는 검색어를 바꾸는 데, 인수가 잘못됐다는 정보는 입력을 수정하는 데 사용합니다.

로컬 함수와 원격 도구를 함께 쓰더라도 실행기는 같은 기준으로 결과를 읽을 수 있도록 정리합니다. 모델은 도구를 선택하고 결과를 해석하며, 실행기는 호출·검사·기록을 담당합니다.

### 3. 여러 앱이 도구를 연결하는 공통 규칙인 MCP

사내 문서 검색 기능을 여러 AI 앱에서 사용하려면 각 앱이 도구 목록과 입력 형식을 알아야 합니다. 같은 기능을 매번 다른 연결 방식으로 붙이는 대신 공통된 메시지 규칙을 사용할 수 있습니다. MCP(Model Context Protocol, 모델 컨텍스트 프로토콜)는 앱과 외부 기능이 정보를 주고받는 규칙을 제공합니다.

| 구성 요소 | 맡는 일 |
|---|---|
| Host(호스트) | 사용자가 이용하는 AI 앱으로, 모델과 연결·권한을 관리합니다. |
| Client(클라이언트) | 호스트 안에서 특정 MCP 서버와 연결하고 메시지를 주고받습니다. |
| Server(서버) | 문서 검색·자료 읽기 등의 기능을 구현해 제공합니다. |

호스트는 여러 클라이언트를 통해 여러 서버에 연결할 수 있습니다. 연결 초기에는 사용할 프로토콜 버전과 지원 기능을 확인합니다. 이후 서버가 제공하는 도구 명세를 읽고, 모델이 고른 도구의 실행 요청을 전달합니다.

MCP의 Tools(도구)는 검색·계산처럼 실행할 기능, Resources(리소스)는 URI로 식별하는 읽을 자료, Prompts(프롬프트)는 재사용할 메시지 템플릿입니다. 실제 문서 검색 알고리즘이나 계산은 서버가 구현합니다.

### 4. 도구 요청과 응답이 왕복하는 과정

호스트가 도구를 사용하려면 먼저 이름과 입력 형식을 알아야 합니다. 클라이언트는 `tools/list`로 목록을 받고, `tools/call`에 도구 이름과 인수를 넣어 실행을 요청합니다. 서버는 처리 결과를 반환하고 호스트는 이를 다음 모델 입력에 연결합니다.

메시지는 JSON-RPC 규칙으로 요청과 응답을 표현합니다. 요청의 `id`는 어느 호출의 응답인지 짝짓는 값이고, `method`는 프로토콜에서 수행할 동작입니다. 실제 도구 이름은 `params` 안에 들어갑니다.

메시지 형식이나 메서드에 문제가 있으면 프로토콜 오류가 발생합니다. 도구를 실행했지만 작업에 실패했다면 결과의 `isError`로 실행 오류를 알릴 수 있습니다. 실패한 위치를 알아야 입력을 고칠지, 도구를 바꿀지, 연결을 복구할지 정할 수 있습니다. [MCP 도구 규격](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

통신에는 하위 프로세스의 표준 입출력을 쓰는 `stdio`, HTTP 요청과 스트리밍을 사용하는 Streamable HTTP 등을 사용합니다. 호스트와 서버는 실행 권한을 관리하며, 반환된 문서의 내용은 답변 근거로 취급합니다.

### 5. 실패 원인에 맞는 복구 방법 선택

요청이 실패했을 때는 같은 작업을 다시 하면 해결되는지부터 판단합니다. 일시적인 연결 문제에는 Retry(재시도)가 도움이 되지만, 필수 인수가 빠졌다면 그 인수를 채워야 합니다.

| 현재 상태 | 다음 처리 |
|---|---|
| 일시적인 연결 실패 | 대기 후 제한된 횟수로 재시도 |
| 입력 형식 오류 | 필요한 필드와 자료형을 수정 |
| 검색 근거 부족 | 검색어·범위·도구 변경 |
| 권한 또는 사용자 결정 필요 | 필요한 정보·확인을 요청하고 대기 |
| 프로그램 결함 | 오류를 기록하고 해당 처리 중단 |

Backoff(재시도 간격 증가)는 1초·2초·4초처럼 대기 간격을 늘려 반복 요청의 부담을 줄입니다. Timeout(시간 제한)은 한 호출을 기다릴 시간을 정합니다. Fallback(대체 경로)은 다른 도구나 방법으로 넘어가는 처리입니다. 대체 결과도 원래 작업의 완료 조건에 맞는지 검사합니다.

### 6. 재시도할 때 이미 적용된 작업을 확인하는 이유

서버가 파일 저장을 마쳤지만 응답만 늦어졌을 수 있습니다. 호출자는 실패한 것처럼 보여 재시도하지만, 서버에는 이미 결과가 생긴 상태입니다. 저장·등록 같은 작업에는 요청을 다시 보내도 의도한 결과가 한 번 적용되도록 하는 Idempotency(멱등성)가 필요합니다.

요청 ID와 처리 결과를 함께 보관하면 같은 요청이 이미 처리됐는지 확인할 수 있습니다. 실행 측에서는 고유 키와 원자적 저장 같은 방법으로 중복 적용을 막습니다. 체크포인트의 진행 상태와 외부 저장소의 실제 결과도 맞춰 보아야 합니다.

작업 취소 역시 별도의 상태입니다. 취소가 들어오면 재시도나 대체 도구로 계속 진행하지 않고 종료를 전달합니다. 복구는 원래 목표를 이어 가는 과정이므로 사용자가 취소한 상태를 존중해야 합니다.

### 7. 진전과 종료 이유를 기록하는 방법

반복할 때는 새 근거가 생겼는지, 검사 실패가 줄었는지, 미완료 항목이 줄었는지 확인합니다. 같은 입력과 같은 실패가 되풀이되면 다음 방법을 바꾸거나 필요한 정보를 요청합니다.

종료 이유는 완료, 횟수·시간 한도, 정체, 외부 확인 필요, 취소로 나누어 기록합니다. 실행한 도구와 입력, 결과, 실패 원인, 소요 시간을 남기면 어느 단계에서 다시 시작할지도 찾기 쉽습니다. 성공 여부는 처음 정한 완료 조건으로 확인합니다.
