---
title: "09. 모델의 선택과 메모리와 비용"
---

한국어 규정에 답하는 서비스를 만들 때는 모델이 필요한 내용을 정확히 설명하고, 사용할 장치에서 원하는 시간 안에 답해야 합니다. 요청이 많아지면 메모리와 비용도 함께 달라집니다. 이 강의에서는 **작업의 품질 기준을 정하고, 실행 자원과 비용을 계산해 모델을 비교하는 방법**을 배웁니다.

## 학습 목표와 흐름

먼저 입력·출력과 운영 조건을 정합니다. 이어서 가중치와 KV 캐시의 메모리를 계산하고 양자화가 바꾸는 부분을 이해합니다. 같은 질문으로 품질·시간을 측정한 뒤 API와 직접 운영의 비용을 비교합니다.

## 자습

### 1. 어떤 작업에 쓸 모델인지 먼저 정하는 이유

짧은 문장을 분류하는 작업과 긴 계약서의 조건을 비교하는 작업은 필요한 능력이 다릅니다. 후보를 고르기 전에 입력 언어·종류·길이, 반드시 맞혀야 할 수치와 조건, 허용 응답 시간, 동시 요청 수를 정합니다.

문서를 처리할 위치도 후보 선택에 영향을 줍니다. 내부에서 실행해야 한다면 가중치를 확보하고 장치에 올릴 수 있어야 합니다. Open weights(공개 가중치) 모델은 가중치를 내려받아 사용할 수 있는 모델이며, 실제 사용·수정·재배포 조건은 해당 판본의 라이선스에서 확인합니다. 모델 이름과 정확한 판본을 함께 기록합니다.

이 조건을 기준으로 후보를 줄인 뒤 같은 평가 질문을 사용합니다. 공개 벤치마크는 후보를 탐색할 단서로 활용하고, 최종 비교에는 실제 업무의 입력과 정답 기준을 적용합니다.

### 2. 가중치를 올리는 데 필요한 메모리 계산

모델을 실행하려면 먼저 학습된 수치인 Parameter(파라미터)를 보관할 공간이 필요합니다. 가중치의 기본 저장량은 값의 개수와 값 하나에 사용하는 비트 수로 계산합니다.

$$\text{가중치 바이트 수}=\text{파라미터 수}\times\frac{\text{비트 수}}{8}$$

1B는 10억 개입니다. 8B 모델을 16비트로 저장하면 가중치 데이터는 160억 바이트, 즉 16GB입니다. 모두 4비트로 저장한다고 가정하면 4GB입니다. GB는 $10^9$바이트, GiB는 $2^{30}$바이트이므로 4GB는 약 3.73GiB입니다.

실제 양자화 모델에는 스케일 같은 추가 값과 높은 정밀도를 유지하는 층도 포함됩니다. 실행 중에는 KV 캐시와 임시 계산 공간이 필요하므로 가중치 계산은 장치 용량을 검토하는 첫 단계입니다.

### 3. 전체 파라미터와 활성 파라미터의 역할

모델 설명에 전체 크기와 토큰당 활성 크기가 함께 적혀 있다면 저장할 양과 계산할 양을 나누어 읽어야 합니다. Dense model(밀집 모델)은 토큰 처리에 대부분의 가중치를 사용합니다. MoE(Mixture of Experts, 전문가 혼합)는 여러 전문가 중 일부를 선택해 계산합니다.

전체 파라미터는 보관해야 할 가중치 규모와 연결되고, 활성 파라미터는 토큰 하나를 처리할 때 사용하는 부분과 연결됩니다. 장치 배치를 정할 때는 전체 전문가를 어느 메모리에 둘지 확인합니다. 사용되는 부분이 작아도 나머지 가중치의 보관 위치는 필요합니다.

### 4. 입력 길이와 동시 요청이 KV 캐시를 늘리는 이유

모델은 다음 토큰을 만들 때 앞 토큰의 Key와 Value를 다시 사용합니다. 이를 보관한 공간이 KV cache(KV 캐시)입니다. 문서가 길거나 동시에 처리할 요청이 늘면 보관할 토큰도 늘어납니다.

층 구조가 같고 전체 문맥을 저장하는 디코더에서는 주요 KV 텐서의 크기를 다음처럼 계산할 수 있습니다.

$$\text{KV 바이트 수}=2LBTH_{KV}Ds$$

$L$은 층 수, $B$는 동시에 처리하는 시퀀스 수, $T$는 각 시퀀스의 보관 토큰 수입니다. $H_{KV}$는 KV 헤드 수, $D$는 헤드 차원, $s$는 원소 하나의 바이트 수입니다. 맨 앞의 2는 Key와 Value를 각각 저장하기 때문입니다.

32층, 한 요청, 4,096토큰, KV 헤드 8개, 헤드 차원 128, 원소당 2바이트라면 0.5GiB입니다. 같은 길이의 요청 네 개는 2GiB입니다. GQA(Grouped-Query Attention)는 여러 Query 헤드가 KV 헤드를 공유하므로 계산에 실제 KV 헤드 수를 넣습니다. 입력·출력 길이와 캐시 자료형, 모델의 층별 저장 규칙을 함께 확인합니다.

### 5. 양자화와 실행 형식을 선택하는 방법

가중치를 더 작은 메모리에 올리려면 숫자를 적은 비트로 표현하는 Quantization(양자화)을 사용할 수 있습니다. 많은 실수 값을 제한된 표현 단계로 대응시키면서 저장량과 메모리에서 읽어 올 양을 줄입니다. 이 과정의 근사 오차가 실제 답변에 어떻게 반영되는지 평가합니다.

가중치 저장은 4비트, 연산은 FP16처럼 저장 형식과 계산 형식을 다르게 사용할 수 있습니다. GPTQ·AWQ는 양자화 값을 정하는 방법이고, GGUF 같은 파일 형식은 모델 데이터와 정보를 담는 방식입니다. 실제 계산 속도는 장치가 지원하는 Kernel(연산 커널), 배치와 입력 길이에 따라 측정합니다.

학습에는 가중치 외에도 기울기·옵티마이저 상태·활성값이 필요합니다. 여기서 계산한 추론 메모리와 학습에 필요한 메모리는 용도를 구분해 사용합니다.

### 6. 같은 질문으로 품질과 시간을 비교하는 방법

모델별 답변을 비교할 때는 질문, 근거, 채점 기준, 최대 답변 길이를 맞춥니다. 토크나이저와 대화 템플릿은 각 모델에 맞게 적용합니다. 수치·조건의 정확성, 형식 준수, 근거 활용, 한국어 표현을 나누어 보고, 짧은 입력과 긴 입력의 결과를 따로 살핍니다.

사용자가 기다리는 시간은 첫 출력과 전체 완료로 나누어 볼 수 있습니다. TTFT(Time to First Token, 첫 토큰까지의 시간)는 입력 처리와 대기를 포함해 첫 토큰이 나올 때까지의 시간입니다. 출력이 시작된 뒤에는 토큰 생성 속도를 측정합니다. 전체 응답 시간에는 도구 호출과 통신도 포함됩니다.

여러 요청을 함께 처리할 때는 단위 시간당 완료한 요청이나 토큰 수인 Throughput(처리량)도 측정합니다. 한 사용자의 대기 시간과 서버 전체 처리량을 함께 보면 서비스 조건에 맞는 구성을 고를 수 있습니다.

### 7. API 사용량과 직접 운영 비용을 비교하는 방법

API가 입력·출력 토큰에 서로 다른 가격을 적용하면 두 사용량을 따로 계산해 합칩니다. 예를 들어 가상의 가격을 100만 토큰당 입력 1단위, 출력 4단위로 정하면, 입력 2,000토큰과 출력 500토큰의 비용은 $0.002+0.002=0.004$단위입니다.

한 질문에 답변 생성·평가·수정으로 여러 번 호출했다면 각 호출의 사용량을 합칩니다. 캐시 입력 가격이 따로 있다면 그 부분을 분리합니다. 모델마다 토크나이저가 달라 같은 한국어 문장도 사용량이 달라질 수 있습니다.

직접 운영에는 서버·전력·저장소·관리 비용이 들어갑니다. 확보한 서버의 고정 비용은 요청이 적을수록 건당 부담이 커집니다. 품질과 응답 조건을 만족한 요청 수를 기준으로 비용을 나누면 API와 직접 운영을 같은 목적에 맞춰 비교할 수 있습니다.
