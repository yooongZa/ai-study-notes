title: "D46. 모델 서빙과 HTTP, 모델 저장"
---

노트북에서 학습한 모델을 웹이나 앱에서 사용하려면, 사용자의 입력을 받아 예측하고 결과를 돌려주는 프로그램이 필요합니다. 모델 파일을 다른 실행 환경에서 다시 읽고, 입력 형식과 전처리를 맞추는 일도 포함됩니다.

여기서는 **학습한 모델을 다른 프로그램이 호출할 수 있도록 준비하는 과정**을 배웁니다. 요청과 응답의 약속을 익힌 뒤, 모델 저장·복원·형식 변환과 출력 확인으로 연결합니다.

## 학습 목표와 흐름

| 배울 내용 | 필요한 상황 |
|---|---|
| 학습·추론·서빙 | 모델 계산을 사용자 기능으로 제공할 때 |
| HTTP·REST·JSON | 서로 다른 프로그램이 입력과 결과를 주고받을 때 |
| 실행 환경과 전처리 | 학습 때의 계산을 서버에서 재현할 때 |
| 모델 저장과 복원 | 프로세스가 끝난 뒤에도 같은 가중치를 사용할 때 |
| 모델 형식 변환 | 다른 추론 엔진에서 모델을 실행할 때 |

## 자습

### 1. 학습한 모델을 서비스로 제공하는 과정

채팅 화면에서 질문을 보내면 서버는 입력을 검사하고 모델에 전달한 뒤 답변을 돌려줍니다. 이 전체 기능을 다른 프로그램에 제공하는 일이 Model serving(모델 서빙)입니다.

Training(학습)은 데이터와 오차를 이용해 가중치를 바꾸고, Inference(추론)는 준비된 가중치로 새 입력의 결과를 계산합니다. 서빙은 추론에 요청 접수·검증·대기·오류 처리·응답 전달을 연결합니다.

**입력 접수 → 입력 검사 → 전처리 → 모델 추론 → 결과 변환 → 응답**

Client(클라이언트)는 기능을 요청하는 프로그램이며 웹 화면·모바일 앱·다른 서버가 될 수 있습니다. Server(서버)는 요청을 받아 처리합니다. API(프로그램 간 요청 규약)는 양쪽이 사용할 주소, 요청 방법, 입력과 응답 항목, 오류 형식을 정합니다.

모델이 반환한 Tensor(텐서)는 전송할 수 있는 숫자·목록·문자열로 바꿉니다. LLM이라면 입력을 토큰으로 바꾸고 다음 토큰을 반복해서 생성하므로, 생성 길이와 종료 조건도 서비스가 관리합니다.

### 2. HTTP 요청과 JSON으로 입력을 전달하는 방법

클라이언트와 서버는 서로 다른 프로세스에서 실행됩니다. 값을 주고받으려면 메시지를 보내는 규칙과 데이터 표현 형식이 필요합니다. HTTP는 요청·응답 통신 규칙이고, JSON은 그 안에 담을 데이터를 표현하는 형식입니다.

HTTP 요청은 메서드·주소·Header(헤더)·Body(본문)로 구성됩니다. `POST /predict`에서 POST는 처리 요청 방식이고 `/predict`는 서버 안의 경로입니다. 헤더는 데이터 형식이나 인증 정보를, 본문은 질문이나 예측할 값을 담습니다. `Content-Type: application/json`은 본문이 JSON이라는 뜻입니다.

응답에는 상태 코드·헤더·본문이 있습니다. 클라이언트는 상태 코드로 처리 상태를 읽고, 본문에서 결과나 구체적인 오류를 확인합니다.

| 상태 코드 | 의미와 확인할 내용 |
|---|---|
| 200·201 | 정상 처리·새 자원 생성 |
| 202 | 요청 접수. 작업 완료 상태는 이후 조회 |
| 400·422 | 요청 내용 또는 입력 검증 오류 |
| 401·403 | 인증 필요 또는 권한 부족 |
| 404 | 요청 경로나 자원을 찾지 못함 |
| 429 | 허용 요청량 초과 |
| 500·503 | 내부 오류 또는 현재 요청을 처리할 수 없는 상태 |

JSON은 문자열·숫자·목록·객체 등을 표현합니다. Python의 딕셔너리는 프로그램 메모리의 객체이고, 이를 JSON 문자열로 바꾸는 과정을 Serialization(직렬화)이라고 합니다. JSON의 `true`, `false`, `null`은 Python의 `True`, `False`, `None`에 대응합니다.

HTTP 도구가 `json=` 인수로 변환을 제공하면 Python 딕셔너리를 전달합니다. 이미 만든 JSON 문자열을 다시 JSON 값으로 보내면 객체 대신 문자열이 전달될 수 있으므로, 어떤 단계에서 직렬화하는지 맞춥니다.

### 3. 자원과 처리 목적에 맞게 API를 설계하는 방법

모델 정보 조회와 예측 실행은 서로 다른 요청입니다. 주소로 자원을 나타내고 HTTP 메서드의 의미에 맞춰 동작을 정하면 클라이언트가 API를 이해하기 쉽습니다. 이런 설계 방식을 REST라고 합니다.

| 메서드 | 대표 용도 | 예 |
|---|---|---|
| GET | 정보 조회 | 모델 정보 읽기 |
| POST | 자원 생성·입력 처리 | 새 예측 작업 요청 |
| PUT | 지정한 자원 교체 | 같은 ID의 설정 전체 갱신 |
| PATCH | 일부 항목 수정 | 특정 설정값 갱신 |
| DELETE | 자원 삭제 | 저장된 작업 삭제 |

같은 요청을 반복해도 의도한 최종 효과가 유지되는 성질은 Idempotency(멱등성)입니다. 같은 자원을 같은 내용으로 교체하는 PUT이 한 예입니다. 매번 새 작업을 만드는 API라면 재시도 시 중복 작업을 구분할 방법을 정합니다.

Stateless(무상태) 요청은 처리에 필요한 입력·인증·식별 정보를 요청에 담습니다. 서버의 모델과 데이터베이스는 계속 보관하면서, 요청이 어떤 자료를 사용할지 명확히 전달합니다. 채팅에는 대화 기록을 보내거나 대화 자원을 가리키는 ID를 사용할 수 있습니다.

### 4. 같은 모델 계산을 재현하기 위한 실행 환경과 전처리

노트북에서는 잘 동작하던 모델이 서버에서 다른 결과를 낸다면 가중치뿐 아니라 환경과 입력 변환을 함께 확인해야 합니다. 같은 숫자 배열도 순서·크기·정규화가 달라지면 모델이 받는 의미가 달라집니다.

| 구성 | 맞춰야 할 정보 |
|---|---|
| 모델 | 구조·가중치·모델 버전 |
| 전처리 | 이미지 크기·정규화 값, 텍스트 토크나이저·대화 형식 |
| 실행 환경 | Python·패키지·운영체제·CPU/GPU·드라이버 |
| 서비스 | 요청 제한·주소·작업 수·응답 규약 |

Virtual environment(가상환경)는 프로젝트별 Python 패키지를 관리하는 공간입니다. 노트북의 Kernel(커널)은 셀 코드를 실행하는 프로세스입니다. 노트북 커널과 API 서버가 어느 Python을 사용하는지 확인하면 서로 다른 환경에 패키지를 설치한 상황을 찾을 수 있습니다.

패키지와 모델 버전을 기록하고 같은 입력의 전처리 결과를 비교합니다. 답변 내용의 변화는 모델·전처리 설정을, 대기 시간의 변화는 계산과 요청 처리 설정을 따라가며 확인합니다.

### 5. 모델 구조와 가중치를 저장하고 복원하는 방법

학습한 값은 처음에는 실행 중인 메모리에 있습니다. 프로그램이 끝난 뒤 같은 계산을 하려면 가중치와 필요한 설정을 파일에 저장해야 합니다. 모델 구조는 계산할 층과 순서를, 가중치는 학습으로 정한 숫자를 나타냅니다.

PyTorch의 `state_dict`는 이름별 매개변수와 등록된 Buffer(버퍼)를 모은 상태입니다. 버퍼에는 Batch Normalization의 이동 평균처럼 추론에 필요한 값이 포함됩니다. 이를 복원할 때는 같은 이름과 형태를 가진 모델 구조를 먼저 만듭니다.

**구조 준비 → 저장된 상태 읽기 → 가중치·버퍼 복원 → 평가 모드 → 추론**

평가 모드는 Dropout과 Batch Normalization처럼 학습·평가에 따라 달라지는 층의 동작을 정합니다. 자동 미분 기록은 추론 구간에서 별도로 생략합니다. 두 설정을 적용한 뒤 저장 전후에 같은 입력을 넣어 출력을 비교합니다.

텍스트 모델의 토크나이저와 이미지 모델의 정규화 값·클래스 이름도 함께 보관합니다. 서버를 여러 작업자 프로세스로 실행하면 모델이 각 프로세스에 로드될 수 있어, 필요한 메모리를 계산할 때 복사본 수를 확인합니다.

### 6. 다른 추론 엔진으로 모델을 변환하고 결과를 확인하는 방법

학습에 사용한 환경을 그대로 설치하기 어렵거나 특정 장치에 맞는 추론 엔진을 사용하려면, 모델 계산을 다른 도구가 읽을 수 있는 형식으로 바꿀 수 있습니다.

저장 목적에 따라 담는 내용이 달라집니다. Pickle은 Python 객체를 직렬화하는 방식이고, 가중치 상태 저장은 모델 구조를 코드에서 준비한 뒤 학습 상태를 복원하는 방식입니다. TorchScript는 PyTorch 계산을 저장해 실행하는 형식으로 다뤄져 왔고, ONNX는 여러 도구가 읽을 계산 그래프를 표현합니다. 사용할 실행 엔진과 지원 연산에 맞춰 형식을 선택합니다.

Computational graph(계산 그래프)는 행렬곱·덧셈·활성화 함수 같은 연산의 연결입니다. ONNX는 그래프와 가중치를 표현하는 형식이고, ONNX Runtime은 이를 읽어 계산하는 실행 엔진입니다. Opset(연산 집합 버전)은 그래프에서 사용하는 연산의 정의 버전입니다.

변환한 모델에는 입력 이름, Shape(형태), Dtype(자료형) 조건이 있습니다. 흑백 이미지의 `(N, 1, 28, 28)`은 이미지 N장·채널 1개·높이와 너비 28을 뜻합니다. Dynamic shape(동적 형태)는 허용 범위 안에서 배치나 입력 길이를 바꾸어 사용할 수 있도록 정한 조건입니다.

전처리가 그래프 밖에 있으면 실행 프로그램에서 같은 방식으로 수행합니다. 모델을 내보낼 때는 지원하는 연산과 입력 조건을 맞추고, 여러 입력값과 허용한 크기에서 결과를 비교합니다. 예제 실행 경로를 기록하는 Trace(추적) 방식은 입력에 따라 달라지는 분기 경로도 확인해야 합니다.

출력 비교에서는 형태를 먼저 맞추고 원소별 차이를 계산합니다. 절대 허용 오차는 작은 값 부근의 차이를, 상대 허용 오차는 값의 크기에 비례한 차이를 판단합니다. 업무에서 필요한 정확도에 맞춰 허용 범위를 정하고, 분류라면 점수와 선택된 클래스도 확인합니다.

계산 결과를 확인한 다음 같은 장치·입력 크기·배치로 속도와 메모리를 비교합니다. 이렇게 **변환 → 입력 조건 확인 → 출력 비교 → 성능 비교**로 이어집니다.
