---
title: "D52. 학습노트를 검색해 답하는 RAG 챗봇"
---

공부한 노트가 많아지면 개념 설명이나 코드를 다시 찾는 데 시간이 걸립니다. 질문에 맞는 부분을 검색하고 그 내용을 근거로 답변을 만들면, 여러 문서를 넘겨보던 과정을 하나의 질문 흐름으로 연결할 수 있습니다.

여기서는 **학습자료 준비·검색·답변 생성·API·화면을 하나의 서비스로 구성하는 방법**을 배웁니다. 앞에서 익힌 데이터 처리와 서빙 지식이 실제 질문 한 건을 처리할 때 어떻게 이어지는지 살펴봅니다.

## 학습 목표와 흐름

| 배울 내용 | 필요한 상황 |
|---|---|
| 자료 준비와 색인 | 노트를 반복해서 검색할 수 있도록 만들 때 |
| 질문 변환·검색 | 사용자의 표현으로 적절한 근거를 찾을 때 |
| 핵심 선택·문맥 확장 | 잘린 설명의 앞뒤 맥락을 회복할 때 |
| 근거 기반 생성·출처 | 답변을 확인하며 공부할 수 있게 할 때 |
| API·인증·화면·평가 | 질문 기능을 서비스로 제공하고 품질을 점검할 때 |

## 자습

### 1. 자료 준비와 질문 처리를 나누는 이유

질문이 들어올 때마다 모든 노트를 읽고 벡터로 바꾸면 같은 준비 작업을 반복하게 됩니다. 자주 바뀌지 않는 문서는 미리 검색 가능한 형태로 저장하고, 질문마다 필요한 검색과 생성만 수행합니다.

RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 관련 자료를 검색해 생성 모델의 입력에 넣는 방식입니다. 전체 흐름은 두 부분으로 나눌 수 있습니다.

| 시점 | 처리 흐름 |
|---|---|
| 자료 준비 | 노트 수집 → 정제 → 청크 분할 → 임베딩 → 본문·벡터 저장 |
| 질문 처리 | 질문 검증 → 관련 청크 검색 → 근거 구성 → 답변 생성 → 출처 표시 |

청크 본문과 출처는 모델이 읽고 사용자가 확인할 자료입니다. 벡터는 질문과 관련된 청크를 찾기 위한 표현입니다. 문서가 바뀌면 해당 청크·벡터·출처 정보가 함께 갱신되도록 관리합니다.

### 2. 설명과 코드를 검색 단위로 나누는 방법

학습노트에는 제목·본문·표·코드가 섞여 있습니다. 길이만 보고 중간을 자르면 함수의 들여쓰기나 표의 열 이름, 수식의 설명이 떨어져 나갈 수 있습니다. 검색한 조각만 읽어도 의미를 이해할 수 있도록 경계를 정해야 합니다.

먼저 제목으로 주제를 나누고, 긴 절을 추가 분할합니다. 코드와 표는 블록 구조를 유지하고 필요한 제목을 붙입니다. 반복되는 이동 링크·목차는 검색 본문에서 정리하고, 문서 제목·단원·소제목은 Metadata(메타데이터)로 보관합니다.

Chunk overlap(청크 중복)은 이웃한 청크의 일부 내용을 겹쳐 경계의 정보를 이어주는 방법입니다. 글자 수로 분할했다면 모델에 넣기 전에 토큰 수를 별도로 확인합니다.

| 청크 정보 | 사용하는 목적 |
|---|---|
| 본문 | 답변을 만들 근거 |
| 문서·소제목·단원 | 어떤 개념의 설명인지 판단 |
| 원본 경로·문서 안 순서 | 출처 표시·주변 문맥 찾기 |
| 청크 ID | 후보 중복 제거·정확한 위치 식별 |
| 본문·원본 해시 | 변경과 중복 확인 |

임베딩할 때 제목과 소제목을 본문 앞에 붙이면 짧은 조각에도 주제 정보를 제공할 수 있습니다. 원본과 청크를 연결해 두면 검색 오류가 생겼을 때 분할부터 다시 살펴볼 수 있습니다.

### 3. 질문 표현을 다듬고 관련 근거를 찾는 방법

사용자는 ‘키 없는 요청을 어떻게 막아?’라고 묻고 노트는 ‘API Key·Depends·401’이라는 용어를 사용할 수 있습니다. 질문 변환은 사용자의 의도를 유지하면서 검색에 도움이 되는 표현을 추가하는 단계입니다.

Few-shot(예시 기반 유도)은 입력 질문과 원하는 변환 결과의 예시를 모델에 제공하는 방법입니다. 대상 개념·숫자·단위·조건·코드 요청 여부를 유지하도록 규칙을 정합니다. 모호한 질문은 필요한 대상이 무엇인지 확인할 수 있도록 처리합니다.

원문 질문과 변환 질문을 모두 검색한 뒤 청크 ID로 중복을 제거하면 두 표현에서 찾은 후보를 모을 수 있습니다. 변환 질문이 너무 넓어졌을 때도 원문 질문의 근거를 후보에 남길 수 있습니다.

Embedding(임베딩)은 질문과 문서를 의미 비교에 사용할 벡터로 바꾸는 작업입니다. 문서 색인과 질문에 같은 모델·차원·정규화 기준을 적용하고 Cosine similarity(코사인 유사도) 같은 기준으로 가까운 후보를 찾습니다.

벡터 저장소에는 본문이나 본문을 찾을 식별자를 함께 보관합니다. Qdrant의 Payload(부가 데이터)에 본문·제목·경로를 넣으면 검색 결과에서 답변 근거와 출처를 꺼낼 수 있습니다.

### 4. 핵심 청크를 고르고 주변 설명을 가져오는 이유

‘Transformer가 무엇인가’라는 질문에 텐서 크기 표만 검색되면 전체 개념을 설명하기 어렵습니다. 검색 후보가 질문의 대상뿐 아니라 설명 수준에도 맞는지 확인해야 합니다.

핵심 청크 선택은 후보 제목·소제목·본문을 보고 질문에 가장 필요한 출발점을 고르는 단계입니다. 개요 질문에는 정의와 목적을, 특정 함수 질문에는 관련 구현을 우선할 수 있습니다. 모델이 후보 번호를 반환하도록 했다면 코드에서 번호의 형식과 범위를 검사합니다.

핵심 청크가 정해지면 같은 문서에서 앞뒤 청크를 가져와 설명을 이어 붙입니다. 이때 순서는 원문 안의 순서입니다. 벡터 검색 순위의 앞뒤는 서로 다른 문서일 수 있으므로 문서 ID와 청크 위치로 주변을 찾습니다.

핵심 앞뒤로 $k$개씩 가져오면 최대 $2k+1$개가 됩니다. 문서의 시작·끝에서는 존재하는 범위만 사용합니다. 문맥이 길어지면 필요한 근거와 입력 토큰 예산을 비교해 범위를 조절합니다.

검색 후보 번호와 최종 근거 번호는 각각의 목록에서 정합니다. 선택 후보가 4번이어도 최종 답변의 인용 번호는 문맥을 구성하며 새로 붙일 수 있습니다.

### 5. 근거를 바탕으로 답변하고 출처를 연결하는 방법

사용자가 답변을 읽고 다시 공부하려면 설명의 근거가 어디에 있는지 확인할 수 있어야 합니다. 생성 모델에는 원래 질문·선택한 문맥·답변 규칙을 주고, 코드에서 근거 번호와 원본 정보를 함께 관리합니다.

Prompt(프롬프트)에는 어떤 내용을 설명할지와 근거를 사용하는 방법을 적습니다. 개요 질문은 정의와 목적부터 설명하도록 하고, 자료에 없는 내용은 확인할 수 있는 범위를 표시하도록 정합니다. 출처의 파일명·경로는 코드가 가진 메타데이터에서 연결합니다.

Tokenizer(토크나이저)는 텍스트를 토큰 번호로 변환합니다. Chat template(대화 형식)은 system·user 메시지를 모델이 학습한 형식으로 배열합니다. 모델이 만든 토큰에서 새 답변 부분을 골라 문자열로 바꿉니다.

생성량은 입력 토큰과 출력 상한을 함께 계산해 정합니다. 검색 벡터를 만드는 모델과 답변을 생성하는 모델은 목적이 다르므로 준비와 실행 자원도 나누어 관리합니다. 저장된 프로젝트에서는 BGE-M3가 검색을, Qwen이 질문 변환·핵심 선택·답변 생성을 담당했습니다.

4비트 로딩은 가중치 표현에 필요한 메모리를 줄이는 추론 설정입니다. 실행 중에는 생성 캐시와 중간값에도 메모리가 필요합니다. 모델과 토크나이저는 시작할 때 준비하고 요청마다 재사용합니다.

### 6. 검색과 생성을 하나의 API로 제공하는 방법

화면은 질문 문자열을 보내고 답변·출처를 받아야 합니다. 검색 함수와 생성 함수를 내부에서 연결한 뒤, 그 결과를 일정한 요청·응답 규칙으로 제공합니다.

**질문 입력 → 인증·입력 검증 → 검색·선택·생성 → 응답 검증 → 답변·출처 표시**

Pydantic은 빈 질문·공백·길이와 응답 필드를 검사합니다. API Key 인증은 호출자를 확인하고, 오류 응답은 인증 실패·입력 오류·내부 처리 실패를 구분합니다. 서버 로그에는 요청 식별자와 실패 단계가 남도록 합니다.

긴 동기 검색·생성을 실행자에 맡기면 이벤트 루프는 다른 요청을 계속 받을 수 있습니다. 작업자가 하나면 생성은 순서대로 진행하고 뒤의 요청은 기다립니다. 여러 사용자 접수·동시 생성·한 사용자만 이용하도록 하는 접속 제한은 각각 별도의 상태와 정책으로 관리합니다.

대기 시간이 길어지면 대기열 크기·요청 제한·취소를 연결합니다. 클라이언트가 기다리기를 멈춘 시점과 서버에서 실제 계산이 끝난 시점을 구분해 자원을 반환합니다.

### 7. 대화 화면과 실행 환경을 유지하는 방법

Streamlit은 질문을 보낼 때 다시 실행되므로 대화와 인증 표시를 세션 상태에 보관합니다. 답변 아래에 출처를 펼쳐 보여주면 사용자가 원문과 설명을 비교할 수 있습니다.

이전 질문을 모델도 사용하게 하려면 API 요청이나 서버 저장소에서 대화 기록을 읽어 모델 입력에 넣어야 합니다. 화면에 과거 메시지를 표시하는 기능과 다음 생성에 대화를 전달하는 기능은 각각 연결합니다.

Colab 같은 임시 실행 환경은 재시작할 때 모델·검색 자료·서버를 다시 준비해야 합니다. 지속 저장소에 필요한 파일을 보관하고 패키지·모델 버전과 색인 정보를 기록하면 복원할 수 있습니다. 준비한 파일을 로컬로 읽은 뒤 API를 실행하고 화면의 API 주소를 연결합니다.

모델 서버와 화면 서버가 다른 곳에 있으면 어느 쪽에서 실패했는지 나누어 확인합니다. 화면 접속 → API 상태 → 인증 → 검색 → 생성 → 출처 표시 순서로 따라가면 연결 문제와 내용 문제를 구분하기 쉽습니다.

### 8. 검색·답변·서비스를 각각 평가하는 이유

API가 정상 응답해도 필요한 근거가 검색되지 않았거나, 근거를 잘못 설명했을 수 있습니다. 어느 단계의 문제인지 찾으려면 단계별 입력과 결과를 함께 남겨야 합니다.

| 평가 대상 | 확인할 질문 |
|---|---|
| 검색 | 정답을 설명할 문서·구절·코드가 후보에 들어왔는가? |
| 핵심 선택 | 질문의 대상과 설명 수준에 맞는 근거인가? |
| 생성 | 주어·조건·관계·인용이 근거와 일치하는가? |
| 서빙 | 인증·입력·오류·응답 시간·화면 표시가 맞는가? |

개요·세부 코드·비교·자료에 없는 질문을 포함해 평가합니다. 문서 ID만 맞는 경우와 답을 쓸 구절까지 포함된 경우도 나누어 기록합니다.

실패 질문에는 원문 질문·변환 질문·검색 후보·선택 결과·최종 문맥·생성 답변을 남깁니다. 그러면 청크 분할을 바꿀지, 검색을 조정할지, 선택·답변 규칙을 고칠지 근거를 가지고 결정할 수 있습니다.

## 이해 확인

> [!question]- 자료 준비와 질문 처리를 나누는 목적은 무엇인가요?
> 문서 정제·청킹·임베딩을 미리 수행하고, 질문마다 저장된 자료를 재사용하기 위해서입니다.

> [!question]- 핵심 청크의 앞뒤는 어떤 순서로 찾나요?
> 같은 문서 안의 원문 순서로 찾습니다. 문서 식별자와 청크 위치를 함께 사용합니다.

> [!question]- 화면 대화와 모델의 대화 입력은 어떻게 연결되나요?
> 이전 대화를 API나 서버 저장소에서 읽어 다음 생성의 입력에 넣도록 구현합니다.

> [!question]- 정상 API 응답과 정확한 답변을 따로 평가하는 이유는 무엇인가요?
> 연결이 동작했는지와 검색 근거·생성 내용이 맞는지는 서로 다른 확인 항목이기 때문입니다.
