---
title: "D47. FastAPI로 모델 추론 API 만들기"
---

학습한 모델을 저장하고 복원할 수 있다면, 이제 다른 프로그램이 입력을 보내고 결과를 받을 수 있도록 연결할 차례입니다. 서버는 입력이 모델에 맞는지 확인하고, 준비된 모델로 계산한 뒤, 클라이언트가 읽을 수 있는 형식으로 결과를 돌려줘야 합니다.

여기서는 **요청이 들어와 예측 결과로 돌아가기까지의 흐름**을 배웁니다. FastAPI의 요청 처리 구조에서 시작해 입력·응답 규칙을 정하고, 모델을 한 번 준비해 여러 요청에서 사용하는 방법으로 이어집니다.

## 학습 목표와 흐름

| 배울 내용 | 필요한 상황 |
|---|---|
| 서버와 경로 함수 | 주소에 맞는 처리 함수를 실행할 때 |
| 요청 데이터의 위치 | 경로·조회 조건·입력 본문을 구분할 때 |
| 입력 검증 | 모델이 처리할 수 있는 값을 받기 위해 |
| 응답 형식 | 화면과 다른 프로그램이 결과를 일관되게 읽도록 |
| 모델 수명과 추론 | 로딩 비용을 줄이고 같은 모델을 재사용할 때 |

## 자습

### 1. 요청을 받아 처리 함수로 연결하는 구조

클라이언트가 `POST /predict`로 데이터를 보내면 네트워크 연결을 받는 프로그램과 예측을 수행할 함수를 연결해야 합니다. 이 역할을 Uvicorn과 FastAPI가 나누어 맡습니다.

Uvicorn은 연결을 받아 애플리케이션에 전달하는 서버입니다. FastAPI는 요청 주소와 메서드에 맞는 함수를 찾고, 입력을 검사하며, 반환값을 응답으로 바꿉니다. 둘은 ASGI라는 Python 서버·애플리케이션 간 규약으로 통신합니다.

**클라이언트 → Uvicorn → FastAPI 입력 검증 → 경로 함수 → 응답 변환 → 클라이언트**

Endpoint(엔드포인트)는 기능을 호출할 경로와 메서드의 조합입니다. 같은 `/models`에서도 GET은 모델 목록 조회, POST는 새 항목 등록처럼 서로 다른 처리를 맡을 수 있습니다.

Python 함수 위의 `@app.post("/predict")` 같은 Decorator(데코레이터)는 해당 함수를 경로에 등록합니다. 서버가 코드를 읽을 때 등록하고, 맞는 요청이 들어오면 그 함수를 실행합니다.

### 2. 경로·조회 조건·본문으로 요청 내용을 나누는 방법

특정 모델을 고르는 정보와 예측할 데이터는 성격이 다릅니다. 각 값을 어디에 넣는지 정하면 API 주소만으로도 요청의 목적을 파악하기 쉽습니다.

| 위치 | 담는 정보 | 예 |
|---|---|---|
| Path parameter(경로 매개변수) | 대상 자원 식별 | `/models/3`의 `3` |
| Query parameter(쿼리 매개변수) | 조회·출력 조건 | `?detail=true` |
| Header(헤더) | 인증·전송 형식 | API Key, Content-Type |
| Request body(요청 본문) | 처리할 입력 데이터 | 질문, 픽셀 목록 |

경로 함수의 매개변수와 자료형은 값을 어떻게 받을지 표현합니다. JSON 본문의 여러 필드는 Pydantic의 입력 모델로 묶어 정의할 수 있습니다. 이 모델에는 필드 이름·자료형·기본값·허용 범위를 적습니다.

FastAPI는 이 정의로 OpenAPI 명세와 `/docs`의 대화형 문서를 만듭니다. 클라이언트를 연결할 때는 여기서 실제 주소·필수 필드·응답 형태를 확인할 수 있습니다.

### 3. 모델에 전달하기 전에 입력을 검사하는 이유

이미지 분류 모델이 픽셀 784개를 요구하는데 100개만 받으면 정해진 형태로 변환할 수 없습니다. 질문이 공백뿐이거나 생성 길이가 지나치게 크면 사용자가 원하는 작업도 정하기 어렵습니다. 입력 검증은 이런 조건을 모델 실행 전에 확인하는 과정입니다.

먼저 필드 존재 여부와 자료형·범위를 검사합니다. 다음으로 서비스에서 허용하는 조건을 확인하고, 통과한 값을 모델 입력으로 전처리합니다.

**형식 검사 → 서비스 조건 확인 → 전처리 → 모델 입력 구성**

숫자 필드에는 최솟값·최댓값을, 목록에는 길이를, 문자열에는 공백 정리와 최소 길이를 정할 수 있습니다. Pydantic은 설정에 따라 변환 가능한 값을 목표 자료형으로 바꾸기도 합니다. 입력 자료형을 엄격하게 제한하려면 해당 필드에 Strict mode(엄격 모드)를 지정합니다.

필수 여부·기본값·빈 값 허용은 따로 정합니다. `int | None`은 정수 또는 `None`을 허용한다는 뜻이고, `= None`은 필드를 생략했을 때 쓸 기본값입니다. 기본값 없는 필드는 요청에 포함해야 합니다.

LLM의 입력 길이는 토크나이저로 계산한 토큰 수로 확인합니다. 문자열 글자 수 제한은 입력 크기를 먼저 제한하는 데 쓸 수 있고, 모델의 문맥 길이는 입력 토큰과 생성할 토큰을 함께 계산해 맞춥니다.

### 4. 클라이언트가 읽기 쉬운 응답 형식을 정하는 방법

화면이 `prediction`이라는 필드를 읽고 있는데 서버가 갑자기 `result`라는 이름으로 바꾸면 연결이 끊깁니다. 응답도 필드 이름·자료형·의미를 정해 양쪽이 같은 약속을 사용해야 합니다.

분류 API라면 예측 클래스와 클래스별 점수를, 질문 API라면 답변과 근거를 반환할 수 있습니다. 모델이 만든 Tensor(텐서)는 단일 값이나 목록으로 바꾸어 JSON에 담습니다. 분류 점수에서 가장 큰 위치를 고르면 예측 클래스가 되고, Softmax(소프트맥스)를 적용하면 클래스별 확률 형태의 값을 얻습니다.

FastAPI의 `response_model`에는 반환할 데이터의 구조를 지정합니다. 반환값이 그 구조에 맞는지 검사하고 응답 필드를 정리합니다. 클라이언트 입력 검증 오류는 요청을 수정할 단서가 되고, 서버가 잘못된 응답을 만든 경우에는 서버의 처리 코드를 점검합니다.

반환할 때는 딕셔너리나 응답 모델 객체를 전달하고 FastAPI가 JSON 응답을 만들도록 할 수 있습니다. Pydantic의 `model_dump()`는 딕셔너리, `model_dump_json()`은 JSON 문자열을 만듭니다. 반환값을 어떤 단계에서 직렬화하는지 맞추면 문자열이 이중으로 감싸지는 일을 피할 수 있습니다.

### 5. 모델을 시작할 때 한 번 준비하고 재사용하는 방법

요청마다 가중치를 읽으면 사용자가 모델 로딩 시간까지 기다립니다. 모델과 토크나이저는 서버 시작 시 준비하고, 요청마다 입력과 추론 결과를 따로 만들어 사용하는 구조가 적합합니다.

Lifespan(앱 수명 관리)은 시작 준비와 종료 정리를 한곳에 정의하는 방법입니다. 시작 구간에서 모델을 읽고 평가 모드를 설정합니다. 준비를 마친 뒤 요청을 받으며, 종료할 때 연결과 자원을 정리합니다.

**앱 시작 → 모델·전처리 준비 → 요청별 추론 → 앱 종료·정리**

공유할 모델은 `app.state` 등에 보관하고 경로 함수에서 꺼내 사용할 수 있습니다. 요청마다 달라지는 입력·대화 내용은 요청별로 관리합니다. Worker(작업 프로세스)를 여러 개 실행하면 프로세스별 모델 복사본에 필요한 메모리도 함께 계산합니다.

PyTorch에서는 모델의 `eval()`로 평가 동작을 정하고, 실제 추론 구간을 `inference_mode()`로 감쌉니다. 입력의 형태·자료형·장치를 맞춘 뒤 모델을 실행하고 결과를 응답 형식으로 바꿉니다.

### 6. API가 준비되었는지 확인하고 다음 병목을 찾는 방법

서버 프로세스가 실행 중이어도 모델이나 필요한 데이터가 준비 중일 수 있습니다. 요청을 보낼 수 있는 상태인지 확인하려면 무엇이 준비되어야 하는지를 서비스 기준으로 정해야 합니다.

Liveness(실행 상태)는 프로세스가 응답하는지, Readiness(요청 처리 준비 상태)는 모델과 의존 서비스가 준비되었는지를 확인합니다. Lifespan의 시작 작업이 완료된 뒤 요청을 받는 구조에서는 모델 준비도 그 시작 과정에 포함됩니다.

정상 입력으로 결과를 확인한 뒤 필수 필드 누락·잘못된 크기·허용 범위 초과를 넣어 검증 동작을 확인합니다. 이어서 여러 요청을 보내면 오래 걸리는 추론이 다른 요청에 미치는 영향을 볼 수 있습니다. 이때 필요한 비동기 처리와 실행 위치 분리를 다음 강의에서 배웁니다.

## 이해 확인

> [!question]- Uvicorn과 FastAPI는 어떤 역할을 나누나요?
> Uvicorn은 네트워크 요청을 앱에 전달하고, FastAPI는 경로 선택·입력 검증·함수 실행·응답 변환을 연결합니다.

> [!question]- 문자열 최소 길이만으로 공백 질문을 걸러내기 어려운 이유는 무엇인가요?
> 공백도 문자열 길이에 포함되므로, 공백 정리 후 남은 내용의 길이를 확인해야 합니다.

> [!question]- 모델을 서버 시작 때 준비하는 목적은 무엇인가요?
> 요청마다 가중치를 다시 읽는 비용을 줄이고 준비된 모델을 재사용하기 위해서입니다.

> [!question]- 요청별로 따로 관리할 값은 무엇인가요?
> 입력·대화 내용·중간 결과·응답처럼 요청마다 달라지는 값입니다.
