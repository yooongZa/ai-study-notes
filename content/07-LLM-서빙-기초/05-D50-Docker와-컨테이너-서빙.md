---
title: "D50. Docker로 실행 환경과 서비스를 묶기"
---

FastAPI와 Streamlit이 내 컴퓨터에서 실행되어도 다른 컴퓨터에서 사용하려면 Python·패키지·시스템 라이브러리·실행 설정을 다시 맞춰야 합니다. 이 준비 과정을 파일로 정의하고 같은 환경을 반복해서 만들 수 있으면 배포와 오류 재현이 쉬워집니다.

여기서는 **애플리케이션의 실행 환경을 이미지로 만들고, 화면과 API를 컨테이너로 연결하는 방법**을 배웁니다. 이미지와 컨테이너를 구분한 뒤 빌드·네트워크·저장 공간·여러 서비스의 실행 관계로 이어집니다.

## 학습 목표와 흐름

| 배울 내용 | 필요한 상황 |
|---|---|
| 이미지·컨테이너 | 같은 실행 환경을 반복해서 만들 때 |
| Dockerfile·빌드 캐시 | 코드와 의존성을 이미지로 구성할 때 |
| 포트·네트워크 주소 | 호스트와 여러 컨테이너를 연결할 때 |
| 마운트·실행 설정 | 모델·로그·환경별 설정을 관리할 때 |
| Compose | API와 화면을 함께 실행할 때 |

## 자습

### 1. 코드와 실행 환경을 함께 준비하는 이유

Python 패키지 버전이 같아도 Python 자체나 시스템 라이브러리·장치 환경이 다르면 실행에 차이가 생길 수 있습니다. 서버를 옮길 때는 코드가 사용할 기반 환경과 설치 과정을 함께 준비해야 합니다.

Docker의 Image(이미지)는 파일·라이브러리·실행 설정을 묶은 읽기 전용 실행 기준입니다. Container(컨테이너)는 그 이미지에서 만든 실행 단위입니다. 하나의 이미지로 여러 컨테이너를 만들 수 있고, 각 컨테이너는 실행 상태와 쓰기 공간을 가집니다.

컨테이너를 중지하면 그 상태와 쓰기 공간이 남아 다시 시작할 수 있습니다. 컨테이너를 삭제하면 해당 쓰기 공간도 제거됩니다. 계속 보관할 데이터는 별도 저장 공간에 연결합니다.

Registry(레지스트리)는 이미지를 저장하는 서비스이며 Docker Hub가 한 예입니다. 이미지의 Tag(태그)는 버전을 구분하는 이름입니다. 같은 태그가 다른 이미지로 갱신될 수 있어 정확한 재현이 필요할 때는 이미지 Digest(내용 식별값)도 기록합니다.

### 2. 컨테이너를 실행하는 컴퓨터와 관리 도구

Docker 명령이 설치되어 있어도 컨테이너를 관리할 실행 엔진과 연결되어야 실제 작업을 할 수 있습니다. Docker CLI는 명령을 전달하고, Docker Engine은 이미지·컨테이너·네트워크를 관리합니다.

Linux 컨테이너는 실행 기반의 Linux 커널을 공유하며 프로세스와 파일·네트워크 환경을 격리합니다. macOS에서는 Docker Desktop이나 Colima의 Linux 가상머신 안에서 실행할 수 있습니다. Host(호스트)는 이 실행을 제공하는 쪽의 환경입니다.

컨테이너의 수명은 주 프로세스와 연결됩니다. 요청을 계속 기다리는 API 서버는 실행 상태를 유지하고, 한 번 작업한 뒤 끝나는 프로그램은 종료 상태가 됩니다. 목록의 `Up`을 확인한 뒤 실제 API 응답과 모델 준비 상태도 확인합니다.

### 3. Dockerfile로 이미지를 만드는 과정

서버를 준비하려면 기반 환경을 고르고, 패키지를 설치하고, 코드를 복사하고, 시작 명령을 정해야 합니다. Dockerfile은 이 순서를 정의한 파일입니다.

**기반 이미지 → 작업 폴더 → 패키지 설치 → 코드 복사 → 시작 명령**

| 지시어 | 정하는 내용 |
|---|---|
| `FROM` | 사용할 기반 이미지 |
| `WORKDIR` | 이후 작업의 컨테이너 내부 폴더 |
| `COPY` | 빌드에 제공된 파일을 넣을 위치 |
| `RUN` | 이미지 빌드 중 실행할 설치·준비 작업 |
| `ENV` | 실행 환경 변수의 기본값 |
| `EXPOSE` | 앱이 사용하는 포트 정보 |
| `CMD` | 컨테이너 시작 때 실행할 기본 명령 |

Build context(빌드 컨텍스트)는 빌드에 제공할 파일의 기준 폴더입니다. 그 폴더의 Dockerfile만 읽는 데서 끝나는 것이 아니라, `COPY`가 사용할 파일도 그 범위 안에 있어야 합니다.

레이어와 빌드 캐시는 앞 단계의 결과를 재사용합니다. 자주 바뀌지 않는 패키지 목록을 먼저 복사·설치하고 앱 코드를 뒤에 복사하면, 코드 수정 뒤에도 패키지 설치 결과를 재사용하기 쉽습니다. 의존성 목록이 바뀌면 설치 단계부터 새로 구성합니다.

### 4. 호스트와 컨테이너 사이에서 주소를 해석하는 방법

화면은 열리는데 API 호출이 실패하면 ‘어디에서 어느 주소를 호출하는가’를 확인합니다. 호스트·화면 컨테이너·API 컨테이너는 각각 자기 네트워크 환경을 가지고 있습니다.

`localhost`와 `127.0.0.1`은 호출하는 프로그램 자신의 환경을 가리킵니다. 화면 컨테이너에서 `localhost:8000`을 부르면 그 화면 컨테이너의 8000번 포트로 요청합니다. 다른 컨테이너의 API를 부를 때는 같은 네트워크의 서비스 이름을 사용합니다.

| 설정·주소 | 의미 |
|---|---|
| API의 `--host 0.0.0.0` | 컨테이너의 모든 IPv4 인터페이스에서 요청 수신 |
| `127.0.0.1:8000:8000` | 호스트 로컬 8000번 포트를 컨테이너 8000번에 연결 |
| UI에서 `http://api:8000` | 같은 Compose 네트워크의 API 서비스 호출 |
| 브라우저에서 `http://localhost:8501` | 호스트에 연결한 화면 포트 접속 |

Port(포트)는 같은 환경에서 어느 서버로 연결할지 구분하는 번호입니다. Docker의 포트 공개 설정은 `호스트 주소:호스트 포트:컨테이너 포트`로 읽습니다. `0.0.0.0`은 수신 범위 설정이며 클라이언트는 실제 목적지 주소로 접속합니다.

`EXPOSE`는 이미지에 포트 정보를 적습니다. 호스트에서 들어오는 연결은 실행 시 `ports` 또는 `-p`로 구성합니다. 같은 Compose 네트워크의 내부 통신은 서비스 이름과 내부 포트를 사용합니다.

### 5. 코드·모델·로그·비밀 설정을 관리하는 위치

모델 파일이 크거나 코드와 다른 주기로 바뀌면 이미지 밖에 두고 실행할 때 연결할 수 있습니다. 실행 중 쌓이는 로그도 별도 저장 공간에 두면 컨테이너 교체 후 계속 읽을 수 있습니다.

Bind mount(바인드 마운트)는 호스트의 파일·폴더를 컨테이너 경로에 연결합니다. Named volume(이름 있는 볼륨)은 Docker가 저장 위치를 관리합니다. 앱은 컨테이너 내부의 경로를 사용하고, 실행 설정이 실제 저장 위치와 연결합니다.

| 자료 | 관리 예 |
|---|---|
| 코드·패키지 | 이미지에 포함 |
| 모델 파일 | `/app/models`에 읽기 전용 연결 |
| 로그·지속 데이터 | 쓰기 가능한 마운트·볼륨에 보관 |
| 환경별 주소·키 | 실행 시 환경 변수·비밀 설정으로 전달 |

모델을 시작 때 읽어 메모리에 보관한다면 파일 변경 후 다시 읽을 시점이 필요합니다. 파일이 연결된 경로와 앱이 읽는 경로도 같아야 합니다.

`.dockerignore`는 빌드에 보낼 파일을, `.gitignore`는 Git이 추적할 파일을 정합니다. 비밀 파일은 빌드 대상에서 처음부터 제외합니다. 이미지에 복사한 뒤 뒤쪽 레이어에서 지워도 앞 레이어의 내용이 남기 때문입니다.

Compose의 `.env` 변수 치환과 컨테이너로의 환경 변수 전달도 구분합니다. 컨테이너에 줄 값은 `environment`나 `env_file`로 지정합니다. GPU 실행은 호스트 드라이버와 컨테이너 런타임의 장치 지원을 함께 준비합니다.

### 6. Compose로 화면과 API를 함께 실행하는 방법

화면과 API를 각각 실행할 때마다 주소·포트·모델 경로를 따로 지정하면 설정을 빠뜨리기 쉽습니다. Docker Compose는 여러 서비스의 빌드·실행·연결 관계를 YAML 파일로 관리합니다.

Dockerfile은 각 이미지의 구성 방법을, Compose는 그 이미지를 어떤 서비스로 실행할지 정합니다. 같은 네트워크에 속한 `ui`는 `api`라는 서비스 이름으로 API에 접근합니다.

시작 순서와 준비 완료도 따로 정합니다. `depends_on`의 짧은 형식은 선행 서비스 시작 순서를 정하고, 준비 상태를 기다리려면 Healthcheck(상태 검사)와 `service_healthy` 조건을 연결합니다.

서비스 실행 후에는 컨테이너 상태 → API 준비 응답 → 모델 파일 경로 → 실제 추론 → 로그 순서로 확인합니다. 이 흐름을 따라가면 네트워크 설정 오류와 모델·애플리케이션 오류를 나누어 찾을 수 있습니다.

## 이해 확인

> [!question]- 이미지와 컨테이너는 어떤 관계인가요?
> 이미지는 실행 기준이고 컨테이너는 그 기준에서 만든 실행 단위입니다. 한 이미지로 여러 컨테이너를 만들 수 있습니다.

> [!question]- 패키지 설치 뒤에 앱 코드를 복사하는 목적은 무엇인가요?
> 앱 코드만 바뀌었을 때 앞의 패키지 설치 결과를 빌드 캐시로 재사용하기 위해서입니다.

> [!question]- UI 컨테이너가 API를 부를 때 서비스 이름을 쓰는 이유는 무엇인가요?
> UI의 localhost는 UI 자신을 가리키므로 같은 네트워크의 API 목적지를 지정해야 합니다.

> [!question]- 로그를 컨테이너 밖의 저장 공간에 두는 목적은 무엇인가요?
> 컨테이너를 교체한 뒤에도 실행 기록을 보관하고 읽기 위해서입니다.
