---
title: "D48. 비동기 처리와 답변 스트리밍"
---

모델 API를 여러 사람이 사용하면 한 요청이 끝날 때까지 다른 요청이 기다리는 상황이 생깁니다. 외부 검색의 응답을 기다리는 시간, 모델이 계산하는 시간, 완성된 내용을 화면에 보내는 시간을 구분하면 어느 부분을 바꿔야 할지 알 수 있습니다.

여기서는 **여러 요청의 대기 시간을 관리하고, 답변을 생성되는 대로 전달하는 방법**을 배웁니다. 비동기의 실행 원리를 익힌 뒤 오래 걸리는 계산의 실행 위치, 스트리밍, 생성 제한과 취소까지 연결합니다.

## 학습 목표와 흐름

| 배울 내용 | 필요한 상황 |
|---|---|
| 비동기·이벤트 루프 | 외부 응답을 기다리는 동안 다른 요청을 처리할 때 |
| 코루틴·태스크 | 여러 작업의 시작·결과·종료를 관리할 때 |
| 스레드·실행자 | 오래 걸리는 동기 함수로 서버 처리가 멈출 때 |
| 스트리밍·SSE | 긴 답변의 앞부분부터 보여줄 때 |
| 생성 제한·취소 | 대기량과 자원 사용을 관리할 때 |

## 자습

### 1. 요청이 기다리는 시간을 활용하는 비동기 처리

검색 서버에 질문을 보낸 뒤 응답이 오기까지는 결과를 사용하는 작업이 기다려야 합니다. 이때 다른 사용자의 입력 검사처럼 진행할 수 있는 일을 실행하면 서버의 대기 시간을 활용할 수 있습니다.

Asynchronous processing(비동기 처리)은 작업이 기다리는 동안 실행을 넘기고, 결과가 준비되면 이어서 진행하는 방식입니다. Event loop(이벤트 루프)는 실행할 작업과 대기 중인 작업을 관리합니다.

Process(프로세스)는 실행 중인 프로그램이고, Thread(스레드)는 그 안에서 코드를 실행하는 흐름입니다. 한 이벤트 루프는 보통 한 스레드에서 여러 작업을 번갈아 진행합니다. 작업이 비동기 대기 지점에서 실행을 넘기면 다음 작업이 실행할 기회를 얻습니다.

Concurrency(동시성)는 여러 작업을 같은 기간에 진행하는 성질입니다. Parallelism(병렬성)은 여러 계산을 실제로 같은 순간에 수행하는 성질입니다. 네트워크 대기는 겹쳐 진행할 수 있고, 모델 계산을 빠르게 하려면 실행 장치·배치·모델 연산도 함께 살펴봅니다.

### 2. 코루틴을 실행하고 여러 결과를 받는 방법

외부 검색 두 개가 서로 독립적이라면 함께 시작해 결과를 모을 수 있습니다. 반대로 두 번째 검색에 첫 번째 결과가 필요하면 먼저 결과를 받은 뒤 다음 작업을 시작해야 합니다. 비동기 코드를 작성할 때는 이 의존 관계를 먼저 정합니다.

`async def`로 정의한 함수를 호출하면 Coroutine(코루틴) 객체가 만들어집니다. 이를 `await`하면 실행을 진행하고 완료 결과를 받습니다. 실행 중 결과가 준비되지 않은 비동기 대기를 만나면 이벤트 루프가 다른 작업을 진행할 수 있습니다.

Task(태스크)는 코루틴의 실행·결과·취소 상태를 관리하는 객체입니다. 별도로 실행을 등록해 두고 나중에 결과를 받거나 취소할 때 사용합니다.

| 표현 | 실행 흐름 |
|---|---|
| `await A()` 다음 `await B()` | A의 결과를 받은 뒤 B를 시작 |
| `create_task(A())` | A를 실행할 작업으로 등록하고 객체를 보관 |
| `gather(A(), B())` | 두 작업을 함께 진행하고 전달한 순서로 결과 수집 |

예를 들어 A와 B가 각각 2초 동안 외부 응답을 기다린다면, 순차 실행에서는 대기 시간이 약 4초가 됩니다. 함께 시작하면 두 대기 구간이 겹쳐 약 2초 뒤 결과를 모을 수 있습니다. B가 먼저 끝나도 `gather()`의 결과 목록은 입력한 A·B 순서입니다.

여러 작업의 성공과 실패를 각각 확인하려면 결과와 예외를 함께 모읍니다. Python의 `gather(return_exceptions=True)`가 이 방식입니다. 서로 묶인 작업을 함께 종료해야 한다면 `TaskGroup`으로 관리할 수 있습니다. 일반 오류가 발생했을 때 다른 작업의 취소와 종료도 함께 처리합니다.

### 3. 오래 걸리는 동기 함수의 실행 위치

모델이 답변을 만드는 동안 `/health` 같은 짧은 상태 조회까지 늦어지면 이벤트 루프가 오래 걸리는 작업을 직접 실행하고 있는지 확인합니다. 동기 함수가 현재 스레드를 계속 사용하면 그 스레드의 이벤트 루프도 다음 요청으로 넘어가지 못합니다.

FastAPI는 `def`로 등록한 경로 함수를 스레드 풀에서, `async def` 경로 함수를 이벤트 루프에서 실행합니다. `async def` 안에서 일반 보조 함수를 직접 호출하면 그 함수는 현재 실행 위치에서 처리됩니다.

동기 함수를 별도 스레드에 맡기면 이벤트 루프는 결과를 비동기로 기다릴 수 있습니다. Executor(실행자)는 스레드나 프로세스에 작업을 맡기고 실행을 관리하는 도구입니다.

| 작업의 특징 | 실행을 정할 때 볼 내용 |
|---|---|
| 비동기 네트워크 I/O | 비동기 클라이언트의 응답을 `await` |
| 동기 파일·네트워크 I/O | 스레드에 맡기고 결과 대기 |
| 순수 Python의 긴 CPU 계산 | 여러 코어를 쓰려면 별도 프로세스와 전달 비용 검토 |
| NumPy·PyTorch 연산 | 내부 연산·GPU·메모리·동시 실행 수 확인 |

일반적인 GIL 사용 CPython에서는 순수 Python 코드의 스레드 실행에 GIL의 영향을 받습니다. 프로세스를 나누면 메모리와 데이터 전달 비용이 생깁니다. 모델 서빙에서는 처리량과 메모리를 함께 측정해 실행 수를 정합니다.

PyTorch 추론을 다른 스레드에 맡길 때는 실제 추론 함수 안에 `inference_mode()`를 적용합니다. 이 설정이 스레드별로 적용되기 때문입니다. 모델은 미리 평가 모드로 준비해 재사용합니다.

### 4. 오류와 지연을 요청 단위로 확인하는 방법

요청이 실패했을 때 사용자는 입력을 고칠 수 있어야 하고, 개발자는 실패한 단계를 찾을 수 있어야 합니다. 응답에는 사용자에게 필요한 상태와 안내를, 로그에는 요청 식별자·실패 단계·처리 시간을 남깁니다.

Exception(예외)은 실행 중 발생한 문제를 전달합니다. `try`에서 처리를 시도하고, `except`에서 해당 오류를 처리하며, `finally`에서 종료 시 필요한 정리를 수행합니다. FastAPI의 `HTTPException`에는 응답 상태 코드와 안내 내용을 담습니다.

처리 시간을 대기열·전처리·모델 계산·전송으로 나누면 지연이 생긴 곳을 찾기 쉽습니다. Middleware(미들웨어)는 요청과 응답의 공통 경로에서 식별자나 시간을 붙일 때 사용합니다. 스트리밍의 완료 시간은 마지막 전송까지 포함해 측정합니다.

입력 오류·내부 오류·사용자 취소를 구분해 기록하면 다음 조치도 명확해집니다. 특히 취소된 요청은 실제 생성이 끝나고 자원이 반환되었는지까지 이어서 확인합니다.

### 5. 답변을 생성되는 대로 보내는 스트리밍

LLM은 다음 토큰을 차례로 생성합니다. 긴 답변을 모두 만든 뒤 보내면 사용자는 완성될 때까지 빈 화면을 봅니다. Streaming(스트리밍)은 준비된 부분부터 보내 사용자가 앞부분을 읽는 동안 뒤의 생성을 이어가는 방식입니다.

Generator(제너레이터)는 값을 하나 내보낸 뒤 다음 요청에서 이어서 실행할 위치를 보관합니다. Python의 `yield`로 값을 내보냅니다. 비동기 제너레이터는 조각 사이에 비동기로 기다릴 수 있고, 받는 쪽은 `async for`로 준비된 값을 읽습니다.

**모델이 조각 생성 → 제너레이터가 전달 → HTTP 응답 전송 → 화면에 덧붙임**

SSE(Server-Sent Events, 서버 발신 이벤트)는 서버가 텍스트 이벤트를 이어 보내는 형식입니다. `event:`에 이벤트 종류를, `data:`에 내용을 적고 빈 줄로 이벤트의 끝을 표시합니다. 답변 조각·정상 완료·오류를 구분하면 화면의 상태도 각각 갱신할 수 있습니다.

네트워크에서 한 번 읽은 덩어리와 이벤트 하나의 경계는 서로 다를 수 있습니다. 클라이언트는 수신 데이터를 모아 빈 줄까지를 이벤트로 해석합니다. 브라우저의 `EventSource`는 GET 연결을 사용하며, 질문을 POST 본문으로 보내는 방식에서는 `fetch` 등으로 응답 스트림을 읽을 수 있습니다.

TTFT(Time To First Token, 첫 토큰 대기 시간)는 요청 후 첫 생성 내용을 받기까지의 시간입니다. 전체 완료 시간과 토큰 도착 간격도 함께 측정합니다. 중간 프록시가 응답을 모아서 보내면 화면 표시가 늦어지므로 생성 시점과 수신 시점을 비교합니다.

응답 전송 중 오류가 생기면 연결이 유지되는 동안 오류 이벤트를 보낼 수 있습니다. 클라이언트는 정상 완료 이벤트를 받은 상태와 완료 전에 연결이 끊긴 상태를 구분합니다.

### 6. 생성 길이와 동시 요청 수를 제한하는 이유

한 요청이 매우 긴 답변을 만들거나 요청이 계속 쌓이면 다른 사용자의 대기가 길어집니다. 서비스가 감당할 수 있는 입력 길이·출력 길이·생성 시간·동시 작업 수를 정하면 자원 사용과 대기를 관리할 수 있습니다.

출력 토큰 상한은 생성할 분량을 제한합니다. 전체 문맥 길이는 입력과 새로 생성할 토큰을 합해 계산합니다. 시간 제한은 접수부터 잴지, 생성 시작부터 잴지 정해야 합니다. 전자는 대기열에서 보낸 시간까지 포함합니다.

Semaphore(세마포어)는 같은 구간에 동시에 들어갈 수 있는 작업 수를 관리합니다. 모델 생성을 시작할 때 자리를 얻고, 실제 생성이 끝나면 반환합니다. 대기열의 최대 크기도 정해 과도하게 쌓이는 요청을 처리합니다.

같은 이벤트 루프의 세마포어는 그 안의 작업들이 공유합니다. 서버 프로세스가 여러 개라면 전체 요청량은 공통 대기열이나 추론 엔진의 스케줄러와 연결해 관리합니다.

### 7. 사용자가 요청을 취소했을 때 끝내야 하는 작업

사용자가 화면을 닫아도 모델 계산이 계속되면 사용하지 않을 답변에 자원이 쓰입니다. 연결 종료를 확인한 뒤 생성 엔진에 중단을 요청하고, 실제 종료를 확인해 자원을 돌려주는 흐름이 필요합니다.

태스크 취소는 작업에 종료를 요청하는 과정입니다. Python에서는 대기 재개 지점 등에서 `CancelledError`를 받아 정리할 수 있습니다. 정리가 끝나면 취소를 호출자에게 전달하고, 호출자는 작업 종료를 기다립니다.

별도 스레드의 추론은 결과를 기다리는 태스크가 취소된 뒤에도 실행 중일 수 있습니다. 생성 엔진의 중단 기능이나 추론 함수가 확인하는 중단 신호를 연결해야 합니다. 스트림을 일찍 닫을 때는 제너레이터의 종료 처리도 함께 실행합니다.

**입력 확인 → 실행 대기 → 자리 확보 → 생성·전송 → 완료·오류·취소 처리 → 실제 종료 확인 → 자원 반환**
