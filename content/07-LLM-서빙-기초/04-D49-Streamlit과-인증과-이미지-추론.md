---
title: "D49. Streamlit 화면과 인증을 갖춘 이미지 추론"
---

이미지 분류 API를 사용하려면 사용자가 파일을 고르고, 추론을 요청하고, 결과를 확인할 화면이 필요합니다. 서버에서는 호출자를 확인하고 서로 다른 크기의 이미지를 모델이 학습한 입력 형태로 바꿔야 합니다.

여기서는 **사용자 입력부터 인증·전처리·예측 결과 표시까지**를 연결합니다. Streamlit의 화면 재실행 원리를 익힌 뒤 FastAPI와 통신하고, 이미지 처리와 키 관리를 하나의 요청 흐름으로 이해합니다.

## 학습 목표와 흐름

| 배울 내용 | 필요한 상황 |
|---|---|
| 화면 재실행과 상태 | 선택한 입력과 마지막 결과를 유지할 때 |
| 화면·API 연결 | 파일과 예측 결과를 주고받을 때 |
| 인증·의존성 주입 | 허용된 호출자의 요청을 처리할 때 |
| 이미지 검사·전처리 | 업로드 파일을 학습 때의 입력으로 맞출 때 |
| 키 보관·교체 | 프로그램별 호출 자격을 관리할 때 |

## 자습

### 1. 입력과 결과를 이어 주는 화면의 역할

API 주소와 JSON을 직접 다루기 어려운 사용자도 파일 선택과 버튼으로 모델을 사용할 수 있습니다. Streamlit은 Python으로 입력 위젯과 결과 영역을 만드는 도구입니다. 화면이 입력을 모아 API에 전달하고, 서버가 돌려준 값을 읽기 쉽게 표시합니다.

Streamlit은 사용자 입력·진행 상태·결과 표시를 맡고, FastAPI는 입력 검증·인증·모델 계산을 맡을 수 있습니다. 같은 API를 모바일 앱이나 자동화 스크립트에서도 호출할 수 있도록 입력·응답 규칙을 공유합니다.

**브라우저 입력 → Streamlit 서버 → FastAPI 서버 → 모델 추론 → 결과 표시**

Python의 HTTP 요청 코드는 Streamlit 서버에서 실행됩니다. 따라서 그 코드의 `localhost`는 Streamlit이 실행되는 컴퓨터를 가리킵니다. 두 서버를 서로 다른 컴퓨터나 컨테이너에 두면 API 주소도 그 위치에 맞춰 지정합니다.

### 2. 화면이 다시 실행되어도 입력과 결과를 유지하는 방법

이미지를 고른 다음 추론 버튼을 눌렀는데 선택한 값이 사라지면 화면 재실행 때 초기화되는 변수를 확인합니다. Streamlit은 위젯 값이 전달되거나 버튼을 누르면 일반적으로 스크립트를 위에서 아래로 다시 실행합니다.

Rerun(재실행)마다 일반 변수의 대입문도 다시 실행됩니다. 버튼은 누른 직후 실행에서 참을 반환하므로, 그 안에서만 만든 결과를 다음 실행에도 표시하려면 별도 상태에 보관해야 합니다.

| 값 | 보관 위치 | 사용하는 범위 |
|---|---|---|
| 선택 이미지·최근 예측·대화 | `session_state` | 현재 사용자 세션 |
| 준비 비용이 큰 연결·모델 객체 | `cache_resource` | 설정한 캐시 범위, 기본은 세션 간 공유 |
| 이번 계산의 중간값 | 일반 변수 | 현재 실행 |

Session state(세션 상태)에 처음 한 번 값을 만들고 이후 갱신하면 재실행 사이에 이어 쓸 수 있습니다. 이미지를 바꾸면 이전 예측도 비워 현재 입력과 결과를 맞춥니다. 장기간 남길 기록은 파일이나 데이터베이스에 저장합니다.

자원 캐시는 같은 객체를 재사용합니다. 여러 세션이 공유하는 객체에는 요청별 입력을 섞어 넣지 않고, 함께 사용할 수 있도록 관리합니다. 모델을 FastAPI가 담당하는 구성에서는 모델의 준비와 수명도 API 서버에서 관리합니다.

### 3. 이미지 파일을 API에 전달하는 두 가지 방법

업로드한 PNG는 바이트로 된 파일입니다. 서버가 어떤 요청 형식을 받는지에 따라 이 바이트를 전달하는 방법이 달라집니다. 클라이언트와 서버가 파일 필드의 이름·형식까지 맞춰야 같은 입력을 읽을 수 있습니다.

| 방식 | 전달 형태 | 서버에서 받는 값 |
|---|---|---|
| Base64를 담은 JSON | 파일 바이트를 문자로 바꿔 JSON 필드에 넣음 | 문자열 필드 |
| Multipart 업로드 | 파일 이름·바이트·미디어 형식을 파일 항목에 넣음 | `UploadFile` |

Base64(베이스64)는 바이트를 문자로 표현하는 인코딩입니다. 세 바이트를 네 문자로 표현하므로 큰 파일의 문자열 크기는 원본의 약 4/3이 됩니다. 서버가 문자열을 다시 바이트로 복원한 뒤 이미지를 읽습니다.

Multipart 요청에서는 JSON으로 바꾸는 과정 없이 파일 항목을 전달합니다. 예를 들어 서버가 `file`이라는 업로드 필드를 받으면 클라이언트도 같은 이름으로 보냅니다. 인증 키는 요청 헤더로 전달합니다.

응답을 받으면 HTTP 오류를 확인하고 JSON을 읽습니다. 화면은 서버가 정한 예측 필드를 사용하며, 요청 시작·진행·성공·실패를 구분해 표시합니다. 연결 실패나 시간 초과가 나면 현재 요청의 실패 상태를 보여주고 이전 결과가 새 결과처럼 남지 않도록 합니다.

### 4. 추론 전에 호출자를 확인하는 인증

모델 추론에 사용할 자원을 허용된 프로그램에 제공하려면 어떤 호출 자격으로 요청했는지 확인해야 합니다. API Key(인증 키)는 요청의 키를 서버 등록 정보와 비교해 호출 프로그램을 식별하는 방법입니다.

Authentication(인증)은 호출 자격을 확인하고, Authorization(인가)은 그 호출자가 사용할 수 있는 기능·모델·데이터를 정합니다. 호출자별 사용량도 같은 식별 정보에 연결할 수 있습니다.

인증 함수를 여러 경로에 공통으로 연결하면 키 검사와 오류 처리를 한곳에서 관리할 수 있습니다. FastAPI의 Dependency injection(의존성 주입)은 경로 함수에 필요한 값을 다른 함수에서 준비해 넣는 구조입니다. 인증 함수가 돌려준 호출자 정보를 경로 함수가 받아 사용합니다.

인증에 실패하면 추론 경로 함수의 본문을 실행하기 전에 오류를 반환합니다. 파일 본문 수신과 파싱은 이보다 먼저 진행될 수 있으므로 전체 업로드 크기는 수신 설정에서도 제한합니다.

프로그램들이 하나의 키를 공유하면 서버가 식별하는 대상은 그 키의 프로그램입니다. 사용자 개인별 권한이 필요할 때는 로그인 정보와 사용자 식별을 함께 연결합니다.

### 5. 이미지 파일을 모델 입력으로 바꾸는 과정

학습에 사용한 손글씨 이미지는 흑백 28×28인데 사용자가 큰 컬러 사진을 보낼 수 있습니다. 입력을 같은 크기와 값의 범위로 맞춰야 모델이 학습한 기준으로 계산할 수 있습니다. 먼저 읽을 수 있는 파일인지 검사하고 전처리를 진행합니다.

**파일 크기 검사 → 이미지 형식·픽셀 수 검사 → 디코딩 → 흑백·크기 변환 → 텐서·정규화 → 배치 축 추가**

파일의 바이트 수는 전송량을, 가로×세로는 디코딩 후 픽셀 배열 크기를 판단하는 데 사용합니다. 압축된 파일이 작아도 픽셀 수가 클 수 있어 두 값을 함께 확인합니다. 업로드의 미디어 형식은 클라이언트가 전달하므로 실제 내용도 이미지 도구로 읽어 확인합니다.

Pillow의 이미지 열기는 픽셀 읽기를 뒤로 미룰 수 있습니다. 이미지 크기를 먼저 확인하고, 디코딩·변환 단계에서 생기는 오류까지 처리합니다.

| 단계 | 형태·값 |
|---|---|
| 파일 | PNG·JPEG의 `bytes` |
| 흑백 이미지 | 28×28, 픽셀 0~255 |
| 실수 텐서 | `(1, 28, 28)`, 픽셀 0~1 |
| 정규화 | `(값 - 학습 평균) / 학습 표준편차` |
| 배치 추가 | `(1, 1, 28, 28)` |

마지막 형태의 첫 번째 1은 이미지 한 장, 두 번째 1은 흑백 채널 한 개를 뜻합니다. 흰 배경에 검은 숫자를 그린 입력은 학습 데이터의 배경·획 방향에 맞추어 반전할 수 있습니다. 숫자 영역·여백·중심 위치도 맞추면 사용자가 그린 이미지와 학습 입력의 차이를 줄일 수 있습니다.

전처리 결과를 미리 확인하면 화면에서 보이는 이미지와 실제 모델 입력의 차이를 찾기 쉽습니다. 예측 점수는 해당 입력에서 모델이 출력한 값이고, Accuracy(정확도)는 여러 평가 샘플 중 정답을 맞힌 비율로 계산합니다.

### 6. 인증 키를 발급하고 보관하고 교체하는 방법

개발 환경과 배포 환경은 사용할 키가 다릅니다. 키를 실행 설정에서 읽도록 구성하면 같은 코드에 환경별 호출 자격을 전달하고, 프로그램별로 키를 교체할 수 있습니다.

호출 프로그램은 키 원문을 비밀 설정에 보관합니다. 서버는 충분히 무작위로 생성한 키의 해시와 호출자 정보를 보관하고, 요청으로 받은 키를 같은 방식으로 해시해 일치 여부를 확인할 수 있습니다. Hash(해시)는 입력에서 일정 길이의 값을 계산하는 방식입니다.

| 위치 | 담는 값 |
|---|---|
| 호출 프로그램의 비밀 설정 | 요청에 사용할 키 원문 |
| 서버의 등록 정보 | 키 해시·호출자·권한·활성 상태 |
| 코드 | 읽기·검증 로직 |
| 로그 | 호출자·요청 식별자·처리 결과 |

전송은 HTTPS로 보호합니다. 키를 교체할 때는 새 키 등록 → 호출 프로그램 설정 변경 → 정상 호출 확인 → 이전 키 해제 순서로 진행합니다. 등록 정보를 메모리에 보관한다면 변경을 다시 읽는 시점도 정합니다.
