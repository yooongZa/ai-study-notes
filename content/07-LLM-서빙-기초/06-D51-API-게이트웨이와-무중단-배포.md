---
title: "D51. API 게이트웨이와 서비스 버전 배포"
---

요청이 늘어나 추론 서버를 여러 대로 운영하면 어느 서버에 요청을 보낼지 결정해야 합니다. 새 모델을 배포할 때는 준비된 서버부터 요청을 받고, 기존 서버에서 진행 중인 답변도 마무리할 수 있어야 합니다.

여기서는 **요청을 받을지 판단하고, 처리할 서버를 고르고, 새 버전으로 전환하는 방법**을 배웁니다. 인증·요청 한도·대기열·준비 상태를 연결한 뒤 배포 전략과 복구 기준으로 이어집니다.

## 학습 목표와 흐름

| 배울 내용 | 필요한 상황 |
|---|---|
| 게이트웨이·부하 분산 | 여러 서버를 하나의 API로 제공할 때 |
| 인증·요청 추적 | 호출 자격과 처리 경로를 확인할 때 |
| 요청 한도·대기열 | 서버 용량 안에서 요청을 받을 때 |
| 준비 상태 | 모델 로딩을 마친 서버에 요청을 보낼 때 |
| API 버전·배포 전략 | 기존 사용을 이어가며 새 기능을 적용할 때 |

## 자습

### 1. 여러 서버 앞에서 요청을 연결하는 게이트웨이

클라이언트가 각 추론 서버의 주소를 직접 관리하면 서버 추가·교체 때마다 연결 설정을 바꿔야 합니다. 요청을 한곳에서 받고 내부 서버로 전달하면 클라이언트가 사용하는 주소를 유지하면서 서버 구성을 바꿀 수 있습니다.

API Gateway(게이트웨이)는 요청 경로·호출자·사용량·서버 상태를 보고 전달 대상을 정하는 진입점입니다. NGINX 같은 Reverse proxy(리버스 프록시)는 앞에서 요청을 받아 내부 서버로 전달하는 역할을 수행할 수 있습니다.

| 기능 | 판단하는 내용 |
|---|---|
| Routing(라우팅) | 요청 경로와 API 버전에 맞는 서비스 |
| Load balancing(부하 분산) | 요청을 맡길 준비된 서버 |
| 인증·인가 | 호출자와 허용 기능 |
| 요청 한도 | 호출자별 남은 사용량 |
| 기록·추적 | 요청이 지나간 단계와 처리 시간 |
| 캐시 | 같은 조건에서 재사용할 수 있는 결과 |

캐시 키에는 입력뿐 아니라 모델·프롬프트 버전과 접근 권한 범위를 반영합니다. 클라이언트의 접근 경로는 게이트웨이를 통하도록 구성하고, 내부 서버에 접근할 수 있는 네트워크 범위를 정합니다.

### 2. 인증과 요청 추적을 먼저 수행하는 이유

대기 중인 요청도 연결과 메모리를 사용합니다. 처리할 자격이 있는지 먼저 확인하면 허용된 요청에 대기 공간과 계산 자원을 배정할 수 있습니다.

요청을 접수할 때 Trace ID(추적 식별자)를 만들고 인증·한도 검사·서버 선택·추론 로그에 같은 값을 전달합니다. 그러면 사용자에게 발생한 오류를 내부 서버 기록과 연결해 찾을 수 있습니다.

**요청 식별 → 인증 → 호출자 한도 확인 → 서비스 수용량·준비 상태 확인 → 서버 배정**

인증 실패·한도 초과·수용량 부족은 각각 다른 단계에서 결정됩니다. 요청을 거절할 때도 식별자를 남기면 추론에 도달하기 전에 끝난 요청을 분석할 수 있습니다.

### 3. 요청량을 조절하는 토큰 버킷

한 프로그램이 짧은 시간에 많은 요청을 보내면 다른 사용자의 대기가 길어질 수 있습니다. 호출자별로 지속적으로 허용할 요청 속도와 순간적으로 몰릴 때의 허용량을 정하면 사용량을 관리할 수 있습니다.

Token bucket(토큰 버킷)은 남은 요청 허용량을 보관하고 시간에 따라 회복하는 방식입니다. 여기서 토큰은 요청을 허용하는 수량 단위입니다. LLM의 텍스트 토큰과는 용도가 다릅니다.

최대 용량을 $C$, 초당 회복량을 $r$, 현재 허용량을 $b$, 지난 시간을 $\Delta t$라고 하면 다음 요청 전에 허용량을 갱신합니다.

$$
b' = \min(C, b + r\Delta t)
$$

요청 한 건의 비용을 1로 정했다면 $b' \geq 1$일 때 통과시키고 1을 차감합니다. 부족하면 1까지 회복하는 시간을 계산해 재시도 시점을 안내합니다.

예를 들어 용량 3·초당 회복량 1이면 가득 찬 시점에 요청 세 건을 허용하고, 같은 시각의 네 번째는 기다리게 합니다. 1초 뒤에는 한 건을 처리할 허용량이 다시 생깁니다. 최대 용량은 순간 요청을, 회복량은 지속적인 요청 속도를 조절합니다.

요청 한도 초과는 429로 알리고 필요하면 `Retry-After`로 대기 시간을 전달합니다. 여러 서버가 한 호출자의 한도를 함께 적용한다면 사용량 상태도 공통으로 관리해야 합니다.

### 4. 처리 자리와 대기열의 크기를 정하는 방법

호출자에게 남은 한도가 있어도 서버가 이미 처리 중이면 요청은 대기하게 됩니다. 사용자가 기다릴 수 있는 시간과 실제 처리량을 함께 보고 대기열 상한을 정해야 합니다.

Slot(처리 자리)은 동시에 실행할 수 있는 작업 수이고, Queue(대기열)는 실행을 기다리는 요청을 보관합니다. 생성 시간은 입력·출력 길이에 따라 달라지므로 실제 대기 시간과 완료 시간의 분포를 함께 측정합니다.

단순한 용량 계산에서는 모든 작업이 같은 시간에 시작하고, 각 요청이 $t$초 걸리며, $S$개 자리가 모두 사용 중이라고 둘 수 있습니다. 접수부터 완료까지 허용 시간 $T$초 안에 처리할 추가 대기 건수는 다음처럼 계산할 수 있습니다.

$$
Q_{\max}=S\max\left(0,\left\lfloor \frac{T}{t}\right\rfloor-1\right)
$$

4자리·요청당 2초·허용 시간 6초라면 현재 4건 다음에 두 회차, 총 8건을 대기시킬 수 있습니다. 실제 설정에는 네트워크·전처리·요청 길이 차이에 필요한 여유를 반영합니다.

| 상태 코드 | 판단 기준 |
|---|---|
| 401 | 인증 정보 누락·오류 |
| 429 | 해당 호출자의 요청 한도 초과 |
| 503 | 준비된 서버 없음·대기열 상한 등 현재 수용량 부족 |

대기 중 취소되거나 제한 시간을 넘긴 요청은 대기열에서 정리합니다. 실행 중인 요청은 실제 생성 종료를 확인한 뒤 자리를 반환합니다.

### 5. 준비된 서버에 부하를 나누는 방법

새 서버가 실행되어도 모델을 읽는 중이면 추론 요청을 처리할 수 없습니다. 모델과 필요한 연결이 준비된 서버만 요청 배정 목록에 넣습니다.

Liveness(실행 상태)는 프로세스의 동작을, Readiness(요청 처리 준비 상태)는 지금 추론할 준비가 되었는지를 확인합니다. 모델 로딩 중인 서버는 초기화를 마치도록 기다리고, 준비 완료 후 배정에 참여시킵니다.

상태 검사는 자주 수행하므로 준비 플래그를 빠르게 확인하도록 구성합니다. 실제 모델 계산 검사는 시작 시나 별도 검증에서 수행할 수 있습니다. 모델 준비 여부와 현재 빈 처리 자리도 따로 관리합니다.

| 분산 방식 | 선택 기준 | 적용할 상황 |
|---|---|---|
| Round robin(라운드로빈) | 목록의 순서대로 배정 | 처리 시간이 비슷한 요청 |
| Least connections(최소 연결) | 활성 연결이 적은 서버 | 요청별 처리 시간이 다른 서비스 |

LLM은 긴 답변이 남아 있는 서버와 작업을 마친 서버의 상태가 달라집니다. 활성 작업 수를 사용한다면 배정 때 증가시키고 완료·오류·취소 정리 후 감소시켜야 합니다.

스트리밍은 받은 조각을 곧바로 전달해 첫 내용 도착 시간을 유지합니다. 클라이언트 연결이 끝나면 백엔드 생성 취소까지 연결합니다.

### 6. 모델 버전과 API 버전을 관리하는 이유

모델을 개선해도 클라이언트가 같은 요청과 응답 필드를 사용할 수 있다면 내부 모델 버전만 바꿀 수 있습니다. 응답의 `response`를 `answer`로 바꾸는 변경은 클라이언트의 읽는 코드에도 영향을 줍니다.

이처럼 외부 입출력 약속이 바뀌면 `/v1`, `/v2` 등의 API 버전으로 전환 경로를 제공합니다. 기존 경로의 사용 중단 일정을 안내하고, 호출 로그로 이전 진행 상황을 확인합니다.

API의 수명은 기획 → 구현 → 테스트 → 배포 → 사용 중단 안내와 종료로 이어집니다. 각 단계에서 요청·응답 규칙과 호환 대상, 종료 기준을 명확히 해두면 배포 시 무엇을 유지해야 할지 알 수 있습니다.

### 7. 새 서버로 요청을 옮기는 배포 전략

버전을 교체할 때는 새 서버의 모델 준비를 마치고, 기존 서버에 남은 요청이 끝날 시간을 확보해야 합니다. Drain(진행 중 요청 정리)은 새 요청의 배정을 중단한 뒤 이미 맡은 요청을 마무리하는 과정입니다.

| 전략 | 전환 방법 | 필요한 준비 |
|---|---|---|
| Blue-green(블루그린) | 준비한 새 환경으로 전체 전환 | 두 환경의 실행 용량·기존 환경 유지 |
| Canary(카나리) | 일부 사용자부터 새 버전 적용 | 사용자 배정·품질과 지연 관찰 |
| Rolling(롤링) | 서버를 한 대씩 순서대로 교체 | 남은 서버의 처리 여유·준비 상태 확인 |

블루그린은 기존 환경을 유지해 문제가 생기면 라우팅을 되돌립니다. 이전 버전도 현재 데이터와 설정을 읽을 수 있어야 복구 후 요청을 처리할 수 있습니다.

카나리는 같은 사용자를 같은 버전에 배정하면 연속된 요청의 동작을 관찰하기 쉽습니다. 사용자 ID의 안정적인 해시로 구간을 나누고 새 버전 비중을 늘립니다. 대화 기록은 사용자·세션 ID로 이어서 읽도록 관리합니다.

오류율·지연·답변 품질을 정한 관찰 구간에서 확인하고 기준을 넘으면 새 버전 비중을 줄이거나 이전 버전으로 복구합니다. 요청 수와 관찰 시간을 함께 기록하면 적은 요청의 결과와 충분히 모인 결과를 구분해 판단할 수 있습니다.
