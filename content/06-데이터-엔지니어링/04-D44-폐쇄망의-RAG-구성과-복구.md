title: "D44. 폐쇄망의 RAG 구성과 복구"
---

사내 문서를 외부에 보내지 않고 검색·답변하는 서비스를 만들려면 모델과 데이터 처리를 내부에서 실행할 수 있어야 합니다. 인터넷 연결이 없는 환경에서는 실행 도중 필요한 파일을 추가로 받기도 어렵습니다. 코드뿐 아니라 패키지·모델·토크나이저와 검색 데이터까지 준비해야 합니다.

여기서는 **외부망과 분리된 환경에서 RAG를 실행할 준비를 하고, 각 서비스를 연결하며, 장애가 났을 때 정상 구성으로 돌아가는 방법**을 배웁니다.

## 학습 목표와 흐름

| 배울 내용 | 필요한 상황 |
|---|---|
| 실행 파일과 의존성 | 외부 다운로드 없이 서비스를 시작할 때 |
| 버전과 호환성 | 준비한 패키지·모델을 내부 장비에서 실행할 때 |
| RAG 서비스 연결 | 임베딩·검색·생성을 하나의 요청으로 이어 줄 때 |
| 검증과 감시 | 파일 누락과 기능 실패, 느린 구간을 찾을 때 |
| 대체 처리와 복구 | 일부 기능이 멈추거나 새 버전에 문제가 생겼을 때 |

## 자습

### 1. 외부 연결 없이 실행할 구성 요소를 준비하는 방법

모델 파일만 옮겼는데 프로그램이 시작되지 않는다면 토크나이저나 패키지의 추가 자료가 빠졌을 수 있습니다. Air-gapped environment(외부망과 분리된 환경)에서는 실행에 필요한 구성 요소를 미리 목록으로 만들어 함께 준비합니다.

| 구성 요소 | 필요한 이유 |
|---|---|
| 코드·설정 | 처리 로직과 모델·데이터 경로 지정 |
| Python 패키지 | 추출·수치 계산·모델 실행 기능 제공 |
| 가중치·모델 설정 | 모델 구조와 학습된 값 로드 |
| 토크나이저·대화 형식 | 문장을 모델에 맞는 입력으로 변환 |
| 추가 자원 | OCR 언어 자료·사전·글꼴 등 개별 기능 지원 |
| 검색 데이터·평가 자료 | 문서 검색과 기능·품질 확인 |

Dependency(의존성)는 프로그램 실행에 필요한 다른 구성 요소입니다. 직접 사용한 패키지가 요구하는 하위 패키지도 포함합니다. 가중치가 여러 파일로 나뉘어 있다면 각 조각과 조각 목록을 함께 준비합니다.

반입 준비 전에는 어떤 외부 연결이 차단되어 있고, 내부 저장소·승인된 반입 경로를 사용할 수 있는지 확인합니다. 반입 검토에 필요한 파일 목록과 사용 조건을 함께 준비하고, 실제 장비와 맞는 환경에서 사전 실행을 마치면 누락 때문에 다시 반입하는 횟수를 줄일 수 있습니다. 로그와 평가 자료도 내부에서 읽고 분석할 수 있도록 두고, 외부로 가져올 수 있는 범위는 해당 환경의 절차에 맞춥니다.

파일 목록과 버전이 정해졌다면 같은 조건의 환경에서 외부 다운로드 없이 시작·추출·임베딩·검색·생성까지 이어지는지 확인합니다. 이 과정으로 실행 중에만 드러나는 추가 자료도 찾을 수 있습니다.

### 2. 내부 장비와 맞는 패키지·모델 버전을 선택하는 방법

다른 컴퓨터에서 받은 패키지를 내부 서버에 설치하려면 실행 환경이 맞아야 합니다. Wheel(휠)은 Python 패키지의 배포 파일이며, 컴파일된 코드를 포함한 파일은 Python 버전·운영체제·CPU 구조 등의 조건을 가집니다.

ABI(바이너리 인터페이스)는 컴파일된 프로그램이 함수와 데이터를 주고받는 규칙입니다. GPU 연산에는 드라이버와 연산 라이브러리의 호환성도 필요합니다. 컨테이너로 환경을 묶을 때도 호스트의 커널과 GPU 드라이버 조건을 함께 확인합니다.

모델은 이름과 함께 Revision(리비전)을 기록합니다. 고정된 커밋 ID는 특정 시점의 파일 조합을 지정할 때 사용합니다. 가중치·모델 설정·토크나이저·대화 형식이 같은 버전에 대응하도록 보관합니다.

임베딩 모델에는 출력 차원과 질문·문서 입력 규칙을, 생성 모델에는 입력 길이 한도와 생성 설정을 기록합니다. 준비한 조합을 다시 실행하려면 버전 목록과 실제 파일, 그 조합에서 확인한 평가 자료가 함께 있어야 합니다.

### 3. 임베딩·검색·생성을 내부 서비스로 연결하는 방법

RAG에는 질문을 벡터로 바꾸는 계산, 근거를 찾는 검색, 답변을 생성하는 계산이 필요합니다. 각 작업은 필요한 자원과 처리 시간이 다릅니다. 역할별 서비스로 나누면 자원을 따로 배정하고 상태를 확인하기 쉽습니다.

**사용자 질문 → 질문 임베딩 → 권한에 맞는 문서 검색 → 질문과 근거로 입력 구성 → 답변 생성**

문서 임베딩은 데이터 준비 시점에 계산하고, 질문 임베딩은 요청이 들어올 때 계산합니다. 두 벡터는 대응하는 모델과 전처리 규칙을 사용해야 같은 기준으로 비교할 수 있습니다.

API(프로그램 간 요청 규약)는 각 서비스의 주소, 입력·응답 형식, 오류 표현을 정합니다. 임베딩 서비스는 텍스트 목록을 받아 벡터 목록과 모델 버전을 반환할 수 있습니다. 생성 서비스는 구성된 입력을 받아 답변·토큰 수·종료 이유를 반환할 수 있습니다.

같은 Request ID(요청 ID)를 서비스 사이에 전달하면 한 질문이 어느 단계에서 오래 걸리거나 실패했는지 찾을 수 있습니다. 서비스별 입력과 출력을 맞추는 일이 전체 RAG 연결의 기준입니다.

### 4. 연결 주소와 요청 처리 시간을 관리하는 방법

여러 프로그램을 연결할 때는 어느 장치의 어떤 서비스로 요청하는지 명확해야 합니다. `127.0.0.1`은 현재 실행 환경의 자기 자신을 가리킵니다. 서버의 `0.0.0.0` 바인딩은 여러 네트워크 인터페이스에서 연결을 받도록 하는 설정입니다. 다른 서버에서 호출할 때는 실제 내부 주소와 포트를 사용합니다.

사용자 인증과 문서 권한은 요청·검색 과정에 적용합니다. 로그에 질문이나 본문을 남길 때도 누가 읽고 얼마나 보관할지 정합니다. 내부 서비스 간 연결 범위와 사용자의 문서 열람 범위를 각각 관리합니다.

응답이 늦으면 임베딩·검색·생성·통신·대기 시간을 나누어 측정합니다. 요청이 몰리는 단계에는 대기열이나 Batch(묶음 처리)를 적용할 수 있습니다. 공유 모델을 보호하는 잠금은 동시에 실행할 작업을 제한하므로, 요청 수에 따른 대기 시간도 함께 확인합니다.

Cache(캐시)는 같은 계산 결과를 재사용합니다. 임베딩 캐시에는 텍스트·모델 버전·전처리 규칙을, 검색·답변 캐시에는 데이터 버전과 권한 범위까지 반영합니다. 그래야 현재 요청에 맞는 결과를 다시 사용할 수 있습니다.

### 5. 반입한 파일과 실제 동작을 검증하는 방법

내부 환경으로 파일을 옮겼다면 먼저 준비한 구성과 일치하는지 확인합니다. Manifest(구성 목록)에 파일 이름·크기·해시·버전을 기록해 두면 빠지거나 바뀐 파일을 찾을 수 있습니다. 배포 출처와 서명 정보는 파일을 제공한 경로를 확인하는 데 사용합니다.

파일 확인 다음에는 프로그램이 실제로 요청을 처리하는지 검사합니다. 프로세스가 실행 중인지 보는 Liveness(생존 상태)와, 모델을 로드하고 요청을 받을 수 있는지 보는 Readiness(준비 상태)를 구분합니다. 모델을 읽는 중에는 프로세스가 살아 있어도 답변 준비는 끝나지 않은 상태입니다.

짧은 입력으로 토큰화·임베딩 차원·검색 연결·생성 응답을 확인한 뒤, 평가 질문으로 필요한 근거와 답변이 나오는지 확인합니다. 오류가 생기면 요청 ID와 실패 단계를 기록합니다.

라이브러리의 오프라인 설정과 운영체제·네트워크의 외부 통신 규칙도 적용합니다. Hugging Face의 로컬 로드 옵션은 해당 라이브러리의 파일 읽기에 사용하고, 서비스 전체 통신은 네트워크에서 관리합니다. 시작·정상 요청·오류·재시도 중 연결 기록을 살피면 남은 외부 연결 시도를 찾을 수 있습니다.

### 6. 장애 중 제공할 기능과 이전 버전으로의 복구

생성 모델이 멈춰도 검색된 근거를 보여줄 수 있고, 일부 문서 처리에 실패해도 다른 문서는 계속 사용할 수 있습니다. 장애가 났을 때 유지할 기능을 정해 두면 사용자에게 가능한 결과를 제공할 수 있습니다. 미리 정한 다른 처리 방식으로 요청을 이어 가는 것을 Fallback(대체 처리)이라고 합니다.

| 실패한 부분 | 준비할 대응 |
|---|---|
| 생성 서비스 | 근거 문서와 출처 제공 |
| 검색 서비스 | 준비한 대체 검색 또는 근거 조회 실패 안내 |
| 임베딩 서비스 | 같은 버전의 유효한 캐시나 대체 검색 사용 |
| 일부 문서 처리 | 해당 문서를 분리하고 재처리 대상 기록 |

사용자에게 어떤 기능과 자료로 결과를 제공했는지 기록하면 장애 중 답변도 확인할 수 있습니다. 대체 처리에 필요한 데이터와 품질 기준은 정상 동작할 때 미리 준비합니다.

Rollback(이전 버전 복원)은 마지막으로 정상 확인한 구성으로 돌아가는 작업입니다. 코드·설정·임베딩 모델·검색 컬렉션·별칭을 맞는 조합으로 복구합니다. 백업에서 실제 데이터를 읽고 대표 질문을 처리해 복구 과정을 확인합니다.

MTTR(평균 복구 시간)은 장애 발생 후 복구까지 걸린 시간의 평균입니다. 실패 단계와 이전 정상 구성, 복구에 사용한 절차를 남기면 다음 장애의 원인을 찾고 복구하는 데 활용할 수 있습니다.
