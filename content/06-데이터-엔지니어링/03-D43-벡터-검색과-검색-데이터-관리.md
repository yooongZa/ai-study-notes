---
title: "D43. 벡터 검색과 검색 데이터 관리"
---

문서가 적을 때는 질문과 모든 문서를 비교해도 빠르게 결과를 얻을 수 있습니다. 문서와 사용자가 늘어나면 검색 시간과 메모리 사용량이 커집니다. 여기에 부서별 열람 범위와 문서 개정까지 반영하려면 검색 방법과 데이터 관리 방식을 함께 정해야 합니다.

여기서는 **벡터 검색의 후보를 줄이고, 벡터를 압축하며, 조건에 맞는 최신 문서를 찾는 방법**을 배웁니다. 검색 속도와 결과의 변화를 비교해 사용할 설정을 선택합니다.

## 학습 목표와 흐름

| 배울 내용 | 이해할 내용 |
|---|---|
| 완전 탐색과 근사 탐색 | 모든 문서를 비교하는 기준과 후보를 줄이는 방법 |
| 검색 인덱스 | HNSW·IVF 등이 빠르게 후보를 찾는 원리 |
| 벡터 양자화 | 숫자 표현을 줄여 메모리와 비교 비용을 낮추는 방법 |
| 필터 | 권한·부서·날짜에 맞는 문서 범위 지정 |
| 갱신과 평가 | 내용·임베딩 버전을 맞추고 품질·시간을 비교하는 방법 |

## 자습

### 1. 문장 벡터를 비교해 검색 결과를 고르는 과정

문장 표현이 달라도 비슷한 의미의 문서를 찾으려면 질문과 문서를 같은 임베딩 모델로 숫자 벡터로 바꿀 수 있습니다. 질문 벡터와 가까운 문서 벡터를 찾아 해당 본문을 반환하는 것이 벡터 검색입니다.

Exact search(완전 탐색)는 검색 대상의 모든 벡터에 같은 거리 계산을 적용합니다. 문서가 $N$개이고 벡터 차원이 $d$라면 한 질문에 대략 $N\times d$에 비례하는 계산이 필요합니다. 결과를 점수순으로 정렬해 상위 $k$개를 선택합니다.

Cosine similarity(코사인 유사도)는 두 벡터의 방향이 얼마나 비슷한지 나타냅니다. 각 벡터를 길이 1로 정규화했다면 내적으로 같은 값을 구할 수 있습니다. 문서 벡터를 행으로 쌓은 행렬과 질문 벡터를 곱하면 문서별 점수가 나옵니다.

Vector database(벡터 데이터베이스)는 이런 벡터와 본문·출처·권한 등의 부가 정보를 저장하고 검색·갱신하는 기능을 제공합니다. 검색 결과의 ID가 원본 문서와 연결되어야 찾은 내용을 답변 근거로 사용할 수 있습니다.

검색 도구를 고를 때는 벡터 비교 기능 외에 갱신·권한 필터·백업·여러 요청 처리를 누가 담당할지 정합니다. 검색 라이브러리를 앱에 넣는 구성, 기존 데이터베이스에 벡터 검색 기능을 더하는 구성, Qdrant 같은 별도 검색 서버를 두는 구성이 있습니다. 데이터 규모·변경 빈도·필터 조건·운영 환경을 정한 뒤 같은 질문과 요청량으로 비교합니다.

### 2. 근사 탐색으로 비교할 후보를 줄이는 방법

데이터가 많아지면 모든 벡터를 매번 읽고 비교하는 비용이 커집니다. 자주 사용할 검색 구조를 미리 만들고, 질문과 가까울 가능성이 높은 후보부터 찾으면 비교량을 줄일 수 있습니다.

Index(인덱스)는 이런 탐색에 사용하는 자료 구조입니다. ANN(근사 최근접 이웃 탐색)은 인덱스를 따라 일부 후보를 조사해 가까운 벡터를 찾습니다. 인덱스를 만드는 시간과 공간을 사용해 이후 여러 검색을 빠르게 처리합니다.

| 방식 | 후보를 찾는 원리 |
|---|---|
| HNSW | 가까운 벡터를 연결한 여러 층의 그래프를 탐색 |
| IVF | 벡터를 여러 묶음으로 나누고 질문에 가까운 묶음 탐색 |
| DiskANN 계열 | 메모리의 압축 정보와 SSD의 데이터를 함께 이용하는 탐색 |

HNSW는 위층에서 넓은 범위를 이동하고 아래층에서 이웃을 자세히 탐색합니다. 연결을 많이 만들거나 검색 후보의 폭을 넓히면 더 많은 경로를 확인할 수 있고, 필요한 메모리와 계산도 늘어납니다.

| HNSW 설정 | 바꾸는 것 |
|---|---|
| `m` | 벡터 사이의 연결 수 |
| `ef_construct` | 인덱스를 만들 때 검토할 이웃 후보의 폭 |
| `hnsw_ef` | Qdrant 검색 중 검토할 후보의 폭 |

최종 반환 개수 $k$와 탐색 후보 수는 역할이 다릅니다. 결과 5개를 고르기 위해 훨씬 많은 후보를 검토할 수 있습니다. IVF의 `nprobe`는 검색할 묶음 수를 정합니다. 각 설정을 바꾸면서 시간과 검색 누락이 어떻게 달라지는지 비교합니다.

### 3. 벡터를 압축하고 원본으로 순위를 다시 계산하는 방법

벡터가 많으면 인덱스뿐 아니라 숫자 배열 자체도 큰 공간을 사용합니다. Quantization(양자화)은 실숫값을 더 적은 비트의 대표값으로 바꾸어 저장량과 비교 비용을 줄이는 방법입니다.

FP32는 차원 하나에 32비트, SQ8(8비트 스칼라 양자화)은 8비트 정수, 1비트 BQ(이진 양자화)는 기준값에 따라 0 또는 1을 저장합니다. 표현이 줄어들면서 원래 거리와 검색 순위도 달라질 수 있어 실제 벡터 분포에서 결과를 비교합니다.

100만 개의 1,024차원 벡터를 저장한다면 값 자체의 용량은 FP32 약 4.096GB, SQ8 약 1.024GB, BQ 약 0.128GB입니다. 실제 서버에는 원본 벡터, 인덱스의 연결 정보, 본문과 관리 정보도 저장합니다.

압축한 벡터로 빠르게 후보를 찾고, 그 후보만 원본 벡터로 다시 계산하는 방법도 있습니다. 최종 10개를 반환할 때 후보 40개를 먼저 확보하는 것이 Oversampling(후보 확대), 원본 벡터로 점수를 다시 구하는 것이 Rescoring(재점수화)입니다.

**압축 벡터로 후보 검색 → 넉넉한 후보 확보 → 원본 벡터로 재점수화 → 상위 결과 반환**

재점수화는 확보한 후보 안에서 순위를 고칩니다. 후보 목록에서 빠진 정답을 줄이려면 후보 수와 탐색 범위를 함께 조정합니다. 원본 벡터를 디스크에서 읽는 시간도 검색 시간에 포함됩니다.

### 4. 부서와 권한 조건을 검색에 적용하는 방법

사내 문서를 검색할 때는 질문과 의미가 비슷하면서 사용자가 읽을 수 있는 자료를 찾아야 합니다. 문서와 함께 저장한 부서·날짜·권한 정보를 조건으로 사용하면 검색 범위를 정할 수 있습니다.

Qdrant에서는 벡터에 붙은 부가 정보를 Payload(페이로드)라고 합니다. Filter(필터)는 이 정보에 적용할 조건입니다. 예를 들어 부서가 HR인 문서를 대상으로 검색하도록 지정할 수 있습니다.

전체 상위 10개를 고른 다음 HR 문서만 남기면 결과가 1개만 남을 수 있습니다. HR 문서 범위에서 검색하면 그 조건 안의 가까운 결과를 찾습니다. 벡터 데이터베이스는 필드 인덱스와 벡터 탐색을 결합해 조건에 맞는 후보를 찾습니다.

실제 권한 필터는 서버가 인증된 사용자 정보로 구성합니다. 허용된 결과만 답변 모델에 전달하고, 검색·답변 캐시에도 사용자 권한과 데이터 버전을 반영합니다. 필터별 통과 비율과 결과 수를 확인하면 조건이 탐색 속도와 결과에 미친 영향을 알 수 있습니다.

### 5. 문서와 임베딩 모델을 바꿀 때 검색 데이터를 갱신하는 방법

규정이 개정되면 새 내용을 검색할 수 있어야 합니다. 문서가 추가되면 청킹과 임베딩을 거쳐 저장하고, 수정되면 새 청크를 만든 뒤 사용하지 않는 이전 청크를 정리합니다. 삭제한 문서의 청크가 다시 검색되는지도 확인합니다.

검색에서 제외하는 논리적 삭제와 저장 공간을 회수하는 정리 작업은 별도로 진행될 수 있습니다. 그래서 삭제 확인에서는 검색 결과와 실제 저장량을 각각 살핍니다.

임베딩 모델을 바꿀 때는 질문과 문서의 표현도 함께 맞춰야 합니다. 같은 차원 수라도 다른 모델은 다른 벡터 공간을 학습합니다. 새 모델로 문서 벡터를 만들고, 질문도 해당 모델의 접두어·정규화 방식에 맞춰 처리합니다. 모델 버전, 차원 수, 청킹 기준을 함께 기록합니다.

Collection(컬렉션)은 벡터와 설정을 관리하는 저장 단위입니다. 기존 컬렉션을 서비스하는 동안 새 컬렉션을 만들고 건수·권한 필터·대표 질문·속도를 확인할 수 있습니다. 검증이 끝나면 서비스가 가리키는 컬렉션을 전환합니다.

Alias(별칭)는 실제 컬렉션을 가리키는 이름입니다. Qdrant는 별칭 변경을 원자적으로 적용할 수 있어 전환 도중 조회 대상을 유지하는 데 사용합니다. 임베딩 모델이 바뀌는 전환에서는 질문 모델과 컬렉션, 진행 중인 요청과 캐시도 같은 버전 조합으로 관리합니다.

### 6. 검색 품질과 속도를 함께 평가하는 방법

검색 설정을 고르려면 빨라진 정도와 놓친 결과를 함께 알아야 합니다. 먼저 같은 문서·질문·거리 계산·필터로 완전 탐색 결과를 구해 비교 기준을 만듭니다.

ANN Recall@k(근사 탐색 재현율)는 근사 검색의 상위 $k$개가 완전 탐색의 상위 $k$개와 얼마나 겹치는지 나타냅니다. 기준이 A·B·C이고 근사 결과가 A·C·D라면 Recall@3은 $2/3$입니다. 여러 질문에서 이를 계산하고 놓친 문서를 확인합니다.

이 값은 벡터상 가까운 문서를 찾는 성능을 보여줍니다. 실제 질문의 정답 근거를 찾는지는 정답 문서를 지정해 따로 평가합니다. 임베딩과 청킹의 품질도 이 결과에 영향을 줍니다.

속도는 같은 장비와 동시 요청 조건에서 측정합니다. 첫 요청의 파일 읽기·초기화가 포함된 시간과 준비가 끝난 뒤의 시간을 나누어 기록합니다. p50은 중간 수준의 응답 시간, p95는 요청의 약 95%가 그 안에 완료된 시간입니다. QPS(초당 처리 요청 수)는 일정 시간에 완료한 요청 수이며 동시 요청 수와 함께 읽습니다.

서버형 데이터베이스는 통신 시간을 포함해 측정하고, 벡터 배열의 크기와 프로세스 전체 메모리를 구분합니다. **기준 검색 → 후보 설정 변경 → 품질·시간·메모리 비교 → 서비스 조건에 맞는 설정 선택**이 평가의 흐름입니다.
