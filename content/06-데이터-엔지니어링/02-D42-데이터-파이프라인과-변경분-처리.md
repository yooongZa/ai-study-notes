---
title: "D42. 데이터 파이프라인과 변경분 처리"
---

문서가 매일 추가되는 서비스에서는 수집·추출·정제·청킹·저장을 반복해야 합니다. 작업 도중 멈추거나 이미 처리한 문서를 다시 받았을 때도, 어떤 결과를 재사용하고 무엇을 다시 만들지 알 수 있어야 합니다.

여기서는 **문서 처리 단계를 연결하고, 변경된 데이터만 반영하며, 실패한 작업을 이어 가는 방법**을 배웁니다. 처리 순서와 상태를 정한 뒤 문서 ID, 내용 해시, 실행 이력을 이용해 반복 실행을 관리합니다.

## 학습 목표와 흐름

| 배울 내용 | 필요한 상황 |
|---|---|
| 단계와 상태 | 문서가 어디까지 처리됐는지 확인할 때 |
| 멱등성과 증분 처리 | 같은 작업을 재시도하거나 변경분만 반영할 때 |
| 검증과 결과 공개 | 완성된 새 결과를 검색 서비스에 적용할 때 |
| 이력과 재개 | 오류를 추적하고 완료 지점부터 이어 갈 때 |
| 실행 관리와 감시 | 정기 작업의 누락·실패·품질 변화를 찾을 때 |

## 자습

### 1. 문서 처리 단계를 파이프라인으로 연결하는 이유

새 규정집을 검색에 넣으려면 본문을 읽고, 필요한 정보를 남기고, 검색할 단위로 나누어 저장해야 합니다. 매번 이 순서를 수동으로 수행하면 일부 단계를 빠뜨리기 쉽습니다. Pipeline(파이프라인)은 필요한 작업을 정해진 순서로 연결해 반복할 수 있게 만든 처리 과정입니다.

**수집 → 추출 → 정제·검사 → 중복 확인 → 청킹 → 임베딩·저장**

각 단계는 앞 단계의 결과를 입력으로 받습니다. 본문 길이는 추출 후에 검사할 수 있고, 열람 범위는 수집 목록의 정보로 먼저 확인할 수 있습니다. 이렇게 어떤 정보가 언제 준비되는지를 기준으로 순서를 정합니다.

단계마다 입력, 출력, 성공 조건을 정해 두면 문제가 생겼을 때 다음 단계로 잘못된 결과를 넘기지 않고 해당 문서를 분리할 수 있습니다. 문서 ID와 본문, 처리 상태, 이력을 문서 한 건의 기록으로 묶어 전달합니다.

### 2. 문서 상태와 전체 실행 결과를 구분하는 방법

손상된 파일 한 건과 저장소 연결 실패로 모든 파일을 읽지 못한 경우는 대응 범위가 다릅니다. 그래서 한 문서의 처리 결과와 전체 실행의 결과를 나누어 판단합니다.

| 문서 상태 | 뜻과 다음 처리 |
|---|---|
| `pending` | 최종 판정 전 상태. 대기하거나 처리 중인 문서 |
| `ok` | 필요한 처리와 검사를 통과한 문서 |
| `excluded` | 중복이나 사용 기준에 따라 대상에서 제외한 문서 |
| `failed` | 필요한 처리를 끝내지 못해 원인 확인이 필요한 문서 |

상태와 이유를 함께 남기면 다시 시도할 문서와 제외 기준을 검토할 문서를 고를 수 있습니다. 예를 들어 빈 양식은 용도에 따라 제외할 수 있고, 손상된 PDF는 복구나 재수집이 필요합니다.

전체 실행에는 별도의 Gate(검증 조건)를 둡니다. 수집 목록이 완성됐는지, 저장에 성공했는지, 통과 문서 수가 예상 범위인지, 대표 질문에서 필요한 근거가 검색되는지 확인합니다. 새 문서가 없어 결과가 0건인 실행과 수집 실패로 0건인 실행도 이 조건과 기록으로 구분합니다.

### 3. 재실행할 때 결과가 중복되지 않게 만드는 방법

문서 저장은 끝났지만 완료 기록을 남기기 전에 프로그램이 멈출 수 있습니다. 다시 실행했을 때 같은 청크가 하나 더 생기면 검색 결과가 반복됩니다. 이를 해결하려면 같은 원본과 처리 조건을 같은 결과 ID로 연결해야 합니다.

Idempotency(멱등성)는 같은 작업을 반복해도 의도한 최종 상태가 유지되는 성질입니다. 문서와 청크의 ID를 일정하게 만들고, 같은 ID에는 기존 결과를 갱신하도록 저장하면 재시도할 수 있습니다. ID가 있으면 갱신하고 없으면 추가하는 방식을 Upsert(업서트)라고 합니다.

문서 ID는 어느 원본인지를, 내용 해시는 그 원본의 내용이 바뀌었는지를 나타냅니다. 파서·정제·청킹·임베딩 설정도 결과에 영향을 주므로 재사용할 결과에는 처리 버전을 함께 기록합니다. 입력과 처리 조건이 같을 때 이전 결과를 재사용합니다.

문서마다 처리 이력도 따로 보관합니다. Python 객체로 이를 표현한다면 각 문서가 자기 이력 목록을 갖도록 구성합니다. 한 문서의 상태 변경이 다른 문서의 기록과 섞이지 않아야 다음 처리 대상을 정확히 정할 수 있습니다.

### 4. 추가·수정·삭제된 문서만 처리하는 증분 처리

문서 10만 건 중 몇 건만 바뀌었는데 매번 전체를 추출하고 임베딩하면 시간과 자원을 반복해서 사용합니다. Incremental processing(증분 처리)은 이전 상태와 현재 상태를 비교해 변경된 부분만 처리하는 방법입니다.

| 비교 결과 | 처리할 내용 |
|---|---|
| 현재 목록에만 있는 ID | 새 문서 수집·처리 |
| 양쪽에 있지만 해시가 다른 ID | 변경된 본문 재처리 |
| 이전 목록에만 있는 ID | 삭제 확인 후 검색 결과 정리 |
| 내용과 처리 버전이 같은 ID | 기존 결과 재사용 |

삭제를 찾으려면 현재 목록을 끝까지 수집해야 합니다. 연결 오류로 일부 목록만 받은 경우에는 수집을 완료한 뒤 이전 목록과 비교합니다. 수정 시각뿐 아니라 ID와 해시를 함께 사용하는 이유도 여기에 있습니다. 오래된 파일을 오늘 복사해 추가하면 수정 시각은 과거일 수 있습니다.

문서가 수정되면 이전 청크도 정리해야 합니다. 이전에 5개였던 청크가 새로 3개가 되었다면, 새 3개를 저장하고 더 이상 사용하지 않는 이전 2개를 제거합니다. 문서별 이전·새 청크 ID를 비교하면 남은 오래된 조항을 찾을 수 있습니다.

처리 규칙이 바뀌었을 때는 그 규칙에 영향을 받는 문서를 재처리합니다. 주기적으로 전체 목록을 대조하면 누락된 추가·삭제도 찾을 수 있습니다.

### 5. 검증한 결과를 공개하고 처리 이력을 남기는 방법

새 데이터를 만드는 중에도 사용자는 기존 데이터를 검색합니다. 새 결과를 별도 공간에서 완성하고 검사한 뒤 사용 버전을 전환하면, 중간 결과가 현재 검색 결과에 섞이는 일을 줄일 수 있습니다.

**새 결과 생성 → 문서·전체 실행 검사 → 사용 버전 전환 → 이전 결과 정리**

전환 전에는 문서 수와 실패 이유, 대표 질문의 검색 결과를 확인합니다. 새 버전에서 문제가 발견되면 이전 정상 버전을 다시 사용하도록 준비합니다. 이때 어떤 원본과 설정으로 각 버전을 만들었는지 알 수 있어야 합니다.

Lineage(처리 계보)는 원본이 어떤 변환을 거쳐 현재 결과가 되었는지 나타냅니다. 문서에는 원본 위치·해시·수집 시각, 청크에는 문서 ID·페이지·청킹 설정·임베딩 버전, 실행에는 실행 ID·코드와 설정 버전·시작과 종료 시각을 연결합니다.

검색된 청크에서 원본과 생성 실행까지 따라갈 수 있으면, 오래된 규정이 나온 원인이 수집·청킹·저장 중 어디에 있는지 찾기 쉽습니다. 로그도 실행 ID와 문서 ID를 포함한 일정한 필드로 남깁니다.

### 6. 중단된 작업을 이어 가고 반복 실행을 관리하는 방법

많은 문서를 처리하는 작업은 일부 결과를 만든 뒤 중단될 수 있습니다. 완료한 결과와 상태를 저장하면 다시 시작할 지점을 정할 수 있습니다. 이 진행 기록이 Checkpoint(체크포인트)입니다.

일시적인 연결 실패에는 Retry(재시도)를 적용하고, 완료한 단계 뒤부터 이어 가는 것은 Resume(재개)라고 합니다. 바뀐 규칙을 과거 데이터에도 적용하는 작업은 Backfill(과거 데이터 재처리)입니다. 재개 전에 입력과 처리 버전이 맞는지 확인하면 오래된 중간 결과를 구분할 수 있습니다.

Snapshot(스냅샷)은 특정 시점의 상태를 나타냅니다. 문서 ID와 해시 목록을 저장한 스냅샷은 변경분 비교에 사용합니다. Backup(백업)은 복구에 필요한 실제 데이터와 설정을 보관합니다. 복구할 때는 원본·설정·검색 데이터의 버전을 맞춥니다.

반복 작업의 시작 시점은 Scheduler(스케줄러)가 관리합니다. 작업 간 순서와 실패·재실행까지 관리하는 도구는 Orchestrator(실행 조정 도구)이며 Airflow·Dagster·Prefect 등이 있습니다. 작업과 선후 관계를 순환 없이 나타낸 것이 DAG(방향성 비순환 그래프)입니다.

도구를 고를 때는 무엇을 관리의 중심에 둘지 봅니다. Airflow는 작업 간 의존 관계와 실행 일정, Dagster는 만들어지는 데이터 자산과 그 관계, Prefect는 Python 함수의 실행 흐름과 상태를 중심으로 구성할 수 있습니다. Kedro는 데이터 처리 코드의 구조화에, dbt는 데이터베이스의 SQL 변환과 검사에 쓰입니다. 반복 작업이 작을 때는 스크립트와 일정 실행으로 시작하고, 단계별 재시도·이력·의존 관계 관리가 필요해지면 실행 조정 도구를 연결합니다.

추출이 끝나야 청킹을 시작할 수 있지만 서로 다른 문서는 동시에 처리할 수 있습니다. 같은 문서 결과를 수정하는 작업은 순서를 정해 충돌을 피합니다. 실행 중에는 마지막 성공 시각, 처리 시간, 문서 수, 실패와 재시도, 빈 본문·중복 비율, 검색 품질을 확인합니다. 경보에는 실패 단계와 영향을 받은 문서, 재개 지점을 연결합니다.
