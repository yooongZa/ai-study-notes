## 전체 흐름 요약

학습을 마친 AI 모델을 서비스하려면 모델을 실행할 서버 환경이 필요하다. 서버에는 모델 가중치뿐 아니라 Python, PyTorch, vLLM, API 코드와 각종 라이브러리가 필요하다. 서버마다 설치 환경이 다르면 같은 모델을 배포하더라도 실행 오류가 발생할 수 있다. Docker를 사용하면 실행에 필요한 환경을 이미지로 만들어 여러 서버에서 일관되게 사용할 수 있다.

하지만 이미지를 만들었다고 안정적인 서비스가 완성되는 것은 아니다. 이미지가 너무 크면 새 서버에 배포하는 시간이 길어진다. API 키가 이미지에 포함되거나 서버가 관리자 권한으로 실행되면 보안 위험이 커진다. 여러 서버를 동시에 운영할 때는 장애가 발생한 서버를 복구하고, 준비된 서버에만 사용자 요청을 보내야 한다.

오늘 학습하는 기술은 이러한 문제를 순서대로 해결한다.

```text
AI 모델과 API 코드 준비
        ↓
Docker 이미지 빌드 — 실행 환경 구성 및 이미지 최적화
        ↓
권한·시크릿 검사 — 안전한 실행 환경 구성
        ↓
다이제스트·전자서명 검증 — 검사한 이미지와 배포할 이미지 일치 확인
        ↓
사내 레지스트리 등록 — 배포용 이미지 보관
        ↓
쿠버네티스 배포 — 서버 배치 및 복제본 유지
        ↓
프로브 검사 — 서버의 초기화·생존·요청 처리 준비 상태 확인
        ↓
Service — 준비된 파드에 사용자 요청 전달
        ↓
롤링 업데이트·롤백 — 버전 교체 및 장애 대응
```

| 기술 | 해결하려는 문제 |
| --- | --- |
| Docker | 여러 서버에서 동일한 애플리케이션 실행 환경을 구성한다. |
| 멀티스테이지 빌드 | 빌드에만 필요한 도구를 최종 이미지에서 제외한다. |
| Non-root / Secret | 실행 권한을 제한하고 API 키를 이미지에서 분리한다. |
| Registry / Digest / Signature | 이미지를 보관하고 내용의 동일성과 서명 주체를 확인한다. |
| Docker Compose | 여러 컨테이너의 실행 설정과 초기 기동 순서를 관리한다. |
| Kubernetes | 여러 서버에 컨테이너를 배치하고 지정한 실행 상태를 유지한다. |
| Probe / Service | 서버 상태를 검사하고 준비된 파드로 요청을 전달한다. |
| Rolling Update | 기존 서버를 유지하면서 새 버전으로 순차 교체한다. |

오늘 실습의 핵심은 **서버가 실행 중인 시점과 사용자 요청을 처리할 수 있는 시점을 구분하는 것**이다. LLM 서버는 프로세스가 시작된 뒤에도 모델 가중치를 불러오고 GPU 메모리에 적재하는 시간이 필요하다. 이때 질문을 보내면 503(Service Unavailable) 오류가 발생할 수 있다. 같은 서버에서 readiness 검사 경로만 변경해 Ready 판정 시점과 준비 전 503 응답 건수를 비교한다.

## 1. Docker와 컨테이너의 기본 원리

### 1.1 왜 Docker를 사용하는가?

개발 환경에서 정상적으로 실행되던 AI 서버도 다른 컴퓨터에서는 실행에 실패할 수 있다. Python 버전이 다르거나, 필요한 라이브러리가 설치되지 않았거나, CUDA 환경이 맞지 않을 수 있기 때문이다.

Docker는 애플리케이션 코드와 실행에 필요한 사용자 공간의 환경을 이미지(Image)로 구성한다. 같은 이미지로 컨테이너를 실행하면 서버마다 Python과 라이브러리를 다시 설치하는 작업을 줄일 수 있다. 다만 호스트 운영체제의 커널, CPU 아키텍처, GPU 드라이버, 외부 데이터와 환경 설정은 별도로 맞춰야 한다.

### 1.2 Dockerfile, 이미지, 컨테이너

| 용어 | 의미 |
| --- | --- |
| Dockerfile | 어떤 운영 환경을 사용하고, 어떤 파일과 패키지를 설치하며, 어떤 명령으로 서버를 시작할지 작성한 파일 |
| Image(이미지) | Dockerfile을 빌드해 만든 실행 환경과 파일의 묶음 |
| Container(컨테이너) | 이미지를 기반으로 생성해 실행하는 독립된 프로세스 환경 |
| Host(호스트) | Docker와 컨테이너가 실행되는 실제 컴퓨터 또는 가상 서버 |
| Registry(레지스트리) | 이미지를 저장하고 배포하는 저장소 |

하나의 이미지에서 여러 컨테이너를 만들 수 있다. 같은 질의응답 서버 이미지로 서버 컨테이너 두 개를 실행하면 각각 독립된 프로세스로 동작한다. 기본적으로 컨테이너마다 쓰기 가능한 파일 시스템 영역이 따로 존재하지만, 연결한 볼륨은 공유할 수도 있다.

컨테이너는 호스트 운영체제의 커널을 공유한다. 가상 머신처럼 각각의 운영체제 커널을 실행하는 방식에 비해 실행 환경 구성과 시작이 가벼운 편이다. 커널을 공유하므로 컨테이너의 권한과 접근 범위를 제한하는 것도 중요하다.

### 1.3 Dockerfile은 어떻게 작성하는가?

다음은 Python API 서버를 위한 간단한 Dockerfile이다. `qa.serve`는 API 서버를 실행하는 Python 모듈이라고 가정한다.

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY qa/ ./qa/
CMD ["python", "-m", "qa.serve"]
```

| 명령어 | 역할 |
| --- | --- |
| `FROM` | 기본 실행 환경이 들어 있는 베이스 이미지를 지정한다. |
| `WORKDIR` | 이후 명령을 실행할 작업 경로를 정한다. |
| `COPY` | 개발 환경의 파일을 이미지 안으로 복사한다. |
| `RUN` | 이미지 빌드 과정에서 실행할 명령을 정한다. |
| `CMD` | 컨테이너가 시작될 때 기본으로 실행할 명령을 정한다. |
| `ENV` | 컨테이너에서 사용할 기본 환경 변수를 설정한다. |
| `USER` | 이후 명령과 서버 프로세스가 실행될 사용자를 지정한다. |

```bash
docker build -t qa-server:1.0 .
docker run --rm -p 8000:8000 qa-server:1.0
```

첫 번째 명령은 현재 폴더의 Dockerfile로 `qa-server:1.0` 이미지를 만든다. 두 번째 명령은 해당 이미지로 컨테이너를 실행하고 호스트의 8000번 포트를 컨테이너의 8000번 포트에 연결한다. API 서버는 외부 연결을 받을 수 있도록 컨테이너 안에서 `0.0.0.0:8000`에 바인딩해야 한다.

Docker 이미지는 배포할 실행 환경을 구성하고, 컨테이너는 그 환경에서 실제 서비스를 실행한다. 이후 학습하는 Kubernetes는 이러한 컨테이너를 여러 서버에서 관리한다.

## 2. Docker 이미지 최적화와 멀티스테이지 빌드

### 2.1 이미지가 크면 어떤 문제가 생기는가?

새로운 서버에 컨테이너를 실행하려면 먼저 이미지를 내려받아야 한다. 이미지가 크면 다운로드, 저장 및 압축 해제에 시간이 더 걸린다. 서버를 여러 대 추가하거나 새 버전을 배포할 때도 같은 문제가 발생할 수 있다. 기존 노드에 필요한 이미지 레이어가 캐시되어 있으면 전송량은 줄어든다.

특히 LLM 서버에는 PyTorch, CUDA 관련 라이브러리, vLLM 등 대용량 패키지가 포함된다. 모델 가중치까지 이미지에 넣으면 크기가 크게 증가한다. 이미지 크기는 배포 속도와 관련된 문제이며, 모델이 GPU 메모리에 올라간 뒤의 추론 속도나 VRAM 사용량은 별도로 측정해야 한다.

### 2.2 멀티스테이지 빌드(Multi-stage Build)

일부 라이브러리를 설치하려면 소스 코드를 컴파일하는 도구와 헤더 파일이 필요하다. 설치가 끝난 뒤 서버를 실행할 때는 이러한 도구가 필요하지 않을 수 있다. 멀티스테이지 빌드는 설치 및 컴파일 환경과 실제 서버 실행 환경을 분리한다.

```dockerfile
# 빌드 스테이지: 실행에 필요한 패키지 설치
FROM python:3.12-slim AS build
WORKDIR /build
RUN python -m venv /opt/venv
COPY requirements.txt .
RUN /opt/venv/bin/pip install --no-cache-dir -r requirements.txt

# 런타임 스테이지: 새로운 이미지에서 실행 환경 구성
FROM python:3.12-slim
WORKDIR /app
COPY --from=build /opt/venv /opt/venv
COPY qa/ ./qa/
ENV PATH="/opt/venv/bin:$PATH"
CMD ["python", "-m", "qa.serve"]
```

첫 번째 `FROM`부터 패키지 설치까지는 빌드 스테이지다. 두 번째 `FROM`은 새로운 베이스 이미지에서 시작한다. `COPY --from=build`는 앞 단계에서 만든 Python 가상환경만 복사한다. 별도의 컴파일러나 임시 빌드 파일이 있다면 필요한 실행 파일만 선별해 가져올 수 있다. 이때 두 환경의 Python과 시스템 라이브러리 호환성을 확인해야 한다.

Docker의 레이어 캐시는 변경되지 않은 빌드 결과를 다시 사용해 빌드 시간을 줄인다. 멀티스테이지 빌드는 최종 이미지에 어떤 파일을 포함할지 제어한다. 목적이 서로 다르다.

FastAPI나 uvicorn처럼 미리 컴파일된 Wheel 패키지를 설치하면 처음부터 별도의 컴파일러가 필요하지 않을 수 있다. 강의 자료의 예시에서도 싱글스테이지와 멀티스테이지 이미지가 모두 274MB였다. 최적화 효과는 실제 빌드 결과로 확인한다.

### 2.3 GPU 이미지와 CUDA 개발 환경

강의 자료에서는 NVIDIA CUDA 이미지를 세 가지 유형으로 구분한다.

| 유형 | 주요 구성 | 사용 목적 |
| --- | --- | --- |
| `base` | 최소 CUDA 실행 라이브러리 | 최소 GPU 실행 환경 구성 |
| `runtime` | base와 추가 수학·GPU 통신 라이브러리 | 필요한 CUDA 라이브러리를 갖춘 실행 환경 |
| `devel` | runtime과 컴파일러·헤더 | CUDA 프로그램의 빌드 및 필요한 런타임 컴파일 |

교안에 제시된 특정 이미지의 압축 크기는 각각 0.14GB, 1.65GB, 3.97GB다. 버전과 플랫폼에 따라 달라지는 수치다. vLLM처럼 실행 중 JIT(Just-in-Time) 컴파일을 사용하는 프로그램은 운영 환경에서도 일부 개발 도구가 필요할 수 있다.

교안에 제시된 vLLM 공식 이미지(v0.30.0, amd64)는 약 8.73GB이며, 그중 Python 패키지가 6.17GB, CUDA 개발 도구가 1.45GB를 차지한다. 베이스 이미지만 바꾸어서는 큰 폭으로 줄이기 어렵다는 것을 보여 준다. 공식 이미지가 요구사항을 만족한다면 검증한 버전과 다이제스트를 고정해 사용하는 방법도 효율적이다.

### 2.4 모델 가중치를 이미지에서 분리한다

모델 가중치를 이미지 안에 복사하면 모델을 바꿀 때마다 이미지를 다시 빌드하고 배포해야 한다. 모델 파일을 별도 저장 공간에 두고 컨테이너에서 그 경로에 연결하면 모델과 애플리케이션의 배포를 분리할 수 있다.

```bash
docker run --rm --gpus all \
  -v "$(pwd)/models:/app/models:ro" \
  qa-server:1.0
```

`-v`는 호스트의 `models` 폴더를 컨테이너 내부 `/app/models`에 연결한다. 이를 마운트(Mount)라고 한다. `:ro`는 읽기 전용 설정이다. Kubernetes에서는 PersistentVolume과 PersistentVolumeClaim을 사용해 외부 저장 공간을 연결할 수 있다.

이미지와 가중치를 분리하면 이미지 버전만 기록해서는 실제로 실행한 모델을 확인하기 어렵다. 모델의 커밋 해시나 파일 체크섬, 설정과 토크나이저 버전 등 재현에 필요한 정보도 함께 관리한다.

## 3. 컨테이너 실행 권한과 시크릿 관리

### 3.1 root와 Non-root 실행

root는 리눅스의 관리자 계정으로 일반 사용자보다 많은 권한을 갖는다. 컨테이너 내부에서 root 권한으로 서버를 실행하면 애플리케이션의 오류나 침해가 발생했을 때 컨테이너의 파일과 시스템 자원에 미치는 영향이 커질 수 있다. 컨테이너 내부 root가 곧바로 호스트 전체를 제어하는 것은 아니지만, 과도한 특권이나 위험한 마운트가 결합되면 피해 범위가 확대될 수 있다.

최소 권한(Least Privilege)은 서비스를 실행하는 데 필요한 권한만 부여하는 원칙이다. 일반 사용자로 서버를 실행하고, 모델은 읽기 전용으로 연결하며, 필요한 로그·캐시·임시 파일 경로에만 쓰기를 허용한다.

```dockerfile
RUN groupadd --system --gid 10001 app \
    && useradd --system --uid 10001 --gid 10001 --no-create-home app
RUN mkdir -p /app/logs /app/cache \
    && chown -R 10001:10001 /app/logs /app/cache
ENV HF_HOME=/app/cache
USER 10001:10001
```

UID(User ID)는 리눅스가 사용자를 구별하는 숫자이고, GID(Group ID)는 그룹을 구별하는 숫자다. `USER 10001:10001`을 지정하면 이후 명령과 기본 서버 프로세스가 해당 사용자·그룹 권한으로 실행된다.

### 3.2 일반 사용자로 변경한 뒤 서버가 실행되지 않는 이유

서버가 시작하면서 `/app/logs`를 만들거나 로그 파일을 저장한다고 가정하자. root는 해당 경로에 쓰기가 가능했지만 UID 10001 사용자는 권한이 없을 수 있다. 일반 사용자로 변경한 뒤 `PermissionError`가 발생하면 실행 계정과 파일 소유권을 확인해야 한다.

| 오류 | 확인할 내용 |
| --- | --- |
| `PermissionError` | 실행 사용자가 파일·디렉터리를 읽거나 쓸 권한이 있는지 확인한다. |
| `Read-only file system` | 읽기 전용 파일 시스템에 쓰려고 하는지 확인한다. |
| 캐시 저장 실패 | Hugging Face 캐시 등 쓰기 경로를 확인하고 필요하면 `HF_HOME`으로 변경한다. |
| 포트 바인딩 실패 | 낮은 번호의 포트에 필요한 권한과 런타임 설정을 확인한다. 일반적으로 8000번 같은 비특권 포트를 사용한다. |

읽기 전용 파일 시스템에서는 `chown`으로 권한을 바꾸더라도 쓰기가 불가능하다. 로그나 캐시가 필요한 경로에 별도의 쓰기 가능한 볼륨을 연결하거나 표준 출력으로 로그를 기록한다. 호스트 폴더를 마운트하면 이미지 안에서 설정한 폴더의 소유권 대신 마운트된 폴더의 권한이 적용되므로 해당 폴더도 확인한다.

### 3.3 API 키는 Secret으로 관리한다

API 키, 데이터베이스 비밀번호, 인증 토큰 같은 민감한 값을 Dockerfile이나 코드에 직접 작성하면 이미지를 공유하는 과정에서 유출될 수 있다. 이미지는 여러 레이어로 구성되므로 앞 레이어에 복사한 키 파일을 나중에 `RUN rm`으로 삭제해도 이전 레이어에 남아 있을 수 있다.

| 방법 | 역할 |
| --- | --- |
| `.dockerignore` | 키 파일을 빌드 컨텍스트에서 제외한다. |
| 런타임 환경 변수 | 컨테이너를 실행할 때 값을 전달한다. |
| Docker BuildKit secret mount | 빌드에 필요한 비밀값을 일반 레이어에 저장하지 않고 전달한다. |
| Kubernetes Secret | 민감한 값을 환경 변수나 파일로 파드에 전달한다. |

Kubernetes Secret의 `data` 필드는 Base64로 표현된다. Base64는 누구나 복원할 수 있는 인코딩 방식이다. 저장소(etcd) 암호화, RBAC(역할 기반 접근 제어), 키 교체 등 추가적인 보안 설정이 필요하다. 값이 들어 있는 Secret YAML을 Git에 올리지 않고, 실제 값을 조회할 수 있는 권한을 필요한 서비스에만 부여한다.

```bash
kubectl create secret generic qa-key --from-file=api-key=./api-key.txt
```

이 명령은 로컬 키 파일에서 `qa-key`라는 Secret을 생성한다. 파드에서는 해당 Secret을 파일로 마운트해 읽을 수 있다. 파일 기반 전달은 환경 변수 덤프에 비밀값이 노출되는 위험을 줄일 수 있지만, 파일 접근 권한과 애플리케이션 로그 관리도 필요하다.

이미지를 반입하기 전에는 완성된 이미지 레이어와 빌드 기록을 검사한다. 스캐너는 민감 정보가 아닌 문자열을 잘못 탐지할 수도 있고 실제 키를 놓칠 수도 있으므로 탐지 결과를 검토한다.

### 3.4 Kubernetes의 추가 보안 설정

| 설정 | 역할 |
| --- | --- |
| `runAsNonRoot: true` | root 사용자로 실행되는 것을 제한한다. |
| `allowPrivilegeEscalation: false` | 실행 중 추가 권한을 얻는 것을 제한한다. |
| `capabilities.drop: ["ALL"]` | 리눅스의 세분화된 커널 특권을 제거한다. |
| `seccompProfile.type: RuntimeDefault` | 런타임의 기본 시스템 호출 필터를 적용한다. |
| `readOnlyRootFilesystem: true` | 컨테이너 루트 파일 시스템을 읽기 전용으로 설정한다. |

앞의 네 가지는 Kubernetes의 Restricted 보안 기준과 관련된 주요 설정이다. 읽기 전용 루트 파일 시스템은 추가적인 보안 강화 설정이며, 서버에 필요한 쓰기 경로를 먼저 확인한 뒤 적용한다.

## 4. 레지스트리, 다이제스트, 전자서명과 SBOM

### 4.1 레지스트리(Registry)는 이미지를 배포하는 저장소다

Kubernetes에서 새로운 파드를 실행하면 파드가 배치된 노드는 지정된 이미지를 레지스트리에서 내려받는다. 여러 노드에 동일한 이미지를 배포하거나 장애로 새로운 노드에 파드를 생성할 때도 같은 저장소를 사용한다.

외부망 접근이 제한된 기업에서는 사내 레지스트리에 검증한 이미지만 등록하고 내부 노드가 해당 레지스트리에서 이미지를 받아 실행하도록 구성할 수 있다.

```text
외부 빌드 환경 → 이미지·검사 결과·서명 생성
                       ↓
               사내 반입 및 검증
                       ↓
                 사내 레지스트리
                       ↓
                  Kubernetes 노드
```

### 4.2 태그(Tag)와 다이제스트(Digest)

`qa-server:1.0`에서 `1.0`은 이미지 태그다. 사람이 버전을 구별하기 쉽지만 레지스트리에서 태그가 다른 이미지를 가리키도록 변경할 수 있다. `latest`처럼 버전을 구체적으로 표시하지 않은 태그는 어떤 이미지인지 추적하기가 특히 어렵다.

다이제스트는 이미지 매니페스트 등의 내용을 해시 함수로 계산한 식별값이다. 이미지의 구성 내용이 변경되면 정상적으로 생성되는 이미지 다이제스트도 달라진다.

```text
qa-server:1.0                     # 태그로 지정
qa-server@sha256:<실제 다이제스트>  # 내용에 기반한 식별자로 지정
```

베이스 이미지와 실제 배포 이미지의 다이제스트를 고정하면 평가한 이미지와 같은 내용을 사용하는 데 도움이 된다. 멀티아키텍처 이미지의 경우 이미지 인덱스 및 플랫폼별 매니페스트의 다이제스트를 구분할 필요가 있다. `docker save`로 내보낸 TAR 파일의 SHA-256 체크섬은 이미지 레지스트리의 다이제스트와 별개이며 반입 파일 자체의 무결성을 확인하는 데 사용한다.

### 4.3 해시와 전자서명(Signature)의 차이

해시는 검사할 파일이 기준 파일과 같은지 확인하는 데 사용한다. 전자서명은 신뢰하는 키로 서명한 정보인지, 서명 이후 정보가 변경되었는지 검증하는 데 사용한다.

외부 빌드 환경에서 이미지 파일의 해시와 검사 결과를 반입 명세서에 기록하고 개인 키로 서명한다. 내부망에서는 미리 신뢰하도록 등록한 공개 키로 서명을 확인하고 파일의 해시를 다시 계산해 비교한다.

| 반입 상황 | 명세서의 해시만 비교 | 명세서 서명도 검증 |
| --- | --- | --- |
| 정상 이미지와 명세서 | 통과 | 통과 |
| 이미지 파일만 변경 | 실패 | 실패 |
| 이미지와 명세서의 해시를 함께 변경 | 통과할 수 있음 | 올바른 개인 키가 없으면 실패 |

전자서명이 유효하더라도 이미지 내부에 취약점이나 잘못된 코드가 있을 수 있다. 서명 검증과 내용 검사는 각각 수행한다. 이미지 서명 도구로는 Sigstore 프로젝트의 `cosign`이 있다. 투명성 로그(Rekor)를 사용하는 방식과 폐쇄망 검증 방식은 키·검증 정책에 맞게 구성해야 한다.

### 4.4 SBOM(Software Bill of Materials)

SBOM은 이미지 안에 실제로 포함된 소프트웨어의 이름과 버전을 정리한 목록이다. `requirements.txt`에는 개발자가 직접 설치하려는 Python 패키지를 작성하는 경우가 많다. 실제 설치 과정에서는 해당 패키지가 필요로 하는 추가 라이브러리와 운영체제 패키지도 포함된다.

보안 취약점이 공개되었을 때 SBOM을 확인하면 어떤 이미지에 해당 패키지와 버전이 들어 있는지 빠르게 조사할 수 있다. 취약점이 실제로 악용 가능한지 확인하는 작업은 별도로 필요하다.

강의 자료의 반입 명세서에는 이미지 파일의 SHA-256, 이미지 ID와 크기, 시크릿 검사 결과, 베이스 이미지 다이제스트, SBOM의 해시와 구성 요소 수, 모델 커밋 해시를 기록한다. 여기에 명세서 전체의 전자서명을 추가한다.

이 과정의 목적은 **검사한 애플리케이션과 모델을 실제 운영 환경에 그대로 배포하고, 문제가 발생했을 때 정확한 버전과 구성 요소를 추적하는 것**이다.

## 5. Docker Compose와 헬스체크

### 5.1 여러 컨테이너를 함께 실행한다

AI 서비스는 추론 서버, API 게이트웨이, 벡터 데이터베이스, 캐시 등 여러 프로그램으로 구성될 수 있다. Docker Compose는 이러한 서비스들의 이미지, 포트, 환경 변수, 볼륨, 실행 관계를 하나의 YAML 설정 파일에 작성하고 함께 실행하는 도구다.

예를 들어 QA 서버가 실행된 뒤 테스트 서버가 질문을 보내는 구성을 만들 수 있다. 그러나 QA 서버의 컨테이너가 시작된 순간에는 모델이 아직 준비되지 않았을 수 있다.

### 5.2 시작과 준비 완료는 다르다

`depends_on`의 짧은 형식은 의존 서비스가 먼저 시작되도록 설정한다. 모델 로딩이 끝날 때까지 대기하려면 헬스체크(Health Check)를 추가하고 `condition: service_healthy`를 지정한다.

```yaml
services:
  qa:
    image: qa-server:1.0
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/ready', timeout=2).close()"]
      start_period: 20s
      start_interval: 1s
      interval: 10s
      timeout: 3s
      retries: 3

  smoke:
    image: qa-smoke:1.0
    depends_on:
      qa:
        condition: service_healthy
```

`/ready`는 모델 로딩 중에는 HTTP 503을 반환하고 요청 처리 준비가 끝나면 HTTP 200을 반환한다고 가정한다. 위 Python 명령은 정상 응답 시 성공하고 503 등 오류 응답에서는 예외가 발생해 실패한다. 헬스체크 명령의 종료 코드가 0이면 Docker는 성공으로 판단한다. `start_interval`은 이를 지원하는 최신 Compose 및 Docker Engine 환경에서 사용한다.

`smoke`는 기본 동작을 확인하는 테스트 서비스다. `qa`가 healthy 상태로 판정된 뒤에 기동한다. 교안의 모의 서버는 모델을 불러오는 데 8초가 걸리며, 짧은 `depends_on`만 사용한 경우 점검 서비스가 준비 전에 요청해 503을 받았다.

### 5.3 헬스체크 설정값

| 설정 | 의미 |
| --- | --- |
| `start_period` | 초기화 중 실패를 일정 기간 허용한다. 이 기간에도 검사는 실행될 수 있다. |
| `start_interval` | 초기 기동 기간의 검사 간격 |
| `interval` | 일반 운영 중 검사 간격 |
| `timeout` | 한 번의 검사가 완료되기를 기다리는 시간 |
| `retries` | unhealthy로 판정하기까지 허용하는 연속 실패 횟수 |

검사 간격이 너무 길면 모델이 준비되었더라도 healthy 판정이 늦어진다. 반대로 너무 짧거나 검사 자체가 무거우면 불필요한 부하가 발생한다. 초기에는 짧은 간격으로 준비 상태를 검사하고 운영 중에는 적절한 간격을 적용한다.

### 5.4 헬스체크를 설정할 때 주의할 점

헬스체크 명령은 호스트 컴퓨터가 아니라 컨테이너 내부에서 실행한다. 호스트에서 `curl`이 정상 실행되더라도 `python:3.12-slim`처럼 경량 이미지에는 `curl`이 설치되어 있지 않을 수 있다. 이미지에 이미 설치된 Python을 사용하거나 필요한 도구를 의도적으로 설치한다.

또한 헬스체크로 실제 LLM 답변을 생성하면 사용자 요청과 GPU 연산 자원을 경쟁한다. 모델이 로드되었는지, 요청을 받을 수 있는지 등을 가볍게 검사하는 전용 경로를 사용한다.

Compose의 `depends_on`은 초기 기동 순서를 관리한다. 이후 의존 서비스가 unhealthy가 되더라도 Docker는 그 이유만으로 자동 재시작하지 않는다. 일반적인 재시작 정책은 프로세스 종료 등을 기준으로 동작한다. 서비스를 호출하는 프로그램도 일시적인 실패를 처리하고 적절한 간격으로 재시도할 수 있어야 한다.

## 6. Kubernetes의 기본 구조

### 6.1 Docker Compose와 Kubernetes의 차이

Docker Compose는 한 호스트에서 여러 컨테이너를 함께 실행하고 관리하기에 적합하다. 서비스 규모가 커져 여러 대의 서버를 사용하면 컨테이너를 어느 서버에 배치할지, 서버가 고장 나면 어디에서 다시 실행할지, 어떻게 새 버전으로 교체할지를 관리해야 한다.

Kubernetes(K8s)는 이러한 작업을 여러 서버에 걸쳐 관리하는 컨테이너 오케스트레이션 도구다. 오케스트레이션(Orchestration)은 여러 실행 단위의 배치, 상태, 복구 및 연결을 조정하는 작업이다.

### 6.2 Cluster, Node, Pod

| 용어 | 의미 |
| --- | --- |
| Cluster(클러스터) | Kubernetes가 하나의 환경으로 관리하는 서버들의 집합 |
| Node(노드) | 파드를 실행하는 물리 서버 또는 가상 머신 |
| Pod(파드) | Kubernetes가 배치하고 실행하는 가장 작은 단위. 하나 이상의 컨테이너를 포함할 수 있다. |
| Deployment | 파드의 복제본 수와 템플릿을 관리하고 버전을 교체하는 객체 |
| Service | 파드 집합에 연결할 안정적인 이름과 네트워크 접근 지점을 제공하는 객체 |
| Namespace | 클러스터 내의 리소스를 논리적으로 구분하는 범위 |

하나의 노드에는 여러 파드가 실행될 수 있다. 일반적으로 하나의 API 서버 컨테이너를 하나의 파드로 구성한다. 같은 파드에 포함된 컨테이너는 네트워크 주소를 공유하고 필요한 볼륨을 함께 사용할 수 있다.

```text
Kubernetes Cluster
├── Node A
│   ├── Pod 1 : QA 서버
│   └── Pod 2 : Gateway 서버
└── Node B
    └── Pod 3 : QA 서버
```

Kubernetes는 파드의 실행 위치를 결정하고 노드의 상태를 관리한다. 노드가 장애로 사용할 수 없게 되면 관리 정책과 가용 자원에 따라 다른 노드에서 대체 파드가 실행될 수 있다.

### 6.3 Deployment와 선언적 상태 관리

매니페스트(Manifest)는 Kubernetes에서 어떤 리소스를 어떤 상태로 유지할지 작성한 설정 파일이다. 서버를 두 개 유지하라는 설정을 적용하면 Kubernetes는 실제 상태와 설정된 목표 상태를 비교하고, 목표 상태에 맞추는 작업을 반복한다. 이를 선언적(Declarative) 상태 관리라고 한다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: qa
spec:
  replicas: 2
  selector:
    matchLabels:
      app: qa
  template:
    metadata:
      labels:
        app: qa
    spec:
      containers:
        - name: qa
          image: registry.internal/ai/qa-server:1.5.0
          ports:
            - containerPort: 8000
```

`replicas: 2`는 동일한 서버 파드 두 개를 유지하도록 지정한다. `template`에는 실행할 이미지와 컨테이너 설정을 작성한다. `labels`는 파드에 부여하는 식별 정보다. `selector`는 Deployment가 관리할 파드를 찾는 조건이며 템플릿의 레이블과 일치해야 한다. 내부적으로 Deployment가 ReplicaSet을 관리하고 ReplicaSet이 지정된 개수의 파드를 유지한다.

```bash
kubectl apply -f deployment.yaml
kubectl get deployments
kubectl get pods -o wide
```

설정 적용과 실제 실행 상태는 따로 확인한다. 위 명령으로 Deployment와 파드의 개수, 상태, 배치된 노드 등을 조회할 수 있다.

### 6.4 Service가 필요한 이유

파드는 종료되거나 다시 생성될 때 IP 주소가 바뀔 수 있다. API 게이트웨이가 파드 IP를 직접 관리하면 파드가 교체될 때마다 연결 주소를 수정해야 한다.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: qa
spec:
  selector:
    app: qa
  ports:
    - port: 8000
      targetPort: 8000
```

Service는 `app: qa` 레이블이 붙은 파드에 연결한다. 기본 ClusterIP Service는 클러스터 내부의 안정적인 가상 IP를 제공하며, 일반적으로 클러스터 DNS를 통해 `qa`라는 이름을 조회할 수 있다. 같은 네임스페이스의 게이트웨이는 `http://qa:8000`으로 접근한다.

```text
API Gateway → Service(qa:8000) ┬→ QA Pod A (Ready)
                              ├→ QA Pod B (Ready)
                              └× QA Pod C (모델 로딩 중)
```

정상적인 Service 구성에서는 readiness 상태가 실패한 파드에 새 요청을 보내지 않는다. Service는 연결 수준의 분산을 제공하며, API 키 인증, 요청 제한, 모델별 라우팅, 버전별 정교한 트래픽 비율 조절은 게이트웨이 등의 역할이다.

## 7. CPU·메모리·GPU 할당과 환경 설정

### 7.1 requests와 limits

Kubernetes는 여러 파드를 한 노드에 배치하므로 각 파드에 필요한 자원을 알아야 한다. `requests`는 파드를 배치할 때 고려하는 자원 요구량이고, `limits`는 컨테이너가 사용할 수 있는 자원의 상한이다.

```yaml
resources:
  requests:
    cpu: "500m"
    memory: "1Gi"
  limits:
    memory: "2Gi"
```

`500m`은 CPU 코어 0.5개에 해당하는 요구량이며 `1Gi`는 1GiB의 메모리다. 스케줄러는 노드에 요청량을 수용할 여유가 있는지 확인한다. CPU 상한을 지정하지 않은 경우에는 다른 작업의 사용량과 노드의 상황에 따라 요청량보다 더 많은 CPU를 사용할 수 있다.

| 자원 | requests | limits 초과 또는 자원 부족 시 |
| --- | --- | --- |
| CPU | 파드 배치 기준 및 CPU 경쟁 시 할당 기준 | CPU 상한을 넘으려 하면 실행 시간이 제한되어 느려질 수 있다. |
| 메모리 | 파드 배치에 필요한 메모리 요구량 | 메모리 상한을 넘으면 컨테이너가 OOMKilled로 종료될 수 있다. 노드의 메모리 부족 시 파드가 축출될 수도 있다. |
| GPU | 확장 자원으로 할당할 GPU 개수 | 가용 GPU가 부족하면 새 파드는 배치되지 못하고 Pending 상태로 대기할 수 있다. |

메모리 상한을 지나치게 낮게 지정하면 서버가 반복 종료될 수 있고, CPU 상한이 낮으면 응답 지연이 증가할 수 있다. 강의 자료에서는 CPU 요청량과 메모리 상한을 설정하고 CPU 상한은 생략하는 예시를 사용한다. 실제 설정은 인프라 정책과 부하 측정 결과에 맞춘다.

### 7.2 컨테이너에서 GPU를 사용하는 방법

GPU를 사용하려면 호스트의 NVIDIA 드라이버, 컨테이너에서 GPU를 사용할 수 있도록 연결하는 런타임 환경, 모델에 필요한 CUDA 라이브러리가 서로 호환되어야 한다.

| 구성 요소 | 설치 또는 설정 위치 | 역할 |
| --- | --- | --- |
| NVIDIA 드라이버 | GPU가 장착된 호스트 | 운영체제와 GPU를 연결한다. |
| NVIDIA Container Toolkit | 호스트 | 컨테이너에 GPU 장치와 드라이버 관련 파일을 제공할 수 있도록 한다. |
| CUDA 라이브러리 | 컨테이너 이미지 | PyTorch, vLLM 등의 프로그램이 GPU 연산을 수행하도록 지원한다. |
| NVIDIA Device Plugin | Kubernetes의 GPU 노드 | 사용 가능한 GPU 자원을 Kubernetes에 등록하고 할당을 지원한다. |

Docker에서는 `--gpus all` 등의 옵션으로 컨테이너에 GPU를 노출한다. Compose에서는 GPU 예약 설정 등을 사용할 수 있다. Kubernetes에서는 일반적으로 NVIDIA Device Plugin이 등록한 자원을 매니페스트에서 요청한다.

```yaml
resources:
  limits:
    nvidia.com/gpu: 1
```

기본적인 전체 GPU 할당 방식에서 위 설정은 GPU 한 장을 할당받는다는 의미다. `requests`를 따로 지정하는 경우 GPU는 `limits`와 같은 값을 사용한다. GPU 분할, 시간 공유, MIG 등 별도 구성에서는 자원 이름과 할당 의미가 달라질 수 있다.

GPU를 한 장 할당받았다는 정보만으로 VRAM 사용량이 자동 최적화되지는 않는다. 모델 가중치, 양자화 방식, KV Cache, 최대 입력 길이와 동시 요청 수 등을 모델 서버에서 별도로 관리한다. Kubernetes의 일반적인 `memory` 설정은 시스템 RAM을 대상으로 한다.

### 7.3 설정값, 비밀값, 모델 파일을 분리한다

컨테이너에 필요한 정보를 모두 이미지에 넣으면 설정 하나를 바꿀 때도 이미지를 다시 빌드해야 한다. 변경되는 데이터를 종류에 따라 분리하면 동일한 이미지에 서로 다른 환경 설정을 적용하기 쉽다.

| 저장 위치 | 관리할 내용 |
| --- | --- |
| 이미지 | 서버 코드, Python 및 라이브러리 |
| ConfigMap | 비밀이 아닌 설정값. 모델 경로, 준비 시간, 요청 제한 값 등 |
| Secret | API 키, 비밀번호 등 민감한 값 |
| PersistentVolume / PVC | 모델 가중치 등 외부에 지속적으로 보관할 파일 |
| emptyDir | 파드가 실행되는 동안 사용할 임시 파일·캐시 |

ConfigMap과 Secret은 객체당 1MiB 크기 제한이 있어 대용량 모델 파일 저장에 적합하지 않다. PersistentVolume은 저장 자원을 표현하며 PVC(PersistentVolumeClaim)는 파드가 사용할 저장 공간을 요청하는 객체다. `emptyDir`은 컨테이너가 재시작되어도 같은 파드 안에서 유지될 수 있지만 파드가 제거되면 사라진다.

## 8. Kubernetes의 프로브(Probe)

### 8.1 서버가 실행 중이어도 요청 처리가 불가능할 수 있다

LLM 서버는 실행 명령을 받은 뒤 모델 가중치를 읽고 GPU 메모리에 적재하며 추론 엔진을 초기화한다. 이 과정에서 HTTP 서버가 먼저 실행되면 간단한 상태 확인 요청에는 정상 응답하면서 실제 사용자 질문은 처리하지 못할 수 있다.

Kubernetes 노드에서 컨테이너의 실행을 관리하는 kubelet은 프로브를 사용해 상태를 검사한다. Kubernetes는 검사 결과에 따라 컨테이너를 재시작할지, 파드를 요청 전달 대상에서 제외할지 결정한다.

### 8.2 세 가지 프로브의 차이

| 프로브 | 검사 목적 | 반복 실패했을 때 |
| --- | --- | --- |
| Startup | 서버의 초기화가 끝났는가? | 컨테이너를 종료하고 정책에 따라 재시작한다. |
| Readiness | 지금 사용자 요청을 처리할 준비가 되었는가? | 파드를 Ready 상태에서 제외하고 일반적인 Service의 새 요청 전달 대상에서 뺀다. |
| Liveness | 서버가 재시작해야 할 정도로 비정상적인 상태인가? | 컨테이너를 종료하고 정책에 따라 재시작한다. |

Startup 프로브를 설정한 경우 이 검사가 성공할 때까지 Readiness와 Liveness 검사는 실행되지 않는다. Startup은 최초 성공 이후 종료되고, 나머지 두 프로브는 운영 중 지속적으로 실행된다.

Readiness는 일시적인 준비 상태의 변화에 대응한다. 모델 로딩이나 일시적으로 요청 처리가 불가능한 상황에서 서버를 종료하지 않고 새로운 요청만 받지 않도록 한다. Liveness는 교착 상태처럼 재시작이 필요한 문제를 검사하도록 설계한다. 외부 데이터베이스나 다른 추론 서버의 일시적인 장애까지 Liveness 실패로 판단하면 정상적인 서버들도 재시작되는 연쇄 장애가 발생할 수 있다.

### 8.3 `/health`와 `/ready`는 무엇을 반환해야 하는가?

경로 이름 자체에는 특별한 기능이 없다. 애플리케이션이 각각 어떤 상태를 검사하고 어떤 상태 코드를 반환하도록 구현했는지가 중요하다. 교안의 상황을 바탕으로 다음처럼 설계할 수 있다.

| 서버 상태 | `/health` (생존 확인) | `/ready` (요청 준비 확인) |
| --- | --- | --- |
| 모델 로딩 중, HTTP 서버는 정상 | 200 | 503 |
| 모델 로딩 완료 | 200 | 200 |
| 일시적으로 요청을 받을 수 없음 | 200 | 503 |
| 서버가 응답하지 않음 | 연결 실패 또는 타임아웃 | 연결 실패 또는 타임아웃 |

Kubernetes의 HTTP 프로브는 200 이상 400 미만의 HTTP 상태 코드를 성공으로 판단한다. 응답 본문에 `{"status": "loading"}`이라고 표시하면서 HTTP 200을 반환하면 HTTP 프로브는 성공으로 판단한다. 따라서 모델을 로딩하는 중에는 readiness 경로가 503 같은 실패 상태 코드를 반환하도록 설계한다.

강의 실습은 동일한 모의 서버에서 readiness 경로를 `/health`와 `/ready`로 변경하여 준비 전 503 응답 건수와 Ready 판정 시점을 비교한다. 적절한 readiness 경로를 사용하면 모델이 준비되기 전의 파드에 요청이 들어가는 문제를 줄일 수 있다. 실제 수치는 실습 환경에서 측정해야 한다.

### 8.4 프로브 매니페스트 설정 예시

```yaml
startupProbe:
  httpGet:
    path: /ready
    port: 8000
  periodSeconds: 5
  failureThreshold: 60
  timeoutSeconds: 2
readinessProbe:
  httpGet:
    path: /ready
    port: 8000
  periodSeconds: 2
  failureThreshold: 2
  timeoutSeconds: 1
livenessProbe:
  httpGet:
    path: /health
    port: 8000
  periodSeconds: 10
  failureThreshold: 3
  timeoutSeconds: 2
```

이 예시는 `/ready`가 초기화 완료를 나타내는 단순한 서버를 가정한다. 초기화 완료와 운영 중 준비 상태의 조건이 다르다면 별도 `/startup` 경로를 만들 수 있다.

| 설정값 | 의미 |
| --- | --- |
| `initialDelaySeconds` | 컨테이너가 시작되고 프로브를 시작하기까지의 초기 지연 시간 |
| `periodSeconds` | 검사 간격 |
| `failureThreshold` | 실패로 처리하기 위한 연속 실패 횟수 |
| `timeoutSeconds` | 각 검사의 응답 제한 시간 |
| `successThreshold` | 실패 상태에서 다시 성공으로 판단하는 데 필요한 연속 성공 횟수. Startup·Liveness는 1이어야 한다. |

위 Startup 설정은 5초 간격으로 최대 60회 연속 실패를 허용한다. 대략 300초 규모의 초기화 허용 구간을 구성한 것이다. 검사 시작 시점과 타임아웃 등에 따라 실제 종료 시점은 달라질 수 있다.

교안에서 인용한 다른 실습에서는 T4에서 0.5B 모델을 처음 다운로드하고 준비하는 데 147초가 걸렸다. 90초 정도만 허용하는 설정이라면 모델이 준비되기 전에 컨테이너를 종료할 수 있다. 배포하는 모델의 실제 초기화 시간을 여러 번 측정하고 여유를 포함해 설정한다.

초기화 도중 계속 종료되면 재시작 사이의 대기 시간이 길어지는 `CrashLoopBackOff` 상태가 나타날 수 있다. 이때는 `kubectl describe pod`의 이벤트와 `kubectl logs --previous`의 이전 컨테이너 로그를 확인한다. 프로브 실패 외에도 코드 오류, 메모리 부족, 파일 권한 문제가 원인일 수 있다.

## 9. 롤링 업데이트, 무중단 배포와 롤백

### 9.1 서비스를 중단하지 않고 버전을 바꾸는 방법

운영 중인 AI 서버 두 대의 버전을 동시에 교체하면 두 서버 모두 모델을 다시 불러오는 동안 사용자 요청을 처리하지 못할 수 있다. 롤링 업데이트(Rolling Update)는 기존 복제본을 유지하면서 새 버전의 파드를 순차적으로 추가하고, 준비가 확인된 뒤 기존 파드를 제거하는 배포 방식이다.

예를 들어 서버 두 대를 유지하는 상태에서 새 파드를 한 개 추가할 수 있다면 다음과 같이 교체할 수 있다.

```text
교체 전        v1 Ready   v1 Ready
새 파드 추가   v1 Ready   v1 Ready   v2 Loading
준비 완료      v1 Ready   v1 Ready   v2 Ready
기존 파드 제거 v1 Ready   v2 Ready
다음 파드 교체 v1 Ready   v2 Ready   v2 Loading
교체 완료      v2 Ready   v2 Ready
```

새 파드가 준비되기 전에는 기존 파드가 요청을 처리한다. 실제 롤아웃은 컨트롤러의 조정과 설정에 따라 세부 순서가 달라질 수 있다. 이 방식의 전제는 readiness 검사가 실제 요청 준비 상태를 정확하게 반영하는 것이다.

### 9.2 maxSurge와 maxUnavailable

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

`maxSurge`는 업데이트 과정에서 목표 복제본 수보다 추가로 생성할 수 있는 파드 수다. `maxUnavailable`은 업데이트 과정에서 목표 복제본 수보다 사용 가능한 파드가 얼마나 줄어들어도 되는지 정한다.

| 설정 | 복제본 3개를 운영하는 경우 |
| --- | --- |
| `maxSurge: 1`, `maxUnavailable: 0` | 새 파드를 먼저 추가한다. 기존 용량을 유지하도록 교체하지만 여유 자원이 필요하다. |
| `maxSurge: 0`, `maxUnavailable: 1` | 기존 파드를 먼저 줄여 자원을 확보한다. 교체 중 사용 가능한 파드가 2개로 줄 수 있다. |

두 설정의 기본값은 각각 25%다. 파드 개수로 환산할 때 maxSurge는 올림하고 maxUnavailable은 내림한다. 복제본이 3개라면 각각 1개와 0개에 해당한다.

GPU 세 장에 파드 세 개를 실행하고 빈 GPU가 없으면 `maxSurge: 1`, `maxUnavailable: 0` 설정으로는 새 파드를 배치하기 어렵다. 새 파드는 Pending으로 대기하고 기존 파드는 사용 가능 개수를 유지하기 위해 종료되지 않아 업데이트가 진행되지 않을 수 있다. GPU를 추가 확보하거나 일시적인 처리 용량 감소를 허용하도록 설정을 변경해야 한다.

롤링 업데이트 도중에는 서로 다른 모델이나 API 버전이 함께 실행된다. 응답 형식이나 데이터 호환성이 달라지는 변경이라면 API 버전을 분리하고 게이트웨이 등에서 전환을 관리하는 방식이 필요할 수 있다.

### 9.3 Graceful Shutdown(안전한 종료)

LLM 서버는 하나의 답변을 생성하는 데 수 초 이상 걸릴 수 있다. 서버가 답변을 생성하는 중에 컨테이너가 강제로 종료되면 기존 사용자 요청이 중단된다.

Kubernetes는 정상적인 파드 종료 과정에서 종료 신호(SIGTERM)를 보내고 일정 시간 동안 종료를 기다린다. 기본 유예 시간은 30초이며 시간이 지나도 프로세스가 남아 있으면 강제 종료한다. 동시에 파드가 일반적인 Service의 신규 요청 대상에서 제외되도록 엔드포인트 상태가 변경된다. 이 변경은 즉시 모든 연결에 반영되는 것이 아니므로 애플리케이션과 게이트웨이의 종료 처리가 필요하다.

```yaml
terminationGracePeriodSeconds: 120
```

서버는 종료 신호를 받으면 새 요청을 제한하고 진행 중인 요청을 가능한 범위에서 마무리한 뒤 종료하도록 구현한다. 위 120초는 설명용 값이며 실제 응답 길이, 스트리밍 시간, 종료 처리 방식에 맞춰 정해야 한다.

Dockerfile의 `CMD`나 파드의 `command`에 exec 형식의 배열을 사용하면 서버 프로세스에 종료 신호가 전달되도록 구성하기 쉽다. 셸 스크립트를 사용하는 경우 `exec`로 서버 프로세스를 시작하거나 신호를 올바르게 전달하도록 구현한다.

### 9.4 배포 결과 확인과 롤백(Rollback)

새 이미지에서 장애가 발생하면 이전에 정상 동작했던 버전으로 되돌릴 수 있다. 이를 롤백이라고 한다.

```bash
kubectl set image deployment/qa qa=registry.internal/ai/qa-server:1.6.0
kubectl rollout status deployment/qa
kubectl rollout history deployment/qa
kubectl rollout undo deployment/qa
```

첫 번째 명령은 Deployment의 `qa` 컨테이너 이미지를 변경한다. 이후 배포 진행 상태와 버전 변경 이력을 확인하고 문제가 발생하면 이전 리비전으로 복구할 수 있다. 운영에서는 검증된 이미지 다이제스트를 함께 사용해 복구 대상을 정확히 지정한다.

Deployment 롤백은 이전 파드 템플릿으로 복구하는 기능이다. 외부 볼륨에 저장된 모델, 별도로 변경된 ConfigMap·Secret이나 데이터베이스까지 자동으로 되돌리지는 않는다. 모델과 설정의 버전을 별도로 관리해야 서비스 전체를 일관되게 복구할 수 있다.

배포 완료 상태는 설정된 파드 가용성 기준을 확인한 결과다. 실제 무중단 여부는 사용자 요청의 성공률, 503 발생 건수, 응답 지연, 진행 중인 스트리밍 요청의 종료 여부 등을 측정해 판단한다.
