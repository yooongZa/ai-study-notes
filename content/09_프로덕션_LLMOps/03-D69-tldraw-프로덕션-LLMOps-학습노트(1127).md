> 모델을 학습하고 설정을 최적화하는 단계부터, 서비스 배포 후 품질을 평가하고 오류와 데이터 변화를 추적하는 단계까지 연결해 정리한 학습 노트.

---

## 한눈에 보는 전체 흐름

프로덕션 LLMOps는 모델을 한 번 학습하고 배포하는 데서 끝나지 않는다. 학습 단계에서는 좋은 설정을 찾고, 배포 전에는 품질 기준을 검사하며, 운영 중에는 실제 요청을 관찰하고 실패 원인을 분석한다. 분석 결과는 다시 평가 데이터와 개선 작업에 반영한다.

1. **모델 최적화**: 하이퍼파라미터를 바꿔가며 성능이 좋은 설정을 찾는다.
2. **실험 기록**: 어떤 설정으로 학습했고 결과가 어땠는지 저장한다.
3. **품질 평가**: 대표 질문과 정답이 있는 평가셋으로 모델·프롬프트를 비교한다.
4. **배포 판정**: 사전에 정한 품질 기준을 통과했는지 확인한다.
5. **운영 관측**: 실제 요청의 실행 경로, 응답 시간, 오류, 토큰 사용량을 기록한다.
6. **오류·드리프트 분석**: 답변이 틀린 이유와 입력 데이터의 변화 여부를 찾는다.
7. **개선과 재검증**: 수정한 버전을 다시 평가하고 운영 결과를 확인한다.

~~~mermaid
flowchart TD
    A[모델·프롬프트 개발] --> B[하이퍼파라미터 최적화]
    B --> C[실험 기록과 결과 비교]
    C --> D[Offline Evaluation]
    D --> E{Quality Gate}
    E -->|PASS| F[배포]
    E -->|FAIL| G[오류 분석·수정]
    G --> D
    F --> H[운영 Trace·Metrics·Logs]
    H --> I[Online Evaluation·Drift 감지]
    I --> J[실패 사례와 새 데이터 수집]
    J --> G
~~~

## 1. 하이퍼파라미터와 모델 학습 설정

### 1.1 파라미터와 하이퍼파라미터

모델 학습에는 두 종류의 값이 사용된다.

- **파라미터(Parameter)**: 학습 데이터를 바탕으로 모델이 학습 과정에서 조정하는 값. 대표적으로 Weight(가중치)와 Bias(편향)가 있다.
- **하이퍼파라미터(Hyperparameter)**: 모델 구조나 학습 방법을 정하기 위해 개발자가 설정하는 값. 예를 들어 Learning Rate, Batch Size, Epoch 등이 있다.

| 구분 | 파라미터 | 하이퍼파라미터 |
|---|---|---|
| 누가 정하는가 | 학습 과정에서 모델이 조정 | 개발자 또는 최적화 도구 |
| 대표 값 | Weight, Bias | Learning Rate, Batch Size, Depth |
| 역할 | 입력을 처리하고 예측하는 데 사용 | 모델 구조와 학습 과정을 결정 |

### 1.2 자주 사용하는 하이퍼파라미터

| 항목 | 의미 | 설정이 미치는 영향 |
|---|---|---|
| Depth | 레이어 또는 Transformer Block의 개수 | 깊어질수록 복잡한 표현을 학습할 수 있지만 연산량·메모리 증가 |
| Width | 레이어 내부 차원. Transformer에서는 주로 Hidden Size | 넓어질수록 표현 용량과 파라미터 수가 증가 |
| Learning Rate | 가중치를 업데이트하는 크기 | 너무 작으면 학습이 느리고, 너무 크면 학습이 불안정해질 수 있음 |
| Batch Size | 한 번의 학습 단계에서 처리하는 데이터 수 | 메모리 사용량과 학습의 변동성에 영향 |
| Epoch | 전체 학습 데이터를 반복해서 학습하는 횟수 | 지나치게 많으면 과적합 가능 |
| Dropout Rate | 학습 중 일부 활성값을 무작위로 제외하는 비율 | 과적합을 줄이는 데 사용 |
| Weight Decay | 가중치가 지나치게 커지는 것을 억제하는 설정 | 모델의 일반화 성능에 영향 |
| Optimizer | 가중치를 업데이트하는 알고리즘 | 학습의 안정성과 수렴 양상에 영향 |

Depth와 Width는 모델의 구조를 정하는 설정이다. Learning Rate, Batch Size, Epoch 등은 주로 학습 과정을 조절한다. 사전학습 모델의 Depth나 Width를 바꾸면 기존 가중치와 호환되지 않을 수 있으므로, 일반적인 LoRA 파인튜닝처럼 기존 모델 구조를 유지하는 작업과 구분해야 한다.

### 1.3 탐색 공간(Search Space)

최적의 설정값을 미리 알기 어렵기 때문에 실험할 후보 값이나 범위를 정한다. 이 범위를 **탐색 공간(Search Space)**이라고 한다.

| 하이퍼파라미터 | 후보 값 예시 |
|---|---|
| Depth | 2, 4, 8 |
| Width | 64, 128, 256, 512 |
| Learning Rate | 0.01, 0.001, 0.0001 |

이산적인 후보 값을 모두 조합하면 3 × 4 × 3 = 36개 조합이 나온다. 각 조합으로 모델을 학습하고 평가해야 하므로 후보가 늘어날수록 실험 비용도 증가한다.

### 1.4 대표적인 탐색 방법

| 방법 | 작동 방식 | 특징 |
|---|---|---|
| Grid Search(격자 탐색) | 지정한 모든 후보 조합을 실험 | 범위 안의 모든 조합을 비교하지만 실험 수가 많음 |
| Random Search(무작위 탐색) | 탐색 공간에서 무작위로 조합을 선택 | 실험 횟수를 제한하기 쉬움 |
| Bayesian Optimization(베이지안 최적화) | 이전 실험 결과를 참고해 다음 후보를 선택 | 성능이 좋을 가능성이 높은 영역을 더 집중적으로 탐색 |

베이지안 최적화는 이전 결과를 활용해 다음 실험을 선택하므로 무작위 탐색보다 효율적일 수 있다. 다만 항상 전역 최적값을 찾는 것은 아니며 탐색 범위와 실험 횟수, 평가 기준에 영향을 받는다.

## 2. Optuna와 AutoGluon

두 도구 모두 모델 개발을 자동화하는 데 활용되지만 담당하는 범위가 다르다.

### 2.1 Optuna

**Optuna**는 하이퍼파라미터 탐색을 자동화하는 Python 라이브러리다. 개발자가 모델 생성 코드, 학습 코드, 탐색 범위, 평가 지표를 정의하면 Optuna가 설정값을 선택하고 실험을 반복한다.

| 구성 요소 | 의미 |
|---|---|
| Trial | 특정 하이퍼파라미터 조합으로 실행하는 실험 1회 |
| Study | 여러 Trial을 묶은 하나의 최적화 작업 |
| Sampler | 다음 Trial에서 사용할 하이퍼파라미터 값을 선택 |
| Pruner | 중간 평가 결과가 좋지 않은 Trial을 조기에 종료 |
| Objective Function | 모델을 학습·평가하고 최적화할 점수를 반환하는 함수 |

작동 흐름은 다음과 같다.

1. 개발자가 탐색할 하이퍼파라미터의 범위를 정의한다.
2. Optuna의 Sampler가 다음 실험에 사용할 값을 선택한다.
3. Objective Function이 해당 값으로 모델을 생성하고 학습한다.
4. 검증 데이터로 성능을 평가하고 점수를 반환한다.
5. Optuna가 결과를 저장하고 다음 Trial을 선택한다.
6. 정해진 실험 횟수만큼 반복한 뒤 가장 좋은 설정을 확인한다.

~~~python
import optuna

def objective(trial):
    depth = trial.suggest_int("depth", 2, 8)
    width = trial.suggest_categorical(
        "width", [64, 128, 256, 512]
    )
    lr = trial.suggest_float(
        "lr", 0.0001, 0.01, log=True
    )

    model = build_model(depth, width)
    score = train_and_evaluate(model, lr)
    return score

study = optuna.create_study(direction="maximize")
study.optimize(objective, n_trials=30)

print(study.best_params)
~~~

이 코드는 작동 구조를 설명하는 예시다. \`build_model()\`과 \`train_and_evaluate()\`는 개발자가 별도로 구현해야 한다. 검증 정확도처럼 높을수록 좋은 지표는 \`maximize\`, Loss처럼 낮을수록 좋은 지표는 \`minimize\`를 사용한다.

Pruner가 실험을 중단하려면 학습 도중 중간 점수를 Optuna에 보고하고, 종료 여부를 확인하는 코드도 구현해야 한다.

### 2.2 AutoGluon

**AutoGluon**은 AWS에서 개발한 AutoML 프레임워크다. 하이퍼파라미터 탐색만 담당하는 것이 아니라 데이터 전처리, 모델 선택, 학습, 평가, 앙상블 등 머신러닝 개발 과정의 상당 부분을 자동화한다.

정형 데이터 예측에서는 다음과 같은 흐름으로 활용할 수 있다.

1. 학습 데이터를 입력하고 예측할 대상 컬럼(Label)을 지정한다.
2. 데이터 전처리와 특징 처리 과정을 자동으로 수행한다.
3. 여러 후보 모델을 학습한다.
4. 검증 성능을 비교하고 좋은 모델을 선택한다.
5. 필요하면 여러 모델의 예측 결과를 결합하는 앙상블을 구성한다.

**앙상블(Ensemble)**은 여러 모델의 예측 결과를 결합하는 방법이다. 서로 다른 모델이 잘하는 부분을 결합해 성능을 높일 수 있지만, 학습 시간과 예측 비용이 증가할 수 있다.

### 2.3 Optuna와 AutoGluon 비교

| 구분 | Optuna | AutoGluon |
|---|---|---|
| 핵심 목적 | 하이퍼파라미터 최적화 | 머신러닝 개발 과정 자동화 |
| 모델 설계 | 개발자가 직접 정의 | 자동 모델 선택 또는 직접 지정 |
| 학습 코드 | 개발자가 작성 | 자동화된 학습 파이프라인 제공 |
| 데이터 전처리 | 개발자가 구성 | 자동화 지원 |
| 앙상블 | 직접 구성하거나 별도 구현 | 자동 앙상블 지원 |
| 적합한 상황 | 직접 만든 PyTorch 모델·RAG 설정 최적화 | 정형 데이터 등에서 여러 후보 모델을 빠르게 비교 |

직접 구현한 트랜스포머나 MLP의 학습률·레이어 수 등을 조정하려면 Optuna가 적합하다. 데이터를 넣고 여러 머신러닝 모델을 빠르게 학습·비교하려면 AutoGluon이 적합하다.

## 3. W&B와 실험 추적

하이퍼파라미터 최적화 도구가 좋은 설정을 찾는 역할이라면, 실험 추적 도구는 **각 실험의 조건과 결과를 저장하고 비교하는 역할**을 한다.

### 3.1 W&B(Weights & Biases)

W&B는 머신러닝 실험과 모델 개발을 관리하는 플랫폼이다. 학습 설정값, Loss, Accuracy, GPU 사용량, 모델 파일 등을 기록하고 웹 대시보드에서 비교할 수 있다.

| 기록 항목 | 예시 |
|---|---|
| 하이퍼파라미터 | Learning Rate, Batch Size, Epoch |
| 학습 지표 | Training Loss, Validation Loss, Accuracy |
| 시스템 자원 | GPU 사용률, GPU 메모리 |
| 실행 정보 | 코드 버전, 데이터셋, 실험 이름 |
| 산출물 | 모델 가중치, 체크포인트, 평가 결과 |

### 3.2 W&B의 주요 기능

- **Experiments / Runs**: 한 번의 학습 실행 조건과 결과를 기록한다.
- **Sweeps**: Grid, Random, Bayesian 방식으로 하이퍼파라미터 탐색을 자동화한다.
- **Artifacts**: 데이터셋, 모델 파일, 평가 결과 등 실험 산출물을 버전과 함께 관리한다.
- **Weave**: LLM 애플리케이션의 실행 Trace와 평가 결과를 기록한다.

W&B Sweeps는 Optuna와 비슷하게 하이퍼파라미터 탐색에 활용할 수 있다. Optuna가 후보 조합을 선택하고, W&B가 실험 지표를 기록하는 식으로 함께 사용할 수도 있다.

### 3.3 모델 개발 도구별 역할 비교

모델 개발에는 여러 후보를 학습하는 작업, 좋은 설정을 찾는 작업, 실험 결과를 기록·비교하는 작업이 필요하다. 다음 도구는 이 과정에서 담당하는 역할을 기준으로 비교할 수 있다.

| 도구 | 중심 역할 |
|---|---|
| TensorBoard | Loss(손실값)·Accuracy(정확도) 등 학습 과정 시각화 |
| MLflow | 실험 설정·결과·모델 파일 기록과 비교 |
| W&B | 실험 기록·시각화·협업, Sweeps를 통한 하이퍼파라미터 탐색 |
| Optuna | 성능이 좋은 하이퍼파라미터 조합 탐색 |
| AutoGluon | 데이터 전처리와 여러 모델의 학습·평가·선택·앙상블 자동화 |

AutoGluon도 `leaderboard()`로 학습한 모델의 성능과 학습·예측 시간을 비교한다. 중심 역할은 여러 모델을 자동으로 학습하고 좋은 모델이나 앙상블을 구성하는 **AutoML(자동 머신러닝)**이다.

Optuna는 **설정 탐색**, AutoGluon은 **학습 과정 자동화**, TensorBoard·MLflow·W&B는 **실험 기록·시각화·비교**를 중심으로 이해하면 된다. W&B는 Sweeps를 통해 설정 탐색도 지원한다.

### 3.4 실험 기록이 필요한 이유

모델이나 프롬프트를 바꾸면 품질뿐 아니라 비용과 응답 시간도 달라질 수 있다. 어떤 버전이 더 나은지 판단하려면 다음 정보를 함께 남겨야 한다.

- 모델 이름과 버전
- 프롬프트 버전
- 하이퍼파라미터와 호출 설정
- 데이터셋과 평가셋 버전
- 품질 점수
- 토큰 사용량과 비용
- 응답 시간

이 기록이 있어야 변경 전후 결과를 비교하고, 성능이 좋아진 원인과 나빠진 원인을 추적할 수 있다.

## 4. Evaluation과 평가 데이터셋

**Evaluation(평가)**은 모델이나 애플리케이션이 요구한 품질을 얼마나 충족하는지 측정하는 과정이다. LLM은 답변이 자연스럽게 보이더라도 사실이 틀리거나 근거가 부족할 수 있으므로 평가 기준을 구체적으로 정해야 한다.

### 4.1 무엇을 평가할까?

| 평가 항목 | 확인할 내용 |
|---|---|
| 정확성(Factual Correctness) | 답변에 사실 오류가 없는가? |
| 완전성(Response Completeness) | 질문에서 요구한 내용을 빠뜨리지 않았는가? |
| 근거성(Groundedness) | 답변의 주요 주장이 검색 문서로 뒷받침되는가? |
| 관련성(Relevance) | 질문과 관계없는 내용을 생성하지 않았는가? |
| 안전성(Safety) | 개인정보·위험한 내용·정책 위반이 없는가? |
| 형식 준수(Format Compliance) | JSON이나 필수 필드 등 지정한 형식을 지켰는가? |
| 지연 시간(Latency) | 응답 시간이 서비스 기준을 충족하는가? |
| 비용(Cost) | 토큰·모델 호출 비용이 허용 범위 안에 있는가? |

### 4.2 Eval Set과 Golden Set

- **Eval Set(평가셋)**: 모델의 성능을 반복해서 측정하기 위한 입력 사례 모음.
- **Golden Set(골든셋)**: 정답이나 기대 동작이 확인되어 기준으로 사용할 수 있는 평가 사례 모음.
- **Public Benchmark(공개 벤치마크)**: 여러 모델을 공통 기준으로 비교하기 위해 공개된 데이터셋과 평가 방법.

공개 벤치마크는 다른 모델과 비교할 때 유용하다. 하지만 실제 서비스의 사용자 질문이나 사내 문서 환경을 충분히 반영하지 못할 수 있다. 따라서 공개 벤치마크와 함께 실제 서비스에 가까운 자체 평가셋을 준비해야 한다.

### 4.3 평가 기준은 테스트 전에 정한다

테스트 결과를 본 다음 유리한 기준으로 평가 방식을 바꾸면 결과를 신뢰하기 어렵다. 평가를 시작하기 전에 다음을 정의해야 한다.

1. 평가할 질문 유형과 난이도
2. 정답 또는 기대 동작
3. 정확성·근거성·안전성 등의 평가 기준
4. PASS에 필요한 점수와 필수 조건
5. 평가 데이터와 최종 테스트 데이터의 분리 기준

몇 개의 테스트 사례에만 맞춰 프롬프트를 반복 수정하면 그 사례에 과적합될 수 있다. 수정에 사용한 사례와 최종 성능을 확인할 사례를 구분해야 한다.

### 4.4 LLM-as-Judge와 사람 평가

LLM-as-Judge는 다른 LLM을 평가자로 사용해 답변의 정확성, 관련성, 근거성 등을 채점하는 방식이다. 대량의 답변을 평가하는 데 유용하지만 평가자 모델도 틀릴 수 있고, 평가 기준이 모호하면 점수가 흔들릴 수 있다.

평가 신뢰도를 높이려면 다음 방식을 사용할 수 있다.

- 운영에 사용하는 모델과 다른 모델을 평가자로 활용한다.
- 가능하면 서로 다른 모델 계열의 평가 결과를 비교한다.
- 여러 평가자가 같은 판정을 내리는지 확인한다.
- 평가자 간 결과가 갈리면 Golden Set과 평가 기준을 재검토한다.
- 중요한 사례는 사람이 원문과 근거를 확인한다.

평가자를 홀수로 두면 다수결에서 동률이 생길 가능성을 줄일 수 있다. 다만 평가자 수가 홀수라는 이유만으로 판단의 객관성이 보장되지는 않는다. 평가자들이 비슷한 편향을 공유할 수도 있다.

### 4.5 평가 결과가 100% PASS라면?

평가가 100% 통과했다고 해서 실제 서비스에서도 오류가 없다고 단정할 수는 없다.

- 평가셋이 너무 작거나 쉬울 수 있다.
- 실제 사용자 질문과 다른 사례만 포함했을 수 있다.
- 경계 조건과 실패 사례가 빠졌을 수 있다.
- 평가 기준이 지나치게 느슨할 수 있다.
- 학습·프롬프트 수정에 사용한 데이터와 평가 데이터가 겹쳤을 수 있다.

따라서 통과율뿐 아니라 평가셋의 범위, 난이도, 데이터 분리, 평가자 일치도도 확인해야 한다.

### 4.6 Offline Evaluation과 Online Evaluation

| 구분 | Offline Evaluation | Online Evaluation |
|---|---|---|
| 시점 | 배포 전 또는 변경 검증 시 | 실제 서비스 운영 중 |
| 데이터 | 고정된 평가셋 | 실제 사용자 요청과 Trace |
| 목적 | 버전 간 성능 비교와 회귀 검사 | 운영 품질 변화와 새로운 오류 감지 |
| 활용 | 배포 승인 | 지속적인 모니터링과 개선 |

운영 중 발견한 실패 사례를 평가셋에 추가하면 다음 변경에서 같은 문제가 재발하는지 확인할 수 있다.

## 5. 오류 분석(Error Analysis)

Evaluation이 성능을 측정하는 과정이라면, **Error Analysis(오류 분석)**는 실패한 사례를 살펴보고 왜 틀렸는지 원인을 찾는 과정이다. 전체 점수만 보면 개선할 위치를 알기 어렵기 때문에 오류 유형을 나눠서 분석한다.

### 5.1 LLM·RAG에서 자주 발생하는 오류

| 오류 유형 | 확인할 문제 |
|---|---|
| 입력 해석 오류 | 질문의 의도나 조건을 잘못 이해했는가? |
| 검색 오류 | 필요한 문서를 검색하지 못했는가? |
| 근거 부족 | 검색된 문서에 답변 근거가 충분하지 않은가? |
| 재정렬 오류 | 관련성이 높은 문서가 뒤로 밀렸는가? |
| 생성 오류 | 근거는 있지만 모델이 잘못된 답변을 만들었는가? |
| 환각(Hallucination) | 근거가 없는 내용을 사실처럼 생성했는가? |
| 프롬프트 오류 | 지시사항이 모호하거나 서로 충돌하는가? |
| 도구 호출 오류 | 잘못된 도구를 선택하거나 인자를 잘못 전달했는가? |
| 형식 오류 | JSON·필수 필드 등 출력 형식을 지키지 못했는가? |
| 운영 오류 | 타임아웃, 서버 오류, 지연, 비용 초과가 발생했는가? |

### 5.2 오류 분석 절차

1. 실패한 요청·응답과 실행 기록을 수집한다.
2. 질문 유형, 사용자 유형, 모델 버전, 프롬프트 버전별로 나눈다.
3. Trace를 확인해 어느 단계에서 문제가 시작됐는지 찾는다.
4. 오류 원인을 데이터·검색·프롬프트·모델·도구·인프라로 분류한다.
5. 개선할 항목을 정하고 수정한다.
6. 같은 평가셋으로 수정 전후 결과를 비교한다.
7. 운영에서 새로 발견한 실패 사례를 Eval Set에 추가한다.

### 5.3 공개 벤치마크와 자체 평가의 역할

공개 벤치마크는 외부 모델과 비교할 기준을 제공한다. 자체 Golden Set은 실제 서비스의 문서, 질문, 업무 규칙을 반영한다. 둘 중 하나만으로는 평가 범위가 부족할 수 있으므로 목적에 맞게 함께 활용한다.

## 6. 데이터 드리프트와 개념 드리프트

모델을 학습할 때 사용한 데이터와 실제 서비스에 들어오는 데이터의 특성이 시간이 지나면서 달라질 수 있다. 이를 **Drift(드리프트)**라고 한다. 변화의 종류를 구분해야 원인을 찾고 대응할 수 있다.

### 6.1 X와 Y로 구분하기

- **X**: 모델에 입력되는 데이터 또는 특징(Feature)
- **Y**: 모델이 예측하는 대상 또는 정답(Label)

| 종류 | 통계적 표현 | 의미 |
|---|---|---|
| Data Drift | P(X)의 변화 | 입력 데이터의 분포가 달라짐 |
| Label Drift / Label Shift | P(Y)의 변화 | 정답 또는 클래스의 비율·분포가 달라짐 |
| Concept Drift | P(Y\|X)의 변화 | 같은 입력에 대한 정답의 관계가 달라짐 |

Label Drift는 문맥에 따라 넓게 쓰일 수 있다. 클래스 비율 변화라는 의미를 명확히 하려면 Label Shift 또는 Prior Probability Shift라는 용어를 함께 확인하는 것이 좋다.

### 6.2 사례로 이해하기

**Data Drift — 입력 X가 달라짐**

바지 브랜드가 허리 사이즈 40까지의 고객 데이터를 중심으로 모델을 만들었다고 하자. 시간이 지나 고객의 평균 허리 사이즈가 42로 높아지면 실제 입력 데이터의 분포가 학습 당시와 달라진다.

**Label Drift — 정답 Y의 비율이 달라짐**

고객 이탈 예측 모델을 학습할 때 이탈 고객 비율이 5%였는데, 최근에는 15%로 증가했다. 정답 클래스의 비율이 달라진 상황이다.

**Concept Drift — X와 Y의 관계가 달라짐**

과거에는 가격이 낮을수록 구매 확률이 높았지만, 소비자 선호나 시장 상황이 바뀌면서 같은 가격 조건에서도 구매 행동이 달라졌다. 입력과 정답 사이의 관계가 변한 것이다.

### 6.3 드리프트를 어떻게 감지할까?

학습 데이터의 분포를 기준으로 저장하고, 운영 데이터의 분포와 주기적으로 비교한다.

| 방법 | 확인하는 내용 |
|---|---|
| 평균(Mean) 비교 | 숫자형 데이터의 중심이 달라졌는가? |
| 분산(Variance) 비교 | 데이터가 퍼진 정도가 달라졌는가? |
| PSI | 두 시점의 데이터 분포가 얼마나 달라졌는가? |
| KS Test | 두 숫자형 분포의 차이가 통계적으로 관찰되는가? |
| Wasserstein Distance | 두 분포 사이의 차이를 거리로 측정 |
| 범주별 빈도 비교 | 지역·상품 유형·언어 등의 비율이 달라졌는가? |
| 임베딩 분포 비교 | 문장·문서 벡터의 분포가 달라졌는가? |
| 정답 기반 평가 | 실제 정답이 확보된 뒤 모델 성능이 떨어졌는가? |

평균과 분산만 비교하면 분포의 다른 변화를 놓칠 수 있다. PSI·KS Test·Wasserstein Distance도 데이터 유형과 표본 수에 맞게 해석해야 한다.

드리프트가 감지됐다고 해서 모델 성능이 반드시 떨어진 것은 아니다. 입력 분포가 달라졌어도 모델이 잘 대응할 수 있다. 반대로 입력 분포가 크게 변하지 않아도 입력과 정답 사이의 관계가 바뀌면 성능이 저하될 수 있다.

### 6.4 드리프트가 발생하면

1. 어떤 입력 변수 또는 정답 분포가 변했는지 확인한다.
2. 특정 사용자·지역·질문 유형에 변화가 집중됐는지 나눈다.
3. 정답이 확보되면 실제 모델 성능도 함께 평가한다.
4. 데이터 수집·전처리 오류인지, 시장·사용자 행동 변화인지 원인을 찾는다.
5. 필요하면 최신 데이터를 확보해 재학습한다.
6. 새 모델을 기존 모델과 비교하고 품질 기준을 통과한 경우 배포한다.

### 6.5 LLM과 RAG에서의 드리프트

LLM 서비스에서는 다음과 같은 변화도 관찰할 수 있다.

- 사용자가 질문하는 주제와 유형의 변화
- 입력 프롬프트의 평균 길이와 언어 비율 변화
- RAG에서 검색되는 문서의 주제와 구성 변화
- 임베딩 벡터 분포 변화
- 실제 정답이나 사용자 피드백을 기준으로 한 답변 품질 변화

드리프트 감지는 변화의 신호를 찾는 일이고, Evaluation은 그 변화가 모델 성능에 어떤 영향을 주었는지 확인하는 일이다. 둘을 함께 운영해야 한다.

## 7. Quality Gate와 서비스 오류 등급

### 7.1 Quality Gate란?

**Quality Gate(품질 게이트)**는 사전에 정한 기준을 충족했는지 검사하고 PASS 또는 FAIL로 판정하는 절차다. 배포 과정에 연결하면 품질 기준을 충족하지 못한 변경의 배포를 차단할 수 있다.

| 구분 | Evaluation | Quality Gate |
|---|---|---|
| 목적 | 성능과 품질을 측정 | 기준 충족 여부를 판정 |
| 결과 | 점수·비율·지연 시간 등 | PASS 또는 FAIL |
| 질문 | 얼마나 잘 작동하는가? | 배포 기준을 통과했는가? |

### 7.2 품질 게이트 기준 예시

| 검사 항목 | 통과 기준 예시 |
|---|---|
| 출력 형식 | JSON Schema 검사 통과 |
| 안전성 | 개인정보 노출·금지 응답 없음 |
| 답변 품질 | 사전에 정한 평가 점수 이상 |
| 근거성 | 필수 근거 확인 |
| 응답 시간 | p95 3초 이하 |
| 비용 | 요청당 토큰·비용 예산 이내 |

기준은 서비스 요구사항에 맞게 정한다. 안전성처럼 하나라도 실패하면 전체를 FAIL로 처리하는 필수 조건을 둘 수도 있다.

### 7.3 게이트를 통과했다고 완벽한 것은 아니다

평가셋이 작거나 쉽다면 실제 서비스에서 발생할 문제를 발견하지 못할 수 있다. 평가셋의 범위와 난이도, 평가 기준, 테스트 데이터 분리, Judge의 일치도를 함께 확인해야 한다.

### 7.4 서비스 Tier와 오류 심각도는 구분한다

서비스 에러 티어를 설계할 때 다음 세 가지를 분리하는 것이 좋다.

- **Service Tier**: 해당 서비스가 비즈니스에서 얼마나 중요한가?
- **Incident Severity**: 발생한 장애가 사용자·업무·데이터에 미치는 영향은 어느 정도인가?
- **Priority**: 장애를 얼마나 빨리 처리해야 하는가?

서비스 중요도가 높다고 모든 오류가 치명적인 것은 아니며, 중요도가 낮은 서비스에서도 데이터 손실이나 보안 사고는 심각한 장애가 될 수 있다.

## 8. Observability: Trace, Span, Metrics, Logs

**Observability(관측성)**는 서비스 내부에서 어떤 일이 일어났는지 실행 결과와 기록을 통해 파악하는 능력이다. 단순히 오류 로그를 보는 것보다 요청이 어떤 경로로 처리됐고, 각 단계에서 얼마나 시간이 걸렸으며, 어디에서 실패했는지 확인하는 데 초점을 둔다.

### 8.1 핵심 용어

| 용어 | 의미 | 예시 |
|---|---|---|
| Trace | 사용자 요청 하나의 전체 실행 경로 | 질문 접수부터 최종 답변까지 |
| Span | Trace 안에 포함된 개별 작업 | 임베딩, 검색, LLM 호출 |
| Metrics | 시간에 따라 측정한 수치 | 요청 수, 오류율, p95 지연 |
| Logs | 특정 시점에 발생한 사건의 기록 | API 오류, 타임아웃 메시지 |

RAG 요청 하나가 하나의 Trace가 되고, 임베딩·검색·재정렬·LLM 호출은 각각 Span이 된다. 각 Span에 실행 시간과 입력·출력 등의 정보를 기록하면 느린 구간과 오류가 시작된 위치를 찾을 수 있다.

~~~mermaid
flowchart TD
    T[Trace: 사용자 질문 1건] --> A[Span: 전체 RAG 요청]
    A --> B[Span: 임베딩 생성]
    A --> C[Span: 문서 검색]
    A --> D[Span: 문서 재정렬]
    A --> E[Span: LLM 답변 생성]
~~~

### 8.2 왜 필요한가?

최종 응답이 틀렸다는 사실만으로는 원인을 알기 어렵다.

- 검색 단계에서 필요한 문서를 찾지 못했는가?
- 재정렬 단계에서 관련 문서가 뒤로 밀렸는가?
- LLM에 잘못된 프롬프트가 전달됐는가?
- 모델이 근거와 다른 답변을 생성했는가?
- 특정 단계의 응답이 느려져 전체 지연이 커졌는가?

Trace와 Span을 보면 각 단계를 분리해 확인할 수 있다.

## 9. OpenTelemetry, OpenInference, OTLP

세 용어는 비슷해 보이지만 역할이 다르다. OpenTelemetry는 관측 데이터 수집 체계, OpenInference는 LLM 작업을 설명하는 규칙과 계측 도구, OTLP는 관측 데이터를 전달하는 프로토콜이다.

### 9.1 OpenTelemetry(OTel)

OpenTelemetry는 애플리케이션에서 관측 데이터를 생성·수집·처리·내보내기 위한 오픈소스 표준과 도구 모음이다. 특정 모니터링 제품에 종속되지 않도록 설계되어 여러 분석·저장 시스템과 연결할 수 있다.

주요 신호(Signal)는 다음과 같다.

| 신호 | 의미 |
|---|---|
| Traces | 요청이 여러 서비스와 작업을 거치는 경로 |
| Metrics | 요청 수, 지연 시간, CPU·메모리 사용량 등의 수치 |
| Logs | 오류나 특정 이벤트의 상세 기록 |
| Baggage | 서비스 사이에 전달하는 문맥 정보 |

OpenTelemetry 자체는 데이터를 저장하고 보여주는 분석 플랫폼이 아니다. 수집한 데이터를 Phoenix, Jaeger, Grafana 등의 백엔드로 보낼 수 있다.

### 9.2 OpenInference

OpenInference는 OpenTelemetry를 기반으로 LLM과 AI 애플리케이션의 작업을 표현하기 위한 의미 규칙(Semantic Conventions)과 계측 도구를 제공한다.

일반적인 API 호출 기록에 AI 작업의 종류를 표시하면 어떤 Span이 모델 호출이고, 어떤 Span이 검색인지 구분하기 쉬워진다.

대표적인 Span Kind는 다음과 같다.

| Span Kind | 의미 |
|---|---|
| LLM | 대규모 언어 모델 호출 |
| EMBEDDING | 임베딩 생성 |
| CHAIN | 여러 LLM 애플리케이션 단계를 연결하는 작업 |
| RETRIEVER | 문서·데이터 검색 |
| RERANKER | 검색 결과 재정렬 |
| TOOL | 외부 도구 또는 함수 호출 |
| AGENT | LLM과 도구를 사용하는 에이전트 실행 |
| GUARDRAIL | 입력·출력 안전성 및 정책 검사 |
| EVALUATOR | 모델 출력 평가 |
| PROMPT | 프롬프트 템플릿 구성 |
| DECISION | 후보 중 선택·분류·점수화하는 결정 작업 |

Span Kind는 각 작업의 역할을 표시한다. 모든 작업을 단순한 LLM 호출로 기록하는 것보다 실행 구조를 명확하게 파악할 수 있다.

OpenInference의 Span에는 다음과 같은 속성을 기록할 수 있다.

| 속성 예시 | 의미 |
|---|---|
| llm.model_name | 사용한 모델 이름 |
| llm.provider | 모델 제공자 |
| llm.invocation_parameters | Temperature 등 호출 설정 |
| llm.token_count.prompt | 입력 토큰 수 |
| llm.token_count.completion | 출력 토큰 수 |
| input.value | 작업 입력 |
| output.value | 작업 출력 |
| exception.message | 오류 메시지 |

실제 기록 속성은 작업 종류와 계측 라이브러리에 따라 달라진다. 프롬프트와 응답에는 개인정보나 비밀정보가 포함될 수 있으므로 마스킹과 수집 범위를 함께 설계해야 한다.

### 9.3 OTLP(OpenTelemetry Protocol)

OTLP는 OpenTelemetry로 수집한 Trace·Metric·Log 데이터를 전송하는 프로토콜이다. 데이터의 인코딩과 전송 방식을 정의하며 HTTP 또는 gRPC를 사용할 수 있다.

- OpenTelemetry: 관측 데이터를 만들고 수집·처리하는 체계
- OTLP: 수집한 데이터를 전달하는 통신 규약

### 9.4 네 가지의 연결 관계

~~~mermaid
flowchart TD
    A[LLM 애플리케이션] --> B[OpenInference 계측]
    B --> C[OpenTelemetry SDK]
    C --> D[OTLP 전송]
    D --> E[Phoenix 등 관측성 백엔드]
    E --> F[Trace 탐색·평가·오류 분석]
~~~

실제 구현에서는 OpenInference 계측 라이브러리가 OpenTelemetry SDK를 함께 활용하므로 개발자가 모든 단계를 직접 구현할 필요는 없다.

## 10. Phoenix와 Arize AI

### 10.1 Arize AI

**Arize AI는 AI 모델과 LLM 서비스의 품질·관측성 기술을 개발하는 회사**다. Phoenix와 Arize AX가 대표적인 제품이며, OpenInference는 관련 오픈소스 계측 기술이다.

| 이름 | 구분 | 역할 |
|---|---|---|
| Arize AI | 회사 | AI 관측성·평가 제품 개발 |
| Phoenix | 오픈소스 플랫폼 | LLM·에이전트 Trace, 평가, 실험 |
| Arize AX | 상용 플랫폼 | 기업용 AI 엔지니어링과 운영 |
| OpenInference | 오픈소스 기술 | LLM 실행 기록의 규칙과 계측 도구 |

### 10.2 Phoenix

Phoenix는 LLM과 AI 에이전트의 실행 과정을 수집하고 분석하는 오픈소스 관측성 플랫폼이다.

주요 활용:
- 요청별 Trace와 Span 확인
- 프롬프트와 모델 응답 확인
- 검색 문서와 재정렬 결과 확인
- 단계별 지연 시간과 오류 분석
- 평가 데이터셋과 실험 관리
- 답변 품질 평가

### 10.3 RAG 요청을 Phoenix에서 분석하는 예시

사용자가 질문 하나를 보냈을 때 다음과 같이 실행되었다고 가정하자.

| 단계 | 실행 시간 | 기록할 내용 |
|---|---:|---|
| 임베딩 생성 | 100ms | 입력 문장, 임베딩 모델 |
| 문서 검색 | 250ms | 검색어, 문서 ID, 검색 점수 |
| 문서 재정렬 | 450ms | 후보 문서와 재정렬 점수 |
| LLM 답변 생성 | 2,000ms | 모델, 프롬프트, 응답, 토큰 수 |
| 전체 요청 | 약 2,800ms | 요청 ID, 전체 상태와 시간 |

이 수치는 이해를 위한 가상 예시다. Phoenix에서는 전체 Trace와 각 Span을 확인하여 어느 단계가 느린지, 검색 결과가 적절했는지, 모델이 어떤 근거로 답했는지 조사할 수 있다.

### 10.4 Phoenix와 Arize AX

Phoenix는 개발자가 직접 설치해 운영할 수 있는 오픈소스 도구다. Arize AX는 기업용 AI 엔지니어링과 운영을 지원하는 상용 플랫폼이다. 두 제품은 같은 회사에서 제공하지만 배포 방식과 운영 지원 범위가 다르다.

## 11. Phoenix·Langfuse·LangSmith·W&B Weave 비교

이 도구들은 LLM 애플리케이션의 실행 과정을 추적하고 품질을 평가한다는 점에서 유사하다. 다만 개발사와 통합 방식, 프롬프트 관리, 배포 형태 등이 다르다.

| 도구 | 개발사 | 주요 역할 |
|---|---|---|
| Phoenix | Arize AI | 오픈소스 LLM 관측성·평가 |
| Langfuse | Langfuse | Trace, 프롬프트 관리, 비용·품질 분석 |
| LangSmith | LangChain | LangChain·LangGraph를 포함한 LLM 앱 추적·평가·디버깅 |
| W&B Weave | Weights & Biases | LLM·에이전트 Trace와 평가 |

### 11.1 LangGraph와 LangSmith는 다르다

이름이 비슷해 혼동하기 쉽지만 역할이 다르다.

- **LangGraph**: 에이전트의 실행 흐름, 상태, 분기, 반복을 구성하는 프레임워크.
- **LangSmith**: 실행 결과를 추적하고 평가하는 플랫폼.

즉, LangGraph로 에이전트 애플리케이션을 만들고 LangSmith로 실행 과정을 관찰할 수 있다.

### 11.2 어떤 도구를 선택할까?

| 목적 | 검토할 도구 |
|---|---|
| 오픈소스 기반 LLM Trace와 평가 | Phoenix |
| 프롬프트·데이터셋·실험과 Trace 관리 | Langfuse |
| LangChain·LangGraph 기반 앱 추적 | LangSmith |
| 기존 W&B 실험 환경과 LLM Trace 연결 | W&B Weave |

기능이 겹치므로 모든 도구를 함께 설치할 필요는 없다. 사용 중인 프레임워크, 자체 호스팅 필요성, 데이터 보안, 평가 기능, 비용을 기준으로 선택한다.

## 12. 전체 운영 흐름으로 연결하기

앞에서 배운 개념을 하나의 RAG 서비스 운영 과정에 연결하면 다음과 같다.

### 12.1 개발과 최적화

- 모델과 프롬프트를 구성한다.
- Optuna 등으로 하이퍼파라미터를 탐색한다.
- W&B 또는 MLflow에 실험 조건과 결과를 기록한다.
- 공개 벤치마크와 자체 Golden Set으로 후보 버전을 비교한다.

### 12.2 배포 전 검증

- 정확성·근거성·안전성·형식·비용·지연 시간을 평가한다.
- 오류 사례를 분류하고 수정한다.
- Quality Gate의 PASS/FAIL 기준을 적용한다.
- 기준을 통과한 버전만 배포한다.

### 12.3 운영 중 관측

- OpenInference로 LLM 작업을 구분해 기록한다.
- OpenTelemetry로 Trace·Metrics·Logs를 수집한다.
- OTLP로 데이터를 전송한다.
- Phoenix·Langfuse·LangSmith·W&B Weave 등에서 실행 결과를 분석한다.

### 12.4 지속적인 개선

- 오류가 발생한 Trace를 모은다.
- 검색·프롬프트·모델·도구·인프라 중 원인을 찾는다.
- Data Drift와 Concept Drift를 감지한다.
- 실패 사례를 Golden Set에 추가한다.
- 수정한 버전을 다시 평가하고 배포 여부를 판단한다.

핵심은 **운영 중 발견한 실패를 다음 평가셋에 반영하는 것**이다. 그래야 한 번 발생한 오류가 이후 변경에서 반복되는지 확인할 수 있다.

## 핵심 용어 정리

| 용어 | 한 줄 설명 |
|---|---|
| Hyperparameter | 모델 구조와 학습 방법을 정하는 설정값 |
| Search Space | 최적화 실험에서 탐색할 후보 값의 범위 |
| Trial | 하이퍼파라미터 조합 하나로 수행한 실험 |
| Study | 여러 Trial을 묶은 최적화 작업 |
| AutoML | 데이터 처리부터 모델 선택·학습·평가까지 자동화하는 접근 |
| W&B | 실험 기록·비교·최적화와 LLM 관측 기능을 제공하는 플랫폼 |
| Evaluation | 모델의 품질과 성능을 측정하는 과정 |
| Golden Set | 정답이나 기대 동작이 확인된 기준 평가 데이터 |
| Error Analysis | 실패 사례를 분류하고 원인을 찾는 과정 |
| Data Drift | 입력 데이터 X의 분포 변화 |
| Label Drift | 정답 Y의 분포 변화 |
| Concept Drift | 입력 X와 정답 Y 사이의 관계 변화 |
| Quality Gate | 사전 기준에 따라 PASS/FAIL을 판정하는 절차 |
| Observability | 실행 기록을 통해 서비스 내부 상태를 파악하는 능력 |
| Trace | 요청 하나의 전체 실행 경로 |
| Span | Trace 안의 개별 작업 |
| OpenTelemetry | 관측 데이터를 생성·수집·처리·내보내는 표준과 도구 |
| OpenInference | LLM 작업을 표현하는 의미 규칙과 계측 도구 |
| OTLP | OpenTelemetry 데이터를 전달하는 프로토콜 |
| Phoenix | Arize AI가 만든 오픈소스 LLM 관측성·평가 플랫폼 |
| Arize AI | Phoenix와 Arize AX 등을 개발하는 회사 |
