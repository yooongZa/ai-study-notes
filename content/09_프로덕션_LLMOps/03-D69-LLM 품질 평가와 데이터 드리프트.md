## 전체 흐름부터 이해하기

LLM 서비스를 출시하기 전에는 미리 준비한 질문으로 모델의 답변 품질을 확인한다. RAG 서비스라면 필요한 문서를 잘 찾는지, 검색한 문서를 근거로 정확하게 답하는지, 답변 형식과 접근 권한을 지키는지 함께 검사해야 한다.

서비스를 출시한 뒤에도 평가가 필요하다. 사용자가 새로운 주제의 질문을 하기 시작하거나 사내 규정이 개정되면, 모델을 바꾸지 않았어도 기존보다 답변 품질이 낮아질 수 있다. 평가 기준이나 사용자의 요구사항도 달라질 수 있다.

운영 환경에서는 실제 질문에 대한 정답을 미리 알기 어렵다. 따라서 응답의 형식, 길이, 거절 비율 등을 자동으로 검사하고, 일부 응답은 별도의 LLM이나 사람이 검토한다. 사용자 피드백과 질문·검색 결과·답변의 분포 변화도 함께 확인한다.

문제가 발견되면 어떤 요청이 실패했는지 찾고, 해당 요청의 **트레이스(Trace)**를 확인한다. 트레이스에는 문서 검색, 프롬프트 구성, 모델 호출 등 요청을 처리하는 과정이 연결되어 있다. 이 기록을 통해 검색 단계의 문제인지, 생성 단계의 문제인지, 최근 배포 과정에서 발생한 문제인지 조사할 수 있다.

문제를 수정한 뒤에는 동일한 질문으로 다시 평가한다. 운영 중 발견한 실패 사례는 기존 평가 데이터셋에 추가해 다음 배포에서도 같은 문제가 발생하는지 검사한다.

```text
[출시 전]
평가 데이터셋 작성 → RAG 실행 → 답변 평가 → 품질 확인 및 배포
                                             ↓
[운영 중]
실제 요청 처리 → 실행 기록 수집 → 품질 평가 및 드리프트 감지
                                             ↓
                         실패 요청 선정 → 트레이스 조사
                                             ↓
                         원인 수정 → 동일 조건에서 재평가
                                             ↓
                         실패 사례를 회귀 평가 세트에 추가
                                             ↓
                              다음 배포 전 품질 검증
```

이 과정에서 익혀야 할 개념은 다음과 같다.

| 개념 | 하는 일 |
|---|---|
| 평가 데이터셋(Evaluation Dataset) | 같은 질문으로 여러 버전의 서비스 품질을 비교한다. |
| 참조 답(Reference Answer) | 문서나 업무 기준을 확인해 실제 응답을 평가할 기준을 마련한다. |
| 회귀 평가(Regression Evaluation) | 모델이나 설정을 변경한 뒤 기존에 잘 처리하던 질문에서 문제가 생겼는지 확인한다. |
| LLM-as-a-Judge | 별도의 LLM으로 답변의 정확성, 근거 충실성, 요청 충족 여부 등을 평가한다. |
| 관측 가능성(Observability) | 서비스의 실행 기록을 통해 내부 동작과 문제의 원인을 조사한다. |
| 드리프트(Drift) | 질문, 검색 결과, 답변 등이 기준 기간과 비교해 어떻게 달라졌는지 확인한다. |
| Phoenix | 요청별 실행 기록, 평가 데이터셋, 실험 결과를 연결해 품질을 분석한다. |
| OpenTelemetry | 서비스의 로그, 지표, 트레이스 등 관측 정보를 생성하고 수집·전달하는 데 사용한다. |

오늘 학습의 핵심은 평가 점수를 계산하는 데서 끝나지 않고, **품질 변화를 발견하고 원인을 분석한 뒤 개선 결과를 다시 검증하는 운영 체계**를 이해하는 것이다.

## 1. LLM 서비스의 품질은 어떻게 평가하는가

### 1.1. 평가 기준을 먼저 정해야 하는 이유

LLM의 답변은 표현이 자연스럽고 자세하더라도 사실관계가 틀릴 수 있다. 특히 RAG에서는 적절한 문서를 검색했더라도 모델이 내용을 잘못 해석하거나 근거에 없는 조건을 추가할 수 있다.

따라서 서비스의 목적에 맞는 평가 항목을 먼저 정해야 한다. 사내 규정 안내 서비스에서는 다음과 같은 항목이 중요하다.

| 평가 항목 | 확인할 내용 |
|---|---|
| 검색 품질(Retrieval Quality) | 질문에 답하는 데 필요한 문서를 검색했는가? |
| 답변 정확성(Correctness) | 답변의 숫자, 날짜, 조건 등이 현재 규정과 일치하는가? |
| 근거 충실성(Faithfulness) | 답변에 포함된 주장을 실제 검색 문서로 뒷받침할 수 있는가? |
| 질문 관련성(Relevance) | 사용자가 요구한 내용을 적절하게 설명했는가? |
| 출처·권한 준수 | 올바른 출처를 표시하고 사용자가 접근할 수 있는 문서만 활용했는가? |
| 출력 형식 준수 | 지정한 형식과 필수 응답 항목을 지켰는가? |

이 항목들을 분리하면 어디를 수정해야 할지 판단하기 쉽다. 검색에 실패했다면 문서, 인덱스, 검색 설정을 검토한다. 올바른 문서를 검색하고도 틀린 답을 생성했다면 프롬프트, 모델, 컨텍스트 구성 등을 조사한다.

근거 충실성과 답변 정확성도 구분해야 한다. 오래된 규정에 충실하게 답변을 생성하면 검색 문서와는 일치하지만 현재 업무 기준으로는 오답이 될 수 있다.

### 1.2. 평가 데이터셋과 참조 답

평가 데이터셋은 서비스의 품질을 반복해서 검사하기 위해 준비한 입력 사례의 모음이다. RAG 서비스에서는 질문 외에 참조 답, 필요한 근거 문서, 사용자 권한 등을 함께 저장하는 것이 좋다.

참조 답은 평가자가 원문이나 업무 규정을 확인해 작성한 비교 기준이다. Ground Truth는 평가에서 정답으로 삼는 사실 또는 라벨을 뜻한다. LLM은 같은 내용을 여러 방식으로 표현할 수 있으므로, 참조 답과 문장이 완전히 같아야만 정답으로 판정하는 방식은 제한적으로 사용해야 한다.

사내 규정 도우미를 예로 들어 평가 데이터셋 한 건을 구성하면 다음과 같다. 아래 값은 개념 설명을 위해 만든 예시다.

| 항목 | 저장 내용 |
|---|---|
| 질문 | 재택근무는 몇 시까지 신청해야 하나요? |
| 사용자 | 일반 직원 |
| 참조 답 | 오후 3시까지 신청한다. |
| 근거 문서 | 재택근무 운영 규정 HR-01 |
| 기대 동작 | 신청 마감 시각과 출처를 정확하게 안내한다. |
| 판정 기준 | 오후 3시, 문서 일치, 근거에 없는 조건 추가 여부 |

권한에 따라 답변이 달라지는 서비스라면 사용자 정보도 평가 조건에 포함한다. 근거가 없거나 접근 권한이 없는 경우에는 적절히 답변을 보류하는지를 평가한다.

참조 답은 평가 단계에서 실제 응답을 검사할 때 사용한다. RAG 서비스에 질문할 때는 정답을 별도로 제공하지 않고 실제 서비스와 같은 조건으로 실행한다.

### 1.3. 정적 평가와 회귀 평가

정적 평가(Static Evaluation)는 고정된 평가 데이터셋과 판정 기준으로 서비스 품질을 측정하는 방법이다. 기존 모델과 새로운 모델을 비교하거나 프롬프트를 수정했을 때 활용한다.

프롬프트의 효과를 확인하려면 기존과 새로운 프롬프트에 동일한 질문을 보내야 한다. 모델, 검색 설정, 문서 버전, 평가 기준 등 다른 조건도 가능한 한 동일하게 유지한다. 여러 설정을 동시에 변경하면 성능 변화의 원인을 구분하기 어렵다.

회귀 평가(Regression Evaluation)는 서비스 변경으로 기존 기능이나 품질이 저하됐는지 확인하는 평가다. 같은 평가 데이터셋을 여러 버전에서 반복 실행한다.

전체 정답률이 개선됐더라도 일부 중요한 질문에서 새롭게 실패할 수 있다. 따라서 평균 점수와 함께 문항별 통과·실패의 변화도 확인한다. 특히 권한 위반, 잘못된 규정 안내처럼 영향이 큰 실패는 전체 점수와 별도로 관리해야 한다.

## 2. 출시 이후에는 품질을 어떻게 평가하는가

### 2.1. 출시 전에 잘 작동하던 서비스에서 문제가 생기는 이유

출시 전 평가는 준비된 데이터셋으로 수행한다. 실제 운영에서는 사용자, 업무 내용, 문서 등이 지속적으로 바뀐다.

강의에서는 크게 세 가지 변화를 다룬다.

| 변화 | 발생하는 상황 | 필요한 대응 |
|---|---|---|
| 질문의 변화 | 새로운 부서가 서비스를 이용하거나 긴 질문이 많아진다. | 새로운 질문 유형의 검색·응답 품질을 검사한다. |
| 문서의 변화 | 사내 규정이 개정되거나 새로운 문서가 추가된다. | 인덱스 갱신 여부와 참조 답의 유효성을 확인한다. |
| 기대치의 변화 | 출처 표시나 필수 안내 항목이 새로 요구된다. | 평가 기준과 프롬프트를 수정한다. |

모델과 프롬프트를 그대로 유지하더라도 운영 환경이 바뀌면 평가 결과가 달라질 수 있다. 따라서 출시 전 평가와 운영 중 평가를 모두 수행해야 한다.

### 2.2. 참조 정답이 없는 질문을 평가하는 방법

실제 사용자가 보내는 모든 질문에 사람이 참조 답을 미리 작성하기는 어렵다. 운영 중에는 정답 없이 측정할 수 있는 지표와 별도의 평가 모델, 사용자 피드백 등을 조합한다.

| 방법 | 측정하는 내용 | 한계 |
|---|---|---|
| 규칙·계산 기반 검사 | 형식 오류, 응답 길이, 출력 언어, 거절 비율 등 | 답변의 전체 의미와 사실관계는 평가하기 어렵다. |
| LLM-as-a-Judge | 근거 충실성, 질문 관련성, 요청 충족 여부 등 | 평가 비용과 판정 오류가 발생할 수 있다. |
| 사용자 피드백 | 좋아요·싫어요, 재질문, 답변 수정 등 | 답변이 정확한지 별도로 확인해야 한다. |
| 분포 비교 | 질문, 임베딩, 검색 결과, 출력의 변화 | 변화가 품질에 어떤 영향을 주었는지 추가 검토가 필요하다. |
| 사람의 검토 | 실제 질문과 답변, 근거, 업무 기준을 종합한 판정 | 검토 시간과 인력이 필요하다. |

강의에서 계산형 센서라고 부르는 것은 정해진 규칙에 따라 출력이나 실행 정보를 자동으로 검사하는 평가 방식이다. JSON 형식 준수 여부나 지정한 문서 ID 포함 여부 등을 코드로 검사할 수 있다.

이러한 자동 검사는 빠르고 비용이 적으므로 모든 요청에 적용하기 좋다. 의미를 판단해야 하는 평가는 별도 LLM을 호출하므로 무작위 표본이나 이상 신호가 발견된 요청에 적용할 수 있다. 무작위 표본을 함께 검사하면 문제가 의심되는 사례만 평가하면서 생기는 표본 편향을 줄일 수 있다.

### 2.3. 운영에서 발견한 실패 사례를 평가 데이터셋에 추가하기

운영에서 틀린 답이 발견되면 먼저 어떤 질문과 근거에서 문제가 발생했는지 확인한다. 이후 해당 사례의 참조 답과 판정 기준을 작성해 회귀 평가 세트에 추가한다.

기존 규정이 바뀐 경우에는 오래된 참조 답도 함께 수정해야 한다. 참조 답이나 평가 기준이 바뀌면 평가 데이터셋의 버전을 기록해 이전 결과와 구분한다.

이 과정을 반복하면 초기에는 없었던 실제 사용자 질문과 실패 유형이 평가 데이터셋에 축적된다. 서비스가 오래 운영될수록 실제 업무 환경을 더 잘 반영하는 평가가 가능해진다.

## 3. LLM-as-a-Judge: LLM으로 답변을 평가하는 방법

### 3.1. 평가 모델의 역할과 작동 원리

LLM-as-a-Judge는 언어 모델을 이용해 다른 모델이나 애플리케이션의 응답을 평가하는 방법이다. 서비스에서 답변을 생성하는 모델과 응답을 평가하는 모델의 역할을 분리한다. 두 역할에 반드시 서로 다른 종류의 모델을 사용할 필요는 없다.

평가 모델에는 사용자 질문, 실제 서비스 응답, 검색한 근거 문서, 평가 기준을 전달한다. 참조 답이 준비되어 있다면 함께 전달할 수 있다.

```text
사용자 질문 → RAG 서비스 → 실제 답변
                              │
사용자 질문 + 실제 답변 + 근거 문서 + 평가 기준
                              ↓
                         평가용 LLM
                              ↓
                      판정 결과 + 판정 이유
```

예를 들어 RAG가 생성한 답변의 근거 충실성을 평가할 경우, 답변에 포함된 주장을 문서와 하나씩 대조하고 문서에서 확인할 수 없는 주장이 있는지 판단하도록 요청한다.

이 방식은 정확한 참조 답이 없는 상황에서도 답변과 검색 근거가 일치하는지를 평가할 수 있다. 다만 검색 문서 자체가 최신이고 정확한지는 별도로 검증해야 한다.

### 3.2. 루브릭(Rubric): 평가 모델에 전달할 채점 기준

평가 모델에 단순히 좋은 답인지 물으면 어떤 기준으로 평가했는지 알기 어렵다. 루브릭은 평가할 항목과 통과·탈락 또는 점수별 조건을 명확하게 정의한 채점 기준이다.

사내 규정 안내 응답을 평가하기 위한 간단한 루브릭은 다음과 같이 구성할 수 있다.

| 판정 | 기준 |
|---|---|
| PASS | 질문에 필요한 내용을 정확히 답했고 근거 문서와 일치한다. |
| FAIL | 날짜·숫자·단위가 틀렸거나 근거에 없는 조건을 추가했다. 답할 수 있는 질문을 불필요하게 거절한 경우도 포함한다. |
| 판정 불가 | 필요한 근거가 부족하거나 입력이 불완전하여 평가를 확정하기 어렵다. |

판정 결과와 함께 이유를 받으면 어떤 기준에서 실패했는지 검토하기 쉽다. JSON처럼 일정한 구조로 받으면 결과를 자동으로 집계할 수도 있다. 결과가 누락되거나 형식이 깨진 경우에는 평가 실패 또는 판정 불가로 별도 기록한다.

업무에 따라 정확성, 근거 충실성, 권한 준수 등을 독립적인 항목으로 평가하는 것이 좋다. 하나의 종합 점수만 기록하면 구체적인 실패 원인을 파악하기 어렵다.

### 3.3. 평가 모델의 일관성과 편향

LLM Judge도 언어 모델이므로 같은 답변을 여러 번 평가했을 때 판정이 달라질 수 있다. 이러한 변동은 서비스 자체의 품질 변화와 구분해야 한다.

| 원인 | 발생하는 문제 |
|---|---|
| 샘플링과 temperature | 같은 입력에서도 토큰 선택이 달라져 판정이 바뀔 수 있다. |
| 입력 순서와 표현 | 근거 문서의 순서, 프롬프트 표현 등의 차이가 판정에 영향을 줄 수 있다. |
| 위치 편향(Position Bias) | 두 답을 비교할 때 답변을 제시한 순서에 따라 특정 답을 더 높게 평가할 수 있다. |
| 길이 편향(Verbosity Bias) | 내용이 정확한 짧은 답보다 길고 자세한 답을 선호할 수 있다. |
| 모델 및 실행 환경 변경 | Judge의 모델 버전, 양자화, 서빙 엔진 등이 바뀌면 기존 판정과 차이가 생길 수 있다. |

`temperature=0`으로 설정하면 샘플링에 의한 변동을 줄일 수 있다. 하지만 판정의 정확성이나 입력 순서에 대한 편향은 별도로 검증해야 한다.

같은 평가 사례를 여러 번 실행해 한 번이라도 판정이 달라진 문항의 비율을 계산하면 판정의 변동성을 확인할 수 있다. 두 답변 중 하나를 고르는 평가라면 A와 B의 순서를 바꿔 다시 평가하는 방법도 활용할 수 있다.

### 3.4. 사람의 판정으로 Judge 검증하기: 보정 세트

평가 모델의 판정이 실제 업무 기준과 일치하는지 확인하려면 사람이 직접 판정한 답변이 필요하다. 이러한 답변과 판정 결과를 모아 만든 데이터셋을 보정 세트(Calibration Set)라고 한다.

일반 평가 데이터셋은 RAG 서비스가 얼마나 잘 답하는지 확인하는 데 사용한다. 보정 세트는 평가 모델이 실제 답변을 올바르게 채점하는지 확인하는 데 사용한다.

보정 세트에는 정확한 답변뿐 아니라 숫자·단위 오류, 근거 없는 주장, 잘못된 거절, 문서에는 존재하지만 질문과 관계없는 내용을 사용한 답변 등 다양한 오답을 포함한다. 특히 문자열 검사만으로 놓치기 쉬운 사례가 필요하다. 재택근무 신청 마감이 오후 3시인데 3일이라고 답한 경우처럼 숫자는 같고 단위나 의미가 다른 답변이 이에 해당한다.

두 사람이 독립적으로 같은 답변을 평가하고, 판정이 다른 문항을 논의해 최종 기준과 판정 이유를 정할 수 있다. 그다음 Judge에게 동일한 답변을 채점하게 하여 사람 판정과 비교한다.

- 전체 판정 일치율: 사람과 Judge의 판정이 일치한 건수 ÷ 전체 판정 건수
- 불량 탐지율: 사람이 FAIL로 판정한 답변 중 Judge도 FAIL로 판정한 건수 ÷ 사람이 FAIL로 판정한 건수
- 정상 답변 오판율: 사람이 PASS로 판정한 답변 중 Judge가 FAIL로 판정한 건수 ÷ 사람이 PASS로 판정한 건수
- 판정 불가 건수: Judge가 최종 판정을 내리지 못한 사례 수

여기서 불량 탐지율은 불량을 양성으로 정의했을 때의 재현율(Recall)이다. 전체 일치율이 높더라도 불량 탐지율이 낮으면 실제 서비스의 오류를 놓칠 수 있다. 반대로 정상 답변 오판율이 높으면 품질이 개선된 버전도 잘못 탈락시킬 수 있다.

### 3.5. Judge 모델을 변경할 때 재보정이 필요한 이유

서비스 모델을 그대로 유지해도 Judge가 달라지면 평가 점수가 바뀔 수 있다. 새로운 Judge가 이전보다 관대하게 평가하면 통과율이 올라가고, 더 엄격하게 평가하면 통과율이 내려갈 수 있다.

Judge의 모델 버전이나 판정 프롬프트를 변경할 때는 다음 순서로 검증한다.

1. 기존 보정 세트로 새로운 Judge의 판정 능력을 측정한다.
2. 사람이 정한 최소 성능 기준을 통과하는지 확인한다. 강의에서는 불량 탐지율 80% 이상, 판정 불가 0건을 예시로 제시한다.
3. 일정 기간 같은 운영 응답을 기존 Judge와 새로운 Judge로 동시에 평가한다.
4. 판정 차이와 통과율 차이를 기록한 뒤 교체 여부를 판단한다.
5. 평가 기록에 Judge 모델, 프롬프트, 판정 기준 버전과 변경 날짜를 남긴다.

예시 기준은 서비스 위험도와 평가 목적에 맞게 조정해야 한다. 가능하면 서비스 모델과 Judge를 동시에 교체하지 않고 변경 효과를 따로 검증한다.

## 4. 관측 가능성(Observability)과 요청 추적

### 4.1. 로그, 지표, 트레이스의 차이

관측 가능성은 서비스가 남긴 기록을 통해 내부에서 어떤 일이 발생했는지 조사할 수 있는 성질이다. 운영 중에는 어떤 문제가 생겼는지 감지하고, 문제를 일으킨 개별 요청과 실행 단계를 찾아야 한다.

| 구분 | 기록하는 내용 | 활용 방법 |
|---|---|---|
| 로그(Log) | 개별 사건과 오류 메시지 | 어떤 오류가 발생했는지 확인한다. |
| 지표(Metric) | 요청 수, 오류율, 응답 시간, 토큰 수 등의 수치 | 서비스의 상태와 시간에 따른 변화를 확인한다. |
| 트레이스(Trace) | 요청 한 건이 처리된 전체 과정 | 어느 처리 단계에서 문제가 발생했는지 조사한다. |

지표에서 오류율이 증가한 사실을 발견했다면 로그와 트레이스를 이용해 실제 실패한 요청을 조사할 수 있다. 전체적인 상태를 파악하는 데는 지표가, 개별 요청의 처리 과정과 원인 분석에는 트레이스가 특히 유용하다.

### 4.2. Trace와 Span

Trace는 요청 한 건의 처리 과정을 연결한 기록이다. Span은 그 과정에서 수행한 개별 작업의 기록이다.

RAG 요청의 경우 검색, 재정렬, 프롬프트 구성, 모델 호출 등을 각각 Span으로 기록할 수 있다. 검색 서비스가 별도로 실행되거나 외부 모델 API를 호출하더라도 요청 간 연결 정보를 전달하면 같은 Trace에서 처리 흐름을 확인할 수 있다.

```text
Trace: 요청 한 건
└─ Span: RAG 전체 요청 처리
   ├─ Span: 질문 임베딩
   ├─ Span: 문서 검색
   │  └─ Span: 벡터 DB 호출
   ├─ Span: 검색 결과 재정렬
   ├─ Span: 프롬프트 구성
   └─ Span: LLM 호출 및 답변 생성
```

각 Span에는 작업 이름, 시작·종료 시각, 상태, 오류 정보, 실행에 사용한 버전 등의 속성을 기록할 수 있다.

| 구간 | 주요 기록 항목 |
|---|---|
| 임베딩 | 사용한 임베딩 모델, 처리 시간 |
| 검색 | 문서 ID, 검색 순위, 유사도, 인덱스 버전 |
| 프롬프트 구성 | 프롬프트 버전, 컨텍스트 길이 |
| 생성 | 모델 버전, 입력·출력 토큰 수, 생성 시간, 종료 사유 |

이처럼 단계별 기록을 남기면 답변 품질과 응답 지연을 함께 조사할 수 있다. 전체 요청에 3초가 걸렸다면 어떤 단계가 대부분의 시간을 사용했는지 확인할 수 있다. 다만 부모 Span의 시간에는 자식 Span의 시간이 포함될 수 있고 여러 작업이 병렬로 실행될 수도 있으므로, 모든 Span의 소요 시간을 단순히 더하면 중복 계산될 수 있다.

### 4.3. Trace ID, Span ID, traceparent

여러 서비스가 하나의 요청을 나누어 처리하는 환경에서는 같은 요청의 기록을 연결할 식별자가 필요하다.

Trace ID는 요청 전체를 식별하는 값이다. 요청이 게이트웨이에서 RAG 서버로 전달되고 검색 서버를 거치더라도 동일한 Trace ID를 유지한다. Span ID는 개별 작업을 식별하며, 부모 Span ID는 해당 작업을 호출한 상위 작업과의 관계를 나타낸다.

일반적인 `X-Request-ID` 헤더는 동일 요청의 로그를 묶는 데 사용할 수 있다. 여러 서비스에서 부모·자식 Span의 관계까지 표준화된 방식으로 전달하려면 W3C Trace Context의 `traceparent` 헤더를 사용한다.

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                └─ trace-flags
             │  │                                └─ parent-id (16자리 16진수)
             │  └─ trace-id (32자리 16진수)
             └─ version (2자리 16진수)
```

- `trace-id`: 전체 Trace를 식별한다. 하위 서비스에도 같은 값이 전달된다.
- `parent-id`: 해당 호출을 보낸 Span의 ID다. 호출하는 Span이 달라지면 이 값도 달라진다. 수신 서비스는 이 값과 연결된 새로운 Span을 생성한다.
- `trace-flags`: 샘플링 여부 등의 추적 관련 플래그를 담는다.

이렇게 정보를 전달하면 여러 서버에서 만들어진 Span을 하나의 부모·자식 구조로 연결할 수 있다. 외부에서 전달된 헤더는 형식과 유효성을 확인한 후 처리한다.

강의 실습에서는 게이트웨이가 반환하는 `X-Request-ID`로 요청을 찾아 서비스별 기록을 연결하는 방식을 사용한다고 설명한다. 이는 요청을 연관 지어 조회하기 위한 실습 설계이며, 임의 형식의 요청 ID와 W3C 표준 Trace ID는 구분해야 한다.

### 4.4. OpenTelemetry의 역할

OpenTelemetry(OTel)는 로그, 지표, 트레이스 등 관측 정보를 생성하고 수집하며 전달하는 표준화된 오픈소스 도구 모음이다.

계측(Instrumentation)이란 애플리케이션의 실행 상태를 기록할 수 있도록 코드나 프레임워크에 관측 기능을 연결하는 작업이다. 기존 라이브러리에 대한 자동 계측을 사용할 수도 있고, 검색이나 권한 검사처럼 서비스에 특화된 단계는 직접 Span을 생성해 기록할 수도 있다.

```text
RAG 애플리케이션
  ↓ 계측을 통해 Span 생성
OpenTelemetry SDK / Exporter
  ↓ OTLP로 관측 정보 전송
Phoenix 등 관측 플랫폼
  ↓
트레이스 저장 · 검색 · 시각화 · 평가 결과 확인
```

OTLP(OpenTelemetry Protocol)는 관측 정보를 전달하는 규약이다. 구성에 따라 중간에 OpenTelemetry Collector를 두고 여러 서비스의 기록을 수집·처리·전달할 수 있다.

OpenTelemetry는 관측 정보를 만들고 전달하는 역할을 하고, Phoenix는 수신한 실행 기록을 조회·분석하고 LLM 품질 평가와 연결하는 역할을 한다. 기록되는 정보의 종류는 실제 계측 설정에 따라 달라진다.

### 4.5. 운영 기록에 민감한 정보를 남기지 않기

LLM 요청과 답변에는 개인정보, 내부 문서, 비밀 정보가 포함될 수 있다. 검색 결과의 원문까지 모든 Span에 저장하면 민감한 정보가 노출될 위험이 커지고 저장 비용도 증가한다.

일반적인 트레이스에는 시간, 모델·프롬프트 버전, 토큰 수, 문서 ID, 오류 상태처럼 분석에 필요한 속성을 우선 기록한다. 질문과 답변 원문을 품질 평가에 활용해야 한다면 필요 범위를 정하고 마스킹과 접근 제어를 적용한 별도 저장소에서 관리할 수 있다. Trace ID로 두 기록을 연결하면 필요한 경우 원문을 검토할 수 있다.

강의에서는 트레이스 90일, 원문 30일 보관을 예로 든다. 실제 보관 기간과 원문 열람 권한은 서비스의 개인정보 보호 정책과 감사 요구사항에 맞게 정해야 한다.

## 5. 사용자 피드백을 평가에 활용하는 방법

### 5.1. 명시적 피드백과 암묵적 피드백

명시적 피드백(Explicit Feedback)은 사용자가 직접 자신의 평가나 의견을 전달하는 행동이다. 좋아요, 싫어요, 신고, 평가 점수, 의견 입력 등이 해당한다.

암묵적 피드백(Implicit Feedback)은 서비스 이용 행동에서 간접적으로 추정한 반응이다. 동일한 질문의 반복, 생성한 초안 수정, 담당자 연결 등이 해당한다.

| 피드백 | 추정할 수 있는 상황 | 해석 시 주의할 점 |
|---|---|---|
| 싫어요 | 답변에 불만이 있다. | 정확한 답을 받았지만 안내된 규정이 마음에 들지 않았을 수 있다. |
| 재질문 | 처음 답변으로 문제가 해결되지 않았다. | 관련된 새로운 내용을 추가로 질문했을 수도 있다. |
| 답변 수정 | 생성한 내용에 수정이 필요했다. | 사실 오류 없이 표현만 바꿨을 수도 있다. |
| 담당자 연결 | 챗봇으로 문제를 해결하기 어려웠다. | 처음부터 사람이 처리해야 하는 업무였을 수 있다. |

### 5.2. 피드백과 실제 품질을 구분하기

싫어요 버튼을 누르는 사용자는 전체 사용자 중 일부다. 틀린 답변을 받고도 버튼을 누르지 않을 수 있고, 특정 유형의 불만을 가진 사용자만 적극적으로 반응할 수 있다. 피드백에 응답한 사람의 특성이 전체 사용자와 달라지는 현상을 표본 편향(Sampling Bias)이라고 한다.

따라서 싫어요 비율을 전체 오답률로 사용하기에는 한계가 있다. 사용자의 부정적인 반응이 있는 요청을 우선 검토하고, 피드백이 없는 요청도 무작위로 선정해 평가한다.

피드백과 요청 ID를 연결해 저장하면 문제가 의심되는 요청의 트레이스와 답변 원문을 조사할 수 있다. 이후 확인된 실패를 회귀 평가 세트에 추가한다.

## 6. 데이터 드리프트(Drift): 운영 환경의 변화를 감지하는 방법

### 6.1. 드리프트의 의미와 측정 방법

드리프트는 운영 데이터의 분포가 기준으로 정한 데이터의 분포와 달라지는 현상이다. 분포는 데이터의 값이 어떤 범위에 얼마나 자주 나타나는지를 뜻한다. 질문 길이의 분포, 업무 주제별 질문 비율, 검색 유사도 점수의 분포 등을 비교할 수 있다.

서비스 출시 초기나 안정적으로 운영되던 기간을 기준 기간(Baseline)으로 정하고, 최근 운영 기간의 동일한 지표와 비교한다. 기준 기간과 비교 기간의 길이, 표본 수, 요일이나 계절의 영향을 고려한다. 기준에 사용한 측정 방식도 유지해야 한다.

LLM 서비스에서는 질문이 들어오고 검색과 생성이 진행되는 주요 구간에 각각 감지 지표를 설정할 수 있다.

```text
사용자 질문 ───→ 임베딩 ───→ 문서 검색 ───→ LLM 생성 ───→ 답변
     │              │              │              │
 입력 드리프트   임베딩 드리프트  근거 문서 드리프트  출력 드리프트
```

드리프트는 조사해야 할 변화가 발생했다는 신호다. 변화한 질문에서도 정확한 답변을 제공하고 있다면 서비스 품질은 유지되고 있을 수 있다. 실제 품질 저하 여부는 응답, 근거, 평가 결과를 확인해 판단한다.

### 6.2. 입력 드리프트(Input Drift)

서비스에 들어오는 질문과 사용자의 구성이 달라지는 현상이다. 원문에서 직접 계산할 수 있는 지표부터 확인한다.

| 측정 항목 | 파악할 수 있는 변화 |
|---|---|
| 사용자 부서별 요청 비율 | 기존과 다른 부서가 서비스를 이용하는지 |
| 질문 길이의 중앙값·p95 | 길고 복잡한 질문이 늘어났는지 |
| 언어·문자 구성 | 다른 언어나 영문이 혼용된 질문이 늘어났는지 |
| 주제별 질문 비율 | 특정 업무에 대한 수요가 달라졌는지 |
| 신규 단어 비율 | 기준 기간에는 없었던 용어나 표현이 늘어났는지 |

새로운 용어가 늘었다면 신사업이나 새 업무가 추가됐을 가능성이 있다. 질문이 길어졌다면 문서나 이메일을 통째로 입력하는 사용자가 많아졌을 수 있다. 긴 입력은 컨텍스트 길이, 검색 성능, 추론 비용에도 영향을 줄 수 있으므로 품질 지표와 함께 확인한다.

### 6.3. 임베딩 분포 드리프트(Embedding Drift)

질문의 의미를 벡터로 변환한 임베딩(Embedding)을 이용해 질문 주제나 의미의 변화를 탐지한다. 질문 길이나 언어가 비슷하더라도 실제로 묻는 내용은 크게 달라질 수 있기 때문이다.

기준 기간 질문들의 임베딩과 최근 질문들의 임베딩을 같은 모델로 계산하고 두 집단의 분포를 비교한다.

가장 간단한 방법은 각 기간의 평균 임베딩 벡터를 구하고, 두 평균 벡터 사이의 코사인 거리 등을 측정하는 것이다. 거리가 커질수록 질문의 의미 구성이 달라졌을 가능성이 높다. 다만 서로 다른 방향의 주제 변화가 평균에서 상쇄될 수 있으므로 평균 벡터만으로 전체 분포를 설명하기에는 한계가 있다.

질문을 의미가 비슷한 군집(Cluster)으로 나눈 뒤 군집별 질문 비율이나 기존 군집에서 멀리 떨어진 질문의 수를 비교하는 방법도 있다. 기준 질문들과 거리가 먼 실제 질문을 확인하면 어떤 새로운 업무 주제가 늘어났는지 조사할 수 있다.

강의에서 소개하는 또 다른 방법은 도메인 분류기(Domain Classifier)다. 여기서는 질문이 어느 업무 도메인인지 맞히는 것이 아니라 어느 기간의 데이터인지 구분하도록 분류기를 학습한다.

1. 기준 기간의 질문에 0, 최근 기간의 질문에 1이라는 라벨을 부여한다.
2. 두 집단의 질문 임베딩을 이용해 이진 분류기를 학습한다.
3. 학습에 사용하지 않은 질문에서도 두 기간을 잘 구분하는지 확인한다.

두 집단을 쉽게 구분한다면 질문 분포에 차이가 있다는 단서가 된다. 클래스 수를 균형 있게 구성하고 검증 데이터로 평가해야 한다. 임베딩 모델이나 전처리를 변경했을 때는 같은 방식으로 비교 벡터를 다시 계산하거나 기준선을 재설정해야 한다.

### 6.4. 근거 문서 드리프트(Retrieval / Evidence Drift)

RAG가 검색하는 문서의 종류, 순위, 유사도 점수 등이 기존과 달라지는 현상이다. 강의에서는 근거 문서 드리프트라고 설명한다.

검색 품질에 이상이 있는지 확인하기 위해 검색 1순위 문서의 유사도 중앙값, p5, 문서별 검색 빈도, 적절한 근거를 찾지 못한 비율 등을 비교한다. p5는 측정값의 낮은 쪽 5%에 해당하는 경계로, 일부 검색 요청에서 유사도가 유난히 낮아지는 변화를 확인할 때 활용할 수 있다.

유사도 점수가 높을수록 유사하다고 정의한 검색 방식에서 상위 문서의 점수가 낮아지는 경우에는 새로 등장한 질문에 답할 문서가 부족하거나 문서 인덱스 갱신 과정에서 문제가 발생했을 가능성을 조사한다.

질문 분포가 그대로인데 검색 결과만 달라졌다면 문서 개정, 재인덱싱, 청킹 방식, 임베딩 모델 또는 검색 설정 변경 이력을 먼저 확인한다.

유사도 점수의 의미와 범위는 검색 모델과 점수 계산 방식에 따라 다르다. 다른 임베딩 모델이나 거리 계산 방식의 점수를 그대로 비교하지 않도록 주의한다. 높은 유사도 역시 해당 문서가 질문의 정확한 답을 포함한다는 보장은 없으므로 실제 검색 문서를 검토해야 한다.

### 6.5. 출력 드리프트(Output Drift)

서비스가 생성하는 답변의 특징이 기존과 달라지는 현상이다. 참조 답이 없어도 대부분의 요청에서 계산할 수 있는 지표가 많다.

| 측정 항목 | 확인하는 이유 |
|---|---|
| 형식 준수율 | 응답을 처리하는 후속 프로그램에서 오류가 발생할 가능성을 감지한다. |
| 응답 길이 중앙값·p95 | 전체 응답 또는 일부 긴 응답의 길이 변화를 확인한다. |
| 생성 상한 도달 비율 | 최대 토큰 수 제한 등으로 답변이 중간에 끝나는 요청이 늘었는지 확인한다. |
| 답변 거절 비율 | 근거 부족 등을 이유로 답변을 보류하는 빈도의 변화를 확인한다. |
| 출력 언어 | 지정한 언어를 유지하는지 확인한다. |

p95는 측정값의 약 95%가 해당 값 이하에 위치하는 경계다. 응답 길이의 중앙값이 그대로여도 p95가 높아졌다면 길이가 긴 응답에서 변화가 발생했을 가능성이 있다.

거절 비율이 높아지면 정상적으로 답할 수 있는 질문을 거절하는지 조사한다. 반대로 거절 비율이 지나치게 낮아졌다면 근거가 없는 상황에서도 답변을 생성하고 있는지 확인한다.

출력 분포가 달라지면 최근 변경된 모델, 프롬프트, 생성 파라미터 등을 확인하고 실제 답변을 읽어 품질에 미친 영향을 판단한다.

## 7. 드리프트가 발견되면 무엇부터 조사해야 하는가

### 7.1. 여러 지표를 함께 비교해 원인 후보 좁히기

RAG에서는 입력, 검색, 생성이 연결되어 있어 한 단계의 문제가 다른 단계의 지표에도 영향을 줄 수 있다. 어떤 지표가 먼저 변했는지, 최근 어떤 구성 요소를 변경했는지 확인하면 조사 순서를 정할 수 있다.

| 관찰한 변화 | 우선 조사할 원인 | 확인할 내용 |
|---|---|---|
| 입력·임베딩 분포가 변화 | 사용자 및 업무 주제의 변화 | 신규 질문 유형, 기준에서 멀어진 질문 목록 |
| 입력·임베딩·검색 결과가 함께 변화 | 기존 문서에 없는 업무 주제의 증가 | 새로운 부서나 질문 유형, 검색된 문서와 근거 부족 비율 |
| 검색 결과만 변화 | 문서 또는 검색 시스템 변경 | 문서 개정, 인덱스 버전, 재인덱싱·검색 설정 이력 |
| 출력만 변화 | 생성 단계의 설정 또는 모델 변경 | 프롬프트, 생성 파라미터, 배포 이력과 모델 버전 |
| Judge 점수만 변화 | 평가 체계의 변경 또는 품질 지표에서 드러나지 않은 오류 | Judge 버전, 보정 세트, 실제 답변 |

이 표는 원인을 확정하기 위한 기준이 아니라 먼저 조사할 항목을 정하는 기준이다. 실제 요청 트레이스와 변경 이력을 함께 검토해야 한다.

예를 들어 프롬프트 변경 후 잘못된 답변이 증가하면 사용자들이 같은 질문을 반복할 수 있다. 그 결과 입력 분포도 뒤늦게 바뀐다. 입력 드리프트만 확인하면 사용자의 질문 변화가 최초 원인이라고 잘못 판단할 수 있다. 지표의 변화 시점과 요청별 처리 기록을 대조해 선후 관계를 구분해야 한다.

### 7.2. 실패한 RAG 요청을 추적하는 순서

사내 규정 도우미에서 틀린 신청 마감 시간이 안내되었다고 가정하자.

먼저 질문과 답변을 확인하고 현재 규정에서 정확한 참조 답을 확인한다. 해당 요청의 Trace ID를 찾아 검색 결과를 확인한 뒤 어떤 문서가 생성 모델의 컨텍스트에 실제로 포함되었는지 조사한다.

오래된 규정이 검색되었다면 문서 동기화, 인덱스 갱신, 검색 순위 등을 점검한다. 최신 규정을 정확하게 검색했는데 잘못 답했다면 프롬프트 구성과 생성 모델의 응답을 확인한다. 실제 답변이 맞는데 평가 모델만 틀렸다고 판정했다면 평가 기준과 Judge를 검토한다.

수정 후에는 동일한 사례를 다시 실행하고 다른 기존 질문도 함께 평가한다. 특정 실패 사례만 고치는 과정에서 다른 유형의 질문의 품질이 저하되지 않았는지 확인하기 위해서다.

## 8. Phoenix를 활용한 LLM 품질 평가와 실험 관리

### 8.1. Phoenix의 주요 기능

Arize Phoenix는 LLM 애플리케이션의 실행 과정을 추적하고 응답 품질을 평가하는 오픈소스 플랫폼이다. 서비스가 어떤 과정을 거쳐 답변을 생성했는지 확인하고, 변경 전후의 결과를 비교하는 데 사용한다.

| 기능 | 활용 방법 |
|---|---|
| Traces / Spans | 요청별 검색·생성 과정, 시간, 오류, 기록된 입출력 등을 확인한다. |
| Datasets | 반복 평가할 질문과 참조 답, 근거 정보 등을 저장한다. |
| Evaluations | 코드 검사, LLM Judge, 사람의 검토 결과 등을 기록한다. |
| Experiments | 같은 데이터셋으로 특정 버전의 애플리케이션을 실행하고 결과를 비교한다. |

Phoenix에서 평가 결과와 개별 요청의 트레이스를 함께 확인하면 실패 사례의 원인 조사와 재평가를 연결할 수 있다. 업무별 참조 답, 평가 기준, 계측할 항목, 저장할 정보는 서비스 개발자와 운영자가 구성해야 한다.

### 8.2. 오늘 강의에서 제시한 실습 흐름

실습은 사내 규정 도우미 RAG 서비스를 실제로 실행하면서 품질을 검사하고, 프롬프트를 변경한 뒤 동일한 평가 세트로 비교하는 방식으로 구성된다.

| 단계 | 수행 내용 | 확인할 결과 |
|---|---|---|
| 1. 평가 세트 작성 | 질문, 사용자, 참조 답, 근거 문서를 준비한다. | 업무 기준에 맞는 평가 사례가 구성됐는가? |
| 2. 서비스 실행 | 소형 언어 모델을 활용한 RAG 서비스와 관측 환경을 준비한다. | 실제 답변과 실행 기록이 생성되는가? |
| 3. 기준 평가(Baseline) | 기존 프롬프트로 준비한 질문에 답변하고 평가한다. | 전체 점수와 개별 문항의 성공·실패 여부 |
| 4. 프롬프트 변경 | 개선할 항목을 정해 프롬프트를 수정한다. | 변경 내용과 버전이 명확한가? |
| 5. 비교 실험 | 동일한 평가 세트와 기준으로 수정된 RAG를 평가한다. | 개선된 문항, 새로 실패한 문항, 유지된 문항 |
| 6. 실패 조사 | Phoenix에서 실패 요청의 검색·생성 트레이스를 확인한다. | 실제 실패한 처리 단계와 원인 후보 |
| 7. 회귀 사례 추가 | 발견한 실패를 재현할 질문과 판정 기준을 저장한다. | 다음 배포에서도 해당 문제를 검사할 수 있는가? |
| 8. 결과 보관 | 평가 결과, 설정, 버전 및 검토 내용을 기록한다. | 실험의 비교 조건과 변경 이력을 확인할 수 있는가? |

숫자나 문서 ID를 확인하는 자동 검사에 통과한 답변이라도 실제 응답 원문을 읽어야 추가 조건, 단위, 문맥 등을 제대로 안내했는지 확인할 수 있다.

이 실습의 목적은 Phoenix에서 높은 점수를 얻는 것보다 평가 기준을 작성하고, 실제 서비스의 검색과 생성 결과를 구분해 조사하며, 개선 결과를 동일한 조건으로 검증하는 과정에 익숙해지는 것이다.

## 학습을 마친 뒤 설명할 수 있어야 하는 내용

| 확인 질문 | 핵심 답변 |
|---|---|
| 정적 평가와 회귀 평가를 왜 수행하는가? | 같은 입력과 기준으로 서비스 변경 전후를 비교하고 기존 품질 저하를 발견하기 위해 수행한다. |
| 정답이 없는 운영 요청은 어떻게 평가하는가? | 규칙 검사, LLM Judge, 사용자 반응, 분포 비교, 사람 검토를 조합한다. |
| 평가 데이터셋과 Judge 보정 세트는 어떻게 다른가? | 평가 데이터셋은 서비스 품질을, 보정 세트는 평가 모델의 판정 능력을 검사한다. |
| Judge 교체 시 무엇을 확인하는가? | 사람 판정과의 일치율, 불량 탐지율, 기존 Judge와 동일 응답에 대한 판정 차이 등을 확인한다. |
| Trace와 Span은 어떻게 다른가? | Trace는 요청 전체의 처리 과정, Span은 개별 처리 작업의 기록이다. |
| OpenTelemetry와 Phoenix의 역할은 무엇인가? | OpenTelemetry는 관측 정보의 생성·수집·전달을 지원하고, Phoenix는 실행 기록 조회와 LLM 품질 평가를 연결한다. |
| 드리프트가 감지되면 품질 저하를 어떻게 확인하는가? | 변화한 구간의 실제 질문·검색 결과·답변·평가 결과를 검토하고 변경 이력을 확인한다. |
| 운영 중 발견한 실패를 어떻게 활용하는가? | 실패 사례와 현재 업무 기준을 회귀 평가 세트에 추가해 수정 후와 다음 배포 전 동일 문제를 검사한다. |

## 핵심 정리

LLM 서비스의 품질은 출시 전 평가뿐 아니라 운영 중에도 지속적으로 검증해야 한다. 규칙 기반 평가와 LLM Judge로 이상 사례를 찾아내고, 드리프트 지표와 트레이스를 통해 변화가 발생한 원인을 조사한다. 서비스를 수정한 뒤에는 동일한 평가 세트로 변경 효과를 확인하고, 운영에서 발견한 실패 사례를 회귀 평가 세트에 추가한다.
