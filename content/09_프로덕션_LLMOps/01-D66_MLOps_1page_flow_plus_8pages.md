## MLOps의 전체 흐름

챗봇을 만들고 나면 모델이나 프롬프트를 바꾸면서 답변을 개선하게 됩니다. 그런데 설정을 바꿀 때마다 확인할 것이 생깁니다. 답변이 실제로 좋아졌는지, 평가할 때 쓴 설정이 서버에도 적용됐는지, 문제가 생기면 이전 상태로 돌아갈 수 있는지 알아야 합니다.

MLOps는 이렇게 모델을 실험하고 실제 서비스에서 사용하는 동안 필요한 기록과 절차를 마련하는 일입니다. 이 수업에서는 그중에서도 실험 결과를 저장하고, 사용할 모델과 설정을 고른 뒤, 버전 번호를 붙여 보관하는 과정을 배웁니다.

먼저 기존 설정과 새 설정을 비교합니다. 기존 설정을 기준선, 새로 시험할 설정을 후보라고 부릅니다. 둘의 차이를 알려면 같은 질문을 주고 같은 기준으로 채점해야 합니다. 청크 수를 바꾼 효과를 보고 싶다면 모델이나 장비 등 다른 조건도 맞춰야 하고요.

평가가 끝나면 점수와 당시 조건을 함께 저장합니다. 어떤 모델을 썼는지, 어떤 질문을 풀었는지, GPU와 설정값은 무엇이었는지 적습니다. 실제 답변과 원본 결과 파일도 첨부합니다. 그래야 나중에 점수를 다시 보면서 그 결과가 어떻게 나왔는지 확인할 수 있습니다. 이번 수업에서는 MLflow라는 도구로 이 기록을 모읍니다.

그다음에는 어떤 모델과 설정을 사용할지 고릅니다. 정답률뿐 아니라 응답 시간, 중요한 질문에서 발생한 오류도 살펴봅니다. 선택한 모델의 정보와 설정을 등록할 때는 버전 번호를 붙입니다. 기존 설정은 버전 1, 새 설정은 버전 2처럼 구별해 두는 것입니다. 어느 평가 결과를 보고 골랐는지도 함께 남깁니다.

여러 버전 중 지금 사용할 버전에는 **‘운영’**이라는 이름을 지정합니다. 버전 2를 쓰기로 했다면 ‘운영’이 버전 2를 가리키게 합니다. 나중에 버전 1로 돌아가고 싶으면 이 이름이 가리키는 대상을 바꿀 수 있습니다. 이렇게 특정 버전을 가리키는 이름을 별칭이라고 합니다.

실제 서비스에 적용할 때는 서버도 해당 모델과 설정을 읽어야 합니다. 이전 버전으로 되돌릴 때 역시 서버가 그 설정을 불러왔는지, 정상적으로 답하는지 확인합니다. 사용할 버전을 지정한 뒤에는 실제 서버의 응답까지 확인해야 복구 여부를 알 수 있습니다.

서비스를 운영하는 동안에는 답변 품질과 응답 시간, 오류를 계속 살펴봅니다. 문제가 발견되면 그때 사용한 버전과 평가 기록을 찾아봅니다. 무엇이 달라졌는지 확인한 뒤 다시 수정하고 평가하는 과정이 이어집니다.

실험 결과와 조건을 저장한다 → 결과를 비교한다 → 사용할 모델과 설정을 고른다 → 버전별로 보관한다 → 서버에 적용하고 확인한다.

오늘의 기본 실습은 CPU에서 만든 모의 결과 파일로 이 중 기록, 비교, 버전 등록과 별칭 변경을 연습합니다. 이 문서는 이론 자료를 풀어 쓴 것으로, 별도 코드 레슨을 실행한 결과는 포함하지 않았습니다.

## 모델을 만든 뒤에도 계속 확인할 것들

### 평가가 끝나도 확인할 일이 남습니다

모델 개발에서는 데이터를 준비하고, 학습하거나 설정을 바꾼 뒤, 결과가 좋아졌는지 평가합니다. 서비스를 운영할 때는 선택한 모델로 실제 요청을 받아 답합니다. 답변이 늦어지거나 오류가 생기면 원인을 찾아 수정해야 합니다.

개발할 때 좋은 결과가 나왔더라도 서버에 다른 설정이 들어가 있으면 같은 성능을 기대하기 어렵습니다. 그래서 평가에 쓴 모델과 설정을 정확히 남기고, 배포할 때 서버가 같은 것을 사용하는지 확인합니다. 여기서 배포는 프로그램과 필요한 파일을 서버에 준비해 사용자의 요청을 처리할 수 있게 하는 작업입니다.

서비스를 운영하다 문제가 생겼을 때도 이 기록을 사용합니다. 사용자가 잘못된 답변을 받았다면 어느 모델과 프롬프트를 썼는지 알아야 원인을 조사할 수 있습니다. 평가에 쓴 모델과 설정을 서버에도 적용하고, 서버에서 문제가 생기면 당시 기록을 찾아보는 것이 MLOps의 중요한 역할입니다.

### 점수만 저장하면 나중에 설명하기 어렵습니다

‘정답 22개’라는 기록을 다시 읽는다고 생각해 보세요. 전체 문제가 몇 개였는지, 어떤 질문을 풀었는지, 모델을 바꿨는지 프롬프트를 바꿨는지가 빠져 있으면 결과를 해석하기 어렵습니다. 응답 시간이 줄었다고 해도 GPU가 달랐다면 그 이유를 다시 살펴봐야 합니다.

그래서 결과와 함께 다음 항목을 남깁니다.

| 달라질 수 있는 항목 | 저장할 내용 |
| --- | --- |
| 프로그램 코드 | 실행한 코드의 커밋 번호나 사본 |
| 설정값 | 모델에 제공한 문서 조각 수, 답 길이 상한 등 |
| 데이터 | 사용한 문서, 평가 질문, 검색 인덱스의 버전 |
| 모델 | 모델 이름, 정확한 수정본, 모델 파일과 어댑터의 위치 |
| 실행 환경 | GPU 종류, 라이브러리와 서빙 엔진의 버전 |

커밋 번호는 코드의 특정 수정 상태를 찾아가는 번호입니다. 모델 저장소에서 사용하는 리비전도 특정 수정본을 가리킵니다. 파일 내용으로 계산한 해시를 함께 남기면 같은 이름의 파일이 나중에 바뀌었는지도 확인하기 쉽습니다.

이 기록은 비교할 출발점을 알려 줍니다. 규정 문서와 서빙 엔진을 동시에 바꿨다면 두 변경 모두 답변에 영향을 줄 수 있습니다. 이전 문서와 엔진 버전을 알아야 한 항목씩 바꾸어 다시 비교할 수 있습니다.

### DevOps에서 모델과 데이터까지 살펴봅니다

DevOps는 개발자와 운영 담당자가 협력하면서 코드 검사와 배포를 반복 가능하게 만드는 방식입니다. MLOps도 이 원칙을 활용합니다. 여기에 학습 데이터, 평가 데이터, 만들어진 모델, 실험 결과를 함께 살펴보는 일이 더해집니다.

머신러닝에서는 프로그램이 오류 없이 실행되어도 답이 틀릴 수 있습니다. 같은 학습 코드를 사용하더라도 학습 데이터가 달라지면 만들어진 모델의 성능이 달라질 수 있고요. 그래서 코드가 정상인지 검사하는 것과 함께 데이터와 모델의 품질도 확인합니다.

LLM을 사용하는 서비스도 마찬가지입니다. 모델 파일을 그대로 두고 프롬프트나 검색 문서만 바꾸어도 답이 달라질 수 있습니다. 모델 이름 외에 무엇을 함께 사용했는지 적어 두는 이유입니다.

처음 시작할 때는 현재 답하기 어려운 질문을 찾아보면 됩니다. 어떤 설정으로 낸 점수인지 모르겠다면 원본 파일에서 조건을 확인합니다. 어떤 후보를 골랐는지 불분명하다면 선택한 설정과 이유를 적습니다. 이전 상태로 돌아가기 어렵다면 필요한 모델 파일과 설정을 먼저 보관합니다.

MLflow는 이런 정보를 저장하고 다시 찾는 일을 도와줍니다. 어떤 점수를 통과 기준으로 삼을지, 누가 새 버전을 적용할지, 변경 후 무엇을 검사할지는 팀이 정해야 합니다. 다른 팀원도 기록을 보고 왜 그 모델을 골랐는지 이해하고, 같은 설정으로 실행할 수 있어야 합니다.

## 실험 결과를 MLflow에 어떻게 저장하나요?

### 한 번의 평가에서 나온 내용을 한곳에 모읍니다

MLflow에서는 한 번의 실험이나 평가에 관한 기록을 run이라고 부릅니다. run에는 당시 사용한 설정과 측정값, 원본 파일을 함께 넣습니다. 각 run에 붙는 run ID로 나중에 같은 기록을 다시 찾을 수 있습니다.

같은 목적의 run을 모아 놓는 그룹은 experiment입니다. 예를 들어 같은 챗봇의 설정을 비교했다면 기준선과 여러 후보의 run을 하나의 experiment에서 함께 볼 수 있습니다. 큰 분류가 experiment이고, 개별 평가의 기록이 run인 셈입니다.

이번 수업에서는 이미 파일에 들어 있는 예제 결과를 읽어서 run으로 저장합니다. run을 등록할 때 하는 일은 그 결과와 조건을 MLflow에 옮겨 적는 것입니다.

### 설정, 점수, 설명, 파일을 구분해서 넣습니다

MLflow의 항목 이름은 낯설지만, 무엇을 저장하는지 보면 구분하기 쉽습니다.

| 항목 | 무엇을 넣나요? | 교안에서 사용하는 내용 |
| --- | --- | --- |
| params | 실행 전에 정한 설정값 | 정밀도, 문서 조각 수, 생성할 토큰 수 상한 |
| metrics | 실행 후 얻은 수치 | 정답 수, 응답 시간, 초당 생성 토큰 수 |
| tags | 결과의 출처와 조건을 설명하는 정보 | 모델 이름, GPU, 질문 세트, 실측·모의 구분 |
| artifacts | 나중에 다시 열어 볼 파일 | 결과 JSON·CSV, 설정 파일, 실제 답변, 모델 카드 |

여기서 params는 사람이 정한 실험 설정을 뜻합니다. 학습된 모델의 가중치는 모델 파일과 버전으로 따로 확인합니다. 같은 ‘파라미터’라는 말이 나와도 지금 무엇을 가리키는지 구분하면 됩니다.

metrics에는 수치의 의미와 단위가 드러나야 합니다. 응답 시간 3.1을 저장했다면 초인지 밀리초인지, 평균인지 p50인지 함께 알아볼 수 있어야 합니다. artifacts에 원본 결과를 첨부하면 요약된 숫자뿐 아니라 문항별 답변도 다시 읽을 수 있습니다.

이렇게 저장하면 한 run에서 어떤 설정을 썼는지, 점수가 얼마였는지, 어디서 나온 결과인지, 실제 답변은 어땠는지를 확인할 수 있습니다.

### 파일마다 다른 형식을 읽어서 옮깁니다

교안에는 양자화, 서빙, RAG 등에서 얻은 결과를 흉내 낸 여러 형식의 파일이 나옵니다. 어떤 파일은 조건을 _conditions에 두고, RAG 파일은 meta에 둡니다. 먼저 각 파일에서 설정과 결과가 어디에 있는지 찾은 뒤 위의 네 항목으로 나누어 저장합니다.

RAG는 질문에 관련된 문서를 검색해서 모델이 답변할 때 참고하도록 주는 방식입니다. 교안의 RAG 파일에서 meta는 모델과 환경 등의 설명을, runs는 기준선과 후보의 결과를 담고 있습니다.

cfg.keep는 모델에 제공할 문서 조각 수입니다. cfg.max_tokens는 답변으로 생성할 토큰 수의 상한입니다. 문항별 ok는 답을 맞혔는지, hit는 필요한 근거를 검색했는지 나타냅니다. 이런 항목을 읽어야 점수와 설정을 정확히 옮길 수 있습니다.

단위도 확인합니다. 교안의 RAG 예제에서는 응답 시간을 밀리초로 기록했습니다. 실습에서는 이 값을 1,000으로 나누어 초로 바꿉니다. 변환한 값과 원본 파일을 함께 남겨 두면 나중에 계산이 맞는지 확인할 수 있습니다.

### 원본에서 확인한 것만 기록합니다

과거 결과에 GPU 이름이 빠져 있다면 ‘미확인’으로 남깁니다. 지금 접속한 컴퓨터의 GPU를 넣으면 당시와 다른 조건을 기록하게 됩니다. 실제로 측정한 결과인지, 연습용으로 만든 모의 결과인지도 표시합니다.

트래킹 서버는 이런 정보를 저장하거나 조회해 달라는 요청을 받는 프로그램입니다. 실행 정보는 데이터베이스에, 첨부한 파일은 아티팩트 저장소에 보관합니다. 나중에 기록을 다시 열려면 두 저장 위치를 모두 유지해야 합니다.

## 점수를 비교하기 전에 확인할 것

### 바꿀 항목과 그대로 둘 항목을 정합니다

모델에 주는 문서 조각을 5개에서 3개로 줄였을 때 답변이 어떻게 달라지는지 알고 싶다고 해봅시다. 이 경우 비교하려는 것은 문서 조각 수입니다. 두 설정에 같은 질문을 주고, 같은 모델과 장비를 사용해야 바꾼 설정의 영향을 살펴보기 쉽습니다.

모델을 교체하는 실험이라면 이번에는 모델이 달라져야 합니다. 대신 질문, 채점 기준, 검색 방식 등 다른 조건을 맞춥니다. 무엇을 바꿀지는 실험의 목적에 따라 정하고, 나머지 조건이 결과에 영향을 주었는지도 살펴보는 것입니다.

여러 항목을 한꺼번에 바꾸었다면 결과는 비교할 수 있어도 무엇 때문에 좋아졌는지 설명하기 어려울 수 있습니다. 이때는 확인한 차이를 적고, 원인을 알려면 어떤 조건으로 다시 평가해야 하는지 정합니다.

### 정답률과 응답 시간은 서로 다른 조건을 살펴봅니다

정답 수를 볼 때는 전체 문제 수도 함께 봅니다. 20/25는 80%이고, 28/30은 약 93.3%입니다. 두 값이 서로 다른 질문에서 나온 결과라면 질문의 내용과 난이도, 채점 기준부터 확인해야 합니다. 질문 원본과 그 버전을 보관하는 이유가 여기에 있습니다.

속도를 비교할 때는 GPU와 입력 길이, 답변 길이, 동시에 보낸 요청 수도 중요합니다. 답변을 짧게 만들면 처리 시간이 줄어들 수 있고, 동시에 요청이 몰리면 대기 시간이 늘어날 수 있습니다. 모델이나 엔진의 차이를 판단하려면 이런 측정 조건도 함께 읽어야 합니다.

### 지표는 무엇을 보여 주는 숫자인지 알아야 합니다

p50은 응답 시간을 짧은 순서대로 놓았을 때 가운데에 해당하는 값입니다. 흔히 중앙값이라고 부릅니다. p95는 측정 요청의 약 95%가 그 시간 이내에 끝났다는 기준입니다. p50으로 전반적인 응답 속도를 보고, p95로 오래 기다린 요청의 상태를 함께 살펴볼 수 있습니다.

처리량은 일정한 시간에 얼마나 많이 처리했는지 나타냅니다. 요청 수를 세면 요청/초, 생성한 토큰 수를 세면 토큰/초입니다. p50은 p50끼리, 같은 단위의 처리량은 서로 같은 측정 조건에서 비교해야 의미를 읽기 쉽습니다.

### 교안의 숫자를 직접 읽어봅니다

다음 값은 이번 수업에서 기록과 비교를 연습하도록 만든 모의 결과입니다.

| 항목 | 기존 설정인 기준선 | 새로 시험할 후보 |
| --- | --- | --- |
| 정답 수 | 20/25 | 22/25 |
| 정답률 | 80% | 88% |
| p50 응답 시간 | 6.2초 | 3.1초 |

표에서는 정답이 2개 늘었고, 정답률은 8%포인트 높아졌습니다. p50은 절반으로 줄었습니다. 여기까지는 적힌 숫자로 계산할 수 있습니다. 다만 이 값은 모의 자료이고, GPU나 패키지 정보도 일부 비어 있습니다. 실제 성능을 판단할 때는 직접 측정한 결과와 당시 조건을 확인해야 합니다.

전체 정답 수 다음에는 어떤 문항의 답이 달라졌는지 봅니다. 예전에는 맞혔지만 이번에는 틀린 문항도 있을 수 있기 때문입니다. 같은 문항의 판정이 정답에서 오답으로, 또는 오답에서 정답으로 바뀐 사례를 flip이라고 합니다.

문항별 ok와 hit를 함께 보면 답을 맞혔는지와 필요한 근거를 찾았는지를 따로 살펴볼 수 있습니다. 잘못된 답이 나온 문항을 직접 읽으면서 검색과 답변 중 어느 부분을 더 확인할지도 정합니다.

### 사용할 후보를 고를 때는 이유도 남깁니다

어떤 후보를 쓸지는 서비스의 목적에 맞춰 결정합니다. 정답률이 높아졌어도 응답이 지나치게 느려졌다면 조정이 필요합니다. 빨라졌더라도 중요한 질문에서 새 오류가 생겼다면 해당 답변을 더 살펴봐야 합니다.

선택할 때는 비교한 run, 바꾼 설정, 결과, 선택 이유를 적습니다. 확인하지 못한 조건도 함께 남깁니다. 다른 팀원이 이 기록을 읽으면 어떤 결과를 보고 그 모델과 설정을 골랐는지 이해할 수 있습니다.

## 모델과 설정을 버전별로 저장하고 되돌리기

### 선택한 모델과 설정을 다시 찾을 수 있게 저장합니다

평가가 끝나면 사용할 모델과 설정을 고릅니다. 이때 기존 설정과 새 설정을 각각 등록하고 버전 번호를 붙여 둡니다. 교안에서는 사내 규정 RAG의 기준선을 버전 1로, 선택한 새 설정을 버전 2로 구별하는 방식으로 설명합니다.

각 버전에는 평가 결과를 다시 찾아갈 수 있도록 run ID도 남깁니다. 버전 2를 열어 해당 run을 확인하면 어떤 설정으로 몇 개를 맞혔고 응답 시간은 얼마였는지 볼 수 있습니다. run에는 평가 내용을 저장하고, 버전에는 나중에 사용할 모델과 설정을 구별해서 등록합니다.

MLflow의 **모델 레지스트리(Model Registry)**는 이렇게 등록한 버전들을 모아 보는 기능입니다. 이번 수업에서는 RAG 설정과 관련 평가 기록을 등록합니다. 실제 모델 파일은 어디에 보관했는지, 정확히 어느 파일을 사용할지도 따로 적어 두어야 합니다.

### ‘운영’과 ‘직전’은 특정 버전을 가리키는 이름입니다

여러 버전을 보관했다면 그중 무엇을 사용할지 정해야 합니다. 이때 특정 버전을 가리키도록 붙이는 이름을 **별칭(alias)**이라고 합니다.

| 교안의 별칭 | 가리키는 버전 | 뜻 |
| --- | --- | --- |
| 운영 | 버전 2 | 지금 사용하기로 선택한 모델과 설정 |
| 직전 | 버전 1 | 필요하면 다시 사용할 이전 모델과 설정 |

버전 2에 문제가 생겨 이전 선택으로 돌아가려면 ‘운영’이 버전 1을 가리키도록 바꿉니다. 무엇에서 무엇으로 바꿨는지와 변경 이유도 남깁니다. 이전에 검증한 상태로 되돌리는 작업을 **롤백(rollback)**이라고 합니다.

### 서버가 이전 설정으로 답하는지까지 확인합니다

별칭을 바꾸면 레지스트리에서 선택한 버전이 달라집니다. 실제로 답변하는 서버는 변경 내용을 다시 읽고 해당 모델과 설정을 불러와야 합니다. 검색 인덱스 등 필요한 파일도 사용할 수 있어야 합니다.

따라서 복구할 때는 서버가 버전 1을 읽었는지 확인한 다음 실제 질문을 보내봅니다. 이전 설정으로 정상 응답하는지 검사해야 복구가 끝났는지 알 수 있습니다. 서버가 언제 별칭을 읽는지에 따라 반영 시점도 달라질 수 있습니다.

여기에는 서로 다른 두 시간이 있습니다. 별칭 변경 시간은 레지스트리에서 가리키는 버전을 바꾸는 데 걸린 시간입니다. 실제 복구 시간은 서버가 이전 설정으로 정상 응답할 때까지 걸린 시간입니다. 오늘의 기본 실습에서는 별칭을 바꾸기 전후의 상태를 확인합니다.

### 레지스트리, 서빙 서버, 게이트웨이가 각각 할 일

레지스트리에서는 사용할 모델과 설정의 버전을 찾습니다. 서빙 서버는 그 모델을 실행해 답변을 만듭니다. API 게이트웨이는 들어온 요청을 어느 서버로 보낼지 결정합니다. 선택한 모델을 서버에 준비한 뒤 요청을 그 서버로 보내도록 해야 실제 사용으로 이어집니다.

블루-그린 방식에서는 새 서버를 준비한 뒤 그쪽으로 요청을 전환합니다. 카나리 방식에서는 먼저 일부 요청만 새 서버로 보냅니다. 두 경우 모두 새 서버가 준비됐는지와 정상적으로 답하는지 확인합니다.

응답 형식을 바꾸었다면 기존 프로그램과도 호환되는지 검사해야 합니다. 예를 들어 answer를 문자열에서 객체로 바꾸면 그 값을 읽는 프로그램에도 영향을 줄 수 있습니다.

### 어떤 실험과 데이터에서 나온 버전인지 찾아갑니다

운영 중인 버전을 조사할 때는 평가한 run을 찾고, 그 기록에서 모델과 데이터의 출처를 확인합니다. 이렇게 결과물에서 출발해 사용한 입력과 작업을 거슬러 찾아가는 관계를 **계보(lineage)**라고 합니다.

교안은 사용 중인 버전 → 평가 실행 → 모델 카드 → 데이터셋 카드 순서로 설명합니다. 모델 카드에는 원본 모델과 변환 방법, 평가 결과를 적습니다. 데이터셋 카드에는 데이터의 출처와 제작 방법, 한계를 적습니다.

각 문서에 다음 자료의 경로나 식별자가 있어야 끝까지 찾아갈 수 있습니다. 중간에서 찾을 수 없다면 어떤 참조가 빠졌는지 기록합니다. 그래야 운영 중 생긴 문제를 조사할 때 필요한 실험과 파일을 다시 확인할 수 있습니다.

## 어디까지 자동화했는지 살펴보기

### 자동화할 작업이 무엇인지 먼저 봅니다

모든 작업을 사람이 실행하는 팀도 있고, 학습은 자동으로 하지만 배포는 사람이 승인하는 팀도 있습니다. 이런 차이를 단계별로 정리한 것이 MLOps 성숙도 모델입니다. 각 단계에서 어떤 작업을 기록하고 자동화하는지 살펴보면 우리 팀에 필요한 다음 작업을 찾을 수 있습니다.

교안에서는 구글과 마이크로소프트의 분류를 함께 소개합니다. 두 분류는 단계를 나누는 기준이 다릅니다. 숫자를 맞춰 외우기보다는 각 단계에서 새로 할 수 있게 되는 일을 읽으면 이해하기 쉽습니다.

### 구글은 실행 절차와 그 절차를 만드는 코드를 구분합니다

여러 작업을 정해진 순서와 조건에 따라 실행하도록 만든 것을 파이프라인이라고 합니다. 데이터 준비가 끝나면 학습하고, 학습이 끝나면 평가하도록 정하는 방식입니다.

| 구글 수준 | 실제로 어떻게 일하나요? |
| --- | --- |
| 0 | 사람이 데이터 준비, 학습, 평가를 실행하고 결과물을 배포 담당자에게 전달합니다. |
| 1 | 데이터 준비부터 학습·검증까지 파이프라인으로 반복 실행합니다. 사용한 입력과 결과도 기록합니다. |
| 2 | 파이프라인을 만드는 코드가 바뀌었을 때도 자동으로 검사하고 배포합니다. |

수준 1에서는 만들어 둔 절차를 반복해서 실행합니다. 수준 2에서는 그 절차 자체를 수정할 때도 검사를 합니다. 평가 함수를 고쳤다면 새 코드가 정상인지, 전체 파이프라인이 계속 의도한 순서로 실행되는지 확인하는 것입니다.

이때 등장하는 CI/CD는 다음과 같이 구분할 수 있습니다.

CI, 지속 통합: 코드 변경을 합치면서 자동 검사를 실행합니다.

지속적 전달(Continuous Delivery): 검사를 마친 코드를 언제든 배포할 수 있는 상태로 준비합니다. 실제 운영 반영 전에 사람이 승인할 수 있습니다.

지속적 배포(Continuous Deployment): 검사를 통과한 변경을 실제 운영에 적용하는 작업까지 자동으로 수행합니다.

### 마이크로소프트는 학습, 배포, 운영 피드백을 더 나눠 봅니다

| 마이크로소프트 수준 | 핵심 변화 |
| --- | --- |
| 0 · No MLOps | 실험과 배포, 운영 피드백이 따로 움직여 결과를 추적하기 어렵습니다. |
| 1 · DevOps but no MLOps | 앱의 코드 검사와 배포는 개선됐지만 모델의 결과를 추적하는 일은 부족합니다. |
| 2 · Automated training | 학습을 반복 실행하고, 사용한 환경과 학습 결과를 기록합니다. |
| 3 · Automated model deployment | 검증한 모델을 자동으로 배포하고, 모델이 만들어진 출처도 찾아갈 수 있습니다. |
| 4 · Full MLOps automated operations | 운영에서 발견한 변화에 따라 개선 작업과 사용할 버전의 선택까지 정해 둔 정책으로 수행합니다. |

구글은 파이프라인 코드의 검사와 배포를 강조합니다. 마이크로소프트는 모델을 학습하고 배포한 뒤 운영 결과를 다음 작업에 반영하는 과정을 더 세분화합니다. 그래서 같은 숫자라도 어떤 일을 하는지 각각 확인해야 합니다.

한 팀 안에서도 실험 기록은 잘 남기지만 배포는 수동일 수 있습니다. 이런 경우에는 ‘몇 단계 팀’이라는 표현보다 ‘평가 기록은 갖췄고, 배포 확인은 사람이 한다’고 적는 편이 다음 개선점을 찾기 쉽습니다.

### 자동으로 다음 단계에 넘기기 전에 검사합니다

자동으로 실행되는 작업에도 통과 기준이 필요합니다. 평가 점수가 기준을 만족하는지, 응답이 너무 느리지 않은지, 필수 모델 정보가 빠지지 않았는지 검사합니다. 이런 **통과 기준을 게이트(gate)**라고 합니다.

자동화하기 전에는 입력, 검사 기준, 남길 기록, 승인 방식, 복구 대상을 정해야 합니다. 사용자 질문이 달라졌다면 먼저 어떤 변화인지 살펴보고 새 평가가 필요한지 판단합니다. 새 모델을 만들었다면 기존 모델과 비교한 뒤 사용할지를 정합니다.

당장 복구할 버전을 찾기 어렵다면 이전 모델과 설정을 보관하는 일부터 시작합니다. 같은 수동 작업에서 실수가 반복된다면 그 작업의 실행 순서와 실패했을 때 할 일을 정리합니다. 현재 겪는 문제에 맞춰 자동화 범위를 넓혀 가는 것입니다.

## 운영 준비가 됐는지 실제 기록으로 확인하기

### ‘할 수 있다’는 말과 함께 확인한 결과를 보여 줍니다

버전을 잘 관리하고 있다고 말하려면 등록한 버전 목록을 보여 줄 수 있어야 합니다. 이전 상태로 되돌릴 수 있다고 말하려면 무엇으로 되돌렸고 어떤 응답을 확인했는지 기록이 있어야 합니다.

교안의 운영 점검표는 이런 확인을 위해 만든 학습용 목록입니다. 각 항목을 읽으면서 어떤 파일이나 실행 결과를 보면 답할 수 있는지 찾아봅니다.

| 번호 | 확인할 내용 | 살펴볼 기록 |
| --- | --- | --- |
| 1 | 어떤 환경에서 실행했나요? | 설치 조건, 패키지 버전 |
| 2 | 어떤 조건에서 나온 결과인가요? | 모델, GPU, 질문 세트, 설정값 |
| 3 | 평가에 쓴 질문을 다시 볼 수 있나요? | 질문 원본과 버전 |
| 4 | 여러 실험의 결과를 함께 볼 수 있나요? | MLflow의 실행 목록 |
| 5 | 지금 사용할 버전이 정해져 있나요? | ‘운영’ 별칭이 가리키는 버전 |
| 6 | 모델과 설정의 출처, 한계를 설명할 수 있나요? | 모델 카드나 사용 설명 |
| 7 | 다른 사람도 같은 절차를 실행했나요? | 실행 안내와 재실행 결과 |
| 8 | 사용한 데이터와 평가 결과를 찾아갈 수 있나요? | 버전에서 run과 원본으로 이어지는 참조 |

| 10 | 어떤 버전이 답한 요청인지 알 수 있나요? | 응답이나 요청 로그에 남긴 버전 |

| 13 | 운영 중 발견한 변화가 갱신 작업을 시작시키나요? | 경보, 시작 조건, 파이프라인 실행 기록 |

처음부터 모든 항목을 갖추기보다는, 현재 확인할 수 있는 것과 앞으로 확인할 것을 나눕니다. 오늘 기록과 버전 등록까지 연습했다면 자동 배포나 운영 모니터링은 후속 학습에서 이어서 확인할 수 있습니다.

### 실행해서 실패한 것과 아직 확인하지 않은 것을 나눕니다

검사했고 기준을 만족했다면 통과, 검사했지만 기준을 만족하지 못했다면 실패입니다. 아직 실행하지 않았거나 판단할 기록이 부족하다면 미확인으로 둡니다.

다른 팀원이 재실행한 기록이 없다면 같은 절차를 실행할 수 있는지는 미확인입니다. 실제로 실행했는데 설정 파일이 없어 중단됐다면 파일 보관과 실행 안내를 고쳐야 합니다. 두 경우에 필요한 다음 행동이 다르기 때문에 상태를 나눠 적습니다.

교안의 선택 실습에서는 근거가 제출됐는지에 따라 채점 결과가 거짓으로 나올 수 있습니다. 이 값만 보고 동작이 실패했다고 판단하기보다, 실제 오류가 있었는지와 근거가 빠졌는지를 확인합니다.

점검한 뒤에는 어떤 기록을 봤는지, 무엇을 확인했는지, 다음에는 무엇을 해야 하는지를 적습니다. 결과의 조건이 빠져 있으면 원본을 찾아보고, 사용할 버전이 정해져 있지 않으면 선택한 버전과 이유를 남깁니다.

### 기록을 저장한 곳도 계속 사용할 수 있어야 합니다

MLflow의 데이터베이스에는 실행 정보가 들어 있고, 아티팩트 저장소에는 원본 결과와 설정 파일이 들어 있습니다. 나중에 평가 내용을 다시 읽으려면 둘 다 보관해야 합니다. 백업 후에는 필요한 기록과 파일을 실제로 복원해 열어볼 수 있는지도 확인합니다.

권한도 나눕니다. 실험 결과를 읽는 권한과 운영 버전을 바꾸는 권한을 각각 정합니다. 버전을 바꿀 때는 변경한 사람과 대상, 이유를 남깁니다. 실습용 로컬 서버를 팀 공용으로 쓸 때는 인증과 접근 범위, 보관 기간도 정해야 합니다.

자동화할 작업이 늘어나면 서버와 저장소, 업데이트, 장애 대응도 관리해야 합니다. 얼마나 자주 바꾸는지와 담당자가 감당할 수 있는 일을 함께 고려합니다. 변경이 적다면 기록과 검증을 갖춘 수동 절차를 유지할 수 있습니다. 같은 실수가 자주 생기는 작업은 먼저 자동화할 만합니다.

## LLM에서는 모델 외에 무엇을 저장해야 하나요?

### 같은 모델을 써도 답변이 달라질 수 있습니다

LLM 서비스에서는 모델을 다시 학습하지 않고도 많은 것을 바꿀 수 있습니다. 프롬프트에 지시를 추가하거나, 검색할 문서를 갱신하거나, 답변 길이를 줄일 수 있습니다. 이 변화만으로도 답의 내용과 형식, 응답 시간이 달라질 수 있습니다.

그래서 어느 모델을 사용했는지만 적으면 당시 답변을 충분히 설명하기 어렵습니다. 그 모델에 어떤 프롬프트와 문서를 주었고, 어떤 설정으로 답을 만들었는지도 남겨야 합니다. LLMOps는 이런 LLM 서비스의 개발과 운영에서 필요한 실험, 배포, 점검을 다룹니다.

### 함께 보관할 항목을 살펴봅니다

| 항목 | 다시 찾아야 할 내용 |
| --- | --- |
| 모델 | 모델 이름, 정확한 수정본, 실제 파일, 양자화 정밀도 |
| 어댑터 | 어느 원본 모델에 적용했는지, 어댑터 파일과 버전 |
| 프롬프트 | 사용한 시스템 지시와 사용자 템플릿 |
| 검색 | 문서, 청크를 나눈 방법, 임베딩 모델, 검색 인덱스 |
| 서빙 엔진 | 실행한 엔진과 라이브러리 버전, 추론 설정 |
| 평가 자료 | 질문, 정답, 채점 기준과 그 버전 |

어댑터는 추가 학습한 결과를 원본 모델에 적용할 때 사용하는 별도 가중치입니다. 원본 모델이 무엇인지와 어느 어댑터 파일을 사용했는지를 함께 알아야 합니다.

검색 쪽에는 여러 단계가 있습니다. 문서를 작은 조각으로 나누는 것이 청킹, 검색에 쓸 수 있도록 내용을 숫자로 표현하는 것이 임베딩입니다. 검색한 후보 문서를 질문과의 관련성에 따라 다시 정렬하는 작업은 재정렬입니다. 어느 단계의 방법을 바꾸더라도 모델이 참고하는 문서가 달라질 수 있습니다.

각 파일은 따로 보관하되, 저장 위치와 정확한 버전 정보를 함께 적어 두면 됩니다. 특정 수정본을 찾을 수 있도록 리비전이나 해시도 남깁니다. 나중에도 같은 파일을 찾아 사용할 수 있어야 합니다. 파일 이름이나 ‘최신 버전’이라는 표시는 시간이 지나면 다른 내용을 가리킬 수 있으므로 정확한 수정본을 함께 남기는 편이 좋습니다.

### 응답 상태와 답변 내용을 각각 확인합니다

HTTP 200은 서버가 요청을 성공으로 처리했다는 응답 상태입니다. 모델이 올바른 규정을 설명했는지, 근거 문서를 밝혔는지는 답변 내용을 보고 확인합니다. 서비스에 맞는 품질 기준이 따로 필요한 이유입니다.

사내 규정 챗봇이라면 규정이 정확한지와 출처가 표시됐는지가 중요합니다. 상담을 돕는 서비스라면 꼭 알려야 할 내용을 빠뜨리지 않았는지도 봅니다. 형식, 누락, 안전성처럼 정답 수만으로 보기 어려운 항목도 평가 기준에 넣습니다.

프롬프트를 고친 뒤 답변에서 출처가 빠졌다면 바꾸기 전후의 지시와 실제 답변을 읽어봅니다. 다음 평가에서는 출처 표시 여부도 같은 질문 세트로 검사합니다. 자동 채점 기준과 결과를 보관하고, 판단이 애매한 답은 직접 읽습니다.

### 품질과 함께 시간, 처리한 분량을 봅니다

정답률이 같아도 답을 만드는 데 쓴 입력과 출력이 길어졌다면 처리 시간과 자원 사용이 달라질 수 있습니다. 그래서 답변 품질, 응답 시간, 입력·출력 토큰 수를 함께 기록합니다. 토큰 수를 보면 모델이 처리한 문서와 답변의 분량을 살펴볼 수 있습니다.

비용을 비교할 때는 사용 기간과 요청량도 맞춰야 합니다. 학습 비용은 학습할 때 발생하고, 추론 비용은 사용자의 요청을 처리할 때마다 누적됩니다. 어떤 기간에 몇 건의 요청을 처리할 것인지에 따라 비교 결과가 달라집니다.

GPU 임대와 구매를 비교할 때도 장비 가격에 더해 가동 시간과 필요한 용량을 봅니다. 실제 비용 계산에는 직접 측정한 사용량과 가격을 확인한 날짜가 필요합니다. 오늘의 모의 결과로는 기록하는 방법을 익히고, 실제 운영 판단에는 그 환경에서 측정한 자료를 사용합니다.

## 도구를 고르고 실습에서 확인할 것

### 먼저 어떤 일을 편하게 만들고 싶은지 정합니다

실험 결과가 여기저기 흩어져 있어 비교하기 어렵다면 결과를 한곳에 모으는 기능이 필요합니다. 매번 같은 순서로 프로그램을 실행하다 실수한다면 실행 절차를 자동화하는 기능이 필요합니다. 지금 겪는 문제를 먼저 적으면 어떤 도구를 찾아야 할지 분명해집니다.

| 하고 싶은 일 | 도구가 맡는 역할 | 교안에 나오는 도구나 후속 학습 |
| --- | --- | --- |
| 실험 결과와 사용한 모델·설정을 다시 찾기 | 조건과 결과를 저장하고 모델·설정을 버전별로 등록 | MLflow |
| 여러 작업을 순서대로 실행하기 | 작업 순서, 시작 조건, 실패했을 때의 처리를 정함 | Airflow |
| 사용자 요청에 모델로 답하기 | 모델을 불러와 추론을 실행 | vLLM, TensorRT-LLM |
| 운영 중 생기는 문제를 발견하기 | 품질, 응답 시간, 오류 등을 수집하고 살펴봄 | 평가·모니터링 수업 |

MLflow에서 사용할 버전을 골랐다면 배포 절차가 그 버전의 모델과 설정을 가져와 서버를 준비합니다. 서버가 준비되면 요청을 보내고 정상 응답하는지 확인합니다. 도구를 함께 쓸 때는 이처럼 앞에서 고른 모델과 설정을 다음 작업에서도 정확히 사용하도록 만들어야 합니다.

### 설치한 뒤 계속 사용할 수 있는지도 확인합니다

도구를 고를 때는 지금 쓰는 시스템부터 살펴봅니다. 기존 저장소나 배포 시스템에 필요한 기능이 있다면 그것을 활용할 수 있습니다. 추가할 기능은 실험 결과 조회나 버전 등록처럼 구체적으로 적습니다.

그다음 설치 장소와 통신 조건을 확인합니다. 사내에 설치할 수 있는지, 외부 접속이 필요한지, 회사의 인증 방식과 함께 쓸 수 있는지 살펴봅니다. 폐쇄망에서는 필요한 패키지와 컨테이너 이미지를 가져올 수 있는지도 확인해야 합니다. 라이선스와 사용 조건은 실제 도입 시점의 공식 문서를 읽습니다.

백업과 업데이트, 장애 대응을 누가 맡을지도 정합니다. 마지막으로 결과 파일과 실행 기록을 내보낼 수 있는지 확인합니다. 다른 도구로 옮겼을 때도 어떤 실험에서 나온 결과인지, 어떤 모델과 설정을 사용했는지 알아볼 수 있어야 합니다.

### 오늘의 실습은 이 순서로 읽으면 됩니다

아래는 이론 자료에 안내된 기본 실습 흐름입니다. 각 단계에서 무엇이 새로 남는지 보면서 읽으면 코드의 목적을 이해하기 쉽습니다.

| 구간 | 하는 일 | 끝난 뒤 확인할 내용 |
| --- | --- | --- |
| Step 0\~2 | 환경을 준비하고 예제 파일을 만들어 읽습니다. | 어떤 조건과 결과가 있고 어떤 정보가 빠졌는지 |
| Step 3\~5 | MLflow에 결과를 기록하고 비교할 run을 고릅니다. | 같은 조건의 비교인지, 왜 그 후보를 선택했는지 |
| Step 6 | 모델·설정 정보를 버전별로 등록하고 별칭을 바꿉니다. | 어느 버전이 어느 run과 관련되는지, 별칭이 무엇을 가리키는지 |
| Step 9 | 기록과 원본 파일을 보관하고 선택 이유를 설명합니다. | 나중에도 결과와 설정을 다시 열 수 있는지 |

기본 실습에서는 CPU에서 만든 모의 자료를 사용합니다. 자신이 실제로 측정한 기록을 사용하는 활동은 선택입니다. 어떤 자료를 사용하든 확인된 조건만 적고, 실제 측정값과 모의 값을 구분합니다.

### 실습을 마치기 전에 다시 열어봅니다

사용하기로 고른 버전을 하나 열고, 관련 run을 찾아봅니다. 그 run에서 모델과 질문, 당시 설정을 확인하고 원본 결과 파일도 열어봅니다. 이 순서로 찾아갈 수 있다면 선택한 이유를 다른 사람에게 설명하기 쉬워집니다.

이어서 ‘운영’과 ‘직전’이 어느 버전을 가리키는지 확인합니다. 별칭을 바꿨다면 변경 전후 대상을 기록합니다. 실제 서버의 복구까지 확인하려면 추가로 어떤 모델과 설정을 불러오고 어떤 요청을 검사해야 하는지도 설명해 봅니다.

실습 환경을 종료하기 전에는 실행 정보가 담긴 데이터베이스와 원본 결과, 설정 파일을 함께 보관합니다. 모델과 문서가 있는 위치도 계속 사용할 수 있어야 합니다. 저장해 둔 기록을 다시 열 수 있는지 확인하는 것까지 마무리합니다.

다음 D67에서는 실행할 프로그램과 라이브러리, 설정을 컨테이너로 묶습니다. 오늘 모델과 설정을 정확히 남겨 두면 그다음 수업에서도 무엇을 실행하고 배포할지 분명하게 정할 수 있습니다.

## MLOps 실습 학습 정리

이번 실습에서는 실험 결과를 조건·원본과 함께 기록하고, 같은 조건의 결과를 비교합니다. 평가한 모델과 설정은 버전별로 등록하고, 사용할 버전을 선택하거나 이전 버전으로 되돌립니다.

이 과정에 사용하는 도구가 MLflow입니다. 실험의 설정값·평가 결과·원본 파일을 저장하고, 모델을 버전별로 등록하는 기능을 제공합니다.

기본 실습은 모의 평가 결과를 사용합니다. 예제 파일에 담긴 성능 수치를 바탕으로 MLflow의 기록·검색·버전 등록·롤백 기능을 익힙니다.

자료: D66 MLOps Intro Code

### 1. 실습 코드의 흐름

결과 파일 준비 → 형식 통일 → 기록 저장 → 검색·비교 → 모델·설정 등록 → 롤백 → 자료 보관

| 단계 | 실습 내용 | 학습 목적 |
| --- | --- | --- |
| Step 0\~1. 준비 | MLflow를 설치하고 예제 결과 파일 7개를 생성합니다. | 실험별로 다른 결과 파일의 구조를 확인합니다. |
| Step 2. 형식 통일 | 각 파일의 설정값, 평가 지표, 실행 조건을 공통 형식으로 정리합니다. | 다양한 실험의 검색·비교가 가능하도록 항목과 단위를 통일합니다. |
| Step 3. 서버 실행 | MLflow 트래킹 서버를 실행합니다. | 실험 기록을 저장·조회할 서버를 준비합니다. |
| Step 4. 기록 저장 | 평가 결과와 원본 파일을 함께 저장합니다. 동일한 결과는 중복 저장하지 않습니다. | 평가 결과의 근거를 보존하고 기록의 중복을 방지합니다. |
| Step 5. 검색·비교 | 조건에 맞는 결과를 검색하고, 평가 조건이 같은 결과를 비교합니다. | 점수와 속도를 비교할 때 확인해야 할 조건을 익힙니다. |
| Step 6. 버전 등록·롤백 | 기준선과 후보의 모델·설정을 각각 등록하고, 사용할 버전을 지정합니다. | 버전별 설정을 구분하고 이전 버전으로 되돌리는 방법을 익힙니다. |
| Step 9. 자료 보관 | 서버를 종료하고 실험 기록과 파일을 ZIP으로 보관합니다. | 실습 이후에도 평가 결과와 원본 파일을 확인할 수 있게 합니다. |

필수 순서는 Step 0~6 → Step 9입니다. Step 7·8과 부록은 선택 실습입니다.

### 2. 실험 결과를 기록할 때 배워야 할 것

#### ① 설정값·평가 결과·실행 조건·원본 파일을 함께 저장한다

관련 코드: make_row(), upload()

평가 점수만으로는 어떤 설정이 어떤 결과를 만들었는지 알기 어렵습니다. 실험을 다시 확인하려면 사용한 설정, 평가 조건, 결과 파일이 함께 있어야 합니다.

코드는 이 정보를 다음과 같이 구분합니다.

| 구분 | 의미 | 기록하는 내용 |
| --- | --- | --- |
| params — 설정값 | 실험에서 지정한 값 | 양자화 방식, 문서 조각 수, 답변 길이 상한 |
| metrics — 평가 지표 | 실험 결과를 나타내는 수치 | 정답 수, 응답 시간, 초당 토큰 수, 메모리 사용량 |
| tags — 조건·출처 | 결과 해석에 필요한 정보 | 모델 이름, GPU, 질문 세트, 패키지 버전, 실측·모의 데이터 구분 |
| artifact — 첨부 파일 | 결과의 상세 내용을 확인할 파일 | 원본 JSON·CSV 파일 |

이 정보를 함께 저장한 평가 기록 한 건이 run, 실행 기록입니다. 같은 목적의 실행 기록들을 모은 그룹은 experiment, 실험입니다.

실행 기록에서 정답 수를 확인하고, 첨부한 원본 파일에서 어떤 질문을 맞히거나 틀렸는지 살펴볼 수 있습니다. 설정값을 확인하면 당시 문서 조각 수나 답변 길이 제한도 알 수 있습니다.

#### ② 항목과 단위를 통일한다

관련 코드: rows_from_measure(), rows_from_d60() 등

실험마다 결과 파일의 구조가 다릅니다. 정답 수나 응답 시간이 서로 다른 항목에 저장될 수 있고, 시간 단위도 다를 수 있습니다.

읽기 함수들은 각 파일의 내용을 공통 항목으로 정리합니다. RAG 원본의 응답 시간은 밀리초(ms)에서 초(s)로 환산합니다.

6,200ms ÷ 1,000 = 6.2초

항목과 단위를 통일하면 여러 실험의 결과를 같은 기준으로 검색·비교할 수 있습니다.

#### ③ 확인할 수 없는 조건은 ‘빠짐’으로 기록한다

원본에 GPU 정보가 없으면 빠짐으로 표시합니다. 패키지 버전이나 질문 세트 정보가 없을 때도 같은 방식으로 처리합니다.

기록에는 실제 평가 당시의 조건을 적어야 합니다. 과거 평가에 사용한 GPU를 모른다면, 현재 노트북의 GPU 정보를 대신 넣을 수 없습니다. 해당 조건을 확인할 때까지 비교를 보류해야 합니다.

이 실습의 일부 예제에는 조건이 의도적으로 빠져 있습니다. 누락된 항목을 찾고, 그 정보가 없을 때 어떤 판단을 보류해야 하는지 연습합니다.

#### ④ 같은 결과의 중복 저장을 방지한다

관련 코드: row_key(), already_logged()

노트북에서는 같은 셀을 반복 실행하기 쉽습니다. 그때마다 동일한 결과가 새 기록으로 저장되면, 한 번의 평가가 여러 번 수행된 것처럼 보일 수 있습니다.

코드는 다음 방식으로 중복을 방지합니다.

설정값·지표·태그 등으로 row_key라는 식별값을 생성합니다.

같은 식별값의 실행 기록을 검색합니다.

기존 기록이 있으면 건너뛰고, 없으면 저장합니다.

row_key는 정리된 결과 내용으로 계산한 해시값입니다. 여기서는 동일한 결과인지 확인하는 데 사용합니다.

실습에서는 upload(ROWS)를 두 번 실행합니다. 두 번째 실행에서 추가 기록이 0개인지 확인하면 됩니다.

이처럼 같은 작업을 반복해도 중복된 변경이 발생하지 않도록 만드는 성질을 멱등성이라고 합니다.

### 3. 실험 결과를 비교할 때 배워야 할 것

#### ① 점수보다 평가 조건을 먼저 확인한다

관련 코드: compare()

두 결과의 점수나 속도가 다르면, 그 차이가 무엇 때문에 발생했는지 판단해야 합니다.

이번 실습의 compare()는 다음 세 조건을 확인합니다.

| 조건 | 확인할 내용 |
| --- | --- |
| 질문 세트 qset | 같은 질문으로 평가했는가? |
| 모델 model | 같은 모델을 사용했는가? |
| GPU gpu | 같은 장비에서 평가했는가? |

세 조건이 각각 같고, 누락된 정보가 없어야 비교를 진행합니다.

두 결과 모두 GPU 정보가 빠져 있다면, 같은 장비를 사용했는지 판단할 수 없습니다. 이 경우 비교를 보류합니다.

실제 성능 차이를 해석할 때는 패키지 버전, 입력·출력 길이, 동시 요청 수, 채점 기준도 확인해야 합니다.

#### ② 질문 세트 식별값의 의미를 이해한다

qset은 질문 목록으로 계산한 해시값입니다. 두 실험에서 같은 질문 집합을 사용했는지 확인하는 데 활용합니다.

일부 예제는 질문 번호만으로 해시값을 계산합니다. 따라서 실제 결과를 비교할 때는 질문 본문과 채점 기준도 확인해야 합니다.

이 실습에는 서로 다른 목적으로 사용하는 두 식별값이 있습니다.

| 식별값 | 확인하는 대상 | 사용 목적 |
| --- | --- | --- |
| qset | 평가에 사용한 질문 집합 | 비교 조건 확인 |
| row\_key | 정리된 평가 결과 한 건 | 중복 저장 방지 |

#### ③ 정답 총수와 함께 새로 틀린 질문도 확인한다

관련 코드: count_flips()

flip은 같은 질문에 대한 정답 여부가 바뀐 경우입니다.

lost: 기준선은 맞혔지만 후보는 틀린 질문

gained: 기준선은 틀렸지만 후보는 맞힌 질문

후보의 정답 총수가 늘어도, 기준선이 맞히던 질문을 새로 틀릴 수 있습니다. 그래서 전체 점수와 함께 flips_lost를 기록합니다.

Step 5에서는 GPU가 T4이고 flips_lost가 0인 결과를 검색합니다. 검색 결과는 초당 토큰 수가 높은 순서로 정렬합니다.

여기서 배울 것은 유지해야 할 품질 기준을 정하고, 그 기준을 만족하는 결과 중에서 속도를 비교하는 방법입니다.

### 4. 모델과 설정을 버전별로 등록하는 이유

#### ① 평가 기록과 모델 버전을 구분한다

관련 코드: create_external_model(), register_model()

실행 기록에는 평가 당시의 설정·조건·점수·원본 파일이 들어갑니다.

모델 버전은 등록한 모델을 버전 번호로 구분한 것입니다. 이번 코드에서는 모델 이름과 RAG 설정 등을 함께 등록합니다.

기준선과 후보에 기록하는 주요 정보는 다음과 같습니다.

사용할 언어 모델

임베딩 모델과 재정렬 모델

검색할 후보 문서 수

답변에 넣을 문서 조각 수

답변 길이 상한

문서 배치 순서

프롬프트 버전

각 버전에는 해당 구성을 평가한 실행 기록의 번호도 남깁니다. 코드에서는 source_run으로 표시합니다.

이 번호를 통해 등록된 버전의 평가 점수와 원본 파일을 찾을 수 있습니다. card_for()는 모델·설정·평가 조건·결과를 설명문으로 정리합니다. 이 설명문을 모델 카드라고 부릅니다.

#### ② ‘운영’과 ‘직전’으로 사용할 버전을 지정한다

등록된 여러 버전 중 사용할 버전을 지정하려면 **별칭(alias)**을 활용합니다. 별칭은 특정 버전을 가리키는 이름입니다.

운영: 현재 사용할 버전

직전: 되돌아갈 이전 버전

처음에는 운영이 고른 설정을, 직전이 기준선을 가리킵니다.

#### ③ 롤백은 이전 버전으로 되돌리는 작업이다

관련 코드: rollback()

rollback()은 운영과 직전이 가리키는 버전을 맞바꿉니다.

| 상태 | 운영 | 직전 |
| --- | --- | --- |
| 처음 | 고른 설정의 버전 | 기준선의 버전 |
| 롤백 한 번 실행 | 기준선의 버전 | 고른 설정의 버전 |
| 롤백 한 번 더 실행 | 고른 설정의 버전 | 기준선의 버전 |

기존 버전은 그대로 보관하고, 사용할 버전의 지정을 변경합니다.

#### ④ 버전 변경 후에는 실제 응답도 확인한다

코드가 출력하는 ms는 MLflow에서 별칭을 변경하는 데 걸린 시간입니다.

실제 서비스에서는 서버가 변경된 버전 정보를 반영해야 합니다. 변경 후에는 요청을 보내 다음을 확인합니다.

기대한 버전이 응답에 사용되었는가?

답변이 정상적으로 생성되는가?

부록 A에서는 모의 서비스가 일정 주기인 ttl마다 버전 정보를 갱신합니다. 따라서 별칭 변경 시점과 응답에 반영되는 시점 사이에 시간 차이가 생길 수 있습니다.

### 5. 선택 실습에서 배우는 내용

| 실습 | 실습 내용 | 배워야 할 점 |
| --- | --- | --- |
| Step 7. 수준 점검 | 실험 조건, 버전 정보, 재현·배포 기록 등 13개 항목을 점검합니다. | 실제 기록과 파일을 근거로 수행 여부를 판단합니다. |
| Step 8. 게이트 | 평가 기준을 통과한 후보만 운영으로 지정합니다. | 사용할 버전을 변경하기 전에 필요한 검사를 수행합니다. |
| 부록 A. 요청별 버전 기록 | 답변마다 사용한 버전을 기록합니다. | 문제가 발생한 답변을 어떤 버전이 생성했는지 확인합니다. |
| 부록 B. 백업·복구 | 데이터베이스와 첨부 파일을 백업하고 복구합니다. | 백업 자료로 실험 기록과 원본 파일을 다시 확인할 수 있는지 검증합니다. |
| 부록 E. 인증·권한 | 로그인 여부와 사용자 권한에 따라 접근과 변경을 제한합니다. | 기록 조회 권한과 운영 버전 변경 권한을 구분합니다. |

**게이트(gate)**는 후보를 사용하기 전에 통과해야 할 검사 기준입니다. Step 8에서는 평가 기록의 존재, 질문 세트 일치, 정답 수 유지, flips_lost=0을 확인합니다. 필요한 기록이 없거나 기준을 충족하지 못하면 변경을 보류하고 이유를 남깁니다.

Step 7의 점검 결과는 정보 누락, 미수행 작업, 증거 부족, 실제 기능 오류를 구분해 해석해야 합니다. 이 실습에는 누락된 정보를 찾도록 만든 예제도 포함되어 있습니다.
