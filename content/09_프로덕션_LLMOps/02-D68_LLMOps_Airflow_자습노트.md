## 전체 흐름 먼저 이해하기

RAG 서비스는 사용자의 질문에 답하기 위해 문서를 검색하고, 검색한 내용을 LLM에 전달한다. 사내 규정을 안내하는 서비스를 운영한다면 근무 시간, 재택근무, 출장비 등의 규정이 바뀔 때마다 검색에 사용하는 문서도 갱신해야 한다.

문서를 갱신하려면 새로운 문서를 수집하고, 오래된 문서와 중복 문서를 제거하고, 검색하기 좋은 크기로 나눈 다음 인덱스를 다시 만들어야 한다. 새 인덱스를 사용했을 때 필요한 문서를 제대로 찾는지 평가하는 과정도 필요하다. 평가에 통과하면 새 인덱스를 운영에 반영하고, 실패하면 기존 인덱스를 유지한다.

이 작업을 매주 사람이 직접 수행하면 실행 순서를 지키거나 실패 원인을 추적하기 어렵다. **Airflow는 여러 작업의 실행 순서와 일정, 성공·실패 상태를 관리하는 워크플로 오케스트레이션 도구**다. 문서를 처리하는 파이썬 함수를 Airflow의 작업으로 등록하면 매주 같은 절차를 자동으로 수행할 수 있다.

이번 실습에서는 다음 여섯 작업을 하나의 DAG로 구성한다.

```text
catalog      문서 목록과 원본을 일정 시점 기준으로 보관
    ↓
prepare      오래된 문서·빈 문서·중복 제거, 청크 생성
    ↓
build_index  새로운 검색 인덱스 생성
    ↓
evaluate     기존 인덱스와 새 인덱스의 검색 품질 비교
    ↓
gate         평가 결과에 따라 운영 반영 허용 여부 결정
    ↓
promote      통과한 구성으로 운영 참조(current) 변경
```

가령 문서의 최소 길이를 지나치게 높게 설정하면 짧지만 중요한 출장비 규정이 제거될 수 있다. 새 인덱스에서 해당 규정을 찾지 못하면 평가 결과가 나빠진다. `gate`에서 실패하도록 설정하면 다음 작업인 `promote`는 실행되지 않는다. 따라서 사용자는 이전에 검증된 인덱스를 계속 사용할 수 있다.

Airflow UI에서는 어느 작업이 성공했고 실패했는지, 어떤 실행 설정을 사용했는지, 각 작업이 다음 작업에 무엇을 전달했는지 확인할 수 있다. 실패한 작업만 다시 실행할 수도 있다. 다만 문서를 잘못 정제한 것이 원인이라면 평가나 게이트만 반복 실행해도 결과는 달라지지 않는다. 정제 기준을 수정하고 영향을 받는 작업을 다시 수행해야 한다.

이번 실습에서 학습할 핵심은 **자동화된 문서 갱신 절차를 만들고, 평가를 통과한 결과만 운영에 반영하며, 실패 시 안전하게 복구하는 방법**이다. 실제 LLM을 로드하거나 답변을 생성하는 실습은 진행하지 않는다. 모델명과 프롬프트 버전은 출시 번들에 기록하고, 품질 평가는 간단한 문자 기반 검색으로 수행한다.

## 1. LLMOps와 Airflow가 필요한 이유

### LLMOps의 관리 대상

MLOps는 모델 학습과 평가, 배포, 모니터링을 반복적으로 수행하고 관리하는 방법이다. LLMOps 역시 이러한 운영 원리를 사용하지만, LLM을 활용하는 서비스에서는 모델 외에 관리할 구성 요소가 더 많다.

RAG 서비스를 기준으로 보면 다음과 같은 변경이 서비스의 답변에 영향을 준다.

| 관리 대상 | 변경에 따른 영향 |
| --- | --- |
| LLM 및 LoRA 어댑터 | 답변 생성 능력과 응답 특성이 달라진다. |
| 프롬프트 | 답변 형식, 지시 준수, 근거 사용 방식이 달라진다. |
| 원본 문서 | 서비스가 참고할 수 있는 정보가 달라진다. |
| 정제 및 청킹 설정 | 검색 대상이 되는 문서의 범위와 구조가 달라진다. |
| 검색 인덱스와 검색 방식 | 동일한 질문에서 검색되는 근거가 달라진다. |
| 평가 데이터와 평가 기준 | 새 구성을 운영에 반영할 수 있는지 판단하는 조건이 달라진다. |

예를 들어 모델과 프롬프트를 그대로 유지해도 인덱스에서 출장비 규정이 사라지면 출장비 관련 답변의 품질은 떨어질 수 있다. 따라서 모델뿐 아니라 문서, 인덱스, 설정, 평가 결과도 함께 관리해야 한다.

LLMOps를 구축하는 실무적인 목적은 다음과 같이 정리할 수 있다. 변경 작업을 반복 가능하게 만들고, 결과의 품질을 검증하고, 어떤 구성을 사용했는지 추적하며, 문제가 발생했을 때 이전 상태로 복구할 수 있도록 만드는 것이다.

### Airflow의 역할

일반 파이썬 프로그램에서도 여러 함수를 순서대로 호출할 수 있다. 그러나 정기적으로 실행하는 운영 파이프라인에서는 다음 조건을 추가로 관리해야 한다.

- 매주 정해진 시간에 실행한다.
- 앞 작업이 성공했을 때만 다음 작업을 수행한다.
- 일시적인 장애가 발생하면 일정 시간 후 재시도한다.
- 실행이 지나치게 오래 걸리면 중단한다.
- 실행 결과와 오류 로그를 작업 단위로 기록한다.
- 전체 작업 또는 필요한 일부 작업을 다시 실행한다.

Airflow는 이와 같은 실행 관리 기능을 제공한다. 실제 문서 수집, 임베딩 생성, 인덱스 구축, 품질 평가는 파이썬 함수나 외부 프로그램이 수행하고, Airflow가 실행 시점과 의존 관계를 관리한다. 이러한 기능을 워크플로 오케스트레이션(Workflow Orchestration)이라고 한다.

Airflow의 주 용도는 문서 갱신이나 데이터 처리와 같이 시작과 종료가 있는 작업을 관리하는 것이다. 사용자 질문에 즉시 답변하는 LLM 서빙 서버는 별도로 운영하고, Airflow는 그 서버가 사용할 검색 인덱스나 모델의 갱신 작업을 관리하는 구조로 사용할 수 있다.

### Airflow를 구성하는 요소

| 구성 요소 | 역할 |
| --- | --- |
| DAG Processor | DAG 파이썬 파일을 읽고 작업과 의존 관계를 해석한다. |
| Scheduler | 일정과 선행 작업의 상태를 확인해 실행 가능한 태스크를 결정한다. |
| Executor | 실행할 태스크를 실행 환경에 전달하는 방식을 관리한다. |
| Worker / 실행 프로세스 | 실제 태스크의 코드를 실행한다. 실행 구조는 Executor에 따라 달라진다. |
| Metadata DB | DAG 실행, 태스크 상태, 설정, XCom 등의 실행 정보를 보관한다. |
| API Server 및 UI | 실행 상태를 확인하고 DAG 실행이나 태스크 초기화 등을 요청할 수 있게 한다. |

3. Airflow의 주요 개념 정리

| 구성 요소 | 역할 |
| --- | --- |
| DAG | 전체 작업의 순서와 의존관계 정의 |
| Task | 개별 작업 단위 |
| Operator | 작업 수행 방법 정의 |
| Sensor | 특정 조건 확인 및 대기 |
| XCom | Task 간 데이터 전달 |
| Scheduler | 작업 실행 시점과 실행 가능 여부 판단 |
| Executor | 실행 가능한 작업을 실행 환경에 배정 |

DAG가 작업의 실행 순서를 관리한다면, XCom은 작업과 작업 사이에 필요한 데이터를 전달합니다.
실습에서는 `airflow standalone` 명령으로 개인 학습에 필요한 구성 요소를 함께 실행한다. 실제 운영 환경에서는 데이터베이스, 스케줄러, 작업 실행 환경 등을 별도로 구성할 수 있다.

## 2. DAG, Task, Operator, Sensor, XCom

### DAG: 작업 간 의존 관계

DAG(Directed Acyclic Graph)는 방향이 있고 순환하지 않는 그래프다. Airflow에서는 어떤 작업을 수행할지, 어떤 작업이 끝난 뒤 다음 작업을 실행할지를 정의하는 데 사용한다.

작업의 의존 관계는 반드시 일렬로 연결할 필요가 없다. 서로 다른 저장소의 문서를 수집하는 작업 두 개를 병렬 실행한 뒤, 두 작업이 모두 성공하면 문서를 통합하는 구조도 가능하다.

```text
수집 A ─┐
        ├─→ 문서 통합 → 인덱스 생성 → 평가
수집 B ─┘
```

순환하지 않는다는 것은 A가 B의 완료를 기다리면서 동시에 B가 A의 완료를 기다리는 형태의 의존 관계가 없다는 의미다. 작업 간 의존 관계가 순환하면 어느 작업부터 시작해야 하는지 결정할 수 없다.

하나의 DAG를 여러 번 실행할 수 있다. 매주 같은 DAG를 실행하더라도 각 실행의 시작 시점, 전달 설정, 실행 결과는 달라질 수 있다.

| 용어 | 의미 |
| --- | --- |
| DAG | 실행할 작업과 일정, 의존 관계를 정의한 구조 |
| DAG Run | DAG를 한 번 실행한 기록 |
| Task | DAG를 구성하는 개별 작업의 정의 |
| Task Instance | 특정 DAG Run에서 실행되는 개별 태스크의 기록 |

`prepare`는 하나의 Task다. 9월 28일 실행과 11월 9일 실행의 `prepare`는 서로 다른 Task Instance이므로 입력과 로그, 성공 여부가 별도로 관리된다.

### Operator와 Task

Operator는 Airflow에서 수행할 작업의 유형과 실행 방식을 정의하는 구성 요소다. 파이썬 함수 실행, 셸 명령 실행, 외부 시스템에 작업 요청 등 실행 목적에 맞는 Operator를 사용할 수 있다. DAG에 Operator를 사용해 정의한 개별 실행 단위가 Task가 된다.

이번 실습은 TaskFlow API를 사용한다. 일반 파이썬 함수에 `@task` 데코레이터를 붙이면 Airflow에서 사용할 수 있는 태스크로 정의할 수 있다. `@dag`는 이러한 태스크들을 하나의 DAG로 구성한다.

```python
from airflow.sdk import dag, task

@dag(schedule=None)
def example_pipeline():
    @task
    def catalog():
        return "snapshots/documents.json"

    @task
    def prepare(snapshot_path):
        print(snapshot_path)

    snapshot = catalog()
    prepare(snapshot)

example_dag = example_pipeline()
```

`@task`가 붙은 `catalog()`를 DAG 정의 안에서 호출하면 문서를 즉시 수집하는 대신 태스크를 생성하고 그 반환값을 참조하는 객체를 만든다. Airflow가 DAG를 실행할 때 함수의 본문이 수행된다. DAG 파일을 읽는 과정에서 문서 수집이나 모델 로드처럼 오래 걸리는 작업을 직접 실행하지 않는 것이 중요하다.

Airflow에는 다른 Operator도 있지만, 이번 실습에서는 여섯 작업을 모두 파이썬 함수로 구현한다.

### Sensor: 조건이 충족될 때까지 대기하는 작업

Sensor는 특정 조건을 확인하고, 조건이 충족되면 후속 작업이 실행될 수 있도록 하는 특수한 Operator다. 외부 저장소에 문서가 도착했는지, 다른 파이프라인이 종료됐는지 확인하는 데 사용할 수 있다.

예를 들어 문서가 매주 월요일 오전 3시 이전에 도착한다는 보장이 없다면, 문서가 준비됐는지 확인하는 Sensor를 수집 작업 앞에 추가할 수 있다.

```text
문서 도착 확인(Sensor) → catalog → prepare → …
```

Sensor는 확인 주기와 대기 시간 상한 등을 설정할 수 있다. Sensor 종류와 실행 방식에 따라 대기 중 워커를 점유하지 않도록 구성할 수도 있다. 일반적인 `gate`는 평가 결과를 한 번 확인하고 통과 또는 실패를 결정하는 태스크다. 조건이 충족될 때까지 반복해서 기다리는 Sensor와 목적이 다르다.

이번 실습의 DAG에는 Sensor가 포함되지 않는다. 문서를 목록화하는 `catalog`가 저장소 접근에 실패하면 예외를 발생시키고, Airflow의 재시도 설정으로 복구를 시도한다.

### XCom: 태스크 간 실행 결과 전달

Airflow의 태스크는 서로 다른 프로세스나 작업 환경에서 실행될 수 있다. 첫 번째 태스크의 파이썬 변수에 저장된 값을 다음 태스크가 직접 사용할 수 있다고 가정하면 안 된다.

XCom(Cross-Communication)은 태스크 간에 작은 데이터를 전달하는 Airflow의 기능이다. 태스크가 생성한 파일 경로, 인덱스 버전, 처리 건수 등의 값을 다음 태스크에 전달할 수 있다. 기본 구성에서는 Airflow의 메타데이터 DB를 통해 관리되며, 설정에 따라 별도의 XCom 저장소도 사용할 수 있다.

```python
snapshot = catalog()
chunks = prepare(snapshot)
index_dir = build_index(chunks)
```

DAG를 정의하는 시점의 `snapshot`, `chunks`, `index_dir`는 실행 결과를 참조하는 `XComArg` 객체다. 실제 실행 시에는 `catalog`가 반환한 경로가 XCom에 기록되고, `prepare`가 이 경로를 입력으로 받는다. 이와 동시에 `catalog`가 먼저 성공해야 한다는 의존 관계도 정의된다.

이번 실습은 원본 문서나 인덱스 전체를 XCom에 넣지 않는다. 파일은 작업 폴더에 저장하고 XCom에는 파일의 위치만 전달한다. 태스크가 서로 다른 서버에서 실행된다면 각 서버에서 접근할 수 있는 공유 저장소나 오브젝트 스토리지를 사용해야 한다. 한 서버에서만 접근할 수 있는 로컬 경로를 전달하면 다른 서버의 태스크는 해당 파일을 읽지 못할 수 있다.

태스크 간에 데이터 전달 없이 실행 순서만 지정하려면 `task_a >> task_b`와 같은 표현도 사용할 수 있다. TaskFlow에서는 앞 태스크의 반환값을 뒤 태스크에 입력하는 것만으로도 의존 관계를 정의할 수 있다.

## 3. 스케줄링, 재시도, 멱등성과 백필

### 스케줄과 논리적 날짜

Airflow는 DAG에 지정한 일정에 따라 DAG Run을 생성할 수 있다. 이번 실습의 주간 DAG에는 다음 설정이 사용된다.

```python
SCHEDULE = "0 3 * * 1"
RETRIES = 2
```

크론(Cron)은 정기적인 작업 일정을 표현하는 방식이다. 다섯 항목은 순서대로 분, 시, 일, 월, 요일을 나타낸다. `0 3 * * 1`은 월요일 오전 3시를 지정한다. DAG의 시간대를 `Asia/Seoul`로 설정했기 때문에 한국 시각을 기준으로 적용된다.

실제 실행 시각과 어떤 기간의 데이터를 처리하는지를 구분할 필요가 있다. Airflow의 Logical Date(논리적 날짜)는 DAG Run이 처리할 데이터 구간이나 논리적 시점을 식별하는 값이다. 일반적인 데이터 구간 기반 스케줄에서는 데이터 구간의 시작을 나타낼 수 있으므로, 실제 DAG가 시작한 시각과 다를 수 있다.

실습에서는 `logical_date`를 한국 시간대의 날짜로 변환하고 문서 목록의 날짜에 사용한다. 9월 28일자 입력을 대상으로 실행한다는 것을 날짜로 식별할 수 있다. 단, 수동 실행과 정기 실행은 논리적 날짜가 부여되는 방식이 다를 수 있으므로 실제 운영에서는 데이터 구간과 스냅샷의 날짜를 어떻게 대응시킬지 명시적으로 정해야 한다.

### 재시도와 실행 시간 제한

작업이 실패했을 때는 오류의 성격에 따라 대응 방법을 달리해야 한다. 네트워크 연결이 일시적으로 끊어진 경우에는 잠시 후 다시 실행하면 성공할 가능성이 있다. 반면 잘못된 설정이나 평가 기준 미달은 원인을 수정해야 한다.

| 설정 | 실습의 값과 동작 |
| --- | --- |
| `retries` | 2: 최초 시도 이후 최대 두 번 추가 시도 |
| `retry_delay` | 3초: 재시도 전 대기 시간 |
| `execution_timeout` | 2분: 태스크의 각 실행 시도에 대한 시간 상한 |
| `max_active_runs` | 1: 해당 DAG의 활성 실행 수를 한 개로 제한 |
| `catchup` | False: 스케줄러가 과거 미실행 구간을 자동으로 모두 따라잡지 않도록 설정 |

실습에서 일반적인 연결 장애는 `DriveUnavailable` 예외를 발생시킨다. Airflow는 재시도 설정에 따라 다시 실행할 수 있다. 잘못된 청크 크기, 보관되지 않은 과거 스냅샷, 평가 실패에는 `AirflowFailException`을 사용해 추가 재시도 없이 실패시킨다. `AirflowSkipException`은 특정 작업을 의도적으로 생략할 때 사용한다.

동시 실행 수를 제한하면 같은 DAG의 여러 실행이 겹쳐 결과를 변경하는 상황을 줄일 수 있다. 다만 이 제한은 DAG별로 적용된다. 여러 DAG가 동일한 저장소나 운영 참조를 수정할 수 있는 환경에서는 별도의 동시성 제어가 필요하다.

### 멱등성과 재현 가능성

멱등성(Idempotency)은 같은 작업을 같은 조건에서 여러 번 수행했을 때 최종 상태가 불필요하게 달라지지 않는 성질이다. Airflow에서는 재시도나 수동 재실행이 가능하므로 이러한 성질이 중요하다.

실습에는 다음과 같은 구현이 포함된다.

- 같은 날짜의 스냅샷이 이미 있으면 공유 드라이브를 다시 읽지 않고 기존 목록을 사용한다.
- 원본 파일의 내용에서 SHA-256 해시를 계산하고, 동일한 내용은 한 벌만 보관한다.
- 문서 목록의 해시, 정제 설정, 검색 방식이 같으면 같은 인덱스 버전을 사용한다.
- 운영에서 이미 동일한 출시 번들을 사용하고 있으면 `current`를 다시 변경하지 않는다.

해시(Hash)는 데이터에서 계산한 식별값이다. 파일 이름이 달라도 파일 내용이 같으면 동일한 SHA-256 해시를 얻을 수 있어 정확히 같은 내용의 중복을 찾는 데 유용하다. 내용이 달라지면 일반적으로 해시도 달라진다. 실습에서는 일부 식별값에 해시 앞부분만 사용한다.

재현 가능성(Reproducibility)은 과거 결과를 만들었던 입력과 설정을 확보해 그 결과를 다시 얻거나 검증할 수 있는 성질이다. 같은 날짜의 문서라고 해도 현재 공유 드라이브에서 다시 가져오면 과거와 다른 내용이 포함될 수 있다. 그래서 날짜별 문서 목록과 당시의 원본 내용을 보관한다.

실습의 청크 파일은 날짜 단위로 저장하므로 같은 날짜에서 설정을 바꾸면 해당 청크 파일을 덮어쓸 수 있다. 인덱스는 입력 목록과 설정에 따라 별도 버전으로 관리한다. 실제 운영에서 모든 실행 결과를 보존하려면 청크 및 평가 산출물에도 설정 해시나 실행 ID 등을 포함하는 방식을 고려해야 한다.

### 백필(Backfill)

백필은 과거에 처리하지 못한 구간이나 다시 계산할 필요가 있는 구간의 데이터를 처리하는 작업이다. 이번 주 문서를 갱신하는 작업과는 달리, 과거 날짜에 실제로 존재했던 문서를 대상으로 수행해야 한다.

실습에는 9월 7일, 21일, 28일의 문서 목록이 저장되며, 9월 14일의 문서 목록은 존재하지 않는다. 9월 14일을 백필하려고 하면 현재 공유 드라이브의 문서로 대체하지 않고 실패하도록 설계했다. 과거의 입력 자료가 없는데 현재 자료를 사용하면 과거에 어떤 결과가 나왔는지 확인할 수 없기 때문이다.

`catchup=False`는 자동으로 지난 구간을 실행하지 않는 설정이며, 명시적으로 수행하는 백필과는 구분된다. 실습 코드에서는 백필이 수행되더라도 `gate`에서 운영 승격을 건너뛰도록 구성한다. 과거 데이터의 평가 결과를 기록하면서 현재 서비스에 영향을 주지 않기 위한 장치다. 실제 백필 실행은 이번 UI 실습의 검증 범위에 포함되지 않는다.

## 4. RAG 문서 갱신: 수집부터 인덱스 생성까지

### 문서 목록과 원본을 함께 보관하는 이유

문서 갱신 파이프라인의 입력은 사내 공유 드라이브에 저장된 문서다. 이번 실습에서는 `corp_docs/` 폴더가 공유 드라이브 역할을 한다. 인사 규정, 정보보안 지침, 시스템 매뉴얼, 출장 여비 규정 등을 합성 문서로 생성한다.

첫 번째 태스크인 `catalog`는 각 문서의 경로, 내용 해시, 파일 크기를 기록해 날짜별 스냅샷을 만든다. 동시에 원본 내용을 해시를 파일명으로 사용해 `blobs/`에 보관한다.

```text
corp_docs/                      현재 공유 드라이브의 문서
    ↓ catalog
snapshots/2026-09-28.json        9월 28일의 문서 경로·해시·크기 목록
blobs/<SHA-256 해시>             해시에 대응하는 실제 원본 내용
```

스냅샷은 특정 시점의 데이터 상태를 저장한 기록이다. 이 실습에서는 문서 목록과 별도로 보관된 원본을 함께 사용해 당시의 입력을 재구성한다. 규정이 개정되면 문서 경로나 내용이 달라지고 새로운 스냅샷에 기록된다. 기존 스냅샷은 이전 문서의 해시를 계속 참조한다.

### 문서를 정제하는 과정

문서 목록을 만들었다고 해서 목록에 있는 모든 파일을 검색 대상으로 사용할 수 있는 것은 아니다. 공유 드라이브에는 폐기된 문서나 미작성 파일, 복사본이 포함되어 있기 때문이다. `prepare`에서는 다음 순서로 문서를 처리한다.

| 단계 | 처리 내용 | 필요한 이유 |
| --- | --- | --- |
| 원본 읽기 | 스냅샷의 해시에 해당하는 원본을 읽는다. | 같은 입력을 사용해 결과를 재현할 수 있다. |
| 필터링 | 보관 폴더의 문서, 짧은 문서, 빈 양식을 제외한다. | 오래되었거나 불필요한 문서가 검색되는 문제를 줄인다. |
| 통과율 확인 | 필터링 후 남은 문서 비율이 기준 이상인지 확인한다. | 수집 또는 정제 과정에서 대부분의 문서가 사라졌을 때 중단할 수 있다. |
| 중복 제거 | 내용 해시가 같은 파일 중 하나만 남긴다. | 같은 내용이 여러 검색 결과를 차지하는 문제를 줄인다. |
| 청킹 | 문서를 조항 단위로 나누고 긴 조항은 추가로 분할한다. | 질문과 관련 있는 부분을 검색할 수 있다. |

실습에서 조절하는 주요 설정은 다음 두 가지다.

- `min_chars=10`: 문서 양끝의 공백을 제거한 본문의 최소 문자 수 기준이다. 10자 미만의 문서는 제외한다. 전체 문서를 대상으로 적용하며, 개별 청크의 최소 길이 조건과는 다르다.
- `chunk_size=400`: 하나의 조항이 길 경우 추가로 나누는 기준이다. 여기서는 토큰이 아니라 문자 단위를 사용한다. 제목을 덧붙이므로 최종 청크 문자열은 400자를 초과할 수도 있다.

`min_chars`를 지나치게 높게 설정하면 중요한 짧은 문서도 제거될 수 있다. 반대로 너무 낮게 설정하면 내용이 충분하지 않은 문서가 검색에 포함될 수 있다. 청크 크기도 마찬가지다. 너무 크면 불필요한 내용이 포함되고, 너무 작으면 조항의 맥락이 끊길 수 있다. 정제 기준과 청크 크기는 검색 품질에 미치는 영향을 평가해 결정해야 한다.

### 하드 게이트와 소프트 게이트

실습은 문서를 준비하는 단계에서도 품질을 확인한다. 모든 검증 실패를 동일하게 처리할 필요는 없기 때문에 중단 기준과 경고 기준을 구분한다.

하드 게이트(Hard Gate)는 반드시 충족해야 하는 기준이다. 이번 정제 단계에서는 필터링을 통과한 문서의 비율이 30% 미만이면 파이프라인을 중단한다. `prepare`가 실패하므로 이후 인덱스 생성과 평가는 실행되지 않는다.

소프트 게이트(Soft Gate)는 이상 징후를 기록하고 후속 검토를 유도하는 기준이다. 실습에서는 이전 날짜에 저장된 청크 수와 비교해 15%를 초과하는 변화가 있으면 경고를 기록한다. 청크 수가 많이 달라졌더라도 정상적인 대규모 문서 개정이 원인일 수 있으므로 경고만으로 실행을 중단하지 않는다.

정제 통과율이 충분하더라도 특정 규정 하나가 잘못 제외될 수 있다. 그래서 정제 단계의 하드 게이트를 통과한 뒤에도 별도의 검색 품질 평가가 필요하다.

### 인덱스 생성과 버전 관리

`build_index`는 정제한 청크를 입력으로 새로운 검색 인덱스를 생성한다. 일반적인 RAG 파이프라인에서는 이 단계에 임베딩 모델과 벡터 데이터베이스 등을 사용할 수 있다. 이번 실습은 파이프라인의 실행 관리에 집중하기 때문에 별도의 임베딩 모델이나 벡터 DB를 사용하지 않는다.

실습에서는 청크의 ID, 원본 문서 경로, 텍스트를 `index.json`에 저장한다. 검색할 때 질문과 각 청크에서 공백을 제거한 후 연속된 두 글자 조합(bigram)을 추출한다. 질문과 청크 사이에 겹치는 조합 수를 청크의 bigram 수에 대한 제곱근으로 나누어 점수를 계산하고, 상위 3개 청크를 반환한다. 검색 방식의 버전명은 `bigram-v1`이다.

새 인덱스는 다음 세 가지를 조합한 해시로 식별한다.

```text
문서 목록의 해시 + 정제·청킹 설정 + 검색 방식 버전
                     ↓
                 인덱스 ID
```

입력 문서와 설정이 같으면 이미 만들어 놓은 인덱스를 재사용할 수 있다. `min_chars`나 `chunk_size`가 달라지면 새로운 인덱스 버전이 생성된다. 새로운 후보 인덱스를 별도 폴더에 생성하므로 평가가 끝나기 전까지 기존 인덱스의 내용을 변경할 필요가 없다.

## 5. 품질 평가와 안전한 운영 반영

### 후보 인덱스와 운영 인덱스 비교

새로 만든 인덱스가 기존 인덱스보다 실제로 유용한지 확인해야 한다. 이를 위해 `evaluate` 태스크에서는 동일한 질문으로 새 인덱스와 현재 운영 인덱스를 평가한다.

실습의 평가 질문은 총 12개다. 각 질문에는 검색 결과에 포함되어야 할 원본 문서의 경로가 지정되어 있다. 예를 들어 국내 출장 일비에 관한 질문은 출장 여비 규정 문서를 찾아야 한다. 검색된 상위 3개 청크 중 하나 이상이 지정한 원본 문서에서 나왔다면 적중으로 기록한다.

이 지표는 문서 단위의 Hit@3에 해당한다. 정확한 답변이 생성됐는지 평가하려면 정답에 해당하는 조항을 찾았는지, 답변에 근거가 반영됐는지, 수치나 조건이 맞는지 등 추가 평가가 필요하다. 이번 실습은 검색 결과에 정해진 근거 문서가 포함되는지를 평가한다.

평가 보고서에는 다음과 같은 정보가 기록된다.

| 항목 | 내용 |
| --- | --- |
| `cand_hit` | 후보 인덱스의 적중 질문 수 |
| `cur_hit` | 현재 운영 인덱스의 적중 질문 수 |
| `total` | 평가 질문 수(12개) |
| `flips` | 운영 인덱스는 적중했으나 후보 인덱스는 놓친 질문 ID |
| `rows` | 질문별 기존 인덱스와 후보 인덱스의 적중 여부 |
| `eval_set` | 평가 데이터의 이름과 해시 |
| `current_release` | 비교 기준으로 사용한 운영 번들의 ID |

### Flip과 회귀(Regression)

서비스를 갱신한 후 기존에 정상적으로 작동하던 기능이나 답변의 품질이 떨어지는 현상을 회귀라고 한다. 전체 평균 성능만 비교하면 개별 항목에서 발생한 회귀를 발견하지 못할 수 있다.

예를 들어 운영 인덱스가 12문항 중 10문항을 적중하고 새 인덱스도 10문항을 적중했다고 가정하자. 기존에 틀렸던 문항 두 개를 새로 맞혔지만, 기존에 맞혔던 문항 두 개를 놓쳤다면 전체 적중 수는 같더라도 회귀가 발생했다. 이때 새로 놓친 두 질문이 `flip`에 기록된다.

실습에서는 다음과 같이 판정한다.

| 평가 상황 | 승격 조건 |
| --- | --- |
| 첫 번째 출시 번들(기존 운영 인덱스 없음) | 12개 중 최소 9개 적중 |
| 기존 출시 번들 있음 | 기존에 적중했던 질문을 하나도 놓치지 않아야 함(`flip=0`) |
| 평가 보고서를 읽을 수 없음 | 승격 거절 |

첫 번째 번들을 운영에 반영할 때는 비교 대상이 없으므로 절대적인 적중 수 기준을 적용한다. 이후에는 이전 서비스의 품질을 보존하는 회귀 기준을 적용한다. 동일한 평가 질문과 검색 방식으로 후보와 기존 인덱스를 비교해야 결과를 해석하기 쉽다.

실제 서비스에서는 평가 질문의 중요도를 고려하고, 응답 정확도와 안전성, 지연 시간, 비용 등을 추가로 검증할 수 있다. 현재 서비스의 성능이 낮은 경우에는 `flip=0` 외에 절대적인 품질 하한도 함께 두는 것이 유용하다.

### Gate와 Promote를 분리하는 이유

`gate`는 평가 보고서를 읽어 운영에 반영해도 되는지 판정한다. `promote`는 운영에서 참조하는 출시 번들을 변경한다. 두 작업을 분리하면 평가 결과를 확인하기 전에 운영 설정이 변경되는 것을 방지할 수 있다.

```text
                평가 보고서
                     ↓
                  gate
             ┌───────┴───────┐
            통과             실패
              ↓                ↓
          promote         후속 실행 차단
              ↓                ↓
       새 번들로 변경       기존 번들 유지
```

실습에서 `gate`는 평가에 실패하면 `AirflowFailException`을 발생시킨다. 후속 태스크인 `promote`는 기본 성공 조건을 충족하지 못해 실행되지 않는다.

### 출시 번들(Release Bundle)

출시 번들은 함께 검증한 서비스 구성 요소의 버전을 묶어 기록한 것이다. 실습의 번들에는 다음 내용이 포함된다.

- 모델 이름과 LoRA 어댑터 정보
- 프롬프트 이름과 내용 해시
- 검색 인덱스 버전
- 평가 질문 세트의 이름과 해시
- 평가 적중 수, flip 수, 경고, Airflow 실행 ID

이 구성 요소들을 함께 기록해야 어떤 조건에서 평가가 수행됐고 운영에 어떤 구성이 반영됐는지 추적할 수 있다. 예를 들어 인덱스를 이전 버전으로 되돌려도 프롬프트가 당시와 다르다면 서비스의 동작이 달라질 수 있다.

실습에서는 모델 이름과 프롬프트를 기록하지만 모델 추론이나 프롬프트의 답변 품질을 직접 평가하지 않는다. 기록된 모델명만으로 모델의 가중치 버전까지 고정할 수도 없으므로, 실제 운영에서는 모델 리비전과 어댑터 식별자 등도 추가로 관리할 필요가 있다.

### current, 승격, 롤백

`current`는 운영에서 사용할 출시 번들을 가리키는 참조다. 실습에서는 `releases/current.json`에 현재 번들과 이전 번들의 ID, 변경 시각을 저장한다.

```text
releases/
├── r-20260928-xxxxxx.json    기존 출시 번들
├── r-20261109-yyyyyy.json    새로운 출시 번들(개념 예시)
└── current.json             현재 운영 번들을 가리키는 파일
```

평가에 통과한 새 번들을 운영에서 사용하도록 `current`를 변경하는 것을 승격(Promotion)이라고 한다. 배포 후 문제가 발견되면 이전 번들로 운영 참조를 되돌리는 롤백(Rollback)을 수행할 수 있다.

실습에서는 `current` 파일을 직접 수정하는 대신 새로운 임시 파일을 완성한 후 기존 파일을 교체한다. 이처럼 결과를 완성한 뒤 한 번에 교체하는 방식을 원자적 파일 교체(Atomic Replace)라고 한다. 읽는 도중에 불완전한 JSON 파일을 만날 위험을 줄여준다.

실제 서비스에서 인덱스 별칭이나 레지스트리 참조를 변경할 때는 서비스가 새 참조를 읽는 시점까지 고려해야 한다. 서빙 서버가 인덱스 설정을 캐싱하면 참조를 바꾼 뒤에도 일정 시간 기존 버전을 사용할 수 있다. 또한 동시 승격을 막는 잠금이나 트랜잭션, 서비스의 실제 응답 확인 등이 필요할 수 있다. 이번 실습에서 승격하는 대상은 로컬 파일의 참조다.
